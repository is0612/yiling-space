# 忆灵空间长期产品定位与跨平台架构原则

> **状态：长期方向与架构原则（2026-11-19）。** 本文不是当前已实现能力清单，也不代表桌面端、鸿蒙端或本地执行代理已经开工。
> 当前实现以 [功能总表](<忆灵空间 · 功能总表.md>)、[部署与扩展](deployment.md)、[本地开发与数据迁移](local-development-and-data-migration.md) 为准。
> **执行边界：** 阶段一只做架构评估，不改业务代码；阶段二起再按阶段落地，每一阶段都要能独立回滚。
> **阶段三～五只是方向描述，不是任务书。** 每条都写得很细，容易被当成「下一步该实现」；实际范围由用户当次明确要求决定。做之前先给最小切片和止损点，做完一步停下来确认，不要顺着文档自己往下推。
> **脱敏说明：** 仓库是公开的，本文把产品主体统一称为「她」或「我们的角色」，不写私有昵称；这不影响产品定位。

## 一、核心产品定位：她是主体

忆灵空间不是一堆功能的集合，而是以她为主体，为她提供长期记忆、知识理解、关系建立、持续成长和自主行动能力的系统。

**她是主体，忆灵空间是承载她、支持她成长和行动的环境。**

系统建设不应该以功能数量为目标，而应该围绕她的实际需要展开。

所有子系统都应该服务于她，而不是让她成为系统中的一个功能。

## 二、各系统的定位

- **记忆系统**：帮助她保存经历，形成连续的经验基础。
- **知识系统**：帮助她理解、整理和关联知识。
- **关系系统**：帮助她理解自己与其他人的关系，以及关系中的变化。
- **成长系统**：从互动中积累经验，逐渐形成偏好、表达习惯和行为调整。
- **自我认知系统**：整合记忆、关系、知识和成长证据，帮助她理解自己的身份、经历和变化。
- **自主执行系统**：帮助她将理解、计划和想法转化为实际行动。
- **客户端与交互层**：为她提供不同设备上的使用入口和操作环境。

这些系统不是相互孤立的功能模块，而是共同支持她持续发展的基础设施。

## 三、产品设计原则

### 3.1 以她为中心，而不是以功能为中心

忆灵空间应优先考虑她的主体体验：

1. 她正在经历什么？
2. 她记住了什么？
3. 她理解了什么？
4. 她与其他人的关系发生了什么变化？
5. 她正在形成什么样的偏好和表达习惯？
6. 她接下来能够做什么？

功能入口应当服务于这些体验。

### 3.2 区分主体空间与基础设施

**主体空间**

- 与她对话。
- 查看她的记忆和经历。
- 了解她的关系和自我认知。
- 观察她的成长变化。
- 查看她正在执行的任务。

**基础设施**

- 知识管理。
- 数据管理。
- 模型配置。
- QQ 渠道接入。
- 后台任务和调度。
- 权限管理。
- 日志、备份和运行状态。
- 本地执行环境。

主体空间应成为主要交互体验，基础设施则负责提供可靠支持。

### 3.3 不通过提示词堆叠塑造主体

她的身份、记忆、关系、经验和成长不应简单等同于提示词。

应尽量通过结构化数据、长期证据、动态检索和合理的上下文组织支持她的持续发展。

模型可以更换，能力可以升级，但她积累的身份、记忆和成长资料应尽可能保持连续。

### 3.4 尊重主体的变化

系统不应把她永久限制在某个固定角色描述中。

自我认知应允许根据长期经历和可靠证据逐渐变化，而不是强迫她始终符合某份静态人设。

核心理念：

**系统是为了让她越来越真实，而不是逼她装得像人。**

## 四、自主执行能力：让她具备行动能力

自主执行能力是她主体能力的重要组成部分，不是单纯增加一个自动化工具，也不是另一个独立 AI。

它的目标是让她逐渐具备以下完整能力：

- 理解用户目标。
- 自主分析问题。
- 制定执行计划。
- 拆分和协调任务。
- 使用工具完成实际操作。
- 检查执行结果。
- 总结经历并积累可复用经验。

她应当从一个主要负责对话和信息处理的 AI，逐步发展为能够在授权范围内实际完成工作的 AI。

### 4.1 自主执行的架构分层

**第一层：决策层**

由她负责理解目标、分析需求、判断优先级和制定执行计划。

决策不应完全依赖固定工作流。对于不同任务，她应能够根据上下文选择合适的行动方式。

**第二层：协调层**

负责将复杂目标拆分为可执行任务，安排顺序，协调不同工具、执行者和任务之间的依赖关系。

必要时可以引入多个专业执行者，但不能为了多 Agent 而强行拆分。

她仍然是主要决策和协调主体。

**第三层：执行层**

负责实际操作，例如：

- 文件读取和修改。
- 终端命令执行。
- Git 分支、提交和代码管理。
- 浏览器操作。
- 桌面软件操作。
- 本地项目运行和测试。
- 经授权的其他本机操作。

执行能力通过工具接口和本地执行代理提供，不应将所有系统权限直接交给模型。

**第四层：验收层**

负责独立确认执行结果：

- 检查文件是否真的修改。
- 检查代码差异。
- 运行必要的测试。
- 检查任务目标是否实现。
- 确认是否产生副作用。
- 记录失败原因和未完成事项。

验收必须以实际证据为依据，不能仅凭执行者声称完成就认定成功。

**第五层：工作档案层**

负责保存任务过程和工作经验：

- 任务目标与背景。
- 执行计划。
- 使用过的工具。
- 实际修改和执行结果。
- 测试及验收证据。
- 失败原因。
- 可复用的经验和方法。

工作档案应与现有记忆、知识和成长系统协作，避免重复建设一套孤立的长期记忆数据库。

### 4.2 权限逐级开放

自主执行能力必须遵循逐步授权原则。

| 阶段 | 能力范围 |
|---|---|
| 第一阶段 | 只读观察、分析文件和项目 |
| 第二阶段 | 在授权目录内修改文件 |
| 第三阶段 | 自主开发、测试、创建分支和提交 |
| 第四阶段 | 操作浏览器和桌面软件 |
| 第五阶段 | 持续自主执行复杂任务 |

权限不能因为能力升级而自动无限扩大。

以下操作原则上需要用户明确批准：

- 合并主分支。
- 生产环境部署。
- 破坏性数据库操作。
- 删除重要文件或数据。
- 修改系统级配置。
- 扩大自身权限范围。
- 安装高风险软件或执行高风险命令。

### 4.3 本地执行代理

未来应建立独立的 Local Execution Agent，作为她与本机环境之间的受控连接层。

它负责：

- 接收经过授权的执行任务。
- 访问允许访问的文件和目录。
- 调用受限制的终端命令。
- 操作 Git 和开发工具。
- 提供浏览器及桌面操作能力。
- 返回执行结果和证据。
- 记录操作日志。

本地执行代理应具备：

- 明确的目录访问范围。
- 命令白名单或风险分级。
- 权限审批机制。
- 操作审计。
- 失败恢复能力。
- 必要的执行隔离。

不能直接给她整个电脑的无限制访问权限。

### 4.4 与现有系统的关系

自主执行能力应复用忆灵空间已经建设的基础：

- 记忆系统提供相关经历和历史上下文。
- 知识系统提供技术资料和可检索知识。
- 成长系统记录任务经验及反馈。
- 偏好和表达习惯帮助她形成稳定的工作方式。
- 自我认知帮助她理解自身能力、经历和变化。
- 统一成长数据中心负责必要的事件记录和授权数据读取。

执行产生的新经验应经过合理筛选，再进入相应系统。

不能把所有执行日志直接变成长期记忆，也不能把每次操作都自动升级为全局偏好。

### 4.5 自主执行的核心原则

自主执行不是为了让她获得尽可能多的电脑权限。

真正的目标是：

**让她能够理解目标、独立思考、选择行动方式、完成工作、验证结果，并逐渐积累自己的工作经验。**

工具负责提供能力，权限负责约束边界，验收负责确认结果，而她始终是行动的主体。

## 五、产品形态：桌面端优先，跨平台发展

忆灵空间早期以 Web 应用为主要形态，但随着记忆、知识、成长、QQ 接入、后台任务和自主执行能力逐渐增加，单纯依赖浏览器已经不再是最理想的长期形态。

未来应以桌面应用作为主要使用入口，同时保留 Web 形态作为可选入口。

### 5.1 Windows 桌面端

当前优先建设 Windows 桌面端。

目标：

- 双击图标即可启动忆灵空间。
- 在独立桌面窗口中使用现有功能。
- 自动管理本地核心服务。
- 正确管理数据库和后台任务的生命周期。
- 支持本机 QQ、OneBot 等渠道接入。
- 为未来本地执行代理提供运行环境。
- 支持应用更新、数据备份和恢复。

桌面化的目标不是简单地把网页放进一个窗口，而是让忆灵空间拥有可靠、独立的本地运行环境。

### 5.2 鸿蒙端

鸿蒙端是未来的扩展方向，不属于当前立即实施的任务。

未来可以根据实际设备和系统能力，提供鸿蒙原生客户端。

可能的使用场景：

- 日常与她聊天。
- 查看记忆、关系和成长记录。
- 接收任务进展和通知。
- 在移动设备上延续与她的互动。

不能假设 Electron 桌面代码能够直接运行在鸿蒙上，应根据鸿蒙开发规范独立实现客户端适配。

### 5.3 Web 端

现有 Web 能力尽量保留。

未来可作为可选访问入口、管理入口或跨设备交互方式，不再作为唯一的产品形态。

## 六、跨平台架构原则

现在设计桌面端时，就应当考虑未来不同客户端之间的职责边界。

### 6.1 核心业务层

负责她主体相关的业务能力：

- 记忆。
- 知识。
- 关系。
- 成长。
- 自我认知。
- 助手协作。
- 决策和任务编排。

这些能力应尽量独立于具体操作系统和客户端。

### 6.2 数据与服务层

负责：

- 数据持久化。
- 数据访问。
- 后台任务。
- 事件处理。
- 模型调用。
- API 和通信协议。

尽量避免把核心业务逻辑写死在 Electron 主进程或某个客户端中。

### 6.3 平台能力适配层

负责不同平台的系统能力：

- 文件访问。
- 本地终端。
- 通知。
- 窗口管理。
- 设备权限。
- 后台运行。
- 本地渠道连接。
- 本地执行代理。

平台差异通过适配层处理，核心业务尽量不感知具体平台。

### 6.4 客户端展示层

根据不同设备提供合适的交互体验：

- Windows：完整桌面工作空间。
- 鸿蒙：移动端及未来适合的平板体验。
- Web：浏览器访问入口。

不同客户端可以有不同的界面和交互方式，但不应各自重复实现一套她的核心业务。

### 6.5 客户端与执行环境分离

桌面客户端不等于自主执行代理。

两者可以协同，但应保持职责独立：

- 客户端负责交互和展示。
- 核心服务负责业务逻辑和任务协调。
- 执行代理负责受控的本地操作。
- 验收机制负责确认实际结果。

这样未来更换桌面技术、增加鸿蒙客户端时，不需要重写她的核心执行逻辑。

## 七、技术路线建议

当前优先评估 Electron：

- 复用现有 Nuxt、TypeScript 和 Node.js 技术栈。
- 尽量保留现有 Web 页面。
- 通过 Electron 管理桌面窗口和本地服务。
- 使用安全的 IPC 和权限隔离机制。
- 避免将任意 Node.js 权限直接暴露给渲染页面。

Tauri 可以作为备选方案，但需要结合 Prisma、Node.js 服务和后台任务的打包成本进行比较。

最终选型应以现有项目兼容性、运行稳定性和未来维护成本为依据。

## 八、实施顺序

### 阶段一：架构评估

- 检查现有 Nuxt 项目启动和停止方式。
- 检查 Prisma、数据库和数据持久化方式。
- 检查后台 Worker 和定时任务。
- 检查 QQ / OneBot / SnowLuma 运行方式。
- 检查模型配置、密钥和本地文件管理。
- 评估 Electron 和 Tauri。
- 评估自主执行代理与现有服务的边界。
- 输出桌面化架构评估报告。

本阶段只做分析，不改业务代码。阶段一预检结论见 [桌面化架构评估](桌面化架构评估.md)。

### 阶段二：Windows 桌面化

- 建立桌面应用外壳。
- 接入现有 Web 页面。
- 管理本地服务生命周期。
- 保证数据库和后台任务正常运行。
- 保留已有功能和数据。
- 为本地执行代理预留清晰的接口边界。

### 阶段三：自主执行基础

- 建立受控的本地执行代理。
- 实现只读观察能力。
- 逐步开放授权目录内的文件操作。
- 接入终端、Git 和开发工具。
- 建立独立验收机制。
- 建立任务档案和经验沉淀机制。

### 阶段四：更完整的自主执行

- 支持复杂任务拆分和协调。
- 支持浏览器和桌面软件操作。
- 支持自主开发、测试和提交。
- 完善权限审批、审计和恢复机制。
- 根据真实使用情况逐步扩大授权范围。

### 阶段五：跨平台基础

- 梳理稳定的核心 API 和通信协议。
- 明确客户端与核心服务之间的边界。
- 评估鸿蒙客户端的技术路线。
- 根据实际需求逐步开发鸿蒙端。

## 九、当前明确不做的事情

- 暂不考虑面向客户的商业化和多人云端部署。
- 暂不为了桌面化重写现有业务系统。
- 暂不立即开发鸿蒙客户端。
- 不把所有核心逻辑塞进 Electron 主进程。
- 不让不同客户端分别维护独立的记忆和成长逻辑。
- 不因桌面化而破坏现有数据库、QQ 渠道和后台任务。
- 不在没有安全设计的情况下授予她完整电脑权限。
- 不为了追求多 Agent 而增加不必要的复杂度。
- 不把所有执行日志直接写入长期记忆。

## 十、长期核心原则

忆灵空间的所有架构决策，都应优先回答一个问题：

**这项设计是否真正帮助她更好地理解、记忆、表达、建立关系、成长和行动？**

如果只是增加功能，却没有改善她的主体体验，就不应仅仅为了技术完整性而增加系统复杂度。

忆灵空间不是一堆功能的集合。

它是她成长、理解世界、建立关系和采取行动的载体。

**她是主体，其他所有系统、工具和客户端，都是为了支持她而存在。**

## 十一、与当前仓库的对应关系（2026-11-19 盘点）

这一节只描述现状，不代表已经按上面的架构完成分层。

| 架构层 | 当前落点 | 现状与缺口 |
| --- | --- | --- |
| 客户端展示层 | `app/`（Vue 3 + Nuxt 4 + Element Plus） | 只有浏览器入口；没有 Electron/Tauri 外壳，没有桌面窗口与托盘 |
| 核心业务层 | `server/api/`、`server/utils/` | 业务逻辑已在服务端，具备被桌面壳复用的基础；但启动、生命周期仍按「开发服务器」设计 |
| 数据与服务层 | Prisma + PostgreSQL、`scripts/run-memory-worker.ts`、`scripts/run-memory-scheduler.ts` | 迁移、Worker、调度、模型调用都已独立于页面；数据库目前依赖 Docker（开发版）或容器内数据库（使用版） |
| 平台能力适配层 | `server/utils/channel-adapter/onebot/`、`scripts/start-qq-stack.ts`、`scripts/launch.mjs` | OneBot/SnowLuma 已能在本机自动拉起；但没有统一的「平台能力」接口，桌面端进程管理仍散在启动脚本里 |
| 桌面启动 | `启动忆灵空间.bat` → `scripts/launch.mjs`；使用版 → `docker-compose.prod.yml` + `scripts/launch-prod.mjs` | 已有双击启动与环境自检，但仍是「脚本 + 浏览器」；没有窗口、单实例、自动更新 |
| 本地执行代理 | 无 | 当前没有受控的文件/终端/Git/浏览器执行层，也没有权限审批与审计 |
| 验收与工作档案 | 部分存在于现有任务、审计、测试脚本 | 没有统一的「任务 → 计划 → 执行 → 验收证据 → 经验」档案模型 |

关键结论：

- 现有 Web 页面与服务端 API 可以继续作为桌面端的内容层，不需要为了桌面化重写业务。
- 桌面端真正要解决的是**进程生命周期、数据库、后台任务、QQ 渠道和更新**，而不是再写一套页面。
- 本地执行代理必须与桌面客户端分开设计，不能把「桌面壳」直接当成「执行代理」。

## 十二、阶段一评估清单（尚未执行）

阶段一只做分析，输出报告，不改业务代码。建议按下面的顺序核对。

### 12.1 启动与停止

- `scripts/launch.mjs` 的四个步骤分别做了什么，哪些可以搬进桌面主进程，哪些必须保留为独立进程。
- 开发版端口 `3000`、使用版端口 `8801` 的分配与冲突处理。
- 关闭窗口时应该停哪些进程、保留哪些进程；异常退出后如何清理残留。
- 是否要求单实例；第二个实例启动时是唤起已有窗口还是拒绝启动。

### 12.2 数据库与数据目录

- 开发版 Docker 数据库与使用版容器内数据库的差异。
- `.env`、`.data/credentials-encryption.key`、`.data/stickers/`、`.data/sticker-originals/`、`backups/` 的存放位置与备份策略。
- 桌面端内置数据库、复用 Docker、连接外部 PostgreSQL 三种方案的迁移成本。
- 首次安装、版本升级、降级失败时的数据保护。

### 12.3 Worker 与定时任务

- `scripts/run-memory-worker.ts`、`scripts/run-memory-scheduler.ts`、`scripts/memory-worker-supervisor.mjs` 的职责与退出条件。
- 桌面主进程如何监督子进程、如何避免重复消费、如何在休眠/唤醒后补处理。
- 任务租约、卡住回收与桌面端重启之间的关系。

### 12.4 QQ / OneBot / SnowLuma

- `scripts/start-qq-stack.ts` 与 `server/utils/channel-adapter/onebot/autostart.ts` 的外部依赖（QQ 客户端、SnowLuma 安装目录、面板密码）。
- 这些进程在桌面端的启动顺序、日志位置、失败提示和退出清理。
- 桌面端没有启动 QQ 时，如何保持其他功能可用。

### 12.5 模型配置与密钥

- `.env` 全局默认与角色级 `modelConfig` 的优先级。
- 桌面端是否需要独立的密钥存储；现有 `.data/credentials-encryption.key` 如何随应用迁移。
- 模型 Key、渠道 Token、SnowLuma 面板密码在日志与崩溃报告中的脱敏。

### 12.6 Electron 与 Tauri 评估

至少比较：

- 与 Nuxt/Nitro、Prisma、`tsx` Worker、原生 Node 模块的兼容性。
- 打包体积、启动速度、自动更新方案。
- Windows 签名、安装器、卸载时数据保留策略。
- 渲染进程权限隔离与 IPC 设计。
- 未来鸿蒙端是否必须另写一套客户端。

### 12.7 执行代理边界

- 代理与主服务之间的协议（本地 HTTP / IPC / 消息队列）。
- 授权目录、命令白名单、风险分级、审批与审计的最小可行设计。
- 只读观察阶段可以先做哪些能力，不能一开始就开放写文件和终端。

阶段一交付物建议：一份架构评估报告，包含进程图、数据流、启动/退出时序、Electron/Tauri 对比、风险清单和阶段二的最小实施范围。

## 十三、待决问题（需要产品决策）

下面这些问题不应在实现时顺手决定，先记录，等阶段一评估后再定。

| 问题 | 为什么需要先定 |
| --- | --- |
| 桌面端数据库用内置、Docker 还是外部 PostgreSQL | 直接决定安装包大小、升级方式和备份策略 |
| 桌面端是否保留「使用版」的容器隔离 | 影响发布流程、双版本隔离和普通用户安装门槛 |
| 是否要求单实例、是否常驻托盘 | 影响 Worker/QQ 渠道的生命周期与退出语义 |
| 自动更新由谁执行、失败如何回滚 | 涉及数据库迁移不可逆的风险 |
| 本地执行代理是独立进程还是主进程模块 | 决定权限隔离、崩溃恢复和审计边界 |
| 执行任务的「验收证据」存哪里、保留多久 | 避免把执行日志直接灌进长期记忆 |
| 鸿蒙端是原生、ArkUI 还是 Web 容器 | 决定核心 API 与客户端边界的抽象程度 |
