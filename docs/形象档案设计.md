# 形象档案

## 定位

形象档案是角色级的视觉身份资料库，为角色绘图、图片编辑与后续多模态生成提供稳定的视觉依据。它与角色设定、记忆、知识系统分离，不承担人格或经历记忆。

## 数据归属

- 所有资料必须绑定 `characterId`，沿用当前角色选择机制。
- 读取、写入、上传、删除和发布操作都必须在服务端校验当前用户对该角色的访问权限。
- 不允许仅凭前端传入的角色 ID 建立跨角色访问。
- 档案资料与原始图片资源应有明确的删除和引用策略。

## 资料结构

### 1. 核心形象

保存相对稳定的外貌特征：发色、眼睛、发型、体型比例、鲸鱼元素、整体视觉气质等。核心形象不包含某一套特定服装。

### 2. 造型

服装、配饰、发饰等作为独立造型记录。允许同一角色拥有多套造型，不应因换装覆盖核心形象。

### 3. 参考图片

图片需记录用途和排序，至少区分：
- 标准形象图
- 三视图：正面、侧面、背面
- 表情参考
- 服装与配饰参考
- 其他补充素材

图片资源应走项目统一的安全上传与本地数据目录机制，不把 base64 长期塞进业务表，也不依赖临时浏览器缓存。

### 4. 绘图提示词

分开保存：
- 核心形象提示词
- 当前造型提示词
- 负面提示词
- 场景/动作扩展提示词
- 可选模型与生成参数

拼装时应保持“核心形象 + 造型 + 场景”的层次，不把所有内容合并成一段不可维护的大提示词。

### 5. 版本与确认

- 编辑先形成草稿。
- 只有用户明确确认后，草稿才成为当前正式版本。
- 历史正式版本可查看、恢复；恢复也应产生新的版本记录，不能抹掉历史。
- 绘图生成结果默认只是候选素材，不自动覆盖正式形象。
- 记录创建者、创建时间、版本说明和素材来源。

## 绘图 API 集成

绘图调用应通过统一的档案读取服务获取当前正式版本。读取失败时可以回退到现有调用方式，但必须明确记录未使用档案；不得静默使用其他角色的资料。

推荐组合顺序：
1. 核心形象提示词
2. 当前选择的造型提示词
3. 场景与动作提示词
4. 负面提示词
5. 当前版本中标记为主要参考的图片

私聊/群聊等不同入口不应各自复制一套形象拼装逻辑。

## 页面与菜单

- 菜单：工作空间 → 形象档案
- 路由：`/visual-profile`
- 使用全局当前角色选择器，页面内容随角色切换。
- 页面分区：概览、核心形象、造型、参考图片/三视图、绘图提示词、版本历史。

## 当前实现进度

已完成：
- 工作空间菜单入口与 `/visual-profile` 页面。
- Prisma 模型：角色档案、参考素材元数据、服装造型、不可变版本快照。
- 角色归属 API：读取与保存草稿均先校验当前用户拥有该角色。
- 保存提示词会产生新的草稿版本；只有显式发布接口才推进 `currentPublishedRevision`。
- 页面已接入核心外貌、核心提示词、负面提示词编辑、草稿保存和显式发布。

尚未完成：
- 图片上传、格式/大小校验、缩略图、素材删除与图片预览。
- 服装造型的增删改。
- 历史版本查看详情与恢复为新草稿。
- 绘图调用读取正式版本的提示词。
- 自动化测试、Prisma validate / generate、迁移与端到端验收。

## 实施顺序

1. 菜单与页面入口（已完成）。
2. Prisma 数据模型、SQL 迁移与角色级核心提示词 CRUD（已完成，待本地 Prisma 验证）。
3. 图片上传、校验、缩略图与安全访问。
4. 服装造型 CRUD、历史版本详情与恢复。
5. 绘图 API 统一读取正式档案提示词。
6. 页面与服务测试、隔离测试、上传安全测试。

## 明确不做

- 不把形象档案写入记忆或知识系统。
- 不让 AI 生成结果自动覆盖正式形象。
- 不强制每次绘图都使用同一套服装。
- 不将向量数据库作为本功能依赖。
