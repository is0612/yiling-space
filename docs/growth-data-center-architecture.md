# 统一成长数据中心架构设计

> 状态：架构方案（待评审，尚未进入数据库实现）
> 日期：2026-11-09
> 适用范围：忆灵空间成长系统

## 1. 目标与非目标

统一成长数据中心不是一张存放所有成长内容的万能表，也不是要求所有系统改用同一套业务模型。它是在现有领域系统之上建立一组稳定的协作约定，让记忆、社交、知识以及后续偏好、语料、状态、反思与成长、目标与愿望系统能够安全地交换事件和读取证据。

目标：

- 每个领域继续拥有自己的数据、业务规则和写入权限。
- 所有角色数据以现有 `Character.id` 为统一角色身份，严格隔离。
- 领域之间采用“事件通知 + 授权 API 读取”。
- 经历正文只保留在原始领域；其他领域通过引用追溯来源。
- AI 更新遵循“低风险自动处理、重要变化确认、不确定内容先成为候选”的策略。
- 事件投递具备持久化、重试和幂等能力。
- 尽量复用现有模型、服务、审计与任务执行机制，避免大规模重构。

非目标：

- 不创建 `GrowthData` 一类万能数据表。
- 不把所有领域的数据复制到统一中心。
- 不建设一个必须调用所有助手的中央 AI 编排器。
- 不在本阶段重写记忆、社交或知识系统。
- 不在没有实际消费者需求前，为所有未来领域一次性创建完整数据表。

## 2. 已确认的架构决策

| 决策 | 选择 | 约束 |
|---|---|---|
| 领域协作 | mixed：事件通知 + 授权 API 读取 | 事件只通知变化；详情通过所属领域接口读取 |
| 经历关联 | reference：引用原始经历 | 不复制原始正文；来源状态可追溯 |
| AI 更新策略 | mixed：低风险自动更新 + 重要变化确认 | 不确定推断先候选化；领域规则优先于模型置信度 |

## 3. 现有结构审查结论

以下结论来自当前默认分支的 Prisma Schema 与相关服务代码审查。实现时仍需在本地分支重新核对，不能仅凭本文推断运行时行为。

### 3.1 可直接复用的模型和机制

| 现有模型 / 机制 | 已有职责 | 在统一架构中的定位 |
|---|---|---|
| `Character.id` | 角色主键 | 全领域统一角色标识，不新增重复 roleId |
| `MemoryScope` | 按角色和范围组织记忆及社交数据 | 记忆/社交领域的范围边界；不取代 Character 身份 |
| `MemoryEvent` | 忆泡事件、时间、参与者、消息来源 | 记忆领域的原始经历来源 |
| `SocialExperience` | 通过 memoryEventId 关联忆泡 | 已有经历引用实践 |
| `SocialRelationChangeEvidence` | 关系变化关联社交经历 | 保留领域专属证据关联 |
| `SocialRelationshipAssessmentEvidence` | 评估关联 NEW / CONTEXT 经历 | 保留评估证据与范围约束 |
| `SocialRelationChange` | 关系变化历史 | 社交领域自己的业务历史 |
| `AuditLog` | 操作审计 | 复用通用操作审计，不替代领域历史 |
| `MemoryJob` 及社交评估任务机制 | 任务状态、幂等、租约/重试等模式 | 参考并复用现有任务执行基础，不把 MemoryJob 改成通用任务表 |
| `KnowledgeItem` 及知识生命周期模型 | 正式知识、候选、版本和关联 | 知识领域继续拥有知识数据 |

### 3.2 关键结论

1. 现有 `SocialExperience → MemoryEvent` 已经体现“引用经历、不复制正文”，不需要为社交重新造一套经历正文存储。
2. `MemoryScope.characterId` 和知识模型的 `characterId` 已经指向统一角色身份。跨领域接口应同时识别角色和领域范围，不能把 MemoryScope 当作全系统角色主键。
3. 社交关系阶段、相处状态、评估历史和人工采纳规则属于社交领域所有权。其他领域只能通过授权接口读取，不能直接写社交表。
4. `AuditLog` 是操作审计，不应取代 `SocialRelationChange` 等领域历史。
5. 现有专用任务队列证明项目已有可靠异步任务经验，但没有发现可直接复用的通用领域 Outbox / Delivery 事件中心。因此需要补齐跨领域事件投递能力。

## 4. 领域所有权与边界

| 领域 | 数据所有权 | 对外提供的读取能力 |
|---|---|---|
| 记忆系统 | 忆泡、长期记忆、快照、阶段总结 | 记忆检索、经历详情、来源状态 |
| 社交关系系统 | 好友关系、社交经历、关系阶段/状态、评估与变化历史 | 好友/关系查询、社交经历证据 |
| 知识系统 | 知识候选、正式知识、版本、关联、归档状态 | 知识查询、知识来源 |
| 偏好系统 | 喜好、厌恶、兴趣和稳定倾向 | 当前有效偏好及其证据 |
| 语料 / 表达习惯系统 | 口头禅、语气、表达方式和语言习惯 | 当前表达特征 |
| 状态系统 | 当前情绪、精力、心境和关注状态 | 当前状态及有效期 |
| 反思与成长系统 | 反思记录、成长结论、认知或行为变化 | 成长历史与结论 |
| 目标与愿望系统 | 愿望、目标、计划、进展 | 目标及进度 |

领域负责自己的写入、验证、冲突处理和生命周期。跨领域调用默认只读；若确实需要改变其他领域数据，必须调用数据所有者提供的命令式业务接口，不能直接写对方数据库模型。

## 5. 统一身份与访问上下文

- 全系统角色身份使用 `Character.id`。
- `MemoryScope.id` 代表记忆/社交领域中的具体范围，不是角色 ID。
- 请求进入服务端后，由可信会话/当前角色上下文解析目标角色；不能仅凭客户端传来的 characterId 就授予访问权限。
- 每次领域读取都必须验证：当前主体是否有权访问该 Character、请求领域是否允许该读取、scope 是否属于该 Character。
- 角色切换必须同步影响后续读取、事件订阅和任务创建；不能从上一个角色沿用缓存或任务上下文。
- 事件消费者处理事件时，以事件中的 Character 身份作为数据范围，并再次通过领域服务验证引用范围。

## 6. 领域事件中心

### 6.1 事件职责

事件回答“哪个角色的哪个领域发生了什么变化”，不承载完整聊天正文或大型业务对象。收到事件的消费者按需通过授权 API 读取详情。

建议事件信封：

| 字段 | 含义 |
|---|---|
| `id` | 事件唯一 ID |
| `characterId` | 事件所属角色 |
| `sourceDomain` | 事件来源领域 |
| `eventType` | 稳定事件名，如 `memory.event.created` |
| `schemaVersion` | 事件载荷版本 |
| `aggregateType` / `aggregateId` | 发生变化的领域对象 |
| `occurredAt` | 业务事件发生时间 |
| `createdAt` | 事件持久化时间 |
| `payload` | 最小必要元数据，不放聊天正文 |
| `idempotencyKey` | 来源侧幂等键，防止重复发布 |

### 6.2 投递记录

事件记录与消费者投递状态分离。一个事件可以被多个消费者独立处理。

投递记录至少需要表达：

- eventId、consumerKey；
- 状态：待处理、处理中、成功、等待重试、终止失败；
- attemptCount、nextAttemptAt；
- leaseToken / lockedAt / lockedBy（按现有任务租约模式确定字段）；
- lastError、processedAt、createdAt、updatedAt。

数据库唯一约束应保证同一个 `eventId + consumerKey` 只有一条投递记录。消费者处理成功后才确认完成；失败按退避策略重试；过期租约可被安全回收。旧租约持有者不得覆盖新持有者的结果。

### 6.3 事务与可靠性

- 领域数据变更与 Outbox 事件写入必须在同一个数据库事务中提交。
- Worker 从持久化事件表领取工作，而不是依赖仅存在于进程内存的 emit / callback。
- 消费者必须幂等：同一事件重试不得重复创建成长结论或重复累计经历。
- 事件投递与业务处理分开；模型调用等耗时操作不应占用数据库事务。
- 事件中心只负责通知和投递，不负责替消费者解释事件或调用所有 AI 助手。
- 复用现有调度、租约、重试和 watchdog 模式；不要把专用 MemoryJob 直接改造成跨领域队列。

### 6.4 初始事件目录（候选）

| 事件 | 发布领域 | 可能的订阅者 | 备注 |
|---|---|---|---|
| `memory.event.created` | 记忆 | 偏好、状态、反思与成长、社交（按需） | 只传 eventId 等元数据 |
| `memory.event.updated` | 记忆 | 已订阅该来源的领域 | 仅在有意义的内容/状态变化时发布 |
| `memory.event.archived` | 记忆 | 所有维护引用的领域 | 使引用状态可见，不复制正文 |
| `social.experience.created` | 社交 | 反思与成长、偏好（按需） | 不意味着必须触发模型 |
| `social.relationship.changed` | 社交 | 状态、反思与成长（按需） | 关系变化仍由社交领域决定 |
| `knowledge.item.updated` | 知识 | 需要该知识的订阅者 | 不广播知识正文 |

事件目录先保持小而稳定；没有实际消费者的事件不必提前实现。

## 7. 授权领域读取 API

跨领域交互采用“通知 + 读取”：

1. 消费者收到事件，取得事件 ID、角色 ID、来源领域和对象引用。
2. 消费者判断本领域是否订阅、是否值得处理。
3. 如需详情，通过来源领域的服务接口读取。
4. 来源领域验证角色、范围、状态和读取权限后返回最小必要数据。
5. 消费者将自己的结论和来源引用写入本领域数据，不直接修改来源领域。

接口约束：

- 默认只读，返回 DTO 而不是 Prisma Model。
- 明确区分“未找到”“已归档”“已删除”“无权访问”，避免把权限错误当成数据不存在。
- 支持批量读取和必要的字段选择，避免 N+1。
- 读取结果必须包含稳定来源 ID、所属角色、来源状态和必要时间信息。
- 任何写操作都回到数据所属领域的业务服务。
- 不允许跨领域直接 import 对方内部 Prisma 查询并绕开授权规则。

## 8. 经历引用与来源生命周期

### 8.1 引用原则

- 原始经历只由原始领域保存。
- 其他领域保存 sourceDomain、sourceType、sourceId、characterId、purpose 等引用元数据。
- 不复制完整正文来“保证引用永远可用”。
- 优先沿用已有的领域专属关联表；只有多个真实领域出现重复、稳定的引用需求后，才抽象通用 Evidence Reference 表。

### 8.2 引用用途

可以按业务需要区分支持结论、反向证据、背景上下文、派生来源等用途。具体枚举由首个真实消费者确定，不在本阶段过度设计。

### 8.3 生命周期

来源被归档、删除或权限撤销时，引用不能伪装成仍可读取。读取 API 必须返回明确来源状态；消费者根据自身规则决定保留引用、标记失效、重算结论或请求人工处理。不得通过复制原文绕过删除语义。

## 9. AI 更新与人工确认策略

### 9.1 三类结果

1. 明确、低风险、可逆且领域规则允许的变化：自动更新，并留下来源与审计记录。
2. 不确定或证据不足的推断：形成候选，等待更多证据或人工确认。
3. 重要、长期、身份/关系/目标层面的变化：按领域规则等待角色明确表达或主人确认。

### 9.2 自动更新前置条件

自动写入必须同时满足：

- 该领域明确允许此类自动更新；
- 证据来源有效且属于同一角色；
- 达到该领域规定的证据门槛；
- 不违反已有人工确认结果；
- 不与更高优先级的现有数据冲突；
- 变更可追溯，必要时可撤销；
- 更新由数据所有者的业务服务执行。

模型置信度不能单独作为跳过人工确认的理由。

### 9.3 领域例子

- 状态：短暂情绪可自动更新，并有有效期或恢复规则。
- 偏好：一次表达可以形成候选；稳定偏好需要重复证据或明确表达。
- 社交：关系阶段和相处状态严格遵守社交系统自己的评估、版本校验和人工采纳流程。
- 目标：重要人生目标不因一次模糊推断自动创建。
- 反思与成长：可以生成待审阅结论，不直接改写核心人格。
- 语料：积累可观察表达习惯，不擅自覆盖角色核心人设。

## 10. 助手协作原则

- 助手是领域能力的执行者，不是数据所有者的替代品。
- 不要求每个领域都必须有独立 AI 助手；简单检索和规则处理不应无谓调用模型。
- 助手按需读取授权数据，只接收完成任务所需的最小上下文。
- 一个领域的分析结果先交由该领域服务验证，再持久化。
- 记忆负责记录事实；社交负责处理关系；知识负责管理知识；其他领域遵循各自所有权。
- 语境助手负责判断当前对话需要什么能力，不应成为所有成长业务的总入口或总执行者。

## 11. 建议的基础模块

| 模块 | 职责 | 实施原则 |
|---|---|---|
| Role Context | 可信角色上下文与访问隔离 | 复用现有角色切换来源 |
| Event Center | 事件持久化、订阅、投递和重试 | 本阶段优先新增 |
| Domain Gateway | 授权读取和 DTO 边界 | 从真实跨领域用例逐步建立 |
| Evidence Reference | 来源引用和状态追溯 | 先统一接口，不急于通用表 |
| Audit Center | 操作审计 | 复用 AuditLog，按需补充关联信息 |
| Lifecycle | 归档、删除、撤销与引用失效语义 | 由来源领域掌握最终决定权 |
| Task Infrastructure | 异步任务、租约、重试、幂等 | 复用现有实现模式，不重造队列 |

## 12. 第一阶段实施范围

第一阶段只建设跨领域协作的最小闭环，不建设五个新领域的业务模型。

### 12.1 先做的内容

1. 在代码中确认可信 Character Context 的解析入口和服务端权限边界。
2. 定义领域事件类型、版本和最小事件信封。
3. 设计并实现 Outbox 事件表与消费者投递表（最终字段以 Prisma 现状审查和迁移评审为准）。
4. 实现事务内发布、Worker 领取、租约保护、重试和幂等。
5. 实现最小领域读取接口约定及一个真实只读消费者示例。
6. 补充可观测性：待投递数、失败数、重试次数、最早积压时间和最近错误。
7. 编写隔离数据库测试和角色隔离测试。

### 12.2 第一阶段暂不做

- 不迁移现有所有记忆和社交数据。
- 不改写记忆快照、忆泡、社交关系评估核心流程。
- 不把 KnowledgeItem 等现有模型迁入统一表。
- 不一次性创建五个新领域的 Prisma 模型。
- 不实现全局 AI Agent 调度器。
- 不默认让每条事件触发模型调用。

## 13. 第一阶段验收标准

### 事件可靠性

- 领域数据与事件记录同事务提交；事务回滚时两者都不存在。
- 同一业务操作重复提交不会生成重复事件。
- Worker 崩溃或进程重启后，未完成事件仍可继续处理。
- 同一事件同一消费者不会重复产生业务结果。
- 过期租约可以回收；旧租约持有者不能确认或覆盖新租约结果。
- 失败按退避策略重试，达到上限后可观测、可人工恢复。

### 角色与权限隔离

- 角色 A 的事件不能读取角色 B 的领域数据。
- 不能把角色 A 的 MemoryScope 或 SocialExperience 引用挂到角色 B 的事件/结论。
- 客户端伪造 characterId 不会绕过服务端角色授权。
- 角色切换后不会复用前一个角色的缓存、投递上下文或查询结果。

### 数据与生命周期

- 事件 payload 不含完整聊天正文或不必要的敏感内容。
- 消费者通过领域 API 读取，而不是直接写其他领域表。
- 来源归档/删除后，引用读取能明确反映来源状态。
- 所有自动变更有来源、执行者/执行机制和审计记录。

### 工程质量

- Prisma migration 可在空数据库和现有数据库正确执行。
- 新增隔离 DB 测试覆盖事务、幂等、租约、重试、角色隔离和生命周期。
- 相关 typecheck、SFC、lint、专项测试通过。
- 现有记忆、社交和知识专项测试不回归。

## 14. 后续推进顺序

1. 评审本文，冻结第一阶段事件契约和访问边界。
2. 在独立分支实现 Event Center 最小闭环。
3. 先用一个低风险、只读的真实消费者验证端到端流程。
4. 让记忆系统发布首批事件并提供授权读取。
5. 社交系统按需接入，不改变其关系决策权和人工采纳规则。
6. 知识系统接入事件和授权查询。
7. 再逐个建设偏好、语料、状态、反思与成长、目标与愿望系统。

---

**架构原则总结：统一的是身份、协作协议、证据追溯和可靠基础设施；保持独立的是各领域的数据所有权、业务规则和生命周期。**
