## 3. 解析器的数据结构

三个导出函数、四个类型、一个常量。

```ts
// 命令名 → 写法
const COMMAND_LABELS = { image: "出图", voice: "语音", vision: "看图", history: "查记录" } as const;
export type CapabilityCommandName = keyof typeof COMMAND_LABELS;
export const CAPABILITY_COMMAND_BODY_MAX_CHARS = 2000;

// 解析结果：判别联合
export type ParsedCapabilityCommand =
  | { kind: "none" }                                                        // 不是命令，普通消息
  | { kind: "invalid"; name: CapabilityCommandName; reason: "missing_colon" | "empty_body" | "too_long"; hint: string }
  | { kind: "command"; name: CapabilityCommandName; body: string };         // 正确命令

// 一条消息的来源信息（入口负责填）
export type CapabilityCommandSource = {
  externalMessageId?: string;
  kind?: "AI" | "HUMAN" | "UNKNOWN";
  readOnly?: boolean;
  content: string;            // 落库/展示用全文，会混入 @ 占位、附件占位、表情摘要
  commandText?: string;      // 用户手打的文字。有它就只认它
  hasAttachments?: boolean;
  addressedToSelf?: boolean;
};

// 带着来源的解析结果（挂到对话输入上的就是它）
export type CapabilityCommandRequest = {
  externalMessageId?: string;
  addressedToSelf: boolean;  // 是不是对她说的。解析不因它改变，执行前必须看它
  command: Exclude<ParsedCapabilityCommand, { kind: "none" }>;
};

parseCapabilityCommand(text): ParsedCapabilityCommand      // 只看文本，谁都能调
readCapabilityCommand(source): CapabilityCommandRequest | null   // 加来源过滤
readCapabilityCommands(sources): CapabilityCommandRequest[]      // 一批消息逐条解析
```

### 识别规则

1. 去掉首尾空白后，必须以 `&` 开头。
2. `&` 后面紧跟命令名（出图 / 语音 / 看图 / 查记录），命令名后**紧跟冒号**，半角 `:` 全角 `：` 都行。
3. 冒号后是正文，去掉首尾空白；正文内部换行和空格原样保留。
4. 任何一步不满足，按对应原因报格式错误，并给一句提示。

### 来源过滤（`readCapabilityCommand`）

| 情况 | 结果 |
| --- | --- |
| `kind === "AI"` | 不解析（AI 自己说的话里出现命令样式是在转述） |
| `readOnly === true` | 不解析（只读观察消息） |
| `kind === "UNKNOWN"` | 照常解析，收件人留给执行前校验 |
| 有 `commandText` | 只认 `commandText` |
| 无 `commandText`、带附件 | 不回落到 `content`，不解析 |
| 无 `commandText`、不带附件 | 用 `content`（网页对话就是这种） |

### 提示文案

| 原因 | 文案 |
| --- | --- |
| `missing_colon` | `格式不对，要写成「&出图：内容」。` |
| `empty_body` | `「&出图：」后面要写上内容。` |
| `too_long` | `「&出图：」后面的内容太长了，请精简后再发。` |

（命令名随实际识别到的那一项替换。）**这些文案本阶段没有接到任何发送路径**，只是数据。

## 4. 两个入口的接入情况

### 4.1 QQ 入口（`channel-adapter/pipeline.ts`）

位置：`runChannelTurn` 里，紧跟在 `currentMessage` 拼好之后。对本轮 `messages` 数组**逐条**调用解析器，结果经 `buildChannelTurnChatInput` 透传到对话输入。

```ts
const capabilityCommands = readCapabilityCommands(messages.map(message => ({
  externalMessageId: message.externalMessageId,
  kind / readOnly / content / commandText / addressedToSelf …,   // 有值才带
  hasAttachments: Boolean(message.images?.length || message.voices?.length),
})));
```

**为什么逐条解析、不用 `currentMessage`：** 群聊攒批时 `currentMessage` 是多人消息拼接后的文本（`某群友：…\n另一人：…`），拿它去找命令会把别人说的话算进来。

**为什么用 `commandText` 不用 `content`：** 盘点 `onebot/types.ts` 确认，`content`（`readOnebotMessageText`）会混入 `@<qq>`、`[表情包：摘要]`、`[语音]` 这些非手打内容；`commandText`（`readOnebotCommandText`）只取 text 段，才是用户本人打的字。

### 4.2 网页入口（`server/api/characters/[id]/chat.post.ts`）

位置：`try {` 之后、调用 `generateConversationReplyWithMemoryAssistant` 之前。

```ts
const capabilityCommand = readCapabilityCommand({ content: message, addressedToSelf: true });
const capabilityCommands = capabilityCommand ? [capabilityCommand] : [];
```

网页入口请求体只有 `message`（trim，≤8000 字），没有引用和附件字段，正文就是用户本人写的，所以直接用 `message`，`addressedToSelf` 恒为 `true`。

### 4.3 为什么能保证「不改变行为」

- `promptInput`（`chat-reply.ts`）和 `publicInput`（`context-assistant.ts`）构建模型请求载荷时是**显式挑字段**的，新增的输入字段不会被带进去。
- 两个入口都是 `...(capabilityCommands.length ? { capabilityCommands } : {})`，没解析到命令时连字段都不出现。
- 测试里用假 `fetch` 抓了请求体，带与不带解析结果两次请求 `deepEqual`，且请求体里不含 `capabilityCommands` 字样。
