# 失效记忆功能专项审查报告

> 审查范围：`server/utils/stale-memory-*.ts`、`app/components/StaleMemoryAudit.vue`、失效标记对检索与上下文注入的链路。
> 审查日期：2026-11-27。以下原审与 R1–R8 记录修复前状态；当前实现、测试和部署说明见末尾「修复与验收」。

---

## 结论速览

| 结论 | 严重程度 |
| --- | --- |
| 失效判定只有「当前有效性」一个维度，历史价值与参考价值在模型输出结构里**根本不存在**，被失效的条目直接退出检索，两类价值随之一并丢失 | 🔴 高 |
| CONTRADICTED 与 OBSOLETE 的判定**完全依赖模型语义**，提示词对「历史事件 vs 临时状态」的区分约束偏软，存在把「已解决的历史故障」判成 OBSOLETE 的误判风险 | 🟠 中高 |
| 长期记忆与忆泡的失效标准**不一致**（阈值、自动归档、硬规则各不相同），但各自有注释说明其取舍理由 | 🟡 中 |
| 失效标记的实际影响是**二元且不可逆于检索**：`status: ACTIVE` 之外的记忆/忆泡都不再进入检索，没有「降权但保留」的中间态 | 🔴 高 |
| 存在「仅凭时间/约定过期」就判过时的入口（OBSOLETE 定义里的「约定那天已过去」），与本次审查提出的原则冲突 | 🟠 中高 |

**总判断**：当前系统在「宁可漏判、不要误删」的大方向上是正确的（模型只提名、人工确认、可恢复、关系/偏好硬豁免），但它把「失效」实现成了「从当前事实里抹掉」，而不是「从当前事实里降级、但仍保留历史与参考价值」。这正是本次审查要解决的核心差距。

## 1. 当前失效记忆的真实判定逻辑

失效体检的完整链路如下（依据代码实况，非设计稿）：

### 1.1 候选收集（`stale-memory-audit.ts`）

- 长期记忆：取 `status = ACTIVE` 且可读范围内的条目，按 `updatedAt` 倒序，最多 200 条。
- 忆泡：取 `status = ACTIVE` 且可读范围内的条目，按 `occurredAt` 倒序，最多 200 条；默认范围最近 7 天，可扩展到 30 天或单日。
- 长期记忆与忆泡各自**独立调一次模型**（一次请求最多两次模型调用，每次调用前都查额度）。

### 1.2 模型判定（`SYSTEM_PROMPT`，`stale-memory-audit.ts:65-82`）

模型只允许输出两种判决，且必须附 `reason` 与 `confidence`：

- **CONTRADICTED**：与清单里更新的条目冲突，或明显被后来的事实推翻（能力已上线却记着不能用、配置/服务商换了、关系或称呼变了、旧状态被新状态替代）。
- **OBSOLETE**：临时状态、临时进度，或已经过期的**明确**约定（答应了某天要做的事，那天已经过去）。

提示词里写了三条「不判失效」的豁免（主观偏好/性格/关系、一次性共同经历、群内玩笑），并要求「看条目的主体」：主体是人物/关系/长期设定的不判失效，只有「整条讲的就是那件已经过去的事」才判 OBSOLETE。

### 1.3 解析与过滤（`stale-memory-parse.ts`）

- 短 id 白名单：模型只能引用本轮清单里的 `M1..Mn` / `E1..En`，编 id、抄错 id、跨轮次 id 一律丢弃。
- verdict 只认 `CONTRADICTED` / `OBSOLETE`，其余（如 `DUPLICATE`）丢弃。
- `confidence < 0.65` 的条目不进列表（低把握不摆出来）。
- **硬规则**：`RELATIONSHIP` / `PREFERENCE` 类长期记忆只接受 CONTRADICTED，不接受 OBSOLETE（`stale-memory-parse.ts:109-110`）。这条只在长期记忆生效，忆泡没有分类字段，不受此约束。

### 1.4 落库（`stale-memory-apply.ts`）

- 长期记忆：`status → INVALIDATED`，并写 `validTo = now`。
- 忆泡：`status → ARCHIVED`。
- 全程 `FOR UPDATE` 行锁 + 指纹复验（`stale-memory-version.ts` 对 `memoryScopeId/category/content/importance/updatedAt` 或 `dayKey/title/detail/participants` 做 sha256），内容变了整批 409，缺指纹 400。
- 写审计日志（`memory.invalidated` / `memory.event_archived`），`reason`、`source`（人工 `stale-memory-audit` / 自动 `stale-memory-audit-auto`）都留痕。

### 1.5 自动归档（仅忆泡，`stale-memory-audit.ts:192-208`）

忆泡被模型判 `OBSOLETE` 且 `confidence >= 0.9` 时，**不等人工确认**，直接归档。代码注释给出的理由是「归档可恢复、审计有记录、时效性本来就强，错清一条代价小；长期记忆错清一条是『她忘了你们之间的事』，永远保留人工确认」。

## 2. CONTRADICTED 与 OBSOLETE 是否存在误判

### 2.1 与本次审查提出的「正确语义」对照

本次审查建议两个判决应满足的约束，与现状对照：

| 建议约束 | 现状 |
| --- | --- |
| CONTRADICTED 必须有明确的新事实作为依据 | ✅ 提示词写了「与清单里更新的条目冲突，或明显被后来的事实推翻」 |
| 新旧记忆必须描述同一对象/属性/状态 | 🟡 仅靠模型语义判断，无结构化校验；提示词未明确「不同时间/场景不算推翻」 |
| 应保留旧记忆作为历史记录 | 🔴 未实现——被推翻的旧记忆 `status → INVALIDATED` 后退出检索，历史价值丢失 |
| OBSOLETE 必须能判断是临时状态/阶段性进度/有期限约定 | 🟡 提示词有此意图，但判定仍靠模型语义 |
| OBSOLETE 必须有证据证明状态已结束 | 🔴 未强制——「约定那天已过去」本身就是仅凭时间的证据 |
| 不能仅凭时间过去判过时 | 🔴 冲突——OBSOLETE 定义明确包含「答应了某天要做的事，那天已经过去」 |
| 一次性经历/故障记录/开发过程/重要讨论不应因事情结束而失效 | 🟡 提示词写了豁免「一次性共同经历」，但**没有覆盖「已解决的历史故障」这一类** |

### 2.2 对示例记忆的实测推演

原始记忆（长期记忆，假设 category = FACT）：

> 她的文字转语音在 2026-11-06 深夜出过问题（前两次只出文字、没真出声），原因是程序没重启；重启后恢复正常，之后能连续发语音。

当前系统的可能处理：

- 模型读到「出过问题……重启后恢复正常」，很可能判 **OBSOLETE**（「临时故障，已恢复」），confidence 大概率 ≥ 0.65。
- 若是长期记忆，人工勾选后 → `INVALIDATED`，退出检索。
- 若是忆泡，且 confidence ≥ 0.9，则**自动归档**，不等人工确认。

处理结果与本审查建议的差距：

| 维度 | 建议 | 现状 |
| --- | --- | --- |
| 当前有效性 | 不再作为「当前语音异常」依据 | ✅ 达成（失效后不参与检索） |
| 历史价值 | 保留（真实发生过的故障） | 🔴 丢失（退出检索，时间线里忆泡只显示 ACTIVE） |
| 参考价值 | 保留（未来排查线索） | 🔴 丢失（同上） |
| 检索表现 | 问「过去是否出过语音故障」应能查到 | 🔴 查不到（ARCHIVED 忆泡不进检索） |

**结论：CONTRADICTED 与 OBSOLETE 存在误判，且误判的代价不是「判错类别」，而是「彻底丢失历史与参考价值」。这是本次审查发现的最核心问题。**

## 3. 长期记忆与忆泡的判断标准是否一致

**不一致**，且差异是刻意设计的（有注释说明），但差异点本身暴露了判断标准的割裂：

| 维度 | 长期记忆 | 忆泡 |
| --- | --- | --- |
| 置信度门槛 | 0.65（人工列表） | 0.65（人工）+ 0.9（自动归档） |
| 自动处理 | 永不自动，必须人工勾选 | OBSOLETE≥0.9 自动归档 |
| 硬规则豁免 | RELATIONSHIP/PREFERENCE 不接受 OBSOLETE | 无（忆泡无分类字段） |
| 失效后状态 | INVALIDATED（+ validTo） | ARCHIVED |
| 失效后是否可回溯 | 时间线可见（`status ≠ TRASHED`） | 时间线不可见（`status = ACTIVE`） |

关键发现——**回溯能力反而倒挂**：

- 长期记忆被标 INVALIDATED 后，在 `/timeline` 里仍可见（`memoryWhere = status: { not: "TRASHED" }`，见 `timeline.get.ts:50`），且记忆列表接口支持按 `status=INVALIDATED` 筛选查看。
- 忆泡被标 ARCHIVED 后，`/timeline` 的 `eventWhere = status: "ACTIVE"`（`timeline.get.ts:52`），`/days` 的查询也全是 `status: "ACTIVE"`。**归档忆泡在默认视图里彻底消失**，只能通过「当天已隐藏」入口恢复，但「已隐藏」本身是否有独立的归档列表接口，代码中未见明确的读接口（`[eventId].patch.ts` 的注释声称「时间线和那天都还要能回溯」，但实际 timeline 查询已把 ARCHIVED 排除）。

这是一个**注释承诺与代码实现不符**的点：`[eventId].patch.ts:16` 说「时间线和『那天』都还要能回溯」，但 `timeline.get.ts:52` 把忆泡限定为 `ACTIVE`，ARCHIVED 忆泡在时间线里并不出现。

## 4. 失效标记对后续检索和上下文注入的实际影响

这是本次审查的关键结论：**失效标记是一个「检索级硬开关」，而不是「降权」**。

### 4.1 检索候选的过滤（证据）

- 长期记忆候选：`prompt-memory-candidates.ts:29` → `status: "ACTIVE"`。
- 忆泡候选：`prompt-event-candidates.ts:27` → `status: "ACTIVE"`。
- 记忆排序/衰减：`memory-retrieval.ts` 只处理候选集内的排序，不涉及状态过滤（过滤发生在更上游的候选加载）。

### 4.2 结论

一旦记忆被标 INVALIDATED、忆泡被标 ARCHIVED：

1. **当前事实检索**：不再参与 —— 这是期望行为。
2. **历史查询**：「过去发生过什么」的检索同样查不到 —— 这是问题。当前系统**没有独立的「历史事件」检索通道**，`status: ACTIVE` 是唯一的入口过滤，历史价值与参考价值没有退路。
3. **上下文注入**：不注入 —— 期望行为（避免历史故障误导当前状态判断）。

换句话说，系统目前只有两种状态：**「ACTIVE = 全量参与检索」** 和 **「非 ACTIVE = 完全不参与检索」**。缺少「当前已失效、但历史/参考价值仍需可检索」的第三态。

这与本次审查的三个维度（当前有效性 / 历史价值 / 参考价值）直接矛盾：当前设计**用「当前有效性」这一个维度，决定了另外两个维度的存亡**。

## 5. 八类场景的现有处理结果

| 场景 | 预期结果 | 现状 | 是否达标 |
| --- | --- | --- | --- |
| 过去发生过、已解决的故障 | 保留历史，不作为当前故障 | 大概率被判 OBSOLETE → INVALIDATED/ARCHIVED，历史与参考价值全丢 | 🔴 不达标 |
| 旧模型被新模型替代 | 旧模型不再是当前事实，可保留历史 | 被判 CONTRADICTED → INVALIDATED，退出检索，历史价值丢 | 🟡 半达标（当前性对了，历史性丢） |
| 已完成的开发任务 | 不再作为进行中任务，可保留开发历史 | 被判 OBSOLETE（临时进度）→ 失效，历史丢 | 🔴 不达标 |
| 一次重要的共同经历 | 不因时间过去而失效 | 提示词有「一次性共同经历」豁免，大概率能保住；但取决于模型是否识别为「共同经历」vs「临时状态」 | 🟡 半达标（靠模型语义，非结构化保证） |
| 已结束的临时配置 | 不再作为当前配置 | 被判 OBSOLETE → 失效 | ✅ 达标（这确实是临时状态，失效合理） |
| 后续信息明确推翻旧事实 | 允许标记旧事实失效 | CONTRADICTED → INVALIDATED | ✅ 达标（当前性正确） |
| 只有时间过去、无新证据 | 不应自动判失效 | **存在反例**：OBSOLETE 定义含「约定那天已过去」，且忆泡 OBSOLETE≥0.9 会自动归档，无需新证据 | 🔴 不达标 |
| 旧记忆仍有故障排查价值 | 应保留参考价值 | 无「参考价值」维度，失效即丢 | 🔴 不达标 |

**总结**：8 类场景中，2 类达标（临时配置、明确推翻），2 类半达标（旧模型替代、共同经历），4 类不达标（历史故障、已完成任务、纯时间流逝、排查参考价值）。不达标的核心原因高度一致——**缺少「历史价值 / 参考价值」的独立维度，以及「失效但可检索」的中间态**。

## 6. 发现的问题及其严重程度

### P0（高，需方案级调整）

1. **「失效 = 退出检索」的二元模型抹掉了历史与参考价值**。
   失效后 `status ≠ ACTIVE` 即彻底退出检索，且无独立的历史事件检索通道。历史故障、开发过程、重要经历一旦被失效就再也查不到。

2. **判定维度单一**。
   模型输出结构只有 `{verdict, reason, confidence}`，没有「历史价值 / 参考价值」字段。无法表达「当前已失效、但仍有保留价值」的语义。

### P1（中高，需约束级补强）

3. **OBSOLETE 存在「仅凭时间判过时」的入口**。
   提示词明确写「答应了某天要做的事，那天已经过去」→ OBSOLETE。这违背「只有时间过去不应自动失效」的原则。对于「已解决的历史故障」，模型很可能把「已恢复」理解为「已过时」。

4. **忆泡高置信自动归档，缺乏「历史故障类」的豁免**。
   `confidence >= 0.9` 的 OBSOLETE 忆泡自动归档，没有类似长期记忆「关系/偏好」的硬豁免。历史故障类忆泡若被判高置信 OBSOLETE，会绕过人工确认直接归档。

5. **「历史故障」这一类没有进入豁免清单**。
   提示词的豁免只覆盖「主观偏好/性格/关系/共同经历/群内玩笑」，没有覆盖「已解决但具排查价值的历史故障/开发过程」。

### P2（中，需一致性收口）

6. **长期记忆与忆泡的失效标准割裂**。
   阈值、自动归档、硬规则、失效后状态、回溯能力五个维度各不相同，且回溯能力倒挂（长期记忆失效后时间线仍可见，忆泡归档后时间线不可见）。

7. **注释承诺与实现不符**。
   `[eventId].patch.ts:16` 声称归档忆泡「时间线和那天都还要能回溯」，但 `timeline.get.ts:52` 把忆泡限定为 `ACTIVE`，归档忆泡在时间线里不可见。

8. **FACT 类别承载了「临时状态」与「长期事实」两类语义**。
   功能总表 `2026-11-24` 已自认「临时进度与长期事实在写入时没有区分，都落在 FACT」。这导致体检时模型难以从类别层面区分「临时状态」和「长期事实」，只能靠语义硬猜。

### P3（低，观察项）

9. 失效判定依赖 `updatedAt` 排序取前 200 条，历史更久远的记忆可能长期不被体检覆盖（但 `MAX_MEMORIES=200` 对当前规模够用，属观察项）。

## 7. 推荐的最小修改方案

> 本阶段只出方案，不落地。方案遵循「最小改动、不引入新数据库或复杂状态系统、不加正则/关键词堆砌」的约束。

### 方案 A：在模型输出里引入「处置」维度（推荐，改动最小）

不改变 `CONTRADICTED` / `OBSOLETE` 的判定本身，而是在**输出结构上区分「当前性」与「价值」**：

1. 模型输出新增一个字段，例如 `keepHistory: boolean`（或 `disposition: "invalidate" | "downgrade"`），表示「这条虽然当前失效，但历史/参考价值仍需保留」。
2. `parseStaleAudit` 解析并保留该字段；`StaleAuditItem` 透传给前端。
3. UI 在列表里对 `keepHistory=true` 的条目展示「将降级为历史记录，仍可在历史查询中检索」的提示，与「彻底失效」区分。
4. **数据库零改动**：可复用现有 `MemoryItemStatus` 的 `ARCHIVED`（语义已是「仍可回溯」，见 schema `:230` 注释）作为「降级但保留」的落点，把当前 `INVALIDATED` 留给「彻底失效」。

关键点：**利用 schema 里已经存在、但当前失效体检没用上的 `ARCHIVED` 状态**。schema `:230` 注释明确写「ARCHIVED 只表示被压缩归档，仍可回溯」——这恰好是「历史价值保留」的语义载体，不需要新增枚举。

### 方案 B：补强提示词，明确「历史事件 vs 临时状态」的区分

在 `SYSTEM_PROMPT` 中新增两条硬约束（对应 P1-3 / P1-5）：

- 明确「已解决的历史故障、已完成的开发过程、一次性经历」**不判 OBSOLETE**，即使事情已结束；只有「描述的就是临时状态本身，且状态已结束」才判 OBSOLETE。
- 明确「只有时间过去、没有新事实」**不构成** CONTRADICTED 或 OBSOLETE 的依据；「约定那天已过去」需同时满足「该约定本身就是临时的、且没有延续价值」。
- 收敛「约定过期」措辞，避免模型把「历史事件的日期」当成「约定到期」。

### 方案 C：给忆泡自动归档加「历史故障」豁免（对应 P1-4）

在自动归档前，增加与长期记忆「关系/偏好」同级的硬豁免：忆泡若被识别为「故障/问题/排查」类（可通过标题/详情的现有信号，或直接改为**把自动归档阈值再抬高、或去掉自动归档、一律人工确认**），不自动归档。最小改动是**先去掉忆泡自动归档**（或把阈值从 0.9 提到 0.98），改回「一律人工确认」，与长期记忆对齐。

### 方案 D：修复回溯不一致（对应 P2-7）

## 9. 数据库结构变更与历史数据迁移评估

### 9.1 数据库结构变更

**不需要新增字段或新表。** 理由：

- `MemoryItemStatus` 已含 `ACTIVE / SUPERSEDED / ARCHIVED / INVALIDATED / TRASHED` 五态，其中 `ARCHIVED` 的 schema 注释（`:230`）已声明「仍可回溯」语义，可直接作为「降级但保留」的落点。
- `MemoryItem.validFrom` / `validTo` 已存在，可继续承载「当前有效性区间」的表达。
- `MemoryEventStatus` 的 `ARCHIVED` 同理。

方案 A 的 `keepHistory` 属于**模型输出与内存对象**层面的字段，不落库（或若需持久化，可复用 `ARCHIVED` 状态本身，无需新列）。

### 9.2 历史数据迁移

**本阶段不需要迁移。** 但需关注一个既有事实：

- 已被标 `INVALIDATED` 的长期记忆、已被标 `ARCHIVED` 的忆泡，**其历史价值目前是「物理上还在库、检索上已不可达」**。数据没有丢失（软状态变更，未物理删除），因此若后续落地「降级但保留」方案，这些历史数据仍可被重新纳入检索，**无需回填**。
- 唯一需要留意的是：若后续决定「重新开放归档忆泡的历史检索」，可能需要对既有 `ARCHIVED` 忆泡做一次**语义甄别**（区分「因降噪/压缩归档」vs「因失效归档」），因为当前两种语义共用同一个 `ARCHIVED` 状态。这属于「未来方案落地时的可选回填」，不是本阶段的迁移义务。

**结论：无需数据库结构变更，无需历史数据迁移；未来方案落地时最多需要一次「归档语义甄别」的软回填，且数据本身完好无损。**

## 2026-11-27 修复与验收

### 判定与归档

- 统一 [体检提示词](../server/utils/stale-memory-audit.ts) 与 [写入提示词](../server/utils/memory-ai.ts) 的历史保护原则。语音故障及排查、已完成的重要开发过程、一次性共同经历按发生时点保留；单纯日期已过或事情有后续不构成失效证据。整条只描述临时配置、状态或待办，且有明确撤回、完成、取消或替代证据时，仍可提名 `OBSOLETE`。`CONTRADICTED` 需要新事实指向同一对象和属性或状态；历史事件只有原记录本身有误才提名。

### 周期总结的实际写入链路

[常驻 Worker](../scripts/run-memory-worker.ts) 调用 [processNextMemoryJob](../server/utils/memory-worker.ts)。常规 `GENERATE_SNAPSHOT` 从本周期来源消息及 ACTIVE 记忆生成结果；模型返回后，Worker 在复验租约和范围锁的事务内创建快照，检查建议置信度、目标及消息白名单，然后以 `actorType: WORKER` 调用 [applyMemoryChange](../server/utils/memory-change-apply.ts)，通过就写 `INVALIDATED`、`validTo` 和 `memory.ai_invalidated` 审计，**没有人工审核开关**。`REGENERATE_SNAPSHOT` 只保存 `NOT_APPLIED_REGENERATION` 建议；[人工复核接口](<../server/api/characters/[id]/snapshots/[snapshotId]/review.post.ts>) 采纳时以 `USER` 走同一落库防线。

两条路径都要求 `INVALIDATE` 声明 `TEMPORARY_STATE_ENDED` 或 `CONTRADICTED`、目标仍是提炼时所见的内容与分类，并能核对至少一条引用的用户原始消息。仅引用助手消息不能落库。临时状态结束还必须与快照 `importantEvents` 共用一条用户来源，不能作用于 EVENT、RELATIONSHIP 或 PREFERENCE。旧快照的无类型失效建议、原始确认来源已被清理的失效建议可忽略；ADD、UPDATE 的历史复核行为照旧。对于混用 FACT 存放的历史经历和临时状态，以及新证据是否真的确认同一件事，仍需模型按提示词判断语义；类型和消息引用本身不能证明语义。周期提炼提示词版本为 `memory-extraction-v11`，按天忆泡及聊天提示词内容未改。

已有 ACTIVE 忆泡经 `periodEvents` 提供给周期总结；新增的来源引用仅限本轮已选原始消息。完成经过可写入快照 `importantEvents`，原文引用随快照来源保存；按天任务尚未整理成忆泡时，也可用明确的本周期原文留下同样可回查的事件。常规 Worker 不创建第二条忆泡，也不归档原忆泡。测试验证了实际写入后的快照事件、来源和原忆泡的 ACTIVE 状态。

## validTo 时间语义专项修正

基于 `6a4e4f8`。原实现对失效建议与 `importantEvents` 共同引用的用户消息取最早时间。计划、背景与完成确认都可能在两处出现，因此该交集能证明来源可追溯，却不能区分哪些消息单独证明状态已经结束。

[周期提炼](../server/utils/memory-ai.ts#L529)（`memory-extraction-v12`）要求 `TEMPORARY_STATE_ENDED` 单独提供 `endingEvidenceMessageIds`，只包含明确确认同一临时状态已完成、取消或被替代的用户原文。计划、背景、进度和事后补充仍可进入普通证据。[Worker](../server/utils/memory-worker.ts#L1557) 为重新提炼的建议保存此字段，[人工复核](<../server/api/characters/[id]/snapshots/[snapshotId]/review.post.ts#L150>) 从快照读回。

[共用落库逻辑](../server/utils/memory-change-apply.ts#L383) 逐条确认所标消息仍可读取、属于该建议的用户证据且被快照事件引用，时间戳必须有效。`validTo` 取这些直接确认中的最早服务器记录时间；重复确认或普通背景的先后不会改变该规则。这是最早可核对的确认时间，不是根据转述倒推出的实际发生时刻。模型仍负责区分语义；代码核对证据身份与引用。字段缺失、任一所标来源不合格或原文已清理时整条不应用；旧版待审临时失效建议可忽略或重新提炼，不回落到其他消息时间。`CONTRADICTED` 的时间选择及 EVENT、RELATIONSHIP、PREFERENCE 保护保持原样。

回归用可控模型和隔离 PostgreSQL 检查普通 Worker 写入的 `status`、`validTo`，以及人工采纳写入的完成确认时间。用例包含单条确认、计划加确认、多条早晚背景、两条逆序确认、无有效确认、`CONTRADICTED` 原时间规则及三个保护分类。另验旧建议缺字段、确认来源被清理、助手消息和未被事件引用的消息不能应用。没有调用真实模型，也没有回填已写入的历史 `validTo`。

## P2-1 事件绑定设计与实现方案（待独立复审）

### 范围与现状核对

设计基准为 `db897fb`（包含 `6ff0803` 的时间修复及 `84ada78` 的复审归档）。本阶段只形成方案，未实施生产代码或测试变更。P2-2、更正确认时间、历史检索 P0 及其他工作线不纳入实现范围；P2-1 所需测试随其实现交付，不延后到下一阶段。

当前 [提炼解析](../server/utils/memory-ai.ts#L452) 将 `importantEvents` 解析为标题、详情和消息证据，没有事件身份或关联记忆。[落库函数](../server/utils/memory-change-apply.ts#L392) 对每条结束证据查找任意包含它的事件，因此事件甲的确认可能被变更乙引用。[Worker](../server/utils/memory-worker.ts#L1546) 的普通自动路径直接传分析结果，重新提炼路径另存审核建议；[人工复核](<../server/api/characters/[id]/snapshots/[snapshotId]/review.post.ts#L137>) 从不可变快照重建建议，事件目前只保留证据列表。三处必须使用同一绑定契约。

[MemorySnapshot](../prisma/schema.prisma#L739) 已有 JSONB `structuredContent`，可保存事件局部身份和绑定；[MemoryReview](../prisma/schema.prisma#L787) 继续按建议数组位置记录决定。无需新增字段、表、枚举、迁移或历史回填。`importantEvents` 是快照内分析事件，不是数据库 `MemoryEvent` 忆泡，不能拿输入 `periodEvents` 的 UUID 代替新契约。

### 建议契约

仅对 `INVALIDATE + TEMPORARY_STATE_ENDED` 增加以下内部 JSON 字段：

```json
{
  "importantEvents": [{
    "eventKey": "I1",
    "title": "完成同一轮回归",
    "detail": "负责人明确确认回归和结果核对均已完成。",
    "evidenceMessageIds": ["背景消息ID", "确认消息ID"],
    "endedMemoryIds": ["回归待办记忆ID", "结果核对待办记忆ID"]
  }],
  "memoryChanges": [{
    "action": "INVALIDATE",
    "invalidationBasis": "TEMPORARY_STATE_ENDED",
    "relatedMemoryId": "回归待办记忆ID",
    "endingEventKey": "I1",
    "evidenceMessageIds": ["背景消息ID", "确认消息ID"],
    "endingEvidenceMessageIds": ["确认消息ID"]
  }]
}
```

示例仅展示绑定字段，其他既有必填字段照旧。`eventKey` 是本次分析内的局部标识，建议固定为 `I1`–`I30`；不是数据库 ID、不是数组下标，也不能跨快照引用。`endedMemoryIds` 明确声明该事件能够结束哪些输入中的临时记忆；该声明仍是模型语义判断，不能作为绕过分类、范围、证据和版本校验的授权。

事件模型输出可保留没有绑定字段的普通历史事件；但临时失效必须引用唯一且完整的绑定事件。单条变更只绑定一个事件，若需要跨多个事件拼凑才能证明结束，本轮不自动应用，先重新整理为一个有完整证据的结果事件。一个事件可列出多个相关记忆，同一确认消息也可支持多个事件或变更；不引入消息已消费标志或事件独占锁。每条变更分别核验目标及其结束证据，不能因为第一条成功就跳过后续校验。

### 校验规则与失败行为

1. 先完整解析事件，再解析变更。保留按原始事件列表统计的键出现次数，不能先过滤无效事件再消除重复；重复键的所有绑定均不可用，防止首条/末条覆盖。事件 ID 不重编号，不按过滤后的数组下标猜绑定。
2. 绑定事件须有有效标题、详情、来源及唯一合法 `eventKey`。`endedMemoryIds` 非空、去重且最多 12 个，每个都须来自本次 active/global memory ID 白名单。绑定字段类型错误、数量越界或含未知 ID 时，将该事件标为不可绑定；可保留合法的描述性历史事件，但不得过滤坏 ID 后让原绑定继续生效。
3. 变更的 `endingEventKey` 必须精确指向一个可绑定事件，该事件的 `endedMemoryIds` 必须包含当前 `relatedMemoryId`。缺字段、不匹配、跨快照键、指向已被过滤的事件或存在歧义时，仅拒绝相关失效，不令合法 ADD/UPDATE 或其他独立建议整批失败。
4. 每条 `endingEvidenceMessageIds` 都须同时属于本变更的普通证据及指定事件的证据，不能再用任意事件的 `some`。继续要求 USER、原文存活、有效时间、目标原分类/正文未变、目标可写范围、既有历史分类保护和置信度门槛；任一指定结束来源不合格则整条拒绝，不只删除那条来源后继续执行。
5. 共用落库函数须重做结构绑定校验，不信任仅由模型解析通过的对象。普通 Worker 和人工复核都传入完整事件身份、目标列表及证据；不要通过 `flatMap` 只留下证据或重排键。可新增一个小型纯校验函数供两处调用，避免两套判据；不抽象成新记忆框架。
6. `validTo` 仍取指定事件内、经校验的直接结束确认中最早的服务器消息时间，不取事件日期、背景时间、当前时间或 `reviewEvidenceFallbackAt`。本轮不改变 `CONTRADICTED` 的任何时间规则。
7. Worker 不应用失败建议，保留现有拒绝计数；人工 ACCEPT 返回现有 409，不写 ACCEPTED 审核结果或失效审计，仍可 IGNORE。成功审计增加 `endingEventKey`，保留结束消息 ID 和快照 ID；不复制额外原文到全局审计。

### Worker、快照与人工复核的贯通

- 模型请求：说明事件与具体待办的对应关系、局部键及多记忆兼容规则；升级周期提炼模板版本（预计 `memory-extraction-v13`，以实施时实际版本为准），按天忆泡提示词不变。
- 普通生成：分析 JSON 保存事件键和目标列表，变更携带引用进入同一事务的共用校验；成功结果与审计也保存事件键，供追溯。
- 重新提炼：仍只生成 `NOT_APPLIED_REGENERATION`，同时保存 `endingEventKey`、`endingEvidenceMessageIds` 和当时的目标分类/正文。审核前不写记忆状态。
- 人工复核：请求体仍只有 `changeIndex` 和 `decision`，客户端不允许提交或覆盖绑定；服务端从该快照读取事件及变更，完整传给共用落库校验。继续复验当前目标和原文。
- 详情 DTO：当前 [DTO](../server/utils/memory-snapshot-dto.ts#L89) 会丢掉额外事件字段。最小实现可将绑定保持为服务端内部字段，审核接口直接读原快照，既有页面继续展示描述与来源；必须测试 DTO 的过滤不会反向改变审核依据。若复审要求页面展示绑定，应作为明确增加的交付项同步共享类型和 API 契约，不在实施中顺手扩展 UI。

### 兼容与语义边界

旧快照不回写。旧普通事件仍可读；旧的临时失效建议因为缺少具体绑定而不能再 ACCEPT，返回 409，可忽略或重新提炼。旧 ADD、UPDATE、CONTRADICTED 和已经完成的人工决定保持原行为。重启时可能有旧模板请求在途：新版落库遇到缺绑定对象拒绝临时失效，不作兼容放行；旧版 Worker 本身不会获得新防线，部署必须停止旧 Worker 并重启，生产 Web 同时加载新复核接口，不能让新旧常驻进程混跑。

**本方案能保证指定事件、指定记忆和指定证据在结构上相互对应，不能证明模型正确理解了正文。** 如果模型同时把乙记忆错列入甲事件的 `endedMemoryIds`，并输出一致的变更，结构校验仍可能通过；计划被模型错误标成直接确认同样不能靠 ID 判断纠正。不加入关键词正则假装解决语义，也不声称此方案彻底消除了误失效。模型应在不明确时不提议；真实语义效果需使用观察。若复审要求对这种自洽但语义错误的输出也提供硬保证，需要另行评估独立审核或人工确认策略，本阶段不擅自增加模型调用或禁止全部自动失效。

| 输出解析 | 合法绑定；缺键/不存在键/非法类型；重复键（含一条事件无效时）；未知目标；事件过滤后不重编号；原白名单不退化 |
| Worker 数据库 | 甲事件完成而乙待办仍 ACTIVE；事件目标列表含乙但变更指向甲时拒绝；正确绑定实际写入 status/validTo；两条相关待办共用同一事件及确认都成功；一条确认支持两个合法事件；任一结束来源不属于指定事件则拒绝 |
| 人工复核数据库 | 真正由 REGENERATE 路径保存绑定，再调用审核接口；错误绑定/旧建议缺绑定返回 409 且无副作用；正确绑定最终 status/validTo；原文清理、目标变更、重复采纳继续拒绝；快照不被回写 |
| 保护与兼容 | EVENT/RELATIONSHIP/PREFERENCE；单条完成及计划加完成；CONTRADICTED 原行为；ADD/UPDATE；自动归档仍关闭；范围和隐私隔离 |
| 已知语义缺口 | 单独记录模型同时错写事件目标与变更、计划错标确认的残余风险；不能把结构测试通过当成语义安全证明 |
