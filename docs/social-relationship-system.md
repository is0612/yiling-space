# 社交关系系统：现状与实施边界

更新日期：2026-11-08

## 1. 本轮目标

将已有的「她的朋友」能力接入成长系统，避免重复建设好友身份与交流策略的数据模型。后续在这套基础上逐步增加身份判断建议、关系发展和重要社交经历。

## 2. 已有数据模型与职责

当前不是一张独立的 Friend 表，而是两层数据：

- `ExternalIdentity`：以 `platform + platformUid` 唯一标识平台账号。身份类型为 `UNKNOWN / HUMAN / AI`，身份来源为 `AUTO / MANUAL`。同一平台账号的身份判断跨角色共享。
- `MemoryScope`（`EXTERNAL_IDENTITY`）：表示某个角色与该平台账号的关系。交流策略 `DEFAULT / ALLOW / BLOCK`、互动次数、最近互动、认识来源和角色自己的备注都在这一层，因此不同角色可以对同一账号作不同决定。

不要另建一套重复的好友档案表，也不要把对方的昵称当作跨平台身份合并依据。跨平台账号绑定必须经过验证。

## 3. 已有行为

- QQ 群成员第一次发言就会建立「遇到过」关系，不增加互动次数；只有角色真正回应对方才按现有口径增加群聊互动次数。
- 私聊和群聊都使用已有的好友身份记录。
- 身份可手动标记为未知、真人或 AI；人工设置会写入 `MANUAL`，普通互动不能覆盖。
- 交流权限按角色生效：默认、允许、禁止。
- OneBot 群聊入口先过滤身份与交流策略，攒批发送前再次校验；被明确禁止的发言不会进入当前回复上下文。
- AI-only 群聊另有连续轮数保护，不能把它与某一个好友的 BLOCK 规则混为一谈。

好友管理现位于 `/growth/social/friends`，旧 `/identities` 地址重定向到新页面；API 仍位于 `/api/admin/identities`。页面复用原有业务逻辑，不复制数据或接口。

## 4. 尚未实现 / 不应误认为已有

- AI / 真人自动识别尚未实现；目前身份分类需要用户手动设置，未知身份保持 `UNKNOWN`。
- 关系亲疏目前只有互动次数、最近互动和排序能力，不等于真正的亲密度或关系等级。
- 尚无群级交流策略覆盖；现有策略是角色级。
- 尚无独立的社交经历时间线。重要经历应与记忆系统协作，不复制一份长期记忆。
- 好友工作区已迁入成长系统，并使用左下角全局角色选择器；切换角色时加载对应角色自己的好友数据。角色级社交关系与权限不跨角色复用。

## 5. 建议实施顺序

1. **接入成长系统（已完成）**：增加社交关系系统总览，说明已有能力和真实边界。
2. **好友管理迁移（本轮）**：将原好友管理页迁入成长系统的「好友档案」，改用左下角全局角色选择器；旧 `/identities` 地址保留重定向，原有筛选、排序、分页、身份、交流权限、备注审核和删除能力均复用。
3. **身份分类辅助交互策略**：真人 / AI / 未知。优先使用平台可信标记；模型推断只能作为待确认建议，不逐条额外调用模型、不覆盖人工分类；证据不足时保持未知。身份分类不是好友资格或关系阶段的门槛。
4. **好友关系发展**：采用「陌生 / 认识 / 朋友 / 好朋友」等可解释的关系阶段，真人和 AI 都可以成为朋友。阶段是角色自己的社交数据；互动次数不能直接等同于亲密度，也不能仅凭次数自动升级。由角色提出关系变化想法，系统核验依据后自动更新，不要求用户审批。
5. **主动联系规则**：用户已确认允许角色主动联系关系良好的朋友，不限真人或 AI，不必每次由用户发起。身份分类只辅助判断交流节奏和 AI 连续对话风险，不决定关系亲疏。现阶段优先在共同 QQ 群中 @ 对方；私聊与主动加好友作为未来渠道能力扩展。需要设计冷却时间、每日次数上限、群聊连续 AI 对话限制及暂停/恢复条件；主动联系应有真实话题或互动缘由，避免无意义的定时消息。
6. **社交经历**：明确哪些事件值得记录，以及它与忆泡、长期记忆、阶段总结的引用关系后再实现；不复制一份长期记忆。

## 6. 验收原则

- 一个账号在不同角色下可以有不同交流权限；身份分类仍是账号级。
- BLOCK 在接收入口和攒批发送前都有效；被屏蔽内容不得进入回复上下文。
- 人工身份分类不被自动更新覆盖。
- 未知身份不被猜测成真人或 AI。
- 关系阶段必须能解释依据，并允许用户修正。
- 真实 QQ 群验收由本地 DSH 执行；代码级修改先通过相关测试、类型检查、SFC、Lint 和构建。


## 7. 第二阶段设计共识（2026-11-08）

本节记录已讨论确认的产品方向，不代表相关功能已经实现。

### 7.1 角色数据隔离沿用现状

- 好友列表、关系阶段、交流权限、互动记录均属于当前选中角色的社交数据。
- 切换全局角色时，好友工作区加载新角色自己的好友数据；不把上一个角色的关系或权限带到新角色。
- 不新增一套跨角色共享的好友关系。账号身份分类仍由现有平台账号身份档案承担；角色与账号之间的关系继续沿用现有角色级数据范围。

### 7.2 身份分类

- 身份类型仍为真人（HUMAN）、AI（AI）、未知（UNKNOWN）。身份分类是对平台账号的事实认知，不是好友资格或关系等级；真人与 AI 都可以成为朋友。
- 优先采用平台提供的可信身份标记；模型推断只能形成待确认建议，不能仅凭语言风格自动定性。
- 证据不足时保持 UNKNOWN；用户人工确认优先，自动结果不得覆盖人工设置。
- 当前自动识别尚未实现，不得在 UI 或文档中描述成已有能力。
- 用户人工修改身份是纠正系统认知与现实不符的情况，不代表用户在替角色选择朋友；人工分类仍优先于未来自动建议。
- 身份分类仅作为交互策略的辅助信号。当前部分 AI 容易把对话持续下去，因此需要节奏和连续对话保护；不能因为对方是 AI 就认定关系不可能发展。

### 7.3 好友关系与主动互动

- 关系阶段可探索「陌生 / 认识 / 朋友 / 好朋友」，最终命名和升级依据待进一步设计。
- 关系阶段不是互动次数的别名；互动次数、关系亲疏和交流权限是不同概念。
- 用户已明确允许角色在没有用户逐次指示的情况下，主动联系关系良好的朋友；对象可以是真人，也可以是 AI。
- 是否主动联系应结合当前角色与该朋友的关系、单独交流权限和实际渠道能力。身份分类只影响交流节奏与防刷屏策略，不决定关系阶段。
- 主动联系不等于无限制发言：需要冷却时间、每日次数上限，并遵守群聊连续 AI 对话的防刷屏限制。
- 主动联系应尽量基于真实的共同话题、此前互动或合理的交流缘由，避免机械定时问候。
- 现有 BLOCK 必须优先；主动联系权限不能绕过好友屏蔽、渠道权限或群聊安全闸门。
- 冷却时长、每日次数、连续轮数及暂停/恢复条件尚未定值，实施前先检查现有 AI-only 连续轮数保护，避免重复造机制。
- 当前交流过滤在 `DEFAULT` 下会屏蔽 AI 发言，这是现有防止低成熟度 AI 无限接话的策略，不应被误解为 AI 不能成为朋友；未来应结合关系授权与节奏控制重新评估默认策略，不能仅凭身份永久否定交流。

### 7.4 社交经历与记忆

- 社交经历尚未实现。先定义哪些互动值得成为社交事件，再决定如何与忆泡、长期记忆和阶段总结关联。
- 社交系统负责关系与社交事件的结构化事实；记忆系统负责筛选、提炼和长期保存。不要在两个系统各复制一份长期记忆。

### 7.5 实施前置原则

- 先只读审查现有身份识别、交流过滤、AI-only 轮数保护和记忆事件管线，再确定最小改动范围。
- 优先复用现有 ExternalIdentity、角色级 MemoryScope 和现有 QQ 入口过滤，不重复建立身份或好友表。
- 本阶段暂不改代码、数据库或 QQ 过滤逻辑；先完成设计与验收标准，再拆成小 PR。


## 8. 第二阶段现状审查（2026-11-08）

本节为基于当前代码的只读盘点；不代表新增功能已实现，也不替代 DSH 在本地的运行验收。

### 8.1 已有基础

- **身份档案与人工分类**：`ExternalIdentity.kind` 已有 `UNKNOWN / HUMAN / AI`；`kindSource` 已有 `AUTO / MANUAL`。管理 API `PATCH /api/admin/identities/:id` 在用户修改身份时写入 `MANUAL`。`kindSource = AUTO` 只是默认来源标记，不代表项目已经有自动识别器。
- **角色级交流权限**：`MemoryScope.friendChatPolicy` 已有 `DEFAULT / ALLOW / BLOCK`。`shouldBlockFriendSpeaker()` 明确规定：BLOCK 始终屏蔽；ALLOW 放行；DEFAULT 下 AI 屏蔽，真人和未知保持原有行为。
- **遇见即建档**：群成员首次发言时可以建立身份和当前角色关系，互动次数不增加，因而可以在第一次正式互动前人工标记身份或设置屏蔽。
- **群聊防刷屏**：`Conversation.consecutiveAiRounds` 已记录连续 AI-only 群聊轮数；`MAX_CONSECUTIVE_AI_ROUNDS = 3`。达到上限后暂停该轮；明确真人参与后计数清零。UNKNOWN 不会被当成 AI 增加轮数，也不会被当成人类清零。
- **已有主动表达管线**：私聊主动找话采用「想 → 判 → 说」目的池与硬闸门，默认关闭；群聊冷场主动起话题也有独立开关、安静时段、冷场阈值、每日上限和最小间隔，默认关闭。群聊主动起话题还受群模式限制，`mention` 模式不主动发起。
- **社交内容与记忆已有连接**：好友关系范围与对话记忆范围复用 `MemoryScope(EXTERNAL_IDENTITY)`；好友范围可以进入周期记忆提炼。现有 `interactionCount` 记录互动量，`listAcquaintances()` 将它用于熟悉程度提示，但代码注释明确它不是亲密度。

### 8.2 尚未发现的能力 / 明确缺口

- **自动身份识别器**：当前盘点到身份字段和人工编辑 API，未发现可信平台信号采集、自动分类执行器或待确认建议工作流。不能把 `AUTO` 默认值解释为自动识别已上线。
- **关系阶段**：未发现陌生 / 认识 / 朋友 / 好朋友等持久化阶段、阶段变化证据或建议机制。
- **针对具体 AI 好友的主动联系**：已有主动私聊目标主要是主人最近的 QQ 私聊会话；群主动表达是群冷场时开话题。尚未发现按某个 AI 好友的关系阶段、单独授权和共同话题来挑选收件人的专属流程。
- **结构化社交经历**：好友范围的对话记忆提炼已经存在，但未发现独立的社交事件/关系变化时间线。不能把普通聊天记忆误当成关系事件系统。

### 8.3 重要边界与风险

- 不要另建好友表或重复实现 `DEFAULT / ALLOW / BLOCK`；优先在现有身份档案、角色级关系范围上扩展。
- 不要把 `kindSource = AUTO` 当作自动识别功能，也不要用模型仅凭语气猜测身份并自动覆盖人工分类。
- 不要让 HUMAN / AI / UNKNOWN 决定关系阶段或好友资格；身份类型仅辅助交互策略。
- 不要把互动次数直接升级成亲密度；关系阶段需要独立证据与可纠正机制。
- 不要把现有群冷场主动发言直接改造成指定好友联系；两者目标对象、触发条件、提示词和社交风险不同。
- 任何好友主动联系都必须先检查当前角色与该好友的 BLOCK/ALLOW、平台和渠道能力、用户配置、每日额度、冷却时间及重复发送保护；未确认关系或目标不明确时不发送。
- 现有 3 轮 AI-only 保护只覆盖 OneBot 群聊轮次，不应误称为跨平台、跨群或私聊的通用对话上限。

### 8.4 建议的实施顺序

1. 先补齐设计与验收标准：关系阶段的含义、由角色提出变化建议并由系统核验后自动保存的流程、主动联系的对象选择和停止条件。
2. 再实现最小的角色级关系阶段数据与管理 UI；不改变现有身份分类和交流权限语义。
3. 在独立设计并确认授权/目标选择/频率闸门后，增加「主动联系指定好友」能力；复用现有主动表达目的池与闸门思路，不直接复用面向主人的收件人解析。
4. 最后设计结构化社交事件，并明确它与现有好友范围记忆提炼、忆泡和长期记忆的分工。

### 8.5 本次审查范围

已只读检查 `friend-chat-policy.ts`、`friends.ts`、OneBot 群聊入口相关逻辑、好友身份 PATCH API、群主动表达设置、主动找话文档，以及成长系统社交关系文档。未修改业务代码、数据库或 QQ 过滤；未运行本地测试、类型检查、Lint、构建或真实 QQ 验收。


## 9. 关系阶段自然成长（已确认方向，尚未实现）

关系阶段用于描述角色与某位朋友的相处状态，不是互动计数器，也不是用户审批出来的等级。真人和 AI 在关系成长上遵循同一套原则。

### 9.1 阶段含义

- **陌生**：知道对方是谁或在群里遇见过，但还没有形成有意义的相处经历。
- **认识**：发生过实际交流，对对方有初步了解。
- **朋友**：有持续或有质量的交流，逐渐形成共同话题、相互了解或共同经历。
- **好朋友**：关系稳定且熟悉，有较多有意义的共同经历，形成独特的默契或回忆。

阶段最终文案可以在 UI 设计时微调，但不能把阶段实现成积分或累计消息数量。

### 9.2 谁提出、谁核验、谁保存

1. 日常聊天与记忆整理照常运行，不要求每条消息都调用关系评估模型。
2. 有新的重要社交经历，或本地任务达到合适的评估时机时，角色可以结合已有关系和真实经历形成阶段变化建议。
3. 社交系统核验建议引用的证据是否真实存在、是否属于当前角色与该朋友、是否已经被重复使用。需要语义理解的工作未来再由成长系统的专职 AI 分工；目前不指定由语境助手、记忆助手、主聊天模型或新助手承担。
4. 证据充分时自动保存新阶段与变化记录，不需要用户逐次批准；证据不足则保持原阶段，等待后续相处。
5. 升级和降级都允许，但降级应更加谨慎。长期没有聊天本身不构成降级证据；新的疏远、矛盾或关系变化才可以成为判断依据。

### 9.3 证据原则

- 参考交流质量、共同话题、相互了解、重要共同经历和关系意愿；多种独立经历相互印证，不设固定聊天次数或认识天数门槛。
- 互动次数、消息数量、消息长度、聊天时长只能作为辅助信息，不能单独触发阶段变化。
- 同一段经历不能通过重复提炼、多个摘要、重叠消息窗口或重复评估反复累加成升级依据。经历可作为背景解释，但不能被再次当成新的升级证据。
- 「独立经历」以真实事件/相处片段为单位，不按消息条数拆分；同一段来回对话可以组成一段互动经历。
- QQ 群聊是主要社交场景。角色与同一平台账号在不同群中的互动，累计到同一段角色级关系；群号、时间和消息来源仍须保留在每段经历上。
- 不要求通过 @ 才认定互动：上下文能够可靠确认双方是在互相回应、接梗或共同参与时，可以记录为关系经历。
- 同群、看到对方发言、双方各自和其他群友聊天，不自动构成双方共同经历；共同活动必须能确认双方实际参与。
- 跨群归并必须依据稳定的平台账号标识（同一平台的 platform UID）；不能只凭昵称、头像或语言风格合并账号。跨平台账号只有在经过可信绑定后才能合并为同一人。
- 关系降级不删除过去的共同经历；关系阶段描述当前状态，历史回忆仍由记忆系统保留。
- 关系阶段和变化记录属于当前角色；不得因同一平台账号被其他角色认识而自动继承。

### 9.4 本地运行边界

- 关系评估采用本地事件驱动的混合触发：重要社交经历进入优先待评估队列；普通经历先积累，再按批量条件或评估周期处理；本地程序重新启动时扫描并恢复尚未完成的任务。
- 不逐条消息评估，也不要求每轮聊天都调用 AI。批量阈值与评估间隔是控制任务成本和响应时机的调度参数，不是关系等级的积分门槛；具体数值在实现时根据本地负载和调用成本确定，不在产品关系规则中写死。
- 待评估事件和任务状态必须持久化。程序关闭期间不执行；重新启动后补做尚未完成且仍有效的评估，不依赖云端常驻服务。
- 评估任务固定绑定 characterId 与目标平台账号/关系标识，不得在执行时读取当前 UI 的全局角色选择来替换任务对象。
- 不预设由哪个 AI 助手执行语义判断。成长系统未来可以按职责分配专职助手；也可以由普通代码完成证据去重、归属校验、冷却与任务调度。

## 10. 主动表达与好友主动联系的关系（已确认方向，尚未实现）

### 10.1 旧主动机制的代码评估

现有主动表达是为早期需求临时搭建的多条链路，不能原样作为新社交主动联系的完整实现：

- `proactive.ts` 的私聊主动找话：使用目的池与「想 → 判 → 说」流程，但收件人通过角色最近的 QQ 私聊会话解析，主要面向已有私聊对象（当前产品语义主要是主人），不是按某位好友的关系选择收件人。
- `group-initiative.ts` 的群聊冷场起话题：按群活跃度、冷场时长和群级/角色级闸门挑选群，再生成一句群消息；它不选择具体好友，现有提示词明确禁止 @ 人。
- `scripts/run-proactive.ts` 是独立的本地 tick 入口，约每 60 秒运行私聊主动找话、群冷场起话题和 QQ 空间主动表达。它不是 Web 请求内的定时器；本地进程未运行时，这些 tick 不会执行。
- 上述机制默认关闭。现状与行为以代码为准，不能把旧文档中的策略直接当作新功能已经具备。

### 10.2 可复用的能力与不能照搬的策略

可优先复用或抽取的基础能力（实施前仍需逐项验证）：

- 纯函数式安全闸门与配置校验；
- 每日额度、最小间隔、安静时段、角色级/群级冷却；
- 发送前重新检查权限、目标与渠道状态；
- 发送结果落库、模型用量记录、失败状态、目的池去重等可靠性设计；实际消息发送的端到端幂等性仍需专项核验，不能假设旧代码已经完整具备。

不能原样照搬的部分：

- 面向主人最近私聊会话的收件人解析；
- 群冷场才开口的触发逻辑；
- 禁止 @ 人的旧群聊提示词；
- 把身份类型直接当成好友关系或唯一交流许可的策略。

现有 `MemoryScope.friendChatPolicy` 在 `DEFAULT` 下屏蔽 AI 发言，是当前针对部分 AI 容易连续接话的保护措施。这个行为与「AI 也能成为朋友」并不矛盾，但未来需要结合明确关系、单独授权和连续 AI 轮数控制重新评估，不能把它固化成 AI 永远不能交流的关系规则。

### 10.3 目标架构

- 社交关系系统产生「想联系谁、为什么联系、想聊什么、在哪个共同群聊可能联系」的结构化主动意图。
- 统一主动表达安全层负责复核当前角色与好友的交流权限（BLOCK 始终优先）、目标是否仍是该群成员、渠道/群模式是否允许主动发言、频率与每日额度、AI-only 连续轮数、重复发送和失败处理。
- QQ 第一阶段优先支持共同群聊中带明确对象的 `@` 互动，不把冷场起话题冒充好友联系。
- 私聊和主动发起好友申请属于未来渠道能力；只有平台、协议和用户配置确实支持时才启用，不能假设群聊天然提供独立私聊能力。
- 没有共同群聊、目标身份不明确、权限被 BLOCK、群模式禁止主动发言或渠道不可用时，不发送；可以保留待处理意图，等待合适渠道或后续能力。

### 10.4 本地执行边界

主动联系也依赖本地 QQ 连接和本地执行进程。程序关闭或 OneBot 不可用时不发送；本地进程恢复后再依据意图有效期、冷却和权限重新判断，不补发已经过期或不再合适的消息。


## 11. 关系经历归并、评估调度与验收标准（2026-11-08 已确认设计）

本节收尾本阶段关系成长设计。它定义产品行为和任务边界，不代表数据表、队列或 AI 助手已经实现。

### 11.1 跨群聊经历归并

- 一段关系的归属键是「当前角色 + 已确认的平台账号身份」。同一角色与同一 QQ 账号在 A 群、B 群及后续其他共同群里的经历，都累计到同一段关系中。
- 群聊是经历发生的场景，不是关系归属边界。每段经历仍需保留来源群、发生时间、参与者以及可追溯的消息/事件引用。
- 跨群归并使用稳定的平台账号标识，不以相同昵称、头像或语言风格作为身份合并依据；跨平台账号只能在可信绑定确认后归并。
- 有效关系经历包括：双方明确的来回交流、上下文可可靠确认的接话/接梗/回应，以及双方确实共同参与的群活动或事件。
- 不要求 @ 才算互动。相反，单纯同群、旁观对方发言、双方分别与其他群友聊天，不构成双方之间的直接互动或共同经历。
- 关系证据要记录来源，但同一段关系不因换群而拆分；同一群中的无关发言也不能因为目标账号在场就算到这段关系里。

### 11.2 关系评估触发与执行流程

采用「重要经历优先 + 普通经历累积 + 本地启动补偿」的混合机制：

1. **形成社交经历候选**：从真实互动、共同活动或记忆整理结果中识别值得保留的社交经历。普通消息不需要逐条触发关系评估。
2. **写入待处理队列**：将新经历关联到当前角色与目标账号；同一段关系已有待评估任务时，优先合并新增证据，而不是无节制地创建重复任务。
3. **重要经历优先**：对有明显关系意义的经历提高评估优先级，但仍要经过统一队列、冷却和资源闸门，不意味着每次重要消息都立即额外调用模型。
4. **普通经历批量评估**：普通经历先积累；达到实施时确定的批量条件、评估间隔或出现关系变化信号时，再安排评估。具体数量和时间间隔属于调度参数，不能变成关系升级的固定次数/天数要求。
5. **启动补偿**：本地程序启动或 Worker 恢复时，扫描未处理事件、等待重试任务和租约已过期任务；重新校验后继续处理。
6. **提出关系变化建议**：角色可以根据整体相处经历提出升级或降级建议。由哪个专职 AI 助手进行语义分析尚未决定，不能默认交给语境助手或记忆助手。
7. **核验并保存**：社交系统检查证据归属、真实性、独立性、重复使用情况和当前关系版本。证据充分才更新阶段，并写入阶段变化历史及证据引用；证据不足则保持原阶段，等待新的独立经历。

### 11.3 去重、冷却与失败恢复

- **经历去重**：同一底层消息/活动因多个记忆摘要、周期提炼、重叠上下文窗口或重复提取而再次出现时，应归并到同一个经历，不得生成多份可累加证据。
- **证据去重**：每次关系阶段变化必须记录使用过的经历引用。同一段经历不能在后续升级中再次充当新的独立证据；可以作为历史背景供理解，但不能重复加权。
- **任务去重**：同一角色、同一目标账号、同一组待处理证据应合并评估；重复触发不能创建并行的重复任务。
- **评估冷却**：同一段关系在一次评估后进入冷却期；冷却内的新经历可以继续积累。特别重要的经历可以提高优先级，但不能绕过证据去重和最终核验。
- **任务状态**：待处理、执行中（带租约/执行标识）、等待重试、已完成等状态必须可恢复；「评估完成但证据不足、关系不变」属于正常完成结果，不属于调用失败。
- **失败重试**：模型、网络或数据库等暂时性错误不等于关系没有变化，必须保留任务和失败原因，采用有上限的退避重试；超过自动重试上限后暂停并保留记录，允许后续人工/系统重新触发，不得静默丢弃。
- **幂等与并发**：任务重试或多个 Worker 并发时，同一证据不能重复消费，同一次阶段变化不能重复写入；保存前再次读取当前阶段/版本，避免过期评估覆盖较新的关系状态。
- **启动恢复**：程序再次启动时恢复待处理、等待重试和租约过期任务；执行前重新核验好友身份、角色归属、证据有效性及当前关系状态。过期的主动联系意图不在这里补发。

### 11.4 关系成长验收标准

实现后至少覆盖以下场景：

1. **跨群累计**：同一角色与同一 QQ UID 在 A 群、B 群的独立互动，累计在同一段关系下；每段经历仍能追溯原群和时间。
2. **身份不误合并**：不同 UID 即使昵称相同也不能合并；同 UID 更换群昵称不应拆成新关系；跨平台账号未验证绑定时不能自动合并。
3. **不依赖 @**：没有 @，但上下文明确是双方互相回应的对话，可以识别为互动；上下文不确定时宁可不记为直接互动。
4. **群聊边界**：仅仅同群或旁观发言不产生关系成长证据；两人都实际参与的共同活动才可作为共同经历。
5. **证据独立性**：同一段对话由多个提炼流程重复产出时只能算一份；多段不同时间/场景的真实经历可以相互印证。
6. **关系判断**：互动次数、消息数量或认识时长单独增加不能自动升级；角色提出变化但证据不足时，关系保持原阶段。
7. **跨级与降级**：充分证据允许跨级成长；降级需要新的实际关系变化，长期不联系本身不能触发降级；降级后过去的共同经历仍可查。
8. **角色隔离**：角色 A 的关系评估任务不能写入角色 B；切换全局角色不能改变已排队任务的归属。
9. **触发成本**：普通消息不逐条调用关系评估；重要事件优先、普通事件批量评估、程序启动补偿均按预期触发；冷却内新增证据能够积累但不会造成重复评估风暴。
10. **失败恢复**：模拟进程退出、模型/网络失败、租约过期和重试；任务不丢失、不重复消费证据、不重复写关系变化；证据不足应是成功完成的无变化结果。
11. **并发与幂等**：同一关系被重复触发或多个 Worker 同时处理时，最终只产生一条有效阶段变化，旧任务不能覆盖新状态。
12. **本地运行约束**：程序关闭时没有云端任务偷偷执行；重新启动后能继续处理有效待办任务。

### 11.5 本阶段设计完成边界

- 已完成关系归属、跨群经历累计、证据独立性、关系建议与系统核验、混合触发、任务去重/冷却/重试/恢复及验收标准的产品设计。
- 尚未决定具体 AI 助手分工、模型供应商、触发数量/时间阈值、数据库表结构和 Worker 实现方式；这些在开发前根据整体成长系统架构与现有任务设施设计。
- 本阶段不改变真人/AI/未知身份语义、现有好友交流权限、QQ 入口过滤和主动联系发送规则；关系成长与指定好友主动联系仍是不同功能。
- 文档完成不代表功能完成。进入实现后仍需代码测试、隔离数据库竞态测试、类型检查、Lint、SFC、构建及本地 DSH 的真实 QQ 验收。

## 14. 第三阶段：关系评估系统架构（2026-11-08 已确认设计）

本节记录第三阶段关系评估系统的设计决定。数据库基础模型与迁移已在 PR #17 实现；Worker、AI 配置、评估服务和 UI 仍未实现。

### 14.1 评估原则

- 触发采用「新经历触发 + 定期回顾」：新经历先合并进待评估状态；重要经历可提高优先级；普通经历批量处理；本地程序启动后补偿未完成任务。
- 每段角色级好友关系独立评估。同一关系同一时刻最多一个有效评估执行；执行期间新增经历进入下一代待处理批次，不与当前批次并行竞争。
- AI 可以建议升级、降级、保持、证据不足或需要关注；不得为了完成任务强行改变阶段。
- 关系阶段与相处状态分离。阶段继续使用 STRANGER / ACQUAINTANCE / FRIEND / CLOSE_FRIEND；相处状态另行描述 NORMAL / DISTANT / CONFLICT / REPAIRING 等观察结果。长期没有联系不自动降级。
- 升级与降级都需要真实经历依据；降级更谨慎。普通分歧先观察，持续关系受损或有充分证据的严重信任破坏可以触发评估；关系修复过程也应被记录。
- 客观经历与角色主观感受分开表达。角色的感受可以作为关系体验，但不能被表述为对方的感受或客观事实。
- 不使用固定积分、聊天次数、消息数量或认识天数作为阶段门槛。AI/真人身份不决定关系资格或亲疏。

### 14.2 AI 能力与安全边界

- 社交关系评估 AI 是独立能力，使用独立服务商、API 地址、API Key、模型名称及调用参数；不共用聊天模型、记忆助手或语境助手的凭据。
- 第一版先实现单一评估能力和稳定输入/输出协议，不提前建设复杂多 Agent 系统。未来由成长系统整体架构决定是否拆分多个专职助手。
- AI 输入由社交系统组装：当前关系阶段/状态、上次评估上下文、新增经历、必要的历史背景。证据只引用 SocialExperience，并可沿引用读取 MemoryEvent；不复制忆泡正文到社交表。
- AI 输出必须结构化，至少包括结论（CHANGE / MAINTAIN / INSUFFICIENT / REVIEW）、当前阶段、建议阶段、建议相处状态、理由、观察、证据经历 ID、信心辅助值和是否需要更多证据。
- 信心值不能单独决定关系变化。模型输出视为不可信建议，不能直接写数据库或调用关系变更接口。

### 14.3 数据职责与建议模型边界

现有数据继续复用：
- MemoryScope（EXTERNAL_IDENTITY）：角色级好友关系、现有 relationshipStage 与 relationshipVersion。
- SocialExperience：关系经历与既有 MemoryEvent 的引用。
- SocialRelationChange / SocialRelationChangeEvidence：实际阶段变化历史及其证据。

目标新增数据职责（具体字段以实现前 schema 审查为准）：
- **评估任务状态**：每个 EXTERNAL_IDENTITY scope 一条可复用任务状态，保存触发原因、待处理/已处理 generation、优先级、计划时间、尝试次数、租约/执行令牌、错误与最近/下次评估时间。新经历在执行中到达时增加待处理 generation，当前批次完成后再排下一批。
- **评估历史**：每次实际模型评估一条不可覆盖的历史记录，保存触发来源、评估时关系阶段/版本、结构化建议、理由、模型与提示词版本、输入截止点、执行状态和错误信息。
- **评估证据**：每条评估关联 NEW 或 CONTEXT 类型的 SocialExperience 引用。历史背景可重复用于理解，但不能被再次累计为新的独立成长证据。
- **关系相处状态**：与关系阶段分离保存；任何关系状态/阶段更新均需核对并递增 relationshipVersion，防止过期评估覆盖新状态。

以上新增模型应保持角色隔离，外键和查询必须沿 scope 校验 characterId；不另建重复好友档案表。

### 14.4 Worker 与可靠性

- 社交系统拥有独立任务状态与处理器；复用项目现有 Worker 的租约、执行令牌 fencing、退避重试和启动恢复设计，不把社交语义硬塞进记忆任务类型。
- 将社交任务接入现有本地 Worker 运行入口；本地程序关闭时不执行，不依赖云端常驻服务。
- 同一好友关系同一时间最多一个有效任务；触发去重不丢失执行期间新增的 generation。
- 任务完成但证据不足/关系不变属于正常完成，不是失败。
- 模型、网络等暂时错误保留任务并按上限退避重试；超过上限后保留失败记录，可再次触发。
- 写入前重新核对关系版本、阶段、证据归属、证据有效性与重复使用情况；并发或重试不得重复创建同一次关系变化。

### 14.5 关系评估与关系变更分层

1. 任务调度层合并经历触发和定期回顾。
2. 证据服务按当前角色与好友关系收集新增证据及历史背景。
3. 独立评估 AI 只生成结构化建议。
4. 确定性核验服务验证证据 ID、scope 归属、证据独立性、状态/阶段合法性及关系版本。
5. 关系变更服务在事务内更新阶段/相处状态、递增 relationshipVersion，并写入阶段变化及证据引用。
6. 每次评估都保留历史；没有变化也记录正常评估结论。

### 14.6 分批实施与验收

1. 数据模型与迁移：任务状态、评估历史、评估证据、相处状态；验证角色隔离、唯一约束和级联行为。
2. 任务队列：经历触发、任务合并、generation、定期回顾、启动恢复与租约恢复。
3. 独立模型配置：凭据加密、DTO 脱敏、连接测试和用量记录。
4. 证据收集与评估协议：输入白名单、结构化输出解析、证据引用核验。
5. 关系变更服务：乐观锁、幂等、阶段/状态更新和历史记录。
6. API/UI：好友详情、当前关系理解、评估历史及状态。
7. 可靠性验收：并发领取、执行中新增经历、模型失败、进程退出、租约过期、重试、过期建议和跨角色隔离。

第一版先让单个独立评估能力跑通闭环，不提前引入通用多 Agent 编排平台。每一批开发完成后单独本地验收，通过并合并后再开始下一批。

### 14.8 任务队列与本地调度第二批（2026-11-08）

- 补齐第一批评估迁移的 Prisma 命名漂移：仅重命名两条组合外键和一个唯一索引，字段、约束语义和业务数据均不变。
- 新经历触发已接入 `SocialExperience` 创建事务：只对 `createManyAndReturn + skipDuplicates` 实际新增的经历排队；重复 sourceKey 被跳过时不增加 generation。关系任务按 scopeId 唯一合并，不为每条消息创建任务。
- 同一任务触发时 generation 原子递增、触发原因去重合并、优先级取较高值。若任务正在 RUNNING，只增加 generation 和下一批触发原因，不更换当前租约；当前批完成后如发现 generation 更新，自动回到 QUEUED。
- 已实现独立的社交任务领取、租约续期、完成、失败退避和过期恢复原语。领取使用数据库行锁与 `SKIP LOCKED`，每次领取生成独立 leaseToken 并递增 fencingToken；提交/续租/失败更新均同时校验执行者、leaseToken、fencingToken 与租约未过期。执行期间若 generation 增长，即使当前批失败或租约过期，也直接重排新一代，不会把新经历一起耗尽重试次数。
- 失败最多自动尝试 3 次，退避从 1 分钟开始按指数递增、上限 6 小时；达到上限后保留 FAILED 任务。新的真实经历会重新唤醒 FAILED 任务并重置尝试次数。租约 5 分钟，过期后无新 generation 时恢复为 RETRY_WAIT 或 FAILED；若执行期间有新 generation，则直接 QUEUED 并重置新一代尝试次数。
- 本地记忆 Worker 已增加队列维护：启动/每轮运行时补齐已有 SocialExperience 但缺少任务的关系、安排到期的周期回顾、回收过期租约。QQ 一键启动原本就会启动该 Worker，因此无需再起独立常驻服务；也可单独运行 `yarn worker:watch`。
- 周期回顾默认间隔为 30 天，可通过 `YILING_SOCIAL_RELATIONSHIP_REVIEW_INTERVAL_DAYS` 设置 1–365 天。该间隔只控制回顾排期，不是关系升级/降级阈值，也不代表到了日期就改变关系。
- **当前批次不执行评估 AI**：Worker 只维护和恢复队列，不领取后空跑、不创建虚假成功记录、不修改关系阶段或相处状态。下一批完成独立评估配置与执行器后，再把真实评估接入 claim/complete/fail 生命周期。
- 隔离 DB 验收入口：`yarn test:social-relationship-queue-isolated`，自动创建一次性本地 PostgreSQL 数据库、执行全部迁移和队列断言后 DROP；已接入 `verify:local`。本批尚需本地 DSH 实跑 Prisma、类型检查、队列隔离测试、Lint、构建及现有忆泡数据库回归。
