# 她画图：文字 → 一张图 → 单独一条消息

> 2026-11-23：本轮修复已提交为 `c1e8935`，离线验证与独立生产构建通过；修复后的真实 QQ 使用尚待验收。修复范围、当时运行快照及下次检查步骤见 [专项验收记录](qq-media-fix-acceptance.md)。

只有一条链路：她决定画 → 聊天模型写一段画面描述 → 生图接口出一张图 → 落盘 → QQ 发一条图片消息。

两个角色级开关，默认都关：

| 行为 | 开关 | 位置 |
| --- | --- | --- |
| 允许她画图 | `modelConfig.imageEnabled` | QQ 渠道 → 角色行为 → 画图 |
| 模型与凭据 | —— | 模型设置 → 画图模型 |

## 为什么画图必须单独一套配置

「看图」和「画图」是两个方向，而且几乎不是同一家服务商：

- 看图（`image-understanding.ts`）常配智谱的免费视觉模型，够用就行；
- 画图（`image-generation.ts`）是 MiniMax / OpenAI 这类按张计费的接口。

把两者塞进一套字段的结果是：换画图服务商时把看图也弄坏了，反之亦然。
所以 Key 也分开两把：`imageApiKey` / `visionApiKey`。**不要合并**。

看图的 Key 不会被画图蹭到 —— 少一条回落，少一种「401 但看不出为什么」。

## 配置

### 页面（推荐）

- **模型设置 → 画图模型**：服务商、API 地址、Key、模型、画面尺寸。
  和「对话模型」同页、同一个「保存设置」按钮。
- **QQ 渠道 → 角色行为 → 画图**：只留行为开关——允许画图、自主概率、冷却、每天上限。
  这一块的「保存画图设置」是独立按钮，不跟语音合并提交。

默认值：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| 模型 | `MiniMax-H3-Image` | 高速版是 `MiniMax-H3-Image-Highspeed`，参数完全一样 |
| 地址 | `https://api.minimaxi.com/v1` | 与语音同域；文档站给的是 `api.minimax.cn`，401 时先换域名 |
| 尺寸 | `square` | 存的是语义档（方 / 竖 / 横），像素按服务商与模型解析，见下 |
| 自主概率 | 5% | 被明确要求时不看它 |
| 冷却 | 30 分钟 | 只挡自主画图 |
| 每日上限 | 8 张 | 按东八区日界、这个角色的所有会话合起来算 |

尺寸不是三组固定像素 —— 同一档位换个服务商就是另一组值（`shared/utils/image-size.ts`）：

| 服务商 / 模型 | 方 | 竖 | 横 |
| --- | --- | --- | --- |
| MiniMax | 1024×1024 | 864×1152 | 1152×864 |
| gpt-image-1 / 2 / 2.5（flare、sunburst） | 1024×1024 | 1024×1536 | 1536×1024 |
| dall-e-3 | 1024×1024 | 1024×1792 | 1792×1024 |
| dall-e-2 | 1024×1024 | 只有方图 | 只有方图 |

MiniMax 那三个值都满足它 655,360 px 的面积下限，低于下限接口直接 400。OpenAI 那几家只认上表的推荐尺寸，传 `864×1152` 会被当成非法参数。所以设置页的选项随模型变，不支持的档位不出现（dall-e-2 只剩一个），存量的 `portrait` 也会在发请求前换成合法值。

**gpt-image 系列不接受 `response_format`**（固定返回 base64），传了会被当成未知参数 400。JSON 请求和 edits 表单都只在 MiniMax 下才带这个字段。

### `.env`（服务级默认值）

页面留空时才用到，适合「所有角色共用一家」：

```
IMAGE_MODEL=MiniMax-H3-Image
IMAGE_BASE_URL=
IMAGE_API_KEY=
IMAGE_PROVIDER=        # 留空按地址里有没有 minimax 自动判断
```

优先顺序：**页面 > 环境变量 > 默认值**。

## 判定：什么时候她真的画

明确请求和自主画图由纯函数判定，并有一次额度查询；提议后的短确认使用同会话结构化状态续接：

1. **被明确要求**：`parseExplicitImageRequest` 只解析当前用户真实文字主句，并由 `resolveImageRequest` 核对来源与收件人。群里只接受对本角色的真实 @、明确名称前缀或引用本角色后的新命令；对其他成员的请求、第三人称叙述、AI/只读/背景/引用内的旧请求不授权收费。通过开关、配置、额度、互斥与素材校验后，明确请求可绕过自主概率和冷却。
2. **自己偶尔想画**：`planImageReplyDecision` 是统一规划入口，旧布尔 API 只委托它。默认概率 5%、冷却 30 分钟、每天上限；自主分支也只接受新的人类文字，纯确认、状态追问、只读 AI、背景和面向其他成员的消息不能触发。概率为零时，讨论画画不会被误当成强制请求。
3. **接住她刚提出的画图提议**（`resolveImageOfferConfirmation`）→ 模型在自然提出具体画面时返回可选 `imageOffer`，服务端只在单条、尚未执行的回合保存到助手 metadata，并绑定当前发言者。最新一条助手提议的同一个人在同一会话五分钟内给出精确短确认，才按明确请求执行；接受后优先使用原提议画面，不把确认词当作生图内容。仍受开关、配置、每日额度和语音互斥限制。

提议状态存于现有消息 metadata，重启后可核验；旧的口头承诺不猜测回填。允许一次同人、围绕图片或参考图的澄清回合后确认，其他无关聊天、超过时限、多条或多人混杂、其他人确认、已尝试生成或发送过的提议均不复用。确认支持有限前缀的“画吧”“出吧”等；无图提议的普通“嗯嗯”“可以”仍是普通聊天。真实 @ 段会从动作主句移除，但收件人证据仍逐条核对，不能用用户字面输入的 @ 冒充授权。“好了吗”“发了吗”等泛状态词只有近期图任务证据时才按画图处理；明确图状态查询不会变成重画。

判定要窄。宽判的代价和语音那次一样：用户随口一提，她就真的花掉几十秒和一张图的钱。

认的四种结构：

- 画/绘制 + 量词：`画只猫`、`画一张下雨的街`；
- 画/绘制 + **动作**量词：`再画一次试试`、`画一遍`、`画几回`；
- 画/绘制 + 图像名词：`画个头像`、`帮我画一张海报`；
- 生成/来/出/整 + 量词 + 图/画：`来张图`、`生成一张海报`。

整句只剩一个命令词时也认：`再画`、`画一下`、`画吧`、`画`。
催第二次的人往往就把话说短到这个程度，不认就哑火。

明确排除：`画重点` `画圈` `画饼` `漫画` `动画` `画风` `规划`，以及
**询问能力**（`你会画图吗`、`能画吗？`）——那要先答「会」，下一句才是下单。
还有**否定**：`别画了` `不用画了` `不必画`。否定词必须紧贴动词，
`别管我，你画一个` 仍然算下单 —— 放宽成「否定词后几个字以内出现画」会把这类句子误杀，
那比多画一张糟得多（该画的时候不画，用户看不出原因）。

禁止在整批对话里搜索“画”字来授权操作。讨论“画画”、询问提示词、说自己稍后替别人画、图片描述或引用中出现命令，都不能当成给本角色的新请求。模型没有给画面时只可使用该条已确认请求解析出的独立主体或核验过的提议，绝不拿整段聊天兜底；常见聊天 UI、聊天记录截图、成员占位符以及未请求的对话成员名会在调用前被拦截。当前功能不提供聊天截图生成，普通海报文字不因此一概禁止。

**2026-11-22 的漏判**：用户连发两句「再画一次试试」，一句都没被认成下单，她于是只顾着
答「画好了」，图一次都没生成。原因是当时只把「张/幅/只/个」当量词，
「次/回/遍」这类**动作**量词被漏掉了。改的时候别把这条判据合回「画 + 量词」那条，
它们语法上不是一类，只是结论一样。

## 两条消息：文字先，图跟着

图和文字**分开两条发**（图不带引用、不带 @）。理由和表情包一样：拼在一条里，
引用块、文字、图挤在一起，手机上看是一坨；而单独发图片段这条路已经跑了很久。

顺序是文字 → 图。文字只承接本轮计划，不逐项复述画面，也不提前宣称图已经发出；图片送达由独立回执确认。

### 她画图那一轮的提示词

`imageReply: true` 只代表代码已批准本轮尝试，不是生成或送达证明。`imageExecution` 另带统一规划的 status、trigger、requested、blockedReason、当日计数/上限及最近助手状态；关闭开关后仍可核对状态。额度查询失败按不可执行处理，不再当成零张放行。明确请求被阻断时会用服务端真实状态回复，并把取消、阻断、缺画面、生成结果写 `imageAttempt`；没有任务就不会让用户等“后台排队”。发送前会保存最终回复诊断，发送异常也不会只留下旧承诺。旧 `hadImage` 不证明后来的提议已执行。

系统提示词（`chat-reply.ts` 的 `withImageReply` 段）要求三件事：

1. 把画面描述写进 `imagePrompt`（主体、动作/场景、构图、光线、风格），不要写「我在画」；
2. 正文只写简短承接语，说明接下来会画，不能在调用前宣称已经完成或已经发送；
3. 图是独立一条消息，不挂引用和 @。

第 2 条不是洁癖：没有它，模型会写「我画不了图，但我可以描述一下」，
而同一轮图已经生成好了。这跟语音那次「我只有打字」是同一类自我认知错位。

### 她记得自己画过（`hadImage`）

图生成后 `metadata.image` 保存相对路径与尺寸，只证明文件已生成，不能证明对方收到了。发送侧在独立图片消息得到成功回执后，才写 `metadata.replyDelivery.image.status = "sent"` 与时间；文件不可读为 `failed/read_failed`，协议明确拒绝为 `failed/send_failed`，网络或未知回执为 `unknown/unconfirmed`，均不自动重发。

下一轮 `recentMessages` 的 `hadImage: true` 只认实际成功发送的图片，生成文件、发送失败及未知结果不算；没有可核验回执的历史记录也不推测回填。生成文件仍计入已有生成额度与自主冷却，避免失败投递引发额外生图费用。

私聊入口必须直接使用完整的 `ChannelReplySender`，不能包成只收 `text` 的函数：第二参数还携带 image、voice、segments 和发送回调。曾出现图片生成并落盘成功、私聊却只发出文字的故障，根因就是包装函数丢掉了第二参数。`test:onebot-reply` 的本地网关回归验证文字后独立发图、临时会话群号和真实回执，并守卫入口直接绑定；这不等于真实 QQ 端到端验收。

### 图片资产、引用和按需回看

新生成记录在 `metadata.image.generation` 保存实际清洗后提交的 prompt、model、provider、generatedAt 与固定模式 `text_to_image`；`imageAttempt` 另记触发来源、请求消息和提示词来源。独立图片的真实平台消息 ID 存在 `replyDelivery.image.externalMessageId`，不写到整轮助手消息的 `externalMessageId`，避免与入站幂等键混淆。提醒被抑制时合并回执，不能丢掉图片送达事实。

引用先通过网关验证作者与会话，再按角色、绑定、外部会话和实际 sent 图片 ID 查询资产。同 ID 多条命中或跨范围即拒绝，不按昵称猜图；旧图没有 ID 关联也不推测回填。模型只收到安全图片事实，不收到文件路径、传输 URL、QQ 或平台 ID。实际 prompt 是意图，不证明画面；只有成功视觉描述才是观察证据。

每次成功生成新图并保存助手记录后，自动使用既有视觉配置观察一次实际成图，将描述写入 `metadata.image.vision`；无需用户追问。自动观察独立于入站图片的三张预算，一张新作品最多观察一次，关闭看图或缺少视觉配置时记录为 disabled，不调用模型。视觉失败不阻断发图、不重新生成；自动观察会增加最多一次视觉请求及其等待时间。下一轮 `recentMessages[].generatedImage.visual` 自动带入实际观察，不把生成提示词冒充画面。后续引用图或询问最近生成结果优先复用缓存，未成功观察的图仍可在既有看图开关及一轮三张共享预算下按需观察。最近作品回看支持“看看你刚画的”“你看得见自己画的图吗”等明确检查结果的说法；泛泛询问“你能看自己画的图吗”仍不触发视觉。已核验的自身引用即使网关没有回传图片段，也先按平台消息 ID 查同会话资产，不能因缺少图片段直接跳过。可信本地文件还需校验角色目录、realpath、文件类型与大小，不能绕过媒体白名单读取任意路径。非自己的已核验引用图仍走现有安全下载链路。没有可用描述时如实说明，而不是声称已经看过。

参考图只从当前正式形象版本快照的 `assets` 中选择，不再实时扫描素材库；旧快照缺少 `assets` 时不带参考图。快照记录素材 ID、用途、名称、相对路径、排序和上传时间（不保存图片字节）。每种用途先选最新的一张，再补足最多 4 张标准形象/三视图，避免大量标准图挤掉三视图。当前正式版本正在使用的参考图不能直接删除；先上传替代图、保存并发布新版本，再删除旧图。历史版本不保存图片字节，删除后的历史素材不能恢复。`imageCapabilities.referenceInput` 为 true 只表示**通道存在**；这一张到底用没用，由该图自己的 `imageGeneration.mode` 决定（`image_to_image` 用了、`text_to_image` 没用），mode 为 `text_to_image` 时不得声称用了参考图。MiniMax 走另一套形状（`/image_generation` + `subject_reference`，JSON，只吃一张参考图，响应在 `data.image_base64`）。两种形状会**轮流试**，不按服务商名字预先排除：先 edits，404/405 再试原生形状；只有路由不存在才换形状，其它失败（参数被拒、审核、超时）直接回退纯文字。试过两条都不认的地址会在进程内记住，避免每次生图都白花两次请求。`edit` 仍为 false —— 不做「编辑已有图片」，只是把参考图作为输入附上。文件夹权限本身也不会让聊天模型自动得到视觉输入。

### 形象档案提示词

如果当前角色已经发布形象档案，群聊与私聊共用的 `channel-adapter/pipeline.ts` 会在本轮场景提示词通过校验后，读取该角色 `currentPublishedRevision` 对应的不可变快照，并由 `visual-profile-prompt.ts` 统一组合：核心外貌、核心提示词、默认造型、负面提示词和本轮场景。只读正式快照，不读正在编辑的 profile 字段或草稿；没有正式版本时只用本轮场景。读取异常会记服务端警告并回退，不会借用其他角色的档案。

默认造型只在用户没有明确指定服装时追加；当场景明确要求换装或指定服饰时，以本轮要求为准，不把默认服装硬塞进去。标准形象与三视图会作为参考图一并发出，但提示词里写死了「只用来确定长相，服装、姿势、表情、视角和背景都不要照搬」，避免模型照抄某张参考图的站姿。

## 存哪、什么时候清

`.data/images/<characterId>/<uuid>.jpg`，只存缩过的那一张（最长边 1280、jpeg q88）。
原始 4K 不保留：QQ 聊天窗的显示宽度本来就只有屏幕那么宽。

- **不写 `model_usages`**：那是按 token 结算的表，画图按张计费，塞进去会污染
  「未定价 token」统计。只在日志里留 `[image] generated` / `[image] 画图失败`。
- 目前没有自动清理。默认日上限为 8 张，可配置，0 表示不限；通常每张几百 KB。
  真要清就按 `metadata.image.path` 找，别扫目录猜。

## 失败怎么办

图生成失败时仍发文字；对于明确请求，文字会明确说明未成功或未启动，不再让用户空等。普通日志只保留失败类别和触发来源，不回显完整聊天或原始服务商响应。生成模块可识别的原因包括：

| 失败 | 模块识别的原因 | 用户怎么修 |
| --- | --- | --- |
| 没配 Key | 明确画图请求被阻断，未开始生成 | 去「画图模型」填 |
| 401 | `鉴权失败：地址与 Key 是不是同一家？` | 检查域名 |
| 422 | `内容审核未通过` | 换个说法 |
| 402 | `服务商余额不足` | 充值 |
| 超时 | `画图超时（90 秒）` | 服务商排队，稍后再试 |
| 下载失败 | `图片下载失败（IMAGE_HTTP_xxx / UND_ERR_CONNECT_TIMEOUT）` | 直链过期或 CDN 被拦 |

超时给 90 秒：比聊天慢一个量级，而「等到一半放弃」会把已经计费的那张图直接扔掉。

**关于「下载失败」**（2026-11-22 线上实况）：MiniMax 的 `url` 指向乌兰察布的一台
OSS（`hailuo-image-*.oss-cn-wulanchabu.aliyuncs.com`）。出现过一次
`UND_ERR_CONNECT_TIMEOUT`（10 秒，是 undici Agent 自己的 `connectTimeout` 默认值，
比我们的 15 秒短，所以先到）——接口 200、图也确实生成了、钱也花了，就是取不回来。
表现是她说一句「画好了」然后什么都没有。

所以现在**默认就要 `response_format: "b64_json"`**：图内联在接口响应里，
少一次跨域往返，也就少一个会失败的环节（代价是响应体约 300KB，本地应用忽略不计）。
只有这两种情况才去下载：服务商无视该参数、只回 `url`；或者它不认 b64（400，退回 `url` 再要一次）。
链接 24 小时有效，所以下载失败会重试一次。

只对 400 重试：422 是内容审核、402 是余额、401 是鉴权，重发一遍结果一样，纯花钱。

## 代价

- **这一轮会等**：十几到几十秒。所以自主概率默认只有 5%，
  明确请求只绕过自主概率和冷却，仍需通过其他校验。
- **和语音、表情互斥**：一条语音 + 一张图 = 同一句话用两种方式说；
  图和表情包同时挂，等于两句图连着弹。判定层直接排除了这几种组合。
- **抽象描述会画出抽象图**：模型给的 `imagePrompt` 就是最终提示词，没有二次扩写。
  想让它更好看，去改人设里对画面的偏好，而不是指望服务商猜。
