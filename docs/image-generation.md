# 她画图：文字 → 一张图 → 单独一条消息

只有一条链路：她决定画 → 聊天模型写一段画面描述 → 生图接口出一张图 → 落盘 → QQ 发一条图片消息。

两个角色级开关，默认都关：

| 行为 | 开关 | 位置 |
| --- | --- | --- |
| 允许她画图 | `modelConfig.imageEnabled` | QQ 渠道 → 角色行为 → 画图 |
| 模型与凭据 | —— | 模型设置 → 画图模型 |

## 为什么画图必须单独一套配置

「看图」和「画图」是两个方向，而且几乎不是同一家服务商：

- 看图（`image-understanding.ts`）常配智谱的免费视觉模型，够用就行；
- 画图（`image-generation.ts`）是 MiniMax / OpenAI 这类按张计费的接口。

把两者塞进一套字段的结果是：换画图服务商时把看图也弄坏了，反之亦然。
所以 Key 也分开两把：`imageApiKey` / `visionApiKey`。**不要合并**。

看图的 Key 不会被画图蹭到 —— 少一条回落，少一种「401 但看不出为什么」。

## 配置

### 页面（推荐）

- **模型设置 → 画图模型**：服务商、API 地址、Key、模型、画面尺寸。
  和「对话模型」同页、同一个「保存设置」按钮。
- **QQ 渠道 → 角色行为 → 画图**：只留行为开关——允许画图、自主概率、冷却、每天上限。
  这一块的「保存画图设置」是独立按钮，不跟语音合并提交。

默认值：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| 模型 | `MiniMax-H3-Image` | 高速版是 `MiniMax-H3-Image-Highspeed`，参数完全一样 |
| 地址 | `https://api.minimaxi.com/v1` | 与语音同域；文档站给的是 `api.minimax.cn`，401 时先换域名 |
| 尺寸 | `square`（1024×1024） | 另两档：`portrait` 864×1152、`landscape` 1152×864 |
| 自主概率 | 5% | 被明确要求时不看它 |
| 冷却 | 30 分钟 | 只挡自主画图 |
| 每日上限 | 8 张 | 按东八区日界、这个角色的所有会话合起来算 |

三个尺寸都满足 MiniMax 的面积下限（655,360 px）。别再往下调，低于下限接口直接 400。

### `.env`（服务级默认值）

页面留空时才用到，适合「所有角色共用一家」：

```
IMAGE_MODEL=MiniMax-H3-Image
IMAGE_BASE_URL=
IMAGE_API_KEY=
IMAGE_PROVIDER=        # 留空按地址里有没有 minimax 自动判断
```

优先顺序：**页面 > 环境变量 > 默认值**。

## 判定：什么时候她真的画

明确请求和自主画图由纯函数判定，并有一次额度查询；提议后的短确认使用同会话结构化状态续接：

1. **被明确要求**（`isImageRequested`）→ 必画，跳过概率与冷却。每日上限仍然生效。
2. **自己偶尔想画**（`planImageReply`）→ 概率 5%、冷却 30 分钟、每天上限。
3. **接住她刚提出的画图提议**（`resolveImageOfferConfirmation`）→ 模型在自然提出具体画面时返回可选 `imageOffer`，服务端只在单条、尚未执行的回合保存到助手 metadata，并绑定当前发言者。最新一条助手提议的同一个人在同一会话五分钟内给出精确短确认，才按明确请求执行；接受后优先使用原提议画面，不把确认词当作生图内容。仍受开关、配置、每日额度和语音互斥限制。

提议状态存于现有消息 metadata，重启后可核验；旧的口头承诺不猜测回填。已有后续聊天、超过时限、多条或多人混杂、其他人确认、已尝试生成或发送过的提议均不复用。短确认必须是单独一条，不含其他任务；群里带额外 @ 前缀的确认暂不识别，可使用明确画图命令。状态追问及明确否定不进入随机画图分支，因此询问进度不会偷偷变成重画。

判定要窄。宽判的代价和语音那次一样：用户随口一提，她就真的花掉几十秒和一张图的钱。

认的四种结构：

- 画/绘制 + 量词：`画只猫`、`画一张下雨的街`；
- 画/绘制 + **动作**量词：`再画一次试试`、`画一遍`、`画几回`；
- 画/绘制 + 图像名词：`画个头像`、`帮我画一张海报`；
- 生成/来/出/整 + 量词 + 图/画：`来张图`、`生成一张海报`。

整句只剩一个命令词时也认：`再画`、`画一下`、`画吧`、`画`。
催第二次的人往往就把话说短到这个程度，不认就哑火。

明确排除：`画重点` `画圈` `画饼` `漫画` `动画` `画风` `规划`，以及
**询问能力**（`你会画图吗`、`能画吗？`）——那要先答「会」，下一句才是下单。
还有**否定**：`别画了` `不用画了` `不必画`。否定词必须紧贴动词，
`别管我，你画一个` 仍然算下单 —— 放宽成「否定词后几个字以内出现画」会把这类句子误杀，
那比多画一张糟得多（该画的时候不画，用户看不出原因）。

不排除「难」的后果是真实的：一个群里说「这图画得真好」，她能立刻去画一张。

**2026-11-22 的漏判**：用户连发两句「再画一次试试」，一句都没被认成下单，她于是只顾着
答「画好了」，图一次都没生成。原因是当时只把「张/幅/只/个」当量词，
「次/回/遍」这类**动作**量词被漏掉了。改的时候别把这条判据合回「画 + 量词」那条，
它们语法上不是一类，只是结论一样。

## 两条消息：文字先，图跟着

图和文字**分开两条发**（图不带引用、不带 @）。理由和表情包一样：拼在一条里，
引用块、文字、图挤在一起，手机上看是一坨；而单独发图片段这条路已经跑了很久。

顺序是文字 → 图。文字只承接本轮计划，不逐项复述画面，也不提前宣称图已经发出；图片送达由独立回执确认。

### 她画图那一轮的提示词

`imageReply: true` 只代表代码已批准本轮调用，不是生成或送达证明。`imageExecution` 另带本轮是否计划执行和最近一条助手消息的可核验状态（未请求、提议、已生成、已发送、失败或未知），关闭开关后也仍可核对状态；这些事实优先于聊天里的自述，旧 `hadImage` 不证明后来的提议已执行。生成失败或缺少画面描述会写 `imageAttempt`，不能被当作完成，也不能复用同一提议。

系统提示词（`chat-reply.ts` 的 `withImageReply` 段）要求三件事：

1. 把画面描述写进 `imagePrompt`（主体、动作/场景、构图、光线、风格），不要写「我在画」；
2. 正文只写简短承接语，说明接下来会画，不能在调用前宣称已经完成或已经发送；
3. 图是独立一条消息，不挂引用和 @。

第 2 条不是洁癖：没有它，模型会写「我画不了图，但我可以描述一下」，
而同一轮图已经生成好了。这跟语音那次「我只有打字」是同一类自我认知错位。

### 她记得自己画过（`hadImage`）

图生成后 `metadata.image` 保存相对路径与尺寸，只证明文件已生成，不能证明对方收到了。发送侧在独立图片消息得到成功回执后，才写 `metadata.replyDelivery.image.status = "sent"` 与时间；文件不可读为 `failed/read_failed`，协议明确拒绝为 `failed/send_failed`，网络或未知回执为 `unknown/unconfirmed`，均不自动重发。

下一轮 `recentMessages` 的 `hadImage: true` 只认实际成功发送的图片，生成文件、发送失败及未知结果不算；没有可核验回执的历史记录也不推测回填。生成文件仍计入已有生成额度与自主冷却，避免失败投递引发额外生图费用。

私聊入口必须直接使用完整的 `ChannelReplySender`，不能包成只收 `text` 的函数：第二参数还携带 image、voice、segments 和发送回调。曾出现图片生成并落盘成功、私聊却只发出文字的故障，根因就是包装函数丢掉了第二参数。`test:onebot-reply` 的本地网关回归验证文字后独立发图、临时会话群号和真实回执，并守卫入口直接绑定；这不等于真实 QQ 端到端验收。

## 存哪、什么时候清

`.data/images/<characterId>/<uuid>.jpg`，只存缩过的那一张（最长边 1280、jpeg q88）。
原始 4K 不保留：QQ 聊天窗的显示宽度本来就只有屏幕那么宽。

- **不写 `model_usages`**：那是按 token 结算的表，画图按张计费，塞进去会污染
  「未定价 token」统计。只在日志里留 `[image] generated` / `[image] 画图失败`。
- 目前没有自动清理。一个角色一天最多 8 张、每张几百 KB，量级可以接受；
  真要清就按 `metadata.image.path` 找，别扫目录猜。

## 失败怎么办

一律**只发文字**，图没有就没有：

| 失败 | 日志里的样子 | 用户怎么修 |
| --- | --- | --- |
| 没配 Key | 静默（整条链路不启用） | 去「画图模型」填 |
| 401 | `鉴权失败：地址与 Key 是不是同一家？` | 检查域名 |
| 422 | `内容审核未通过` | 换个说法 |
| 402 | `服务商余额不足` | 充值 |
| 超时 | `画图超时（90 秒）` | 服务商排队，稍后再试 |
| 下载失败 | `图片下载失败（IMAGE_HTTP_xxx / UND_ERR_CONNECT_TIMEOUT）` | 直链过期或 CDN 被拦 |

超时给 90 秒：比聊天慢一个量级，而「等到一半放弃」会把已经计费的那张图直接扔掉。

**关于「下载失败」**（2026-11-22 线上实况）：MiniMax 的 `url` 指向乌兰察布的一台
OSS（`hailuo-image-*.oss-cn-wulanchabu.aliyuncs.com`）。出现过一次
`UND_ERR_CONNECT_TIMEOUT`（10 秒，是 undici Agent 自己的 `connectTimeout` 默认值，
比我们的 15 秒短，所以先到）——接口 200、图也确实生成了、钱也花了，就是取不回来。
表现是她说一句「画好了」然后什么都没有。

所以现在**默认就要 `response_format: "b64_json"`**：图内联在接口响应里，
少一次跨域往返，也就少一个会失败的环节（代价是响应体约 300KB，本地应用忽略不计）。
只有这两种情况才去下载：服务商无视该参数、只回 `url`；或者它不认 b64（400，退回 `url` 再要一次）。
链接 24 小时有效，所以下载失败会重试一次。

只对 400 重试：422 是内容审核、402 是余额、401 是鉴权，重发一遍结果一样，纯花钱。

## 代价

- **这一轮会等**：十几到几十秒。所以自主概率默认只有 5%，
  被明确要求时才无条件画 —— 那种时候等人本来就在等。
- **和语音、表情互斥**：一条语音 + 一张图 = 同一句话用两种方式说；
  图和表情包同时挂，等于两句图连着弹。判定层直接排除了这几种组合。
- **抽象描述会画出抽象图**：模型给的 `imagePrompt` 就是最终提示词，没有二次扩写。
  想让它更好看，去改人设里对画面的偏好，而不是指望服务商猜。
