# 知识系统

## 定位

知识系统负责收集、处理、整理、保存和检索角色学到的知识。它与记忆系统、社交关系系统并列，按角色独立积累。

- **记忆系统**回答：发生过什么、经历过什么。
- **知识系统**回答：学到了什么、理解了什么。
- **社交关系系统**回答：她认识谁、与对方处于什么关系。

知识可以来自经历，但不能把经历记录本身直接当作知识；用户偏好也不应仅因被提及就自动变成知识。

## 核心原则

1. **先处理，后入库**：聊天或资料中出现的内容只是候选，不等于正式知识。
2. **来源可追溯**：每条知识应尽可能保留来源类型、来源引用和获取时间；不能把模型推测伪装成来源事实。
3. **保留不确定性**：对来源不可靠、内容不完整或仍有争议的知识标记置信状态，不强行写成确定结论。
4. **去重与冲突并存**：重复内容应合并或关联；相互矛盾的说法应保留冲突关系，不能静默覆盖旧知识。
5. **角色隔离**：不同角色的知识默认独立；不因平台账号或相同标题而跨角色共享。
6. **按需检索**：不把整个知识库塞进每次聊天。语境助手判断是否需要知识检索，再按问题召回少量相关条目。
7. **知识与记忆分工**：知识条目不复制整段聊天经历；需要证据时引用记忆事件或原始来源。

## 建议的数据流

`来源 → 候选 → 处理 → 待确认/可入库 → 正式知识 → 按需检索`

### 来源

首批考虑三类来源：

- 聊天中出现、可能值得学习的内容；
- 用户主动提供或导入的资料；
- 用户手动创建的知识条目。

接入时保留来源引用和必要的元信息。不要默认把所有聊天内容都送去知识处理。

### 候选与处理

知识处理助手负责判断候选是否属于可复用知识，并执行：

- 提炼主题、核心结论和必要解释；
- 识别知识类别、关键词和关联概念；
- 检查已有知识中的重复项；
- 发现与现有知识不一致的内容并建立冲突提示；
- 记录来源与不确定性；
- 给出建议动作：丢弃、补充现有条目、创建新条目或标记待核实。

处理助手的输出先进入候选处理结果，不直接覆盖正式知识。

### 正式入库

正式知识与候选分开管理。入库操作应保留处理结果、来源引用和变更历史。对于冲突、低可信度或来源不足的内容，先进入待确认状态；明确可靠且符合规则的内容才可自动入库。具体自动入库门槛和人工确认策略在实现前结合现有 AI 助手调用方式确定。

### 检索与使用

检索由语境助手按需触发。知识系统只返回与当前问题相关的条目、来源和可信状态；主聊天模型仍负责最终回复。检索结果不能越过角色隔离，也不能把未确认候选当成正式知识。

## 与其他系统的边界

- 不接管忆泡、日记或长期记忆的写入职责。
- 不把「发生过的事」自动改写成知识；只有可复用的概念、规律、事实或技能等才适合进入知识系统。
- 不负责记录用户偏好；偏好由偏好系统负责。
- 不负责维护朋友身份或关系阶段；由社交关系系统负责。
- 可以引用其他系统的数据作为证据，但不复制其正文作为另一份事实来源。

## 页面结构（首阶段）

- **知识候选**：查看待处理内容、处理状态、来源和处理建议。
- **知识库**：查看已入库知识，支持搜索、分类、详情、修订、归档和来源追溯。
- **处理记录**：追踪处理助手的运行结果、失败和人工处置。
- **知识设置**：配置知识处理助手及其独立模型凭据、自动收集/处理范围和入库策略。

首阶段先完成候选—处理—入库—检索的主链路；批量资料解析、复杂知识图谱和自动推理暂不作为前置条件。

### 私聊候选发现与按需检索（已通过本地验收）

- 默认（`knowledgeCollectScope = ALL`）下，所有好友与角色的私聊均适用，不按主人身份或好友身份做额外限制；切到 `SELECTED` 后只收被标记为知识来源的人，见下节。
- 本地预筛先过滤问候、普通闲聊和纯情绪表达；出现概念解释、知识问答、纠错、方法技巧、步骤、规则、语法/算法等信号时，才考虑调用语境助手。保留短知识问句（如“猫是什么？”），不因字数不长直接过滤。
- 使用私聊专用提示词和输入结构，不复用群聊分析入口；只提交当前轮消息 ID、发言人显示名和原始正文，不提交记忆、群聊背景、跨会话历史、其他好友数据或账号标识。
- 模型返回的消息 ID 必须通过当前轮白名单校验；候选正文由程序从原始消息拼接，不能使用模型改写。
- 候选来源引用包含 conversationId、messageIds、发言人、理由、采集时间及 PRIVATE 标记；同角色 30 天内相同原文去重。
- 自动收集开关默认关闭，只控制是否创建候选，不控制正式知识检索。语境助手失败、知识检索失败、候选持久化失败或用量记账失败均不得影响私聊正常回复。
- 私聊的 `knowledgeQuery` 由同一次私聊语境分析返回，不新增第二次模型调用；数据库检索只查当前角色 `KnowledgeItem(status=ACTIVE)`，经相关度排序最多返回 8 条给主聊天模型。检索不读取候选，也不跨角色或查询好友的私人记忆。
- 新增 `yarn test:private-knowledge-candidate`，并已并入 `yarn test:context-assistant`；覆盖候选 ID 白名单、仅检索无候选、查询长度上限、短知识问题预筛，以及私聊最终回复能收到已确认知识条目。DSH 已报告候选发现阶段六项检查全部通过；本轮私聊检索管道仍待专项验收。

### 知识来源白名单（按人过滤收集入口）

解决「收得太多」：只要语境助手判出知识点就落候选，可大部分人的日常闲聊成不了知识，候选列表很快变成一屏待清噪音。
收集入口因此在角色级自动收集开关之后，再加一层「收谁的」判断。

- 角色级 `modelConfig.knowledgeCollectScope`：`ALL`（默认，任何人）／`SELECTED`（只收选定的人）。没有这个键的老角色按 `ALL` 处理，升级不改变既有行为。
- 人级 `MemoryScope.knowledgeCollectEnabled`：与 `proactiveContactEnabled`、`educationEnabled` 同构，在好友档案里逐人开关；只有角色主人能改（同一事务内复核，并写审计 `friend.knowledge_source_updated`）。
- 主人不受这一列影响，永远算来源：主人私聊挂在 `USER_PRIVATE` 范围上，那一行没有这个字段的语义，按列取值只会得到 false。
- 私聊判定看这条会话挂的外部身份范围；群聊判定看候选证据消息的实际作者账号 —— 证据里只要有一位选定的人说过话就收，不要求他是主要发言者（「主人问、别人答」这类轮次最该记）。
- 作者认不出来（证据 id 一条都对不上人）时 fail-closed：宁可不收，也不把别人的话记成知识。
- 昵称不参与判定，只认平台账号：群里同名不同人是常态。
- 只作用于群聊／私聊的自动收集。手动添加、文件导入、网页采集、忆泡提议都是用户主动动作，本来就已经筛过一遍，不拦。
- 知识条目本身不加归属人字段：入库后仍是角色公共知识，检索范围不变。
- 迁移：`20261115180000_knowledge_collect_source`；`yarn test:knowledge-collect-policy` 覆盖缺省 `ALL`、主人直通、fail-closed 与同一人多条证据只查一次库。

## 下一阶段：正式知识治理

知识库主链路稳定后，下一阶段补齐正式知识的维护能力。按风险和依赖拆批实施，不把编辑、合并、冲突、归档和资料导入一次性混成大改。

### 第一批：正式知识编辑与版本历史

- 允许用户编辑 ACTIVE 正式知识的标题、正文、分类、标签和可信度；来源类型、来源引用及其原始出处保持只读，避免人工编辑抹掉溯源信息。
- 每次成功编辑都保留被替换的完整版本快照，至少包含版本号、标题、正文、分类、标签、可信度、来源类型和来源引用；历史记录不可覆盖。
- 使用 KnowledgeItem.revision 做乐观并发控制。编辑请求必须携带读取时的 revision；若版本已变化，返回冲突并要求刷新，不允许旧表单覆盖新内容。
- 版本快照与正式知识更新必须在同一数据库事务提交；任何一端失败都整体回滚。
- 历史记录与正式知识按 characterId 隔离，不能通过其他角色的条目 ID 读取或修改。
- 当前检索仍只读取 ACTIVE 正式知识的最新版本，不把历史版本重复注入聊天上下文。
- 第一批提供查看历史版本的能力；版本回滚作为新的修订写入，不直接覆盖或删除历史版本，具体恢复操作可在本批实现后再验收。


### 第二批实施设计：重复知识与冲突治理

本批先建立“可追溯的关联与人工处置”基础，不让知识处理助手直接修改正式知识。实现按两个小步推进：先让候选建议可信、可查看、可建立关联；再实现用户确认后的合并与冲突处置事务。

#### 1. 候选关联必须由服务端核验

- `processKnowledgeWithAssistant` 返回的 `relatedItemIds` 只是模型建议。服务端必须用本次传给模型的当前角色 ACTIVE 知识 ID 白名单过滤，不能信任模型自行编造的 ID，也不能接受其他角色或已归档/已合并条目。
- 处理结果保留 recommendation 与 relatedItemIds；若建议为 DUPLICATE / CONFLICT 却没有任何有效关联条目，不得将其伪装成已找到重复/冲突对象，页面应明确显示“关联对象待确认/未找到”。
- 处理助手不能在处理阶段创建关系记录、修改正式知识或自动合并。

#### 2. 正式知识关联记录

新增角色隔离的知识关联记录，至少记录 characterId、sourceItemId、targetItemId、relationType（DUPLICATE / CONFLICT / MERGED_INTO）、status（OPEN / RESOLVED / DISMISSED）、处置方式、创建/处置时间及必要的来源快照元数据。

- DUPLICATE 与 CONFLICT 是对称关系：服务端规范化条目 ID 顺序并防止自关联/重复边；MERGED_INTO 是有方向的 source → target。
- 对称关系的去重不依赖应用层自觉：数据库在 `(characterId, LEAST(sourceItemId, targetItemId), GREATEST(sourceItemId, targetItemId), relationType)` 上建了部分唯一索引（仅覆盖 DUPLICATE / CONFLICT），A→B 与 B→A 同时写入会被直接拒绝。MERGED_INTO 不受该索引影响，仍保持有向语义。
- 两端条目必须属于同一 characterId；跨角色关联一律拒绝。条目 ID 必须由服务端验证，不接受模型直接创建的关联。
- 关联不能替代来源或版本历史。合并后源条目保留为可追溯记录，状态从 ACTIVE 转为 MERGED，不物理删除；目标条目仍为 ACTIVE。
- 正式检索只查 ACTIVE，因此 MERGED 源条目不再单独召回；关系详情仍可回溯到源条目、来源和历史版本。

#### 3. 人工处置动作

- 对 DUPLICATE：用户可以选择“合并到指定条目”“保留为独立知识/仅标记重复”或“忽略建议”。合并前展示双方内容、来源、可信度和版本；用户确认目标条目及最终合并正文后，服务端在一个事务中校验双方 revision、保存源条目旧版本、更新目标条目并递增 revision、将源条目标记 MERGED、创建 MERGED_INTO 关系。任何一步失败整体回滚。
- 合并不得仅凭标题相似自动执行；不得以更新时间或模型置信度自动决定保留哪一条。目标条目内容由用户确认，来源证据以关联记录保留，不覆盖目标原始来源。
- 对 CONFLICT：用户可以“确认冲突并保留双方”“标记待核实”或“忽略建议”。冲突双方均保持 ACTIVE、原内容和来源不变；建立 CONFLICT 关系及人工处置记录。待核实状态不等于认定哪一方错误。
- 任何操作都必须携带 revision（必要时双方 revision），用乐观锁阻止过期页面覆盖新内容；接口先验证 owner + character + item。

#### 4. 页面与检索边界

- 候选卡片展示建议类型、理由和经服务端核验的关联知识摘要；点击可查看双方完整正文、来源与版本。
- 正式知识卡片展示重复/冲突关联及处置状态；用户明确确认后才提交处置。
- 默认知识检索仍只返回 ACTIVE 正式知识当前版本；候选、关联记录、历史版本、MERGED 源条目均不直接注入聊天上下文。
- 本批暂不实现自动聚类、语义向量检索、批量合并、归档恢复和文档/网页导入。（2026-11-16 追记：归档恢复与文件/网页导入后来已实现，见文末「来源接入第二批」；自动聚类与语义检索仍未做。）

#### 5. 验收重点

- 模型返回伪造 ID、跨角色 ID、非 ACTIVE ID、自身 ID 均不能形成关联。
- DUPLICATE / CONFLICT 建议不会在处理时改变正式知识。
- 重复关系无向且幂等；冲突双方均保留原文与来源。
- 合并事务中目标 revision 递增、源条目转 MERGED、旧版本快照与关联记录完整；并发或中途失败不得产生半成品。
- 角色隔离、并发编辑、旧页面竞态均有专项测试；检索不返回 MERGED 条目。


### 第三批：归档与恢复

- 归档不等于删除；保留条目、版本和来源。
- 只有 ACTIVE 条目参与默认知识检索；归档条目仍可在管理界面查看并恢复。
- 归档、恢复均记录操作者与时间，并采用版本/状态并发校验。

#### 第一阶段实现（2026-11-09）

**状态模型**：`ACTIVE` / `ARCHIVED` / `TRASHED` / `MERGED`，四态写进 `knowledge_items_status_check` 约束，防止拼写漂移。

| 操作 | 起点 | 终点 | 说明 |
| --- | --- | --- | --- |
| 归档 | ACTIVE | ARCHIVED | 退出检索，可随时取消归档 |
| 取消归档 | ARCHIVED | ACTIVE | 重新参与检索 |
| 移入回收站 | ACTIVE | TRASHED | 退出检索，可恢复或永久删除 |
| 从回收站恢复 | TRASHED | ACTIVE | 重新参与检索 |

`MERGED` 只能由合并事务产生，没有人工入口；不允许恢复、归档或移入回收站。归档不经过回收站，`ARCHIVED → TRASHED` 必须先把知识取消归档，避免「两步删」被一步绕过。

**Schema 变更**：`knowledge_item_revisions` 增加 `action VARCHAR(20) NOT NULL DEFAULT 'CONTENT_EDIT'`，取值 `CONTENT_EDIT / MERGE / ARCHIVE / UNARCHIVE / TRASH / RESTORE`，并加 CHECK 约束。迁移 `20261109160000_knowledge_item_lifecycle` 同时给 `knowledge_items.status` 加 CHECK。历史行统一回填为 `CONTENT_EDIT`（该字段引入之前无法区分，不做时间窗猜测式回填）。

**快照语义**：一次生命周期操作 = 一条快照 + 版本号 +1。快照记录的是**变更前**的完整状态（标题/正文/分类/标签/可信度/来源/状态），`revision` 取变更前版本号，与内容编辑、合并保持一致：第 N 行代表被第 N+1 版取代的那一版。合并事务的两条快照标记为 `action=MERGE`，生命周期快照标记为对应操作，因此历史里能一眼区分「内容改了什么」与「状态怎么变的」。

**API 清单**（均在 `/api/characters/{id}/growth/knowledge` 下，全部要求登录且校验角色归属）：

| 方法 | 路径 | 请求体 | 成功 |
| --- | --- | --- | --- |
| POST | `/items/{itemId}/archive` | `{ expectedRevision }` | `{ item, message }` |
| POST | `/items/{itemId}/unarchive` | `{ expectedRevision }` | `{ item, message }` |
| POST | `/items/{itemId}/trash` | `{ expectedRevision }` | `{ item, message }` |
| POST | `/items/{itemId}/restore` | `{ expectedRevision }` | `{ item, message }` |
| GET | `/trash` | — | `{ characterId, items, itemCount }` |
| DELETE | `/items/{itemId}` | `{ expectedRevision, confirm: "PERMANENT_DELETE" }` | `{ ok, deletedRelations, deletedRevisions, message }` |
| DELETE | `/candidates/{candidateId}` | — | `{ ok, candidateId, deletedStatus, knowledgeItemId, knowledgeItemRetained }` |
| POST | `/candidates/purge-dismissed` | `{}` | `{ ok, deletedCount }` |

状态转换统一在 `server/utils/knowledge-lifecycle.ts` 里：读当前行 → 校验起点状态 → 校验 `expectedRevision` → **条件更新**（`where` 同时带状态与 revision，`count !== 1` 即 409）→ 写快照。读与写之间被抢先改动时，条件更新会失败，保证并发下只有一个请求成功。错误码：角色/知识不存在或跨角色 404；状态不允许、revision 过期、并发生效失败 409；请求体多余字段或格式错误 400。

**永久删除的三重闸门**：
1. 只允许 `TRASHED`，其它状态一律 409；
2. 必须带 `confirm: "PERMANENT_DELETE"`，字段名与取值都写死，缺少或写错都是 400；
3. 存在任何 `MERGED_INTO` 关系（作为源或目标）即拒绝，保护合并审计链。

事务内按「普通关系 → 版本历史 → 知识主体」顺序显式清理，最后一步 `deleteMany` 仍带 `status = TRASHED` 条件兜底。虽然 `knowledge_item_relations` 与 `knowledge_item_revisions` 外键都是级联删除，显式清理仍保留：一是让删除范围在代码里可读，二是避免未来外键行为变化时留下孤立关系。

**候选清理边界**：`KnowledgeItem.candidateId` 是 `onDelete: SetNull`，因此删除 ACCEPTED 候选只会让入库知识解除指向，正文、来源、版本历史都留在知识自己身上。单条删除拒绝 `PROCESSING` / `ACCEPTING`（避免后台任务写到一半失去宿主）；批量清理的 `where` 写死 `status = DISMISSED` 且 `knowledgeItem.is: null`，待处理、待复核、已入库候选都不会被带动。候选删除不可恢复。

**检索隔离**：`knowledge_items` 的读取入口一律带显式状态过滤——聊天侧 `pipeline.ts` 的 `loadKnowledge`、`search.get.ts`、`index.get.ts` 默认列表都只取 `ACTIVE`。归档与回收站知识天然不会进入检索；`/trash` 只返回当前角色的 `TRASHED`。永久删除只接受用户会话，没有任何 AI 助手调用路径。

**本阶段不做**：页面与交互、定时清理、正式知识批量永久删除、自动删除候选关联的正式知识、社交关系系统的改动。（页面与交互已在第二阶段完成，见下节。）

**测试**：`yarn test:knowledge-lifecycle-isolated` 自建一次性数据库（`yiling_knowledge_lifecycle_test_*`）跑完整迁移后执行，结束后删库，不触碰真实知识。覆盖：四种合法转换（含快照 action 与状态）、非法转换、过期 revision 与同版本并发、归档/回收站不参与检索、恢复后可检索、永久删除的状态与确认限制、MERGED_INTO 审计链保护、删除后关系与历史零残留、删除候选不删正式知识、批量清理不误删、跨角色与未登录拒绝。

#### 第二阶段实现：页面与交互（2026-11-09）

本阶段只接页面，未改动生命周期状态机；唯一后端改动是回收站查询补一个展示派生字段。

**页面分区**：知识页在原「候选 / 正式知识库」结构上增加三个分区，同一时间只显示一个。

| 分区 | 数据来源 | 展示状态 | 可用操作 |
| --- | --- | --- | --- |
| 知识库 | `GET /growth/knowledge`（`itemStatus` 默认 ACTIVE） | ACTIVE | 查看、编辑、版本历史、归档、移入回收站 |
| 归档知识 | `GET /growth/knowledge?itemStatus=ARCHIVED` | ARCHIVED | 恢复到知识库、移入回收站 |
| 回收站 | `GET /growth/knowledge/trash` | TRASHED | 恢复到知识库、永久删除 |

页面在三处都按 `status` 再做一次过滤：接口过滤失效时，混进来的其它状态不会显示。分区切换会收起正在编辑的表单、版本历史与确认弹窗，并用同一个请求版本号作废旧分区的在途请求。

**回收站派生字段 `canPermanentlyDelete`**：`trash.get.ts` 查询该角色所有 `MERGED_INTO` 关系（源或目标命中回收站条目即可），返回 `{ ...item, canPermanentlyDelete: boolean }`。它只用于页面禁用「永久删除」并展示「参与过合并，属于合并审计链」的说明；**永久删除接口仍会在事务内重新检查同一关系**，前端标记不参与任何写入判断。

**归档知识移入回收站（明确的取舍）**：状态机只允许 `ACTIVE → TRASHED`，`ARCHIVED → TRASHED` 是 409，且第一阶段的设计意图就是不允许「两步删」被一步绕过。为满足「归档知识可以移入回收站」的需求，页面按两次合法转换执行：先 `unarchive`（拿到新 revision），再 `trash`。确认框写明这是两步操作、版本号会 +2、历史里会留下两条状态快照；第二步失败时提示「已取消归档、知识现在在知识库，移入回收站失败」，不会让用户误判知识的位置。如果后续认为这个入口违背原设计意图，可改为归档区只保留「恢复到知识库」，或单独放开后端转移。

**候选清理**：与正式知识删除完全分开，不复用同一个操作。

- 单条删除：`DELETE /candidates/{id}`，所有状态可删，但 `PROCESSING` / `ACCEPTING` 按钮禁用（后端同样拒绝）。删除 ACCEPTED 候选时确认框明确写「只移除候选记录，不会删除已入库的正式知识」，成功后提示「候选已删除，已入库的正式知识保留」。
- 批量删除：只对已忽略候选提供复选框；批量入口先用对话框显示「将删除 N 条」，确认后逐条 `DELETE`，逐条前再校验一次状态，切角色立即停止后续请求。待处理、处理中、已入库候选不能选中，脏选择集会被二次过滤并提示「请先选择要删除的已忽略候选」。
- 清理全部已忽略：走 `POST /candidates/purge-dismissed`，边界由后端 `where` 写死。

**交互与安全**：

- 重复提交：所有写操作走统一的 `withAction`，同一时刻只跑一个，期间相关按钮全部禁用；永久删除与移入回收站需在确认框里二次确认。
- 409：直接展示服务端 `statusMessage` 并立即重新拉取，同时关闭已过期的确认框，避免用户对着旧 revision 反复提交。
- 其它失败：保留确认框让用户重试，同时刷新列表，避免页面停在过期状态。
- 成功：按服务端返回的 `message` 提示，并刷新当前分区的列表与计数；其它分区计数先显示「—」，等真正打开该分区再读取，避免显示过期数字。
- 角色切换：沿用「角色代际 + 请求序号」，三个分区共用一个 `loadVersion`；切角色立即清空三个分区的数据、候选选择集、确认框与分区位置，旧角色的在途响应不写数据、不弹提示、不触发新角色刷新。

**键盘可访问性**：新增 `app/components/AccessibleDialog.vue`，合并确认框与新的操作确认框都改用它。打开后焦点进入弹窗（优先 `[data-autofocus]`，其次第一个可聚焦元素，最后弹窗容器）；Tab / Shift+Tab 在弹窗内循环；Esc 关闭；关闭后焦点回到打开它的元素；打开期间锁定背景滚动。焦点落点计算抽到 `app/utils/focus-trap.ts`（纯函数，不碰全局状态），可用假 DOM 单测。

**状态不只用颜色表达**：分区选中态用字重 + 描边 + 底色 + `aria-pressed`；归档、回收站条目带「已归档」「回收站」文字徽标；合并审计链提示带符号与完整句子，不只靠红色。

**测试**：新增 `yarn test:knowledge-lifecycle-page`（19 项），沿用脚本级 harness。覆盖：三分区只展示对应状态、四种生命周期操作的请求契约与刷新、归档→回收站两步与新 revision、永久删除的二次确认与口令、合并审计链禁止永久删除、候选单条/多选批量删除、待处理候选不被误删、409 反馈与刷新、非 409 失败保留确认框、角色切换竞态、加载失败与空列表、Tab 焦点落点计算、模板与弹窗组件静态断言。`scripts/test-knowledge-lifecycle-db.ts` 增加回收站 `canPermanentlyDelete` 的接口断言（合并审计链条目 false、普通条目 true）。

**验收结果（2026-11-09 晚）**：`yarn test:knowledge-lifecycle-isolated` 在本机隔离库通过（含 `canPermanentlyDelete` 派生字段断言）；`yarn build` 通过；浏览器人工验收用「临时库 + 无头 Chrome 真按键」跑通 15 项：焦点进入弹窗（落在「取消」）、Tab / Shift+Tab 各 6 次不逃出、Esc 关闭后焦点回到触发按钮、375px 下确认框与回收站/知识库列表均无横向溢出、合并审计链条目永久删除禁用且说明可读、候选批量条数量文案正确。截图留存在本机临时目录（未入库）。

覆盖范围（14 项）：
- 关联状态文案：待处理 / 已合并 / 源知识已合并 / 待核实 / 已处理 / 已忽略 六种都必须有独立文案。
- 双向合并入口：`startMerge(item, relatedItem)` 与 `startMerge(relation.relatedItem, item)` 生成的草稿必须互换 source/target，双方 revision 各自取自对应条目。
- 合并对照框：源与目标的标题、正文、分类、可信度、标签、来源类型、来源快照、版本号都必须进入草稿；目标可信度为 null 时可编辑框留空而不是 0。
- 合并提交字段：请求体键集合必须与服务端 `parseKnowledgeMergeInput` 的允许集合完全一致（多一个字段即 400），并通过真实解析函数验证可被接受；`targetItemId`、双方 revision、用户最终确认的标题/正文/分类、逗号拆分后的标签、数字型可信度逐项断言。
- 冲突三操作：`CONFIRM_CONFLICT` / `NEEDS_VERIFICATION` / `DISMISS` 各自携带正确 action，并按当前条目在关系中真实是 source 还是 target 决定 `expectedSourceRevision` / `expectedTargetRevision` 的顺序（两个方向都测）。
- 幂等与状态：已处置关系不重复发请求；非法可信度不发请求且保留草稿。
- 角色切换：合并草稿、合并中标记、处置中列表、busy 列表全部清空；合并请求在途中切角色后，旧响应不得提示成功、不得触发新角色刷新。
- 失败反馈：409 提示服务端原因、关闭草稿并刷新；非 409 失败保留用户已输入的草稿；关系处置失败提示并刷新。
- 模板绑定：两个合并入口只出现在 `OPEN + DUPLICATE` 区块内，三个冲突操作只出现在 `OPEN + CONFLICT` 区块内，合并提交按钮在标题/正文/分类为空时禁用。

**仍未覆盖（真实浏览器验收缺口）**：按钮点击是否真的触发、弹层是否真的可见、长文对照框的实际排版与滚动、移动端窄屏下的按钮换行、键盘操作与焦点管理、以及页面与真实后端的联调。这些必须在浏览器里人工确认，脚本级测试不能替代。

该测试全部使用内存模拟数据，不连接数据库、不读写任何真实知识条目。

## 自动主题聚类：第一阶段设计（2026-11-17）

### 目标与边界

主题聚类用于发现多条正式知识之间的主题联系，帮助用户从零散条目中看见较大的知识脉络。它是知识库的组织视图，不是新的知识事实来源，也不替代分类、标签、重复/冲突治理。

第一版遵循以下边界：

- 只处理当前角色的 `ACTIVE` 正式知识；候选、归档、回收站、已合并条目和历史版本不参与聚类。
- 只由用户在知识系统页面主动发起，不在每条聊天消息、每次知识检索或候选处理时触发。
- 主题结果是建议，不自动改写知识标题、正文、分类、标签或来源，不创建重复/冲突/合并关系。
- 不自动合并知识，不改变现有知识检索结果，也不把主题摘要直接注入聊天上下文。
- 所有输入、输出和持久化结果都按 characterId 隔离；模型返回的知识 ID 必须通过本次输入的 ACTIVE 条目白名单校验。

### 现有数据可复用的部分

当前 `KnowledgeItem` 已有 `title`、`content`、`category`、`tags`、`confidence`、`status`、`revision` 和来源信息；知识关联已有 `DUPLICATE`、`CONFLICT`、`MERGED_INTO` 三类治理关系。

- 分类和标签可作为主题发现的线索，但不能直接等同于主题：同一分类下可能有多个主题，同一主题也可能跨分类。
- 标题与正文提供语义内容；可信度可用于提示审核优先级，不应作为主题归属的唯一依据。
- 重复/冲突关系是知识治理关系，不是一般主题边。第一版不得把它们直接当作聚类连接边，更不能因关系存在就自动合并主题。
- 已有来源和版本历史继续留在知识条目自身；主题分组只引用知识 ID，不复制知识正文或来源快照。

### 第一版建议流程

1. 用户点击“发现主题”，服务端读取当前角色的 ACTIVE 知识条目，并记录本次输入集合及各条目的 revision。
2. 使用标题、正文、分类和标签生成主题分组建议。首版可先采用一次显式批处理的模型分析；不在聊天链路中调用，也不逐条触发模型。
3. 模型只能返回本次输入白名单内的知识 ID、主题名称、简短说明和归组理由。服务端丢弃未知 ID、重复 ID、非本次输入 ID；输出格式或覆盖率不合格时整批标记失败，不静默保存部分结果。
4. 用户查看建议，可逐组采纳、改名、拆分、移出条目或忽略。一个知识条目允许出现在多个主题中；未归组的知识仍正常留在知识库。
5. 采纳只建立“主题—知识条目”的引用关系，不改动知识条目本身。主题分组暂不参与聊天检索。

### 主题与知识条目的关系

第一版采用扁平主题组，不预设父子层级。主题不是知识分类的替代品，也不强迫每条知识只能属于一个主题。

主题组至少需要：角色归属、主题名称、说明、状态、创建/更新时间、来源批次或输入摘要；成员关系至少需要主题 ID、知识条目 ID、采纳时的条目 revision 和加入时间。数据库结构、删除语义和审计字段在进入开发前再根据页面交互定稿。

主题组只保存必要的组织信息，不复制完整知识正文。读取主题详情时再按角色和 ACTIVE 状态读取成员条目；若成员条目已归档、移入回收站或合并，应从当前主题视图中隐藏或提示失效，不得让其重新进入聊天检索。

### 更新与失效规则

- 新知识入库或旧知识编辑后，不自动重跑聚类；用户可手动重新发现主题。
- 每次聚类记录输入条目集合及 revision 摘要。若分析期间条目发生变化，保存前必须检测 revision；发生变化的结果应提示过期并要求重新生成，不能覆盖较新知识。
- 重新生成主题建议不自动覆盖用户已采纳的主题组。旧批次可保留为历史建议或明确标记为过期，具体保留策略在开发设计阶段确定。
- 删除主题组不得删除知识条目；移出主题不得改变知识内容、分类或标签。

### 暂不引入向量数据库

首版先验证“主题发现”本身是否有实际价值。当前数据模型没有 embedding 字段，检索仍是词项匹配；本阶段不增加 pgvector、独立向量数据库或新的向量基础设施。

后续只有在知识规模、语义检索效果或主题发现质量证明词项/模型批处理不足时，再单独评估 Embedding 与 pgvector。向量相似度只提供候选联系，不能作为自动合并或自动改写知识的依据。

### 第一版设计决策（2026-11-17）

为避免开发阶段反复变更，第一版先采用以下默认规则：

1. **单次处理上限：50 条 ACTIVE 知识。** 用户可在页面选择本次参与分析的知识范围；超过 50 条时不静默截断，也不自动拆批，而是提示用户缩小范围。这样可避免跨批主题被错误拆散。后续根据真实知识规模和模型上下文成本再评估分批任务。
2. **复用现有知识助手模型配置。** 主题聚类使用知识系统已有的模型服务商、模型和凭据配置，但使用独立的主题聚类提示词与任务入口；不复用候选处理流程，不在聊天消息中触发。
3. **已采纳主题独立保留。** 每次“发现主题”都生成一批新的待审核建议，不覆盖已采纳主题。用户可把建议应用为新主题，或选择性调整现有主题；应用变更时产生主题修订快照，支持查看历史与撤销到先前版本。旧建议批次可标记为已处理或忽略，不作为当前主题数据。
4. **支持人工维护主题。** 用户可以新建、改名、拆分、合并主题组、添加/移除成员和忽略建议。这里的“合并主题”只合并主题分组及其成员引用，不合并、不改写任何 KnowledgeItem；同一知识允许属于多个主题。

页面第一版至少区分：待审核建议、已采纳主题、未归组知识；主题详情展示成员当前状态，对已归档、回收站或已合并的成员显示失效提示，不提供把它们重新纳入聊天检索的入口。

**开发边界补充：** 单次 50 条上限按用户显式选择的 ACTIVE 条目计数；保存前仍须逐条校验角色归属、状态和 revision。若任一输入条目在分析期间发生变化，本批建议整体标记为过期，不部分覆盖。人工编辑主题成员时也必须校验条目仍为当前角色的 ACTIVE 知识。

**本节状态：第一版设计决策已定，可进入技术设计；尚未授权直接开始编码。** 下一步先据此细化数据模型、API 契约和页面状态，再单独评审后开发。


## 自动主题聚类：技术设计草案（2026-11-17）

本节将已确定的产品边界落到候选数据结构与 API 契约，作为编码前评审稿；不代表已经创建模型或接口。

### 建议的数据模型

建议新增五类数据，全部以 `characterId` 隔离：

1. **KnowledgeTopicRun**：一次“发现主题”的执行记录，同时作为 Worker 任务记录。保存角色 ID、状态（QUEUED / PROCESSING / READY / FAILED / STALE）、本次输入知识 ID 与 revision 快照、模型配置标识（不保存 API Key）、租约/重试字段、错误摘要及时间。`READY` 表示建议已生成并可审核；建议是否处理完由 Suggestion 状态表达，不再另设含义重叠的 Run `COMPLETED` / `DISMISSED`。
2. **KnowledgeTopicSuggestion**：某次 Run 产出的一个待审核主题建议。保存名称、说明、归组理由、建议成员 ID 列表及状态（PENDING / ACCEPTED / DISMISSED）。建议成员 ID 必须是 Run 输入快照的子集；部分采纳时记录实际采纳的成员，不能修改原始建议快照。
3. **KnowledgeTopic**：用户采纳后的正式主题。保存名称、说明、状态、revision 和时间。主题不复制知识正文。
4. **KnowledgeTopicMember**：正式主题与知识条目的多对多引用。保存 topicId、itemId、采纳时的 itemRevision 和加入时间；同一主题内同一知识只出现一次，不同主题之间允许重复归属。
5. **KnowledgeTopicRevision**：主题每次修改前的完整快照，包含名称、说明、状态及成员 ID/revision 列表，用于历史查看和撤销。

主题成员表应有 topic/item 唯一约束及查询索引。所有写接口必须同时验证主题、知识条目属于当前角色；不能只相信客户端传入的 ID。建议成员表冗余 characterId 以便隔离查询，但仍须在事务内核对 topic 与 item 的真实归属。删除主题只删除主题组织数据和其历史，不删除 KnowledgeItem；知识条目被删除时主题成员引用应安全失效或级联清理，具体外键策略在 Prisma 评审时确定。

### 批次一致性与过期检测

- 创建 Run 时，在服务端读取最多 50 条用户选定的 ACTIVE 知识，保存每条 ID、revision 及必要的输入摘要；模型输入只取本次白名单条目。
- 模型返回后先做结构校验：主题名称/说明长度、组数上限、每组成员数上限、ID 白名单、去重及单条知识多主题归属规则。无效 ID 不得落库。
- 保存建议前重新读取所有输入条目；只要任一条目不再 ACTIVE、角色不匹配或 revision 变化，Run 整体标记 STALE，不保存可采纳的部分建议。
- 模型输出应要求覆盖所有输入 ID，未归组条目通过明确的 ungroupedIds 返回；服务端校验所有输入 ID 恰好出现在某个主题建议或 ungroupedIds 中。允许同一条目出现在多个主题的产品决策与“恰好一次”冲突，因此实现时应将覆盖校验定义为“至少出现一次或明确未归组”，重复出现在多个主题是合法的。
- 应限制主题建议数量、单组成员数、总输出长度和模型调用超时；具体数值随提示词与模型配置专项测试确定，不在文档阶段臆造。

### 采纳与人工维护事务

- 采纳建议时，服务端再次校验 Run 未过期、建议仍待审核、成员仍为当前角色 ACTIVE 条目且 revision 未变化。
- 用户可选择创建新主题，或将建议成员应用到现有主题；现有主题修改前写入 KnowledgeTopicRevision，再在同一事务内更新主题 revision 和成员关系。
- 改名、拆分、主题合并、增删成员均写主题历史快照。主题合并仅迁移成员引用；遇到重复成员按唯一约束去重，不改动知识条目。
- 撤销操作不是删除历史，而是将某个历史快照恢复为新的 revision，保留完整审计链。
- 用户忽略建议只更新建议状态，不触碰正式主题和知识条目。

### API 契约（第一版）

统一前缀：`/api/characters/:characterId/growth/knowledge`。所有接口沿用现有 owner 鉴权；服务端从已鉴权角色上下文确定 characterId，并在每次读写时校验资源归属，不能只依赖 URL 或客户端传入的 ID。

| 方法 | 完整路径 | 用途与关键约束 |
|---|---|---|
| POST | `/topics/runs` | 创建发现任务；请求体为 `{ itemIds: string[] }`，必须是 1–50 个不重复 ID，服务端逐条确认属于当前角色且为 ACTIVE。成功创建返回 202 与 runId，重复提交视为用户明确发起的新批次。 |
| GET | `/topics/runs` | 分页查询当前角色的批次历史，返回状态、创建时间、输入数量与建议数量。 |
| GET | `/topics/runs/:runId` | 查询批次详情、建议、明确未归组条目及失败/过期原因；不得返回其他角色数据。 |
| POST | `/topics/runs/:runId/suggestions/:suggestionId/accept` | 采纳建议。请求体明确指定 `{ mode: "CREATE" }` 或 `{ mode: "APPLY", topicId: string }`，并可传 `memberItemIds` 选择部分成员；省略时默认使用建议全部成员。只能选择建议成员的子集，且采纳前重新校验 ACTIVE 与 revision。 |
| POST | `/topics/suggestions/:suggestionId/dismiss` | 将待审核建议标记为 DISMISSED，不修改主题或知识条目。 |
| GET | `/topics`、`/topics/:topicId` | 查询主题列表/详情；详情包含成员当前状态与失效提示。 |
| POST | `/topics` | 手动创建空主题，支持名称与说明。 |
| PATCH / DELETE | `/topics/:topicId` | 修改名称/说明；删除只删除主题组织数据及其修订历史，不删除知识条目。 |
| POST / DELETE | `/topics/:topicId/members`、`/topics/:topicId/members/:itemId` | 添加/移除成员；添加只允许当前角色 ACTIVE 知识，且每次变更先写修订快照。 |
| POST | `/topics/:topicId/split` | 拆分主题；请求体提供新主题名称/说明与要移动的成员 ID，必须是源主题当前有效成员的非空子集；源主题保留其余成员。 |
| POST | `/topics/merge` | 合并主题组；请求体提供同一角色下至少两个 topicIds 与目标主题信息。保留一个目标主题，将其他主题的成员引用去重迁入；每个受影响主题均写修订快照。 |
| GET | `/topics/:topicId/revisions` | 查询主题修订历史。 |
| POST | `/topics/:topicId/revert` | 请求体提供 revisionId；将该快照恢复为新的 revision，不删除或改写历史记录。 |

**状态与并发约定：**

- Run 状态仅使用 `QUEUED`、`PROCESSING`、`READY`、`FAILED`、`STALE`。Worker 领取任务后通过租约/fencing token 防止过期 Worker 覆盖新结果；失败重试耗尽后为 FAILED。
- Suggestion 状态仅使用 `PENDING`、`ACCEPTED`、`DISMISSED`。Run 为 READY 后，建议可以逐条审核；不额外维护含义重叠的“批次已完成”状态。
- 创建 Run 时服务端保存输入 ID/revision 快照。模型输出必须满足 ID 白名单与结构约束；每个输入 ID 至少出现在一个主题建议或 `ungroupedIds` 中，允许同一知识出现在多个主题。
- 保存建议前若任一输入条目不再属于当前角色、状态不再 ACTIVE 或 revision 变化，整批 Run 标记 STALE，不保存部分建议。
- 所有主题写操作在事务中先保存受影响主题的修改前快照，再更新主题与成员关系；同一主题同一知识唯一。对主题或成员的跨角色 ID 一律按不可访问处理。
- 主题成员读取时实时关联 KnowledgeItem；失效成员只展示状态提示，不作为有效成员参与主题建议或聊天检索。

Run 的模型调用与 HTTP 请求生命周期解耦：POST 只创建 QUEUED 记录并快速返回，由现有常驻 Worker 宿主领取；新增知识主题专属处理步骤与租约字段，不复用 MemoryJob 或社交任务业务表，也不新建第二套 Worker。主题发现仅由用户在知识页面显式触发。

### 页面状态草案

知识工作区正式知识库旁增加“主题”视图，不改变候选整理和现有知识库默认入口。主题视图分为：

- **发现主题**：选择最多 50 条 ACTIVE 知识，展示所选数量、开始按钮和运行状态。
- **待审核建议**：按批次查看建议主题、归组理由、成员预览、未归组条目；提供采纳、改名后采纳、拆分调整、忽略。
- **已采纳主题**：列表显示主题名称和成员数；详情可改名、增删成员、拆分/合并主题、查看历史与撤销。
- **未归组知识**：仅是当前主题视图的辅助筛选，不改变知识库条目状态。
- **失效成员提示**：主题成员已不再 ACTIVE 时明确标记，不提供把归档/回收站/已合并条目直接加入主题的操作。

### 后台任务基础设施核查结论（2026-11-17）

已核对当前 main 的 `scripts/run-memory-worker.ts`、`server/utils/memory-worker.ts`、`server/utils/social-relationship-assessment-ai.ts` 与 Prisma 任务模型：

- 项目已有常驻 Worker 进程，并在同一轮中顺序处理记忆、社交评估、互动经验、教育迁移和反思任务；可复用的是**Worker 宿主与启动/部署入口**。
- 记忆任务 `MemoryJob` 绑定 `MemoryScope`，承载记忆快照等专属语义，不适合塞入主题聚类任务。
- 社交评估已有独立任务表、租约、fencing token、重试与历史记录，更接近主题分析任务需要的执行治理；但它绑定社交关系 scope，也不应直接复用其业务表。
- 当前没有证据表明项目已有可供任意领域复用的通用任务队列。因此不建议把主题聚类伪装成 MemoryJob，也不建议新造第二套常驻 Worker。

**建议实现方式：** 新增知识主题专属 Run/Task 状态与租约字段，复用现有 Worker 宿主增加一个 `processNextKnowledgeTopicRun` 步骤；模型执行、租约续期、失败重试、失效检测和结果保存由知识主题领域模块自己负责。Run 记录本身兼任任务记录，不再额外造一张重复的 Task 表。模型调用仍复用知识助手的模型连接解析方式，但提示词、输入白名单、输出校验与用量记账独立。

**结论：** 后台任务方案复用现有进程入口，任务数据与领域逻辑保持知识主题专属。实现前仍需由实现者按当前代码复核 Worker 调度顺序、租约工具和部署脚本；不将 MemoryJob 或 SocialRelationshipAssessmentTask 改造成通用表。


### 技术契约评审结论与裁决（2026-11-17）

本节是本技术设计草案的规范性补充。若前文存在措辞不一致，以本节为准。此处完成的是文档评审，不代表数据库、API、Worker 或页面已经实现。

#### 1. Run 输入快照与 Worker 读取时机

- 创建 Run 的 HTTP 请求必须在事务内验证所选条目属于当前角色且状态为 ACTIVE，并记录不可变的 `itemId + revision` 输入快照；请求只负责快速创建 QUEUED Run，不执行模型调用。
- Worker 领取任务后，必须先校验租约/fencing token，再按 Run 快照读取当前知识条目；只有角色归属仍匹配、状态仍为 ACTIVE、revision 与快照一致的条目才可组成模型输入。
- 模型输入正文只在本次 Worker 执行期间读取和使用。Run 持久化必要的 ID/revision 快照及可审计的非正文摘要即可；不得为了重放而额外长期复制整段知识正文或来源原文。
- 若 Worker 读取时发现任一输入条目不满足角色、ACTIVE 或 revision 条件，Run 直接标记 STALE，不调用模型。模型调用结束、写入建议之前必须再次完整校验同一批输入；任一条目变化则整批 STALE，不能部分保存。
- 若租约已失效或 fencing token 不匹配，旧 Worker 不得写入结果、更新 Run 状态或覆盖新 Worker 的执行结果。

#### 2. 模型输出采用整批严格校验

- 模型输出先进入内存中的未信任暂存对象；通过完整结构、长度、数量、白名单和覆盖校验后，才允许在一个事务内写入 Suggestion 并将 Run 置为 READY。
- 任意成员 ID 不在本次 Run 输入白名单、主题结构非法、输出超限、成员重复规则不满足，或输入覆盖不完整时，整批输出判为无效：不保存任何 Suggestion，Run 按可重试错误处理；重试耗尽后 FAILED。不得“丢弃非法 ID 后继续保存剩余部分”，以免静默改变模型分组含义。
- 每个输入知识 ID 至少出现于一个主题建议，或明确列入 `ungroupedIds`。同一知识出现在多个主题建议中是合法的，因此覆盖校验不是“恰好出现一次”；同一主题内部则不得重复出现同一知识 ID。
- `ungroupedIds` 必须是输入白名单子集，且不得与任何主题成员重复。主题建议成员与 `ungroupedIds` 的并集必须覆盖全部输入 ID。
- 主题组数、单组成员数、字段长度、总输出长度与模型超时上限应由实现阶段结合所选模型配置确定，并通过边界测试固定；在没有测试依据前不写入臆造的硬编码数值。

#### 3. 成员 revision 的语义与知识后续编辑

- `KnowledgeTopicMember.itemRevision` 表示该知识被加入此主题时的知识版本，是历史审计信息，不是成员关系的持续有效性锁。
- 知识条目后续编辑但仍为当前角色 ACTIVE 时，成员关系继续有效，不自动移出主题，也不要求用户重新采纳。
- 主题详情应比较成员记录的 `itemRevision` 与当前 KnowledgeItem.revision；不一致时显示“加入主题后知识已更新”的版本变化提示，并以当前 ACTIVE 正文展示知识内容。
- 知识变为 ARCHIVED、TRASHED、MERGED 或不再属于当前角色时，成员不再作为有效成员参与主题发现、有效成员计数或任何未来检索；保留引用/审计信息并显示失效原因。若底层删除导致外键无法保留，则按已评审的删除语义安全清理引用，不得因此删除其他知识或主题。

#### 4. 主题合并、删除与撤销

- 主题合并请求必须显式指定一个保留的目标 `topicId` 和至少一个不同的源主题 ID；所有主题必须属于同一已鉴权角色。目标主题保留名称、说明和身份，源主题的有效成员引用迁入目标主题并按唯一约束去重。
- 每个受影响主题在事务内先写修改前快照。迁移成功后，源主题标记为 `MERGED`（或等价的不可编辑归档状态，具体枚举在 Schema 评审中固定），记录合并目标与时间；不得直接物理删除源主题及其修订历史。源主题详情应可追溯到目标主题。
- 源主题合并后不得再独立添加成员或修改内容。撤销合并通过恢复相关主题快照形成新的 revision，并恢复源主题可编辑状态；不得删除合并前后的审计历史。
- 普通删除仅允许删除未被合并、且用户明确选择删除的主题组织数据；必须在事务内处理成员引用，并明确删除其修订历史是不可逆操作。第一版 UI 应优先提供“归档/停用主题”或二次确认，避免误删。若主题已有合并历史，不提供物理删除入口。
- 合并与撤销必须对所有受影响主题加并发保护；任一主题 revision 已变化时整笔事务返回冲突，不产生部分迁移。

#### 5. 实现前置约束

- 正式成员关系必须有数据库唯一约束 `(topicId, itemId)`；跨角色归属必须由服务端在事务内核验，不能只依赖冗余 `characterId`。
- 所有主题写操作都以角色鉴权上下文为根，并对目标主题、源主题、知识条目逐一做归属验证。
- 本批仍不引入向量数据库、embedding 字段、自动知识合并或聊天链路触发。主题分组仅是用户审核后的组织视图。
- 实现前必须复核现有 Worker 的租约/fencing token 工具、调度顺序和进程退出行为；若现有设施不能保证旧 Worker 无法提交，则先补齐可验证的 fencing 保护，再接入主题任务。

### 主题拆分与合并 API（2026-11-17，开发分支）

#### 拆分主题

- 路径：`POST /api/characters/:id/growth/knowledge/topics/:topicId/split`
- 请求：`{ name, description?, memberItemIds, revision }`。
- `memberItemIds` 必须是来源主题当前成员的非空真子集；至少为原主题保留一条知识。请求不能凭空把其他主题或其他角色的知识加入新主题。
- 事务内锁定来源主题并校验 ACTIVE 状态及 revision，先保存来源主题完整修改前快照，再从来源主题移出选中成员并创建新主题。新主题成员保留原有 `itemRevision`，来源主题 revision 递增，新主题从 revision 1 开始。
- 任一校验或写入失败整体回滚；拆分不会修改 KnowledgeItem 正文、状态、来源或版本。

#### 合并主题

- 路径：`POST /api/characters/:id/growth/knowledge/topics/:topicId/merge`，路径中的 `topicId` 是来源主题。
- 请求：`{ targetTopicId, sourceRevision, targetRevision }`。来源与目标必须是两个不同、同角色、ACTIVE 的主题；两个 revision 都必填。
- 事务内按主题 ID 排序加行锁，避免并发合并时锁顺序不一致；先保存来源主题修改前快照，再将来源标记为 MERGED，写入 `mergedIntoId` / `mergedAt` 并递增 revision。
- 目标主题保留名称、说明和身份。来源成员合并到目标时按 `(topicId, itemId)` 唯一约束去重；已有成员不重复添加，新增成员保留来源的 `itemRevision`。目标只有在成员集合实际变化时才保存快照并递增 revision。
- MERGED 来源主题保留原成员和历史用于追溯，不物理删除；后续不可再编辑、归档或作为合并目标。合并不改变任何 KnowledgeItem。
- 任一 revision 过期、角色不匹配、主题状态不允许或其他写入失败，整笔事务回滚，不产生部分迁移。

### 正式主题历史查询与撤销 API（开发中）

- 主题历史列表：`GET /api/characters/{id}/growth/knowledge/topics/{topicId}/revisions`，返回当前 revision 与最近历史快照摘要；默认 50 条，最多 100 条。
- 历史详情：`GET /api/characters/{id}/growth/knowledge/topics/{topicId}/revisions/{revision}`，读取指定主题版本的完整快照。
- 历史恢复：`POST /api/characters/{id}/growth/knowledge/topics/{topicId}/revisions/{revision}/restore`，请求体携带 `expectedRevision`。恢复不是覆盖旧历史，而是先保存当前版本快照，再以新 revision 恢复所选版本的名称、说明、状态与成员。
- 安全边界：所有接口校验登录用户、角色归属与主题归属；恢复使用主题行锁和 revision 乐观并发校验。已合并主题不可恢复，也不能恢复到 MERGED 快照。
- 完整性边界：恢复前要求快照中的知识成员仍存在、属于当前角色且处于 ACTIVE；若成员已删除、归档或失效，整笔恢复返回冲突，不静默丢成员。
- 默认知识检索不读取主题历史快照；主题历史只用于管理和审计。
- 当前实现等待专项数据库测试与 GitHub Actions，尚未标记为验收完成。
