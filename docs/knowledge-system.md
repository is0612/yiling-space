# 知识系统

## 定位

知识系统负责收集、处理、整理、保存和检索角色学到的知识。它与记忆系统、社交关系系统并列，按角色独立积累。

- **记忆系统**回答：发生过什么、经历过什么。
- **知识系统**回答：学到了什么、理解了什么。
- **社交关系系统**回答：她认识谁、与对方处于什么关系。

知识可以来自经历，但不能把经历记录本身直接当作知识；用户偏好也不应仅因被提及就自动变成知识。

## 核心原则

1. **先处理，后入库**：聊天或资料中出现的内容只是候选，不等于正式知识。
2. **来源可追溯**：每条知识应尽可能保留来源类型、来源引用和获取时间；不能把模型推测伪装成来源事实。
3. **保留不确定性**：对来源不可靠、内容不完整或仍有争议的知识标记置信状态，不强行写成确定结论。
4. **去重与冲突并存**：重复内容应合并或关联；相互矛盾的说法应保留冲突关系，不能静默覆盖旧知识。
5. **角色隔离**：不同角色的知识默认独立；不因平台账号或相同标题而跨角色共享。
6. **按需检索**：不把整个知识库塞进每次聊天。语境助手判断是否需要知识检索，再按问题召回少量相关条目。
7. **知识与记忆分工**：知识条目不复制整段聊天经历；需要证据时引用记忆事件或原始来源。

## 建议的数据流

`来源 → 候选 → 处理 → 待确认/可入库 → 正式知识 → 按需检索`

### 来源

首批考虑三类来源：

- 聊天中出现、可能值得学习的内容；
- 用户主动提供或导入的资料；
- 用户手动创建的知识条目。

接入时保留来源引用和必要的元信息。不要默认把所有聊天内容都送去知识处理。

### 候选与处理

知识处理助手负责判断候选是否属于可复用知识，并执行：

- 提炼主题、核心结论和必要解释；
- 识别知识类别、关键词和关联概念；
- 检查已有知识中的重复项；
- 发现与现有知识不一致的内容并建立冲突提示；
- 记录来源与不确定性；
- 给出建议动作：丢弃、补充现有条目、创建新条目或标记待核实。

处理助手的输出先进入候选处理结果，不直接覆盖正式知识。

### 正式入库

正式知识与候选分开管理。入库操作应保留处理结果、来源引用和变更历史。对于冲突、低可信度或来源不足的内容，先进入待确认状态；明确可靠且符合规则的内容才可自动入库。具体自动入库门槛和人工确认策略在实现前结合现有 AI 助手调用方式确定。

### 检索与使用

检索由语境助手按需触发。知识系统只返回与当前问题相关的条目、来源和可信状态；主聊天模型仍负责最终回复。检索结果不能越过角色隔离，也不能把未确认候选当成正式知识。

## 与其他系统的边界

- 不接管忆泡、日记或长期记忆的写入职责。
- 不把「发生过的事」自动改写成知识；只有可复用的概念、规律、事实或技能等才适合进入知识系统。
- 不负责记录用户偏好；偏好由偏好系统负责。
- 不负责维护朋友身份或关系阶段；由社交关系系统负责。
- 可以引用其他系统的数据作为证据，但不复制其正文作为另一份事实来源。

## 页面结构（首阶段）

- **知识候选**：查看待处理内容、处理状态、来源和处理建议。
- **知识库**：查看已入库知识，支持搜索、分类、详情、修订、归档和来源追溯。
- **处理记录**：追踪处理助手的运行结果、失败和人工处置。
- **知识设置**：配置知识处理助手及其独立模型凭据、自动收集/处理范围和入库策略。

首阶段先完成候选—处理—入库—检索的主链路；批量资料解析、复杂知识图谱和自动推理暂不作为前置条件。

## 下一阶段：正式知识治理

知识库主链路稳定后，下一阶段补齐正式知识的维护能力。按风险和依赖拆批实施，不把编辑、合并、冲突、归档和资料导入一次性混成大改。

### 第一批：正式知识编辑与版本历史

- 允许用户编辑 ACTIVE 正式知识的标题、正文、分类、标签和可信度；来源类型、来源引用及其原始出处保持只读，避免人工编辑抹掉溯源信息。
- 每次成功编辑都保留被替换的完整版本快照，至少包含版本号、标题、正文、分类、标签、可信度、来源类型和来源引用；历史记录不可覆盖。
- 使用 KnowledgeItem.revision 做乐观并发控制。编辑请求必须携带读取时的 revision；若版本已变化，返回冲突并要求刷新，不允许旧表单覆盖新内容。
- 版本快照与正式知识更新必须在同一数据库事务提交；任何一端失败都整体回滚。
- 历史记录与正式知识按 characterId 隔离，不能通过其他角色的条目 ID 读取或修改。
- 当前检索仍只读取 ACTIVE 正式知识的最新版本，不把历史版本重复注入聊天上下文。
- 第一批提供查看历史版本的能力；版本回滚作为新的修订写入，不直接覆盖或删除历史版本，具体恢复操作可在本批实现后再验收。


### 第二批实施设计：重复知识与冲突治理

本批先建立“可追溯的关联与人工处置”基础，不让知识处理助手直接修改正式知识。实现按两个小步推进：先让候选建议可信、可查看、可建立关联；再实现用户确认后的合并与冲突处置事务。

#### 1. 候选关联必须由服务端核验

- `processKnowledgeWithAssistant` 返回的 `relatedItemIds` 只是模型建议。服务端必须用本次传给模型的当前角色 ACTIVE 知识 ID 白名单过滤，不能信任模型自行编造的 ID，也不能接受其他角色或已归档/已合并条目。
- 处理结果保留 recommendation 与 relatedItemIds；若建议为 DUPLICATE / CONFLICT 却没有任何有效关联条目，不得将其伪装成已找到重复/冲突对象，页面应明确显示“关联对象待确认/未找到”。
- 处理助手不能在处理阶段创建关系记录、修改正式知识或自动合并。

#### 2. 正式知识关联记录

新增角色隔离的知识关联记录，至少记录 characterId、sourceItemId、targetItemId、relationType（DUPLICATE / CONFLICT / MERGED_INTO）、status（OPEN / RESOLVED / DISMISSED）、处置方式、创建/处置时间及必要的来源快照元数据。

- DUPLICATE 与 CONFLICT 是对称关系：服务端规范化条目 ID 顺序并防止自关联/重复边；MERGED_INTO 是有方向的 source → target。
- 对称关系的去重不依赖应用层自觉：数据库在 `(characterId, LEAST(sourceItemId, targetItemId), GREATEST(sourceItemId, targetItemId), relationType)` 上建了部分唯一索引（仅覆盖 DUPLICATE / CONFLICT），A→B 与 B→A 同时写入会被直接拒绝。MERGED_INTO 不受该索引影响，仍保持有向语义。
- 两端条目必须属于同一 characterId；跨角色关联一律拒绝。条目 ID 必须由服务端验证，不接受模型直接创建的关联。
- 关联不能替代来源或版本历史。合并后源条目保留为可追溯记录，状态从 ACTIVE 转为 MERGED，不物理删除；目标条目仍为 ACTIVE。
- 正式检索只查 ACTIVE，因此 MERGED 源条目不再单独召回；关系详情仍可回溯到源条目、来源和历史版本。

#### 3. 人工处置动作

- 对 DUPLICATE：用户可以选择“合并到指定条目”“保留为独立知识/仅标记重复”或“忽略建议”。合并前展示双方内容、来源、可信度和版本；用户确认目标条目及最终合并正文后，服务端在一个事务中校验双方 revision、保存源条目旧版本、更新目标条目并递增 revision、将源条目标记 MERGED、创建 MERGED_INTO 关系。任何一步失败整体回滚。
- 合并不得仅凭标题相似自动执行；不得以更新时间或模型置信度自动决定保留哪一条。目标条目内容由用户确认，来源证据以关联记录保留，不覆盖目标原始来源。
- 对 CONFLICT：用户可以“确认冲突并保留双方”“标记待核实”或“忽略建议”。冲突双方均保持 ACTIVE、原内容和来源不变；建立 CONFLICT 关系及人工处置记录。待核实状态不等于认定哪一方错误。
- 任何操作都必须携带 revision（必要时双方 revision），用乐观锁阻止过期页面覆盖新内容；接口先验证 owner + character + item。

#### 4. 页面与检索边界

- 候选卡片展示建议类型、理由和经服务端核验的关联知识摘要；点击可查看双方完整正文、来源与版本。
- 正式知识卡片展示重复/冲突关联及处置状态；用户明确确认后才提交处置。
- 默认知识检索仍只返回 ACTIVE 正式知识当前版本；候选、关联记录、历史版本、MERGED 源条目均不直接注入聊天上下文。
- 本批暂不实现自动聚类、语义向量检索、批量合并、归档恢复和文档/网页导入。

#### 5. 验收重点

- 模型返回伪造 ID、跨角色 ID、非 ACTIVE ID、自身 ID 均不能形成关联。
- DUPLICATE / CONFLICT 建议不会在处理时改变正式知识。
- 重复关系无向且幂等；冲突双方均保留原文与来源。
- 合并事务中目标 revision 递增、源条目转 MERGED、旧版本快照与关联记录完整；并发或中途失败不得产生半成品。
- 角色隔离、并发编辑、旧页面竞态均有专项测试；检索不返回 MERGED 条目。


### 第三批：归档与恢复

- 归档不等于删除；保留条目、版本和来源。
- 只有 ACTIVE 条目参与默认知识检索；归档条目仍可在管理界面查看并恢复。
- 归档、恢复均记录操作者与时间，并采用版本/状态并发校验。

#### 第一阶段实现（2026-11-09）

**状态模型**：`ACTIVE` / `ARCHIVED` / `TRASHED` / `MERGED`，四态写进 `knowledge_items_status_check` 约束，防止拼写漂移。

| 操作 | 起点 | 终点 | 说明 |
| --- | --- | --- | --- |
| 归档 | ACTIVE | ARCHIVED | 退出检索，可随时取消归档 |
| 取消归档 | ARCHIVED | ACTIVE | 重新参与检索 |
| 移入回收站 | ACTIVE | TRASHED | 退出检索，可恢复或永久删除 |
| 从回收站恢复 | TRASHED | ACTIVE | 重新参与检索 |

`MERGED` 只能由合并事务产生，没有人工入口；不允许恢复、归档或移入回收站。归档不经过回收站，`ARCHIVED → TRASHED` 必须先把知识取消归档，避免「两步删」被一步绕过。

**Schema 变更**：`knowledge_item_revisions` 增加 `action VARCHAR(20) NOT NULL DEFAULT 'CONTENT_EDIT'`，取值 `CONTENT_EDIT / MERGE / ARCHIVE / UNARCHIVE / TRASH / RESTORE`，并加 CHECK 约束。迁移 `20261109160000_knowledge_item_lifecycle` 同时给 `knowledge_items.status` 加 CHECK。历史行统一回填为 `CONTENT_EDIT`（该字段引入之前无法区分，不做时间窗猜测式回填）。

**快照语义**：一次生命周期操作 = 一条快照 + 版本号 +1。快照记录的是**变更前**的完整状态（标题/正文/分类/标签/可信度/来源/状态），`revision` 取变更前版本号，与内容编辑、合并保持一致：第 N 行代表被第 N+1 版取代的那一版。合并事务的两条快照标记为 `action=MERGE`，生命周期快照标记为对应操作，因此历史里能一眼区分「内容改了什么」与「状态怎么变的」。

| DELETE | `/candidates/{candidateId}` | — | `{ ok, candidateId, deletedStatus, knowledgeItemId, knowledgeItemRetained }` |
| POST | `/candidates/purge-dismissed` | `{}` | `{ ok, deletedCount }` |

状态转换统一在 `server/utils/knowledge-lifecycle.ts` 里：读当前行 → 校验起点状态 → 校验 `expectedRevision` → **条件更新**（`where` 同时带状态与 revision，`count !== 1` 即 409）→ 写快照。读与写之间被抢先改动时，条件更新会失败，保证并发下只有一个请求成功。错误码：角色/知识不存在或跨角色 404；状态不允许、revision 过期、并发生效失败 409；请求体多余字段或格式错误 400。

**永久删除的三重闸门**：
1. 只允许 `TRASHED`，其它状态一律 409；
2. 必须带 `confirm: "PERMANENT_DELETE"`，字段名与取值都写死，缺少或写错都是 400；
3. 存在任何 `MERGED_INTO` 关系（作为源或目标）即拒绝，保护合并审计链。

事务内按「普通关系 → 版本历史 → 知识主体」顺序显式清理，最后一步 `deleteMany` 仍带 `status = TRASHED` 条件兜底。虽然 `knowledge_item_relations` 与 `knowledge_item_revisions` 外键都是级联删除，显式清理仍保留：一是让删除范围在代码里可读，二是避免未来外键行为变化时留下孤立关系。

**候选清理边界**：`KnowledgeItem.candidateId` 是 `onDelete: SetNull`，因此删除 ACCEPTED 候选只会让入库知识解除指向，正文、来源、版本历史都留在知识自己身上。单条删除拒绝 `PROCESSING` / `ACCEPTING`（避免后台任务写到一半失去宿主）；批量清理的 `where` 写死 `status = DISMISSED` 且 `knowledgeItem.is: null`，待处理、待复核、已入库候选都不会被带动。候选删除不可恢复。

**检索隔离**：`knowledge_items` 的读取入口一律带显式状态过滤——聊天侧 `pipeline.ts` 的 `loadKnowledge`、`search.get.ts`、`index.get.ts` 默认列表都只取 `ACTIVE`。归档与回收站知识天然不会进入检索；`/trash` 只返回当前角色的 `TRASHED`。永久删除只接受用户会话，没有任何 AI 助手调用路径。

**本阶段不做**：页面与交互、定时清理、正式知识批量永久删除、自动删除候选关联的正式知识、社交关系系统的改动。（页面与交互已在第二阶段完成，见下节。）

**测试**：`yarn test:knowledge-lifecycle-isolated` 自建一次性数据库（`yiling_knowledge_lifecycle_test_*`）跑完整迁移后执行，结束后删库，不触碰真实知识。覆盖：四种合法转换（含快照 action 与状态）、非法转换、过期 revision 与同版本并发、归档/回收站不参与检索、恢复后可检索、永久删除的状态与确认限制、MERGED_INTO 审计链保护、删除后关系与历史零残留、删除候选不删正式知识、批量清理不误删、跨角色与未登录拒绝。

#### 第二阶段实现：页面与交互（2026-11-09）

本阶段只接页面，未改动生命周期状态机；唯一后端改动是回收站查询补一个展示派生字段。

**页面分区**：知识页在原「候选 / 正式知识库」结构上增加三个分区，同一时间只显示一个。

| 分区 | 数据来源 | 展示状态 | 可用操作 |
| --- | --- | --- | --- |
| 知识库 | `GET /growth/knowledge`（`itemStatus` 默认 ACTIVE） | ACTIVE | 查看、编辑、版本历史、归档、移入回收站 |
| 归档知识 | `GET /growth/knowledge?itemStatus=ARCHIVED` | ARCHIVED | 恢复到知识库、移入回收站 |
| 回收站 | `GET /growth/knowledge/trash` | TRASHED | 恢复到知识库、永久删除 |

页面在三处都按 `status` 再做一次过滤：接口过滤失效时，混进来的其它状态不会显示。分区切换会收起正在编辑的表单、版本历史与确认弹窗，并用同一个请求版本号作废旧分区的在途请求。

**回收站派生字段 `canPermanentlyDelete`**：`trash.get.ts` 查询该角色所有 `MERGED_INTO` 关系（源或目标命中回收站条目即可），返回 `{ ...item, canPermanentlyDelete: boolean }`。它只用于页面禁用「永久删除」并展示「参与过合并，属于合并审计链」的说明；**永久删除接口仍会在事务内重新检查同一关系**，前端标记不参与任何写入判断。

**归档知识移入回收站（明确的取舍）**：状态机只允许 `ACTIVE → TRASHED`，`ARCHIVED → TRASHED` 是 409，且第一阶段的设计意图就是不允许「两步删」被一步绕过。为满足「归档知识可以移入回收站」的需求，页面按两次合法转换执行：先 `unarchive`（拿到新 revision），再 `trash`。确认框写明这是两步操作、版本号会 +2、历史里会留下两条状态快照；第二步失败时提示「已取消归档、知识现在在知识库，移入回收站失败」，不会让用户误判知识的位置。如果后续认为这个入口违背原设计意图，可改为归档区只保留「恢复到知识库」，或单独放开后端转移。

**候选清理**：与正式知识删除完全分开，不复用同一个操作。

- 单条删除：`DELETE /candidates/{id}`，所有状态可删，但 `PROCESSING` / `ACCEPTING` 按钮禁用（后端同样拒绝）。删除 ACCEPTED 候选时确认框明确写「只移除候选记录，不会删除已入库的正式知识」，成功后提示「候选已删除，已入库的正式知识保留」。
- 批量删除：只对已忽略候选提供复选框；批量入口先用对话框显示「将删除 N 条」，确认后逐条 `DELETE`，逐条前再校验一次状态，切角色立即停止后续请求。待处理、处理中、已入库候选不能选中，脏选择集会被二次过滤并提示「请先选择要删除的已忽略候选」。
- 清理全部已忽略：走 `POST /candidates/purge-dismissed`，边界由后端 `where` 写死。

**交互与安全**：

- 重复提交：所有写操作走统一的 `withAction`，同一时刻只跑一个，期间相关按钮全部禁用；永久删除与移入回收站需在确认框里二次确认。
- 409：直接展示服务端 `statusMessage` 并立即重新拉取，同时关闭已过期的确认框，避免用户对着旧 revision 反复提交。
- 其它失败：保留确认框让用户重试，同时刷新列表，避免页面停在过期状态。
- 成功：按服务端返回的 `message` 提示，并刷新当前分区的列表与计数；其它分区计数先显示「—」，等真正打开该分区再读取，避免显示过期数字。
- 角色切换：沿用「角色代际 + 请求序号」，三个分区共用一个 `loadVersion`；切角色立即清空三个分区的数据、候选选择集、确认框与分区位置，旧角色的在途响应不写数据、不弹提示、不触发新角色刷新。

**键盘可访问性**：新增 `app/components/AccessibleDialog.vue`，合并确认框与新的操作确认框都改用它。打开后焦点进入弹窗（优先 `[data-autofocus]`，其次第一个可聚焦元素，最后弹窗容器）；Tab / Shift+Tab 在弹窗内循环；Esc 关闭；关闭后焦点回到打开它的元素；打开期间锁定背景滚动。焦点落点计算抽到 `app/utils/focus-trap.ts`（纯函数，不碰全局状态），可用假 DOM 单测。

**状态不只用颜色表达**：分区选中态用字重 + 描边 + 底色 + `aria-pressed`；归档、回收站条目带「已归档」「回收站」文字徽标；合并审计链提示带符号与完整句子，不只靠红色。

**测试**：新增 `yarn test:knowledge-lifecycle-page`（19 项），沿用脚本级 harness。覆盖：三分区只展示对应状态、四种生命周期操作的请求契约与刷新、归档→回收站两步与新 revision、永久删除的二次确认与口令、合并审计链禁止永久删除、候选单条/多选批量删除、待处理候选不被误删、409 反馈与刷新、非 409 失败保留确认框、角色切换竞态、加载失败与空列表、Tab 焦点落点计算、模板与弹窗组件静态断言。`scripts/test-knowledge-lifecycle-db.ts` 增加回收站 `canPermanentlyDelete` 的接口断言（合并审计链条目 false、普通条目 true）。

**验收结果（2026-11-09 晚）**：`yarn test:knowledge-lifecycle-isolated` 在本机隔离库通过（含 `canPermanentlyDelete` 派生字段断言）；`yarn build` 通过；浏览器人工验收用「临时库 + 无头 Chrome 真按键」跑通 15 项：焦点进入弹窗（落在「取消」）、Tab / Shift+Tab 各 6 次不逃出、Esc 关闭后焦点回到触发按钮、375px 下确认框与回收站/知识库列表均无横向溢出、合并审计链条目永久删除禁用且说明可读、候选批量条数量文案正确。截图留存在本机临时目录（未入库）。

## 知识系统收尾范围

进入统一成长数据中心实现前，知识系统还需完成来源接入能力：

1. 文件/文档导入：导入只创建 `IMPORT` 候选，不绕过知识处理助手和人工确认。
2. 网页来源采集：明确 URL 白名单、重定向限制、响应大小/类型/超时和来源快照；网页内容同样进入候选。
3. 来源追溯：正式知识保留来源类型、来源引用和必要的来源快照；编辑、合并不得悄悄覆盖原始来源。
4. 完成一次知识系统整体回归，明确知识系统的数据所有权、读取 API 和事件发布点，作为统一成长数据中心接入依据。

## 来源接入第二批：网页来源采集（2026-11-09，开发分支待验收）

- 知识候选区新增网页导入入口，输入 HTTP/HTTPS URL 后由服务端采集，不依赖浏览器端抓取。
- 新增 `server/utils/knowledge-web-import.ts`：支持 HTML、XHTML 与纯文本；提取标题和正文，移除 script/style/nav/footer/header/aside/form 等非正文区域，规范化空白与常见 HTML 实体。
- **SSRF 防护复用统一安全下载器**：仅允许 HTTP/HTTPS；拒绝 localhost、内网、link-local、保留地址及带凭据 URL；DNS 的全部 A/AAAA 结果必须是公网地址；实际 socket 连接时再次解析、校验并固定 IP，防止 DNS rebinding；每次重定向重新校验，最多 5 跳。

- 页面角色切换会清空 URL 输入和导入状态；请求返回前若角色已切换，旧结果不会污染新角色工作区。

## 成长事件接入：公开忆泡人工提议知识候选（2026-11-10）

- 忆泡日历中，角色全局范围的 ACTIVE 忆泡可由拥有者选择20～2000字符的连续原文摘录，明确点击“提出知识候选”。私人/外部身份范围和归档来源不开放；不自动扫描每条忆泡、不额外调用模型。
- `MemoryKnowledgeCandidateRequest` 与 `memory.knowledge-candidate.requested` 同事务提交；Outbox只保存请求引用，不保存正文。知识消费者经记忆领域Gateway验证公开来源后，创建 `sourceType=MEMORY_EVENT`、`status=PENDING` 候选，不创建正式知识。
- 每角色每忆泡只允许一个请求。持久请求记录独立于Outbox保留和候选删除，重复请求不改写摘录；CREATED/SKIPPED终态不会重新建候选。SKIPPED后即使恢复原来源也不会重新开启此请求，当前可另走手工候选录入。
- 来源标题与详情保存SHA-256版本摘要，消费前归档、删除、转私人或内容变化时跳过；来源范围与行在短事务中共享锁定，标记、候选与投递确认共同提交或回滚。
- 终态请求清空摘录和说明，只保留来源/候选ID、摘要、状态和必要时间。候选自身的摘录是用户主动提交的待整理资料，不随来源隐藏自动删除，用户可删除候选；处理模型调用前、返回保存前和正式采纳事务内都会重查来源及版本，不允许失效来源继续整理/采纳。模型调用发出后无法撤回供应商已接收的数据。
- 正式知识仍由原有知识助手整理并由用户明确采纳；正式入库后作为独立结论保留，不因来源归档/删除自动删除。来源变动不自动改写已确认知识，需用户依据追溯信息编辑或撤销。
- 当前不迁移聊天语境助手已有的候选采集路径，不把用户偏好/一次经历自动判成知识，不回填历史事件。
