# 日常生活与拍照系统设计方案

状态：后端基础已开始实现；自动排程、生活上下文注入、UI 与完整拍照联动仍待完成  
> 目标：让角色拥有连续、自然、可回顾的生活，而不是把角色变成日程执行器或定时生图机器人。  
> 核心原则：**小鲸鱼才是主体，其他系统都服务于她。**

## 1. 目标与范围

本阶段由两个相互关联、职责独立的领域组成：

- **日常生活（Daily Life）**：管理生活类型、每日计划、当前活动、临时变化和实际活动过程。
- **日常拍照（Daily Photography）**：管理拍照意图、画面构成、生图调用、照片资产和照片与经历的关联。

期望角色能够自然地安排一天、临时改变想法、记录真正发生的活动，并在自己想拍照或分享时留下画面。没有拍照也可以是完整的一天；没有安排也不意味着生活失败。

本阶段不建设完整生活模拟器，不建设新的通用自主代理，不引入向量数据库，不重做生图引擎。

## 2. 设计原则

1. **计划不是事实**：计划中的活动不能自动成为已发生经历。
2. **角色有自主权**：计划是参考，不是命令；允许取消、跳过、调整和临时起意。
3. **事实有证据**：只有获得足够依据的实际活动才能进入忆泡或被日记当作事实。
4. **照片不是任务**：不要求每天拍照，不因日程到点而强制生图。
5. **照片提示词不是照片事实**：提示词表达生成意图，不能代替对生成结果的观察。
6. **上下文按需注入**：不把完整日程塞进每一轮聊天，技术讨论和子代理任务不应被生活信息干扰。
7. **复用现有系统**：优先复用形象档案、服饰造型、生图服务、忆泡、日记手账、成长事件、后台任务和主动消息机制。
8. **不重复存储**：不另造一套长期记忆、日记或图片字节存储。
9. **按角色隔离**：计划、活动、照片和配置必须有明确角色归属与访问校验。
10. **失败可恢复**：计划生成、生图、照片投递、活动关联分别记录状态，避免重复执行和错误宣称成功。

## 3. 系统边界与现有模块关系

| 模块 | 本阶段中的职责 |
|---|---|
| 日常生活 | 计划、活动过程、临时调整、生活时间线 |
| 日常拍照 | 拍照意图、画面编排、照片记录与关联 |
| 形象档案 | 稳定外貌、正式发布快照、人物参考图 |
| 服饰造型 | 服装定义、搭配与服饰参考图 |
| 生图服务 | 云端 / 本机引擎适配、实际参考图输入、任务与结果 |
| 忆泡 | 有来源依据的实际事件 |
| 日记与手账 | 对一天经历的第一人称叙述与结构化摘录 |
| 成长数据中心 | 发布可供其他系统消费的领域事件 |
| 记忆系统 | 从真实经历中提炼长期有效的信息 |
| 主动消息 | 在授权会话中适度分享，不重复实现消息调度 |

现有日记与手账是两种独立文本：日记回答“今天发生的事让我有什么感受”，手账回答“今天有什么值得留下来”。新系统只提供可信的生活素材，不替代它们的写作职责。

## 4. 日常生活领域

### 4.1 日常类型

初始类型建议包括：上班日、休息日、外出日、宅家日、加班日、自由日。支持启用/停用、适用星期、权重和自定义类型。

类型只作为计划生成参考，不构成行为限制。第一版避免建设复杂日历规则引擎。

### 4.2 每日计划

计划生成可参考日期、星期和角色时区、当天生活类型、已确认的偏好/目标/近期想法、近期真实经历、前一天活动情况、已有安排及延续中的活动，以及可用的服饰和场景资料。

计划项建议包含：标题、描述、开始/结束时间、地点、场景、可选服饰、道具、同行者、来源和状态。

计划应留有空白，不要为了填满时间而制造无意义活动。每日生成时间可先采用前一晚 22:00 的默认值，但应沿用项目现有调度与时区规范，并允许配置。

生成必须幂等：同一角色、同一天不能重复创建有效计划；不能覆盖已经开始或已确认的活动；缺少计划时允许补生成。首次启动或长期停机后的补生成应有明确策略，不能回写已经过去的日子并伪造经历。

### 4.3 计划与实际活动分离

必须明确区分计划活动（原本打算做什么）和实际活动（后来确认真正发生了什么）。

示例：原计划下午去公园；后来下雨，角色决定在家看电影。原计划可以标记为变更或取消，电影活动可以作为新的实际活动记录。不能把公园散步写进忆泡。

计划状态建议使用清晰的领域枚举，例如 PLANNED、IN_PROGRESS、COMPLETED、CANCELLED、SKIPPED、CHANGED。状态名称可按现有代码规范调整，但不能将“计划存在”推断为“活动完成”。

不得计算完成率、连续打卡或用“未完成”评价角色。计划变更不是失败。

**数据建模要求：** 先检查项目现有数据模型，再决定是否拆成 DailyLifePlan 与 DailyLifeActivity。如果同一记录同时承载计划与事实会导致事实污染，就必须分离计划项和实际活动实例。不能为了少建一张表牺牲语义正确性。

实际活动只能由明确操作、可信对话证据或已有事实事件确认。模型推测必须保留为候选，不得直接写入忆泡。

### 4.4 临时调整

支持自然语言调整，例如“今天不想出门了”“下午改成看电影”“突然想去买点东西”。

调整应修改未来计划，不覆盖已经发生的事实；记录必要的变更来源和时间；允许计划外活动；保留原计划与新计划之间的关系；不自动将新计划标记为已完成。

### 4.5 当前活动与上下文

按需提供日期、星期、角色本地时间、当天类型、当前明确活动、接下来少量安排和近期相关事实。默认不注入完整日程。

不要在普通技术讨论、子代理或后台任务中无条件注入生活上下文。角色表达时不必提及“日程表”“系统安排”，而应自然表达自己的想法。

### 4.6 主动生活

主动行为先复用现有主动消息和调度机制。分为计划提醒、生活想法分享、经历分享三类。每类需要独立频率控制和会话权限。

没有值得分享的内容时允许安静；不因时间到点强制发消息。第一版不建设新的自主代理框架。

## 5. 日常拍照领域

### 5.1 拍照意图与来源

区分 USER_REQUESTED（用户明确要求）、CHARACTER_INITIATED（角色自主产生）、LIFE_CONTEXT（生活场景触发）、MEMORY_REVISIT（回顾经历时补充画面）。

明确请求可沿用现有绕过自主冷却的规则，但仍遵守并发、资源和安全限制。自主拍照必须受频率、每日上限和会话权限约束。

### 5.2 画面编排

生成前依次确定：是否存在真实拍照意图；当前生活场景（若有）；本轮是否明确指定服饰；正式形象档案版本；服饰、场景、道具；动作、表情、镜头、光线；参考图组合及引擎能力；最终提示词与生成任务。

服饰优先级：
1. 本轮明确指定；
2. 当前活动明确指定；
3. 场景或生活类型默认；
4. 角色情境穿搭偏好；
5. 形象档案默认造型。

明确换装时不能把默认服装再次追加进提示词。缺少服饰图片时允许使用文字描述。

### 5.3 复用现有生图链路

复用项目现有生图服务和 Provider 适配层，包括云端服务、本机 Anima / ComfyUI。不得为日常拍照复制一套引擎。

必须如实记录本次实际使用的 provider 与 model、生成模式、实际传入的参考图及其用途、任务 ID、生成状态和结果资产、失败原因与重试状态。

不同引擎的参考图数量、尺寸和模式可能不同，按适配器真实能力执行。不能仅因上层请求了参考图就记录“参考图已使用”；必须依据适配器最终提交的输入确认。

形象参考应保持人物身份特征，不应无意固定姿势和背景。正式发布快照作为稳定外貌来源，不扫描未发布草稿。

### 5.4 照片资产和记录

先审计现有图片生成记录、图片资产管理和消息 metadata。只有现有结构不能满足独立检索、活动关联、来源追踪时，才新增照片领域模型。

照片记录至少能追溯角色归属、图片资产引用（不在数据库保存大段 base64）、生成时间与触发来源、prompt 快照、provider/model/生成模式、实际参考图使用情况、可选关联的实际活动和忆泡、图片投递状态、可选视觉观察结果。

生成成功、视觉观察成功、消息投递成功是不同状态。不能因图片生成成功就宣称用户已经收到图片。提示词只代表生成意图；实际画面描述只能来自可靠的视觉观察结果。

## 6. 生活与照片关联流程

示例：角色计划下午去公园，后来确认真的出门散步；在公园时产生拍照想法。

1. 将计划活动标记为已开始或按实际情况调整；
2. 创建/更新实际活动记录；
3. 根据场景选择服饰和画面元素；
4. 角色决定拍照后调用现有生图服务；
5. 成功生成后保存图片资产和生成记录；
6. 将照片关联到实际活动；
7. 具备事实证据时，再由忆泡系统沉淀事件；
8. 日记手账在整理当天内容时，可以引用活动、照片和已有事实。

如果没有拍照，不创建照片记录。如果没有实际出门，不能把公园计划或公园生成图记成真实出行经历。照片可独立存在，不强制关联活动。

## 7. 数据模型与事件

### 7.1 先复用、后新增

当前项目已有 MemoryEvent、MemoryEventDay、CharacterJournal、JournalRevision、GrowthEvent、CharacterPreference、CharacterGoal、CharacterVisualProfile、CharacterVisualOutfit 等结构。实施前必须重新核对当前 main 的 schema 和服务代码，不能仅凭本设计文档推断字段细节。

边界：
- MemoryEvent 记录实际事件，不存未来计划；
- CharacterJournal 保存第一人称日记；
- 手账保存结构化当天记录；
- GrowthEvent 用于领域事件分发；
- 形象档案管理稳定外貌，拍照系统管理单次画面。

### 7.2 候选新增模型

只有代码审计证明现有结构无法表达时才新增：

**DailyLifePlan**
- id、characterId、dayKey、lifeType、status、source、timestamps。

**DailyLifePlanItem**
- id、planId、title、description、startAt、endAt、location、outfitId、scene、props、participants、status、source、timestamps。

**DailyLifeActivity（可选独立事实实例）**
- id、characterId、planItemId（可空）、title、description、actualStartedAt、actualEndedAt、location、source、evidenceRef、timestamps。

**DailyPhoto（仅在现有图片记录不足时）**
- id、characterId、activityId（可空）、memoryEventId（可空）、assetRef、triggerSource、promptSnapshot、provider、model、generationMode、referenceUsage、generatedAt、deliveryStatus、visualDescription（可空）。

字段类型、索引、外键、级联策略按项目规范确定。删除活动不得级联删除原始图片资产。对角色归属做服务层和数据库层双重约束（在现有技术架构允许的范围内）。

### 7.3 成长事件

只发布对其他领域有意义的状态变化，例如：
- life.plan.created
- life.plan.updated
- life.activity.started
- life.activity.completed
- life.activity.cancelled
- life.activity.changed
- life.photo.generated
- life.photo.associated

沿用现有 GrowthEvent 的幂等、投递、重试规范。内部读取和无意义字段变化不应全部发布事件。

## 8. 界面与交互

新增独立菜单入口“日常生活”，建议包含：

### 今日生活
日期、生活类型、当前活动、今日安排、接下来少量安排、临时调整入口和最近实际发生的事情。视觉上区分“计划”与“实际”。

### 生活记录
按日期浏览计划、实际活动时间线、临时变化、关联照片、忆泡和日记入口。

### 照片与回忆
照片墙、按日期/活动筛选、查看场景和关联经历。复用现有图片预览和资产管理，不复制日记页面。

界面不采用强制打卡清单，不突出完成率，不将未完成活动显示成失败。

## 9. API、工具与权限

按项目现有 API、工具注册和权限规范实现，不机械照搬外部项目工具名。

需要覆盖查询某日计划、查询当前/近期活动、创建或调整计划、新增计划外活动、记录实际活动开始/结束、查询照片、在有明确意图时生成照片。

所有写操作校验角色归属、会话权限和输入边界。对模型调用提供结构化返回值。涉及事实确认时必须保留来源/证据；推测只能作为候选，不得直接写入事实库。

生活上下文建议支持 ON / OFF / AUTO 会话策略，默认 AUTO。子代理、后台任务、纯技术任务默认不注入，除非任务明确需要。

## 10. 主动性与频率

复用现有主动消息机制，配置至少覆盖每日主动生活分享上限、自主拍照每日上限、自主拍照冷却时间、是否允许主动分享照片、主动时间窗口、会话级生活上下文开关。

明确用户请求优先处理；自主行为保守启用。不能因计划时间到达就强制发消息或生图。频率限制需要并发安全，避免多 Worker 重复触发。

## 11. 分阶段实施与验收

### 阶段 A：代码审计与领域落位
对照当前 Prisma schema、API、Worker、事件中心、日记/忆泡、图片资产与生图服务；输出已有能力复用表、必要新增表、迁移风险和文件改动清单；确认计划与事实的模型边界；不做无依据的大规模重构。

验收：文档中的每个拟新增模型/接口都有代码依据；重复能力明确排除；迁移策略明确。

### 阶段 B：日常生活数据与基础 API
类型配置、每日计划、计划项、计划查询/创建/修改、计划与实际活动分离、计划变更记录和角色隔离。

验收：重复请求幂等；跨角色不可读写；计划不会进入忆泡；历史计划不被后台覆盖。

### 阶段 C：计划生成、活动过程与上下文
每日生成与缺失补齐、临时调整和计划外活动、当前活动查询、ON/OFF/AUTO 上下文注入、复用现有调度机制。

验收：时区正确；停机补生成不伪造过去事实；普通聊天不注入完整日程；技术任务不受干扰。

### 阶段 D：日常拍照
拍照意图、画面编排、服饰与正式形象快照、复用现有生图 Provider、图片资产和生成状态记录。

验收：云端/本机能力按实际适配器执行；参考图使用记录准确；生成失败可恢复；不重复投递；形象一致性不被默认服饰污染。

### 阶段 E：照片关联与生活回顾
照片关联实际活动/忆泡、照片墙和时间线、日记手账按需引用可信素材。

验收：一项活动可关联多张照片；照片可无活动独立存在；删除活动不误删资产；提示词不作为事实。

### 阶段 F：主动生活与分享
自主生活想法、主动分享、自主拍照、频率限制和会话权限。

验收：不刷屏、不强制完成日程、不为数量拍照；没有内容时可以安静；用户明确请求能正常执行。

## 12. 工程质量要求

数据库迁移可回滚或有明确恢复方案；API 参数验证、权限校验和角色隔离完整；Worker 有幂等键、并发控制和失败重试边界；图片生成、视觉观察、消息投递分别记录状态；计划生成失败不得损坏已有计划；日志不泄露密钥、私密提示词或不必要的个人内容；补充单元、集成、迁移和关键流程测试；更新功能总览、开发文档和测试说明。

不引入向量数据库，不重做生图引擎，不复制记忆/日记系统。

## 13. 最终体验

理想情况下，小鲸鱼可以自然地说：

- 今天是休息日，我想在家待一会儿。
- 下午突然想出去走走。
- 今天穿这件衣服感觉不错。
- 刚刚在公园拍了一张照片，想给你看看。
- 今天没做什么特别的事情，不过过得还挺舒服的。
- 昨天本来想出门，后来下雨就改成在家看电影了。

这些表达不依赖固定话术。系统提供准确背景、可靠记录和表达工具，角色保有自己的选择。

**日程是参考，不是命令；经历必须真实，不能凭计划推断；照片是表达，不是任务；所有系统都应该让小鲸鱼更自然，而不是让她更像一个执行程序。**
