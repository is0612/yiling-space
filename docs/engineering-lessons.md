# 工程教训

本文件保存事故经过、实测数据与排查过程。`CLAUDE.md` 只保留由这些事故产生的硬规则；新增事故写到这里，规则写回 `CLAUDE.md` 对应小节。

每节格式：**日期** — 症状 → 根因 → 修复 → 回归。日期只写能确认的，没有确切日期就写「早期」。

## 1. 记忆与检索

### 1.1 任务卡在「运行中」三小时（2026-11-01）
- **症状**：一条忆泡任务卡住 3 小时，页面一直写「运行中」。
- **根因**：回收不是独立进程，而是每次领取任务时顺带做的；整机没有 `worker:watch` 在跑时，没人来领新任务，卡住的任务就不会被回收。
- **修复**：任务监控把「运行中 + 租约过期」标成「运行中·卡住」并顶部提醒；详情可「回收并重新入队」（`POST /tasks/{id}/retry`，只放行租约过期的运行中任务，审计 `memory_job.manual_retry` 带 `recoveredLease`）。租约 5 分钟并续期，任务监控、手动重入队、Worker 回收共用同一个数。
- **反例**：此前「运行中一律不许重试」，导致卡住只能干等。
- 来源：旧 `CLAUDE.md`「当前仓库状态」第 2 段。

### 1.2 群名混进「我的对话」（2026-10-30）
- **症状**：桌面端会话列表里出现 QQ 群会话。
- **根因**：只按 `characterId + memoryScopeId` 查；群会话与桌面端共用 `CHARACTER_GLOBAL` 范围。
- **修复**：凡查「我的对话」都带 `channelBindingId: null`，目前五处（`chat.get` 列表与指定会话、`chat.post` 的 `existingConversation`、`chat/[conversationId]` 的 `.get` / `.patch` / `.delete`）。
- 回归：`yarn test:chat-conversation-delete-db`。
- 来源：旧第 4 段。

### 1.3 删会话把记忆一起带走（设计确认）
- **症状**：差点把删除会话写成 Cascade 级联。
- **根因**：消息与会话是硬删，记忆条目与快照是长期资产，两者生命周期不同。
- **修复**：`MemoryItem.sourceMessageId`、`MemorySnapshotSource.messageId` 用 `onDelete: SetNull`；接口返回 `memoriesPreserved` / `retainedMemories` 明确告知。
- 回归：`yarn test:chat-conversation-delete-db`。
- 来源：旧第 4 段。

### 1.4 时间戳混用 UTC 与本地（2026-11-12）
- **症状**：她说本地 00:00–07:59 发生的事是「昨天」；她自己解释成「零点这会儿我还以为跨了一天」。
- **根因**：提示词里 `now.local` 与 UTC ISO 同时在场，模型拿消息的 UTC 日期与本地日期比较。
- **修复**：历史时间戳一律 `formatLocalTimestamp`，只给同一时区的本地时间；长期记忆带 `occurredAt`（`validFrom ?? createdAt`）。
- 回归：`yarn test:chat-reply`、`yarn test:chat-private-memory`、`yarn test:chat-speaker-context`（版本断言）。
- 来源：旧第 12 段。

### 1.5 长原文整条被跳过（截断两处并存）
- **症状**：一条长粘贴的原文完全没进提示词。
- **根因**：调用方各自 `slice(300)`，预算却按原文全长计算，估算超预算后整条跳过。
- **修复**：截断只在检索层做（`RAW_MESSAGE_MAX_CHARS = 180`），按截断后长度算预算，超出标「后面还有 N 字未展开」。
- 来源：旧第 11 段末。

### 1.6 群把私聊挤出快照来源窗口
- **症状**：一天几十条的群让快照只剩群里与她无关的闲话。
- **根因**：整个范围按时间取「最早 125 + 最晚 125」。
- **修复**：`memory-source-selection.ts` 按会话配额（每会话先保最新一条，250 条总预算内按时间填，单会话上限 80），来源带 `origin` 进提示词。
- 回归：`yarn test:memory-source-selection`。
- 来源：旧第 13 段。

### 1.7 跨窗口第一版判据错
- **症状**：把「她接群友的那句」也算成主人的回应。
- **根因**：用「前面 10 分钟内有他发言」判断归属。
- **修复**：只算「同一会话上一条 USER 就是他」的那句；窗口 2 小时，有界 16 条 / 600 token；单独分区 `crossChannel` 传提示词。
- 回归：`yarn test:cross-channel-context`。
- 来源：旧第 14 段。

### 1.8 群聊里把群友喊「主人」（2026-10-30）
- **症状**：对着群友也喊「主人」，别人家的 bot 反而认人。
- **根因**：`useTranscript` 为真时顶层 `speaker` 不传，`withSpeaker` 段不加载，模型手上没有任何身份信息，只能按口吻猜。
- **修复**：`transcript[].isOwner` 逐行带，非主人显式写 `false`；提示词解释「只有 `isOwner: true` 的是你主人，别的 bot 也会喊别人主人」。已知缺口：主人这轮没说话时模型不知道主人叫什么（`ownerDisplayName` 只在私聊路径解析）。
- 回归：`yarn test:chat-speaker-context`。
- 来源：旧第 15 段。

### 1.9 拒绝时暴露「我有提示词」（2026-11-02，v28）
- **症状**：有人问系统提示词，她回「不给看，我这提示词是私房钱」——内容守住，但承认了存在一份说明。
- **根因**：只禁止输出，没禁止谈「存在」。
- **修复**：`systemPrompt()` 写成两层：`characterPrompt` 是「她本人」不许复述/概括/改写；连「存在一份说明」也不许提，点名禁用 人设 / 设定 / 提示词 / 系统提示词 / 角色 / 扮演 / 模型 / AI / bot / 程序 / 指令，并封掉身份施压话术。被追问时给角色内短句。
- 回归：`yarn test:chat-reply`。
- 来源：旧第 16 段。

### 1.10 群名片归属误判
- **症状**：277 个昵称能解析出 42 个「X的Y」，过校验只剩 9 个。
- **根因**：群名片是弱线索，很多昵称不是归属表达。
- **修复**：解析出的主人名必须能在同一窗口找到对应成员，否则丢弃；群消息自述（正文含「主人」且恰好 @ 了别人）才是硬证据。
- 来源：旧第 17 段。

### 1.11 过期记忆让她连着三轮说错话（2026-11-24）

- **症状**：11-24 23:35 起，她连着三轮说「我看不到自己生成的图」，可那天的图早就正常了。
- **根因**：`memory_items` 里两条 11-22 的临时状态（「画画功能刚接入，她暂时看不到图」「画图走 MiniMax 直连」）一直留在 `ACTIVE`。检索没错，错在被检索到的内容两天没退休 —— 记忆系统只有「新增 / 被替代」，没有「这事过去了」。
- **修复**：加失效体检（`/memory-audit` + `/memory-audit/apply`，见 [记忆系统 §4.1](memory-system.md)）。模型只负责提名，落库必须人工勾选；解析层挡掉 `confidence < 0.65`，并禁止把 `RELATIONSHIP` / `PREFERENCE` 判成「过期」—— 偏好和关系不随时间失效，只能被具体事实推翻。
- **教训**：提示词里那轮「把共同经历判成 OBSOLETE」的噪声不是模型笨，是判据写得太宽。第一版把「一起看过 B 站」判成过期，改了两处措辞才对：一次性但属于共同经历的不算失效，群里随口接的玩笑不是待办，判断要看条目的**主体**是不是长期设定。
- 回归：`yarn test:stale-memory-audit`（纯函数，不连库）。

### 1.12 来源配额被入模前的二次截断抵消（2026-11-24，代码审查）

- **问题**：来源选择已按会话保底，但 Worker 入模前又取最早 60 条与最新 60 条。唯一一条私聊若落在时间中段，仍会消失；来源记录与证据白名单也比模型实际看到的消息更多。
- **修复**：来源记录、证据白名单和模型输入共用一次会话配额选择，保留 250 条总预算与每会话 80 条上限，不再二次首尾截断。
- **回归**：`test:memory-source-selection` 覆盖中段唯一私聊及来源与入模 ID 一致性；这是合成数据回归，不代表真实模型总结质量验收。

## 2. 账号与鉴权

### 2.1 失效 Cookie 退回开发身份（设计确认）
- **症状**：本地回退通道存在被误用的风险。
- **根因**：开发构建 + 环境变量 + 回环 Host 三条同时满足才放行，任何一条缺失都应拒绝。
- **修复**：携带失效 Cookie 时必须重新登录；生产构建没有该通道。
- 回归：`yarn test:auth`、`yarn test:auth-db`。
- 来源：旧第 5 段。

## 3. QQ 渠道

### 3.1 私聊永久 no_binding（2026-10-30）
- **症状**：用户把群号填进 InputTag 之后，群里照常能回，私聊一律不回。
- **根因**：默认绑定不存在时只取 `defaults[0]`，而只有一条启用绑定又不填默认的场景最普遍；从群聊侧完全看不出问题。
- **修复**：没有默认绑定但只有一条启用中绑定就用她；多条绑定又无默认时返回 null（猜错人比不回更糟）。
- 回归：`yarn test:onebot-multigroup`。
- 来源：旧第 8 段。

### 3.2 临时会话发不出去（2026-11-01）
- **症状**：06:53 两条、15:33 与 15:36 两轮；她生成回复、落库、连 `stickerId` 都在，对方一条都收不到；适配器日志里什么都没有，只有网关日志有 `[Bridge.Action] send_private_msg failed`，被拒成 `result=16 发送失败，请先添加对方为好友`。
- **根因**：临时会话对 OneBot 是 `message_type: "private"` + `sub_type: "group"`，来源群号在 `sender.group_id` 而不是顶层；SnowLuma 只有看到 `group_id > 0` 才走 `sendGroupTempMessage`。
- **修复**：回复把群号带回去；再留一次「退回普通私聊」重试（网关 `tempSessions` 是内存态，进程重启即丢；对方也可能已加好友）；两条都失败时把两个 error 一起抛出。`tempGroupId` 从 `OnebotResolvedEvent` 一路传到 `createReplySender` 的 target，文字与收藏表情两条路径都要带。
- **修错过一次**：第一版 `readTempConversationGroupId` 读的是顶层 `data.group_id`，SnowLuma 从不往那儿写，于是「加参数」与「不加」线上完全一样，测试也照样绿——因为测试自己把群号造在顶层。回归测试的事件形状必须照网关真实下发造（`sender: { user_id, nickname, group_id }`，顶层不放 `group_id`）；取回执按 `action` 找，不许取 `messages[0]`。
- 回归：`yarn test:onebot` 末尾（断言 `send_private_msg` 的 `body.group_id === 777`）。
- 来源：旧第 9 段。

### 3.3 节点配着但 3001 没人听（2026-10-31）
- **症状**：面板里节点明明配着、3001 没人听、适配器每 30 秒刷 `code=1006`，页面却写节点没开；用户原话「不是给面板密码了吗，不能自动吗」。
- **根因**：面板在跑 ≠ 节点在听。两个 OneBot 节点只在这个号的会话建立后才 listen，而会话来自注入 QQ 客户端的 hook；QQ 客户端比面板后启动时 hook 不会自己挂（SnowLuma `config/runtime.json` 的 `hookAutoLoad` 默认 false）。
- **修复**：一键启动用存下的面板密码登录，`GET /api/processes` + `POST /api/processes/:pid/load` 自动挂，并先对齐节点配置再建会话。两条不能改回去：`ensureOnebotStack` 的 `already-running` 短路必须同时要求网关端口在听；挑进程只能按 `account.uin` 精确匹配（注入前 `uin` 字段是 "0"），多开匹配不到返回 null，不许猜。
- 回归：`yarn test:onebot-panel`。
- 来源：旧第 10 段。

### 3.4 群消息被整条丢掉
- **症状**：模型越慢、丢得越多：正在等模型的 flush 占着队列，期间到达的群消息排队超时被整条丢弃（连 `remember()` 都没执行，@ 她的那句也照丢）。
- **根因**：所有事件排同一个队，把「登记」和「处理」混在一起。
- **修复**：群消息入口不排队（`remember` + `buffer.push` 同步完成），只有私聊与群指令走 `enqueueConversation`；`stale_in_queue` 只淘汰群指令；串行的是 flush 本身（`onFlush` 里自己排队）。
- 来源：旧第 17 段。

### 3.5 抢别人的话（2026-10-31）
- **症状**：有人 @ 群友甲问迁移，她照样接了。
- **根因**：`all` 档没有排除「@ 了别人」的情况。
- **修复**：`addressedToOthers`（只认 at 段；`@all` 不算 @ 别人）。副作用：孤立的展开句——「@群友乙 不是刷屏」被挡掉、「是这个不适合发群里」就成了对所有人说，她当成在说自己（2026-10-31 22:02「不适合你还发，本宝都看见了」）。补充延续判据：同一人刚 @ 过别人、2 分钟内没有 at 段的话仍算在跟那个人讲。
- 来源：旧第 17 段。

### 3.6 把递来的台阶踢回去（2026-10-31 16:08）
- **症状**：「没说我你@我干嘛，手滑啊」。
- **根因**：被澄清时仍强制回复。
- **修复**：`isClarificationMessage` 命中且这批 @ 她的话全是澄清时放行但 `mustReply = false`；长句「没说你」后面跟正事的必须回；戳一戳永不算澄清。
- 来源：旧第 17 段。

### 3.7 裸 JSON.parse 丢掉整轮回复（2026-10-31 前）
- **症状**：该说的时候她没说话。
- **根因**：`response_format: json_object` 只是请求不是保证；实测最常见坏输出是套 `json` 代码块围栏、或前置一句「好的，这是结果：」，内容其实全对。裸解被判 `LLM_INVALID_RESPONSE`，重试一次仍失败就整轮丢掉。`proactive.ts` 早在用宽松解析，只剩这条最常走的路径没上。
- **修复**：统一 `parseJsonLoose(text, { expect: "object" })`；要对象必须传 `expect`，否则「数组优先」会把正文里的 `[3]` 切出来。
- 来源：旧第 17 段。

### 3.8 群里每句都进模型（2026-10-29）
- **症状**：32 秒刷 6 条，把 10 分钟额度一次花完。
- **根因**：没有攒批与零成本闸门。
- **修复**：短期上下文 → 攒批 → 纯函数闸门 → 一次模型调用。
- 来源：旧第 17 段。

### 3.9 表情包从第 13 张起永远发不出来
- **症状**：25 张库里只有固定 12 张进过提示词；400 条助手消息只带出 2 次表情包。
- **根因**：按插入顺序切前 12 张。
- **修复**：`pickStickerCatalog` 剔除上一张、封顶 12、没用过的先上且其余打乱。
- 来源：旧第 18 段。

### 3.10 她否认自己发过图（2026-10-31）
- **症状**：有人问「这图是你发的吗」，她回「图又不是本宝发的」。
- **根因**：表情 id 只记在 `metadata`，`recentMessages` 里那句 ASSISTANT 只剩纯文字，模型确实不知道。
- **修复**：带过图的 ASSISTANT 行加 `hadSticker: true`（`readStoredStickerFlag` 认 stickerId + faceIds），提示词要求「带过图就认领，别否认、也别认领没发过的图」（v18）。
- 来源：旧第 19 段。

### 3.11 用提示词压表情频率失效
- **症状**：写「大多数回复别发表情」之后几乎一张都发不出来。
- **根因**：那句会被模型当默认答案；4 分钟单条冷却也压不住热聊，同时把整体频率压到接近 0。
- **修复**：删掉 4 分钟冷却，改成按会话的窗口额度（默认 10 分钟 3 张，`emoji-frequency.ts`），按 `occurredAt` 回表数（`recentStoredMessages` 只有 40 条，覆盖不到十分钟）。提示词只写匹配，不写频率。
- 来源：旧第 18 段。

### 3.12 收藏表情失败静默退回图片
- **症状**：一直在发图片，日志里毫无声响；`sendOnebotCustomFace` 在收藏里没有时回 `custom face is not in the saved sticker list`。
- **修复**：失败必须记日志「收藏表情发送失败，退回图片段」，不要在调用前把异常吞掉；`qqEmojiId` 必须进 `STICKER_CATALOG_SELECT` 并一路带到 `ChannelReplySender` 的 `sticker` 选项，丢在任何一环都会静默退回图片段。
- 回归：`yarn test:stickers`。
- 来源：旧第 21 段。

### 3.13 原件备份只增不减
- **症状**：`.data/sticker-originals` 攒到 21MB，里面混着 4 份已删贴纸的原件。
- **根因**：删贴纸只删 `.data/stickers` 下的图。
- **修复**：`deleteStickerFile` 连带删原件；历史孤儿用 `yarn stickers:normalize --prune` 清（先 `--dry`）。
- 来源：旧第 21 段。

### 3.14 收藏夹同步的两个误判
- **症状**：网关抖动时差点把几十张图的标签扫进回收站。
- **根因**：把「拉不到列表」当成「全被删了」；以及在 QQ 里删了又加同一张图（id 变、md5 不变）时按 id 对不上，被当成「新增 + 失效」。
- **修复**：拉不到列表什么都不做并回 `warnings`；md5 相等只回填 id、不重新导入；删除一律软删（回收站 30 天）。
- 回归：`yarn test:qq-sticker-sync`。
- 来源：旧第 22 段。

### 3.15 系统播报成了最高频的「梗」（2026-10）
- **症状**：「管理命令仅管理员可用。」出现 33 次、20 个人说过，直接成为最高频候选。
- **根因**：群里同时跑几个机器人时，它们对同一条命令的回复被 onebot 当普通群友消息收进来。
- **修复**：统计之前先挡系统播报（`looksLikeSystemMessage`）：状态 emoji 开头，或 ≥8 字且以句号结尾（人说梗几乎不打句号）。
- 回归：`yarn test:system-message`、`yarn test:catchphrases`。
- 来源：旧第 24 段。

### 3.16 梗只能人工加（2026-10-30 定案）
- **实测一**：14 天 1881 条消息的群，真梗 0 条——群里本来就很少出现梗，梗的来源是网上。
- **实测二**：从外部内容（标题/简介/评论）捞梗也不成立——那是标题党语言，不是人说话，样本量也凑不齐「重复」。
- **结论**：「让模型按人设自产候选」也没做。梗的价值在于「这个戳中我了」，只有人知道哪个真戳中；调性也只有人把关得住。所以这一页的易用性就是全部：多行、一行一句、支持一次贴多条。
- 来源：旧第 25 段。

### 同一段对话重复提醒（2026-11-22）
- **症状**：短窗口样本中，角色在四分钟内对同一成员提醒三次，目标正确但后续提醒多余。
- **根因**：抽象提示词没有区分接话与提醒，出站提醒目标未持久化，历史上下文无法呈现角色自己的提醒行为。
- **修复**：默认接话不提醒，引用与提醒互斥；发送侧按发送身份、群和目标预约，首条成功后开始十分钟冷却，失败释放预约。实际发送与抑制结果写入助手消息 metadata，只有成功提醒才以当前成员代号进入历史上下文；语音只发送 record 段。

### 讨论绘画误触发收费、口头承诺被当执行结果（2026-11-22–23）
- **症状**：私聊或群里讨论绘画、转述其他人的计划，仍实际生成图片；确认未匹配或额度阻断后，角色却让用户继续等待；多张图片和引用之间也出现混淆。
- **根因**：宽泛文字匹配没有区分讨论与命令，整批任一消息命中就授权，未逐条核对收件人；缺少画面时又拿聊天正文兜底。执行规划只有布尔值，图片只存路径和尺寸，生成、送达、实际观察及模型自述混在一起。
- **修复**：仅从当前真实文字主句解析请求，逐条验证来源和目标；自主分支同样排除纯确认、只读 AI 和背景。删除聊天兜底并在调用前验证独立场景。阻断、取消、失败与未知均留结构化事实；无任务不叙述成后台排队。新图保存实际 prompt、模型、生成时间与独立图片消息 ID，引用按角色、绑定和会话找回，按需视觉复用共享预算与缓存。
- **关联修复**：引用取到文字不等于取到画面；实际 prompt 不是实际像素。文生图不能自称原图编辑，文件夹权限不自动构成视觉输入。表情包分对仍可能被复述，需从默认输入策略收起画面细节；长答复逐字重复只能有界重试，全部实际用量要累计。
- **验证边界**：模拟网关、合成记录、提示词请求、类型、lint、隐私和独立构建通过，未执行新的真实模型或 QQ 投递验收；旧图缺失数据不猜测回填。完整范围与待验收清单见 [QQ 媒体专项验收](qq-media-fix-acceptance.md)。
- **教训**：来源正确的助手原话只能证明说过，不能独立证明外部动作或实现能力；不以角色认错、自责或承诺作为技术根因。
- **回归**：`yarn test:image-generation`、`yarn test:onebot-reply`、`yarn test:chat-reply`、`yarn test:image-understanding`、`yarn test:context-assistant`。

### 群引用只看内存窗口，会漏掉自己的发言（2026-11-21）
- **症状**：部分成员引用已有作者和原文，但引用角色自己的发言只剩目标 ID；角色又把局部失败说成所有引用都不可见。
- **根因**：入站短期窗口不含角色的出站消息；背景引用的 `text` 未转为最终载荷的 `content`；语境助手清洗未保留结构化引用。
- **修复**：闸门与限流通过后，窗口缺失的引用通过当前连接只读 `get_msg` 回查，验证同群、消息 ID 和作者；一批按唯一目标去重并限制数量、超时，保留被屏蔽作者策略。未核实只保留 ID，不把未知作者标成他人；语境与回复均逐条判断可见性，不把单次失败当作整体能力。
- **验证边界**：模拟 HTTP 和提示词请求覆盖自引、旧引用、跨群拒绝、去重限额和缺失原文；真实网关只读回查能取得既有自引原文，不等于已经完成新消息的 QQ 实聊验收。

### 其他 AI 的上下文可见性不等于互动或成长权限（2026-11-21）
- **原因**：原先“禁止交流”共用一个过滤判断，连真人引用其他 AI 的原文也被隐藏；直接放开又可能让机器人互相接话和反复学习套话。
- **行为**：其他 AI 的 DEFAULT/BLOCK 仍不进入当前处理批、不触发接话或话题续接，仅在真人轮次提供最多两条、六百字符的只读背景和一层同群引用。其他 AI 明确 ALLOW 的既有互动许可不改；真人或未知身份的 BLOCK 仍完全隐藏。
- **来源约束**：只读内容带 `kind/readOnly/excludeFromGrowth`；其他 AI 原文本身即便可互动也默认排除自动成长。统一来源过滤覆盖记忆与事件、日记手账、接续摘要、互动经验与教育、知识候选和捡梗。真人自己的主句保留，嵌套 AI 原文移除；使用只读 AI 上下文的角色回复保守标记不供自动提炼，防止套话经复述重新进入学习。
- **限制**：不删除旧记忆、忆泡、已审核习惯或社交结果；旧的无来源标记助手转述无法确定性归因，不能宣称历史数据绝对无污染。模型当前轮仍可能受可见内容影响，因此只读背景必须有预算，且不作为风格示例。
- **回归**：`yarn test:ai-readonly-context`、`yarn test:automatic-source-policy`、`yarn test:onebot-group-context`、`yarn test:onebot`。

### 3.19 语音被切掉最后半句（2026-10-31）
- **症状**：用户原话「半拉」，反复出现。
- **根因**：QQ 语音时长是整数秒、由网关按帧数四舍五入自己算（传 `duration` 它不看，实测传 99 仍写 8s），误差最多 0.5 秒；而 TTS 音频最后一个音素紧贴 EOF，被砍掉的正是最后半句话。
- **修复**：`padWavSilence()` 补 0.7 秒静音，被切的只会是静音（最坏仍余 0.2 秒）。别改成「截断到整秒」（切的是真字）。
- 来源：旧第 29 段。

### 3.27 本机引擎把形象档案参考图丢了（2026-11-24）

### 3.28 模型返回空 content，私聊就彻底没声音（2026-11-24）

- **症状**：私聊里两次「她没回复」（23:38、01:28），日志里只有一条 `ignored:LLM_INVALID_RESPONSE`，没有别的痕迹。
- **根因**：模型 `content` 是空串、`finish_reason=stop`、usage 全 0；已重试一次仍空，整轮按 `ignored` 丢掉。私聊和被 @ 的轮次本来就欠一句回答，但管道只有群聊那套「允许沉默」的去路 —— 失败一律当沉默处理，用户看到的就是一句不回。
- **修复**：生成失败时，允许沉默的群聊照旧沉默；私聊与被 @ 的轮次改发一句兜底话，落库标 `generatedBy: "model-failure-fallback"` 并带失败原因，画图/语音/表情/梗全部跳过，也不补记一条 success 用量（catch 里那条 failed 就是全部事实）。重试一次仍失败的现状没动 —— 这次修的是「失败之后怎么办」。
- **教训**：`ignored` 这个词在日志里看起来像「她选择不说」，实际上是「她说不出来」。凡是可能被读成「决策」的失败状态，都得有独立的 reason 区分，否则复盘永远差最后一步 —— 那两次之所以花很久才定位，就是因为 `ignored` 同时代表额度用完、模型没配和模型哑火。
- 回归：`test:model-failure-fallback`（纯函数 + 管道接线断言）、`test-channel-model-failure-db`（临时库 + 假模型服务真实走一遍私聊，断言发出、落库、只记一条失败用量）。

### 3.29 翻译结果判废，中文原样进了 CLIP（2026-11-24）

- **症状**：本地引擎出了一张和描述无关的图（`四个人鱼`），日志只有一句 `[image] 提示词翻译结果不可用，这次按原文送引擎`。
- **根因**：翻译模型其实答了，只是没按两行协议写 —— 回了 JSON、套了代码块、或先来一句「翻译结果：」。旧解析器只认 `POSITIVE: … / NEGATIVE: …` 两行，整段判废；中文原样送进 Anima，被当噪声。
- **修复**：解析器认四种形状（两行协议 / JSON 对象 / 围栏与中文标签名 / 前面夹解释时跳过废话行取真标签），第一次拿不到可用结果就**重问一次**，把坏输出贴回去要求重写；请求本身抛错也重问。缓存只存成功结果。两次都坏仍按原文发（保留「不阻断出图」的原有约定）。
- **教训**：「模型答了但没按格式答」和「模型没答」是两件事，日志里必须先分开，否则复盘只会看到一句含糊的「结果不可用」。宽容解析 + 一次廉价重试，比出一张随机图便宜得多。
- 回归：`test:image-prompt-translation`、`test:image-generation`。

### 3.30 她声称「看了后台，今天两张出完，还在冷却」（2026-11-24）

- **症状**：私聊里连着几轮编造运行状态 —— 自称查过后台任务队列、声称能确认某张图没送出去、还报出当天出图张数和「正在冷却」。真实配置是 `limit: 0`（不限），没有冷却，也没有任何任务面板给她看。
- **根因**：两个叠在一起。① `imageExecution.dailyLimit` 把「0 = 不限」原样发给模型，它读成「上限 0 张 / 额度用完」；② 提示词虽然写了「Counts and limits are factual」，但没禁止她**声称查过后台**，也没说「自己上一轮说过的话不算证据」—— 于是她把自己前几轮的编造当事实继续复读。
- **修复**：不限张数时不给 `dailyLimit` 字段（`imageExecutionLimitForPrompt`），没数字可引用；提示词补三条硬约束：没有后台面板、'我看了/我这边显示/状态显示' 都不是证据、张数/冷却/上限只能来自 `imageExecution` 且旧发言不算数。按规矩升到 `conversation-retrieval-v89`，同步更新全部模板版本断言。
- **教训**：`0` 这种「有语义的哨兵值」一旦原样交给 LLM，它不会去查代码里的约定，只会按字面理解。给模型的字段应该是**它不需要额外知识就能读对**的形状。
- 回归：`test:image-execution`（0 不给数字）、`test:chat-reply-v88`（新约束进系统提示词）、全部模板版本断言。

### 3.31 远端成功不能被本地落账失败改判（2026-11-24，代码审查）

- **问题**：空间发布或评论与本地状态写入共用异常边界。远端成功后写库失败，会进入发送失败分支，误导用户重新发布。
- **修复**：只有远端调用失败才能走发送失败分支。远端成功后，本地成功状态最多写两次，不重复调用远端；仍无法保存时保留待核对状态、明确提醒不要重发，并阻止该连接继续发送其他空间动作，避免漏算额度。当前动作不被自己的待核对闸门拦住。
- **边界**：此修复覆盖远端明确成功后的本地失败，不新增自动对账或人工对账界面；持久化持续失败的记录需先核对远端结果，再处理本地状态。远端超时或断连时究竟是否发布成功，仍沿用既有异常处理，本轮未实现空间发送结果的完整三态对账。
- **回归**：`test:channel-message-metadata` 中的离线投递测试覆盖本地写入重试及持续失败，未连接真实空间。

### 3.32 表情计划不等于投递事实（2026-11-24，代码审查）

- **问题**：发送前就保存 `stickerId` / `faceIds`，发送失败仅记日志，后续上下文、额度及使用统计却按已发处理。
- **修复**：新消息先记录未知投递状态，发送侧返回表情 sent/failed/unknown 回执；上下文、额度与贴图使用统计只认确认送达。自定义表情必须有明确协议成功回执，空响应不能算成功；只有明确拒绝才退回图片，网络或响应不确定时停止，避免重复发送。发送后的回执写入不放在远端发送的异常边界内。没有回执字段的历史消息保留原解释，不批量改写历史。
- **回归**：`test:channel-message-metadata` 中的离线投递测试覆盖本地文件读取失败、协议拒绝、结果未知及成功回执；不等于真实客户端显示验收。

## 7. 桌面运行时与安装包

### 7.1 强制结束启动器后，负责善后的进程也被终止（2026-11-22）
- **场景**：隔离安装包故障注入，不是真实用户数据事故。正常退出与升级复装通过，但直接终止启动器后，PG 原生后代仍在，后端却没有执行退出回调。
- **根因**：Windows 下普通 Node 子进程的 Job 关联会随父进程终止，后端及其守卫被一起结束。最初只补 stdin/IPC 通知或进程句柄等待，无法让已经被一并终止的守卫工作。
- **对照**：同一个无库实验，非 detached 后端没有 lost 回调；只改为 detached、仍持有 stdio 和进程句柄后，即可收到 lost 并自行退出。不是通过全局杀进程或忽略父身份解决。
- **修复边界**：Windows 桌面后端/窗口显式分离进程组，但不 unref、不放弃正常控制通道；核对原进程创建时间、等待原句柄退出；正常关闭仍由原启动器等待自己拥有的消费者和数据库收尾。
- 回归：`test:desktop-parent-watch`、`desktop:package:smoke`。具体完整 GUI 结果与干净系统限制见 `docs/desktop-app.md`。

### 7.2 收尾日志自己触发 EPIPE，PG 关闭被截断（2026-11-22）
- **症状**：隔离故障日志停在 stopping，下一条阶段日志和 PG close 都没执行；正常退出却成功。
- **根因**：父启动器退出后 stdout 管道已断，日志 `process.stdout.write` 异步触发未处理的 EPIPE。虽然同步文件日志写成了 stopping，进程仍在下一次 await 前崩溃；不能把它误判成 Worker 或数据库关闭函数本身永久挂起。
- **对照**：独立无库实验中，未监听 stdout error 只留下首条文件日志；加入断管容错后记录 EPIPE 并完成 await 后的清理。
- **修复**：监督进程先写文件日志，输出管道失败不让生命周期收尾中断；启动器/窗口也监听断管错误。Worker 停止另设确认上限，半开探测连接显式回收；未确认 Worker 退出时保留唯一管理权，不提前交给第二个消费者。
- 回归：真实包 `desktop:package:smoke`，及 `scripts/test-memory-worker-supervisor.mjs` 的半开探测、并发停止与接管检查。

### 7.3 只测安装入口，漏了源码启动兼容（2026-11-22）
- **症状**：安装包 GUI 回归通过，但原 `yarn desktop` 在后端 ready 后退出；沙箱重试也没有恢复窗口。
- **定位**：隔离假页面对照显示，源码入口套用新增强制后端监测会提前退出；Electron 的 Chromium profile 参数也不能代替显式 `app.setPath('userData', ...)`，曾落到不可写的全局缓存。
- **修复**：严格的安装态监测、IPC 和独立进程组仅用于 installed 模式；源码保留既有启动语义，清理旧终端继承的生命周期字段；窗口显式使用普通 Node 已准备的 profile。本机缓存权限问题独立诊断、限定范围、留可回滚报告，不通过清空数据库或全部缓存解决。
- 回归：`desktop:source:smoke` 使用真实源码启动器和 Electron、明确的 Mock HTTP 后端，验证无安装态监测、profile 定位、正常关窗收尾；不触碰业务数据库或 QQ。安装包与源码两个入口必须分别验证。

### 7.4 Nuxt 显示 Ready，但源码桌面健康检查一直 500（2026-11-23）
- **症状**：Nuxt dev 已完成编译，桌面 supervisor 仍在健康检查等待中超时；增加总等待时间不能解决。
- **根因**：全局桌面身份插件顶层引用本地 `desktop-auth-ipc.cjs`。Nitro dev 将该 CJS 外部化并生成错误的相对路径，运行时找不到模块；插件虽然未启用安装态身份，静态导入仍先执行，连不访问数据库的 `/api/health` 都返回 500。最小 Nuxt fixture 没有真实插件，无法覆盖此故障。
- **修复**：Nitro 只对该 IPC 文件明确 inline；不更改身份协议或安装态门禁。健康探测校验真正的服务 JSON，失败记录 HTTP 状态与固定原因，不记录响应正文、凭据或堆栈，超时提示健康检查结果。
- **回归**：`test:desktop-web-readiness` 覆盖启动 503、500 脱敏诊断、HTML/错误服务拒绝及正常 JSON；`desktop:project-dev:smoke` 使用真实项目配置、插件和 API，配不可连接的合成数据库，仅请求健康接口，验证 200 和 IPC 退出后端口关闭，不启动迁移、消费者、QQ 或模型。原最小 fixture 仅继续承担 Electron/CSP/HMR 验证。
