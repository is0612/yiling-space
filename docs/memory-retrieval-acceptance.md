# 核心记忆检索改进与验收

## 第一批范围

普通网页聊天与 QQ 的长期记忆、快照候选读取统一到 `server/utils/prompt-memory-candidates.ts`。调用方先确定可读范围，模块不解析身份、不扩大范围；群聊仍由渠道入口只传角色全局范围。忆泡仍保留本群会话过滤和原有选择逻辑。本批不是完整 ContextPlan 的实现，不改变提示词模板、渠道发送或预算规则。

## 修复的断点

原有普通聊天只读最新 300 条长期记忆、80 份快照，再按相关度和 token 预算筛选。合成隔离库中插入 305 条无关新记忆与 85 份无关新快照，较早的明确主题记录在库中存在，却无法进入原候选集。

现保留近期样本；某类近期样本达到上限时，使用现有主题词提取器在授权范围内补查最多 180 条主题记忆和 120 份主题快照，再按 ID 去重。未达到上限表示该类有效记录已经全部读取，不重复执行主题扫描。两入口调用同一模块，后续仍走现有相关度、重要度、时间衰减、条数和 token 预算。ACTIVE / 未删除记忆及 CURRENT 快照限制应用于近期和主题两条查询。

## 验收分层

`test-prompt-memory-candidates-db.ts` 由 `yarn test:chat-isolated` 在一次性数据库中执行，不允许直接指向业务库。它分别验证：

1. 存在层：合成旧记录已入库；旧的近期窗口无法选回它们。
2. 候选层：共享读取模块能按明确主题补回旧记忆和快照。
3. 提供层：原有预算选择器最终保留这些记录，具备传入提示词的条件。
4. 回答层：本测试不调用真实模型，不声称角色最终回答正确。

同组用例验证已授权私人记忆可读取、群聊不扩大私人范围、其他身份不能混入、已删除和已替代记忆不复活、重复候选不重复注入、没有主题命中时预算结果为空、空授权范围返回空。

现有网页 HTTP 隔离测试与 OneBot 回归用于检查入口兼容；合成数据库验收不能代替真实 QQ 语义质量观察。

## 仍有的限制

- 主题补查是有限的词面 contains 查询，不是向量或完整语义检索；同义改写和宽泛词仍可能漏召回。
- 补查结果仍有数量上限。主题记录过多时不能声称找遍了历史；大数据量下的查询耗时需另行量测，不以这次合成数据推断生产性能。
- 忆泡、原文、第一次经历、改名人物以及深度检索仍沿用现有链路，未在这一批全部统一。
- “被预算选择”不等于模型实际采用，更不等于最终答案正确。后续自然使用应按入口、来源和实际回答分别核对。

- `yarn test:growth-event-center-isolated`：含反思、偏好、表达习惯和目标隔离链路，验证新审核协议与现有后台兼容。
- 最终 `yarn typecheck`、`yarn build`、变更 TypeScript 文件的定向 ESLint、隐私与差异格式检查。

新增用例首次运行时断言通过但测试清理顺序违反角色外键，已修正并完整重跑通过；快速路径编辑期间的一次类型检查捕获了临时变量未定义，完成编辑后最终类型及构建均通过。构建仍有既有媒体下载模块的 BigInt/es2019 目标警告及打包耗时提示，本批不扩展修改该模块。

## 第二批：明确日期、人物与首次经历的忆泡补查

网页与 QQ 已共享 `server/utils/prompt-event-candidates.ts`。先保留最近 200 条有效忆泡；未达到上限时直接返回。达到上限且问句明确指向日期、人物或首次/最近一次时，在同一授权范围补查：日期区间最多 500 条，否则最多 350 条；无人物约束时另按主题最多补 350 条，避免取首时最早一批无关事件挤掉主题事件。结果按 ID 去重，再交给原有忆泡选择器与 token 预算。

日期先由服务端按角色时区换算为左闭右开区间。补查与最终选择共用同一个 now，避免跨零点错位。人物先沿用原入口的名字到账号解析；补查按已有结构化 externalId 引用或精确显示名，不推断跨平台身份。群聊在所有查询中都同时限定可读范围和本群 conversationId；本群会话尚未建立时返回空。私人范围仍由入口授权，不因历史查询扩大。

本批还修复了一个选择器缺陷：明确人物没有匹配时，原逻辑继续走通用时间线，“第一次见到某人”可能选中他人的最早事件。现保留人物/取首模式并返回空，不借用他人事件。

### 第二批验收与限制

新增 `test-prompt-event-candidates-db.ts`，由原有聊天隔离运行器执行，使用约一千条合成忆泡及合成改名消息：

- 证明旧日期、旧人物和旧主题事件不在原 200 条窗口中，却能经补查进入候选及预算结果。
- 用真实人物账号解析器和 PostgreSQL JSON 引用查询，验证新昵称能查到旧名记录的最早经历；超过 350 条同人物后续记录不挤掉最早事件。
- 超过 350 条更早无关事件不挤掉主题首次事件。
- 验证角色时区日期的起止边界、空日期、未知人物、重复候选、已归档排除、其他群和私人范围隔离、空授权、未建立群会话及小库直接读取。

本批没有扩展原文检索，没有新增表或迁移，没有重写存量数据，也没有更换提示词模板。补查仍有上限，显示名补查为精确匹配，语义改写、歧义昵称及更大历史集合的完整性没有被证明；“现存记录中最早”也不能证明现实中第一次。候选和预算通过不等于模型正确采用。真实模型及 QQ 自然会话尚未验收，生产大数据量查询耗时未量测。

第二批已实际通过 `yarn test:memory-events`、`yarn test:chat-isolated`（含新增忆泡隔离库验收）、`yarn test:assistant-collaboration-isolated`（实际 QQ 管道历史及证据边界）、`yarn test:onebot`、`yarn test:owner-timeline-retrieval`、`yarn test:chat-private-memory`，以及最终 `yarn typecheck`、`yarn build` 和变更文件定向 ESLint。新增数据库用例首次清理顺序触发会话外键，调整后成功复现未知人物错误回退；选择器修复后相关断言、清理及完整隔离运行器均通过。构建仍保留既有 BigInt/es2019 目标与打包耗时警告。本批不运行全部项目测试或宣称自然语义效果通过。

## 第三批：选择与整形层共用（2026-11-21）

网页 `chat.post.ts` 与 QQ `channel-adapter/pipeline.ts` 此前各写一遍：预算装配、scope 标签、忆泡 600 字截断、参与者名字刷新。已抽到 `server/utils/prompt-memory-selection.ts`，两入口只保留各自的范围判定（网页按会话范围来源，QQ 按「是不是角色全局范围」）、候选读取和后续提示词组装。

顺带修掉一处时钟不一致：近期忆泡（`eventRecentDays`）原本在共用函数内重新取 `new Date()`，与同一轮的日期补查不是同一时刻；现在共用入口传入的 `now`，跨零点时「最近几天」和「某一天」不会对不上。

同批修正第二批引入的过度收紧：`parseEventParticipantQuery` 会把「海边的约定」里的「海边」当成人名，若一律按「未知人物→空」处理，正常提问会一条忆泡都拿不到。现在只有拿到真实账号、或明确问「第一次见到某人」时才强制空结果；只有名字没有账号时退回关键词检索，命中不了自然也是空。

新增 `test-prompt-memory-selection.ts`（入口 `test:memory-selection`）覆盖：范围标签、`validFrom` 回退、忆泡截断与改名、近期忆泡去重与下标对齐、预算首条保底、空结果不查参与者名字。两入口的类型检查与实际回归见提交记录；本批不新增表、不改提示词文案。

## 第四批：把「这轮放了什么」写进诊断（2026-11-21）

选择层算出的统计此前没有落盘：用户问「她为什么没想起那件事」时，看得到用了哪些来源，却看不到「找到几条、被预算挤掉几条」。现在两入口都把同一份统计写进回合详情（`ModelTurnDetail.retrieval`）：记忆 / 快照 / 忆泡各自的 `count`、`usedTokens`、`dropped`，忆泡另记选取方式（`range` / `participant` / `first` / `latest` / `keyword`）与近期背景条数。

写入前过白名单清洗：缺字段、类型不对、未知模式整块丢弃；负数取 0、超大值截到上限；不落任何正文。回合详情面板「记忆检索」下方加一行摘要（「本轮放入：记忆 3 条（挤掉 7）…」），没有这项诊断时不显示。

这部分只回答「放进去多少」，不回答「模型用没用」——后者仍看模型自报引用与回复本身。

### 补充：把「用了没用上」也记下来（2026-11-21）

同一块里再记一组 `used`：模型自报引用、且确实在这一轮提供清单里的条数（记忆 / 快照 / 忆泡各一个）。有了它才能把排查中的三种情况分开：

- `count = 0`：根本没检索到；
- `count > 0`、`used = 0`、`dropped > 0`：找到的更相关条目被预算挤掉；
- `count > 0`、`used = 0`、`dropped = 0`：放进去了，模型没用（提示词权重、指令冲突或模型判断无关）。

`used` 是**模型自报**，不等于真的用了；它只表示那几条进入了模型视野并被点名。与 `dropped` 同属计数，不含正文。面板摘要末尾会显示「模型引用：记忆 1 / 快照 0 / 忆泡 2」。

## 验收脚本：一条记忆为什么没进提示词

`yarn probe:memory-reach --character=<角色id> --query="<问句>" [--memory=<记忆id>]` 用与网页聊天相同的可读范围、候选读取和预算跑一遍，只读、不调模型。它回答链路前三个断点：

| 结论 | 含义 |
| --- | --- |
| 已放入提示词 | 候选命中且没有被预算挤掉，问题不在检索 |
| 关键词没命中 | 问句和这条记忆没有共同词，词面检索拿不到 |
| 命中但被预算挤掉 | 排序在，但条数或 token 上限没容下 |
| 不在候选集 | 范围不可读、已删除，或在候选窗口之外 |

第 4 档「放进去了但模型没用」不在这个脚本里，看回合详情的 `used`。

本机实测（164 条记忆的角色）：候选 118 条，命中 7 条全部放入、无挤掉；换一个无关问句后同一目标被判「关键词没命中」。这两条只证明脚本能区分档位，不代表检索质量。

判定逻辑本身抽在 `server/utils/memory-reach-diagnosis.ts`，由 `test:memory-reach` 覆盖八种输入（查不到、软删、范围外、已替代/失效、候选外、命中未进、被挤掉、已放入），并锁住两条顺序：已放入优先于后续档位；状态失效要先说状态，不能只说「没命中」。脚本里的判定与回归共用同一份实现，改检索顺序时判定不会悄悄漂移。
