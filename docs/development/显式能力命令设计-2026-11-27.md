# 显式能力命令设计（2026-11-27）

> 状态：第一阶段（统一能力命令解析器）已实现并提交，专项复审通过，等待第二阶段设计  
> 基准分支：`main`  
> 基准提交：`d78db12866bea251dcadd0724f4764dff0b8654b`  
> 目标：用明确的命令前缀替代对话前置阶段对自然语言的能力触发猜测。

## 1. 背景与目标

当前能力触发分散在多处逻辑中，部分在模型调用前通过正则判断用户是否要出图、发语音、看图或查询群历史。自然语言中的普通词语可能被误认为功能意图，导致模型尚未理解用户真实意思，系统已经规划了工具或高成本动作。

本次改造的目标：

1. 普通自然语言默认只进入正常对话，不再通过宽泛正则触发用户主动请求型能力。
2. 用户确实要调用某项能力时，用明确、可见、可预测的命令前缀指定。
3. 命令后的内容仍然是自然语言，由模型和现有领域逻辑理解，不设计第二套复杂的语义正则。
4. 命令解析与权限、安全、预算、参数校验分离；命令本身不授予越权能力。
5. 统一 QQ 与网页对话入口，避免各渠道各写一套不一致的解析规则。

核心原则：

**理解交给模型，明确指令交给用户，执行交给受控工具，安全交给系统。**

## 2. 第一批命令格式

命令必须出现在当前用户真实消息的开头（允许开头有空白），命令名与冒号之间不允许插入其他文本。冒号同时接受半角 `:` 和全角 `：`。

| 命令 | 示例 | 用途 |
|---|---|---|
| `&出图：` | `&出图：在海边的自拍` | 用户明确要求生成图片 |
| `&语音：` | `&语音：晚安，明天见` | 用户明确要求把本轮回复合成为语音 |
| `&看图：` | `&看图：这张图片里有什么？` | 明确请求调用图片理解 |
| `&查记录：` | `&查记录：昨天群里讨论了什么？` | 明确启动群历史/记录查询 |

本阶段只支持一条消息中的一个能力命令，不支持命令串联、嵌套或在正文中途启动命令。

## 3. 触发规则

### 3.1 只有开头的显式命令触发

以下内容应正常聊天，不触发用户主动请求型能力：

- `来一盘游戏吧`
- `帮我画一只猫`
- `给我发一段语音`
- `群里之前讨论过这个吗`
- `你会画图吗`

对应的显式命令才触发：

- `&出图：一只猫`
- `&语音：你好呀`
- `&查记录：帮我找昨天关于这个话题的讨论`

### 3.2 不得从引用、转述、历史或 AI 消息触发

只解析当前轮、当前用户本人发出的真实文本内容。以下来源不能触发命令：

- 引用消息正文、转发消息正文、附件 OCR/图片描述；
- 历史消息、系统提示词、工具结果；
- AI 自己生成的文本或只读观察消息；
- 用户正文中间出现的命令字符串；
- 仅仅在讨论命令格式或展示示例的内容。

命令解析应发生在消息来源与消息类型已经明确之后，不能对拼接后的整段上下文做全局搜索。

### 3.3 错误格式

- 已知命令名缺少冒号或命令内容为空：返回简短格式提示，不得猜测并执行。
- 未知的 `&xxx`：按普通文本处理，不要把任意 `&` 开头都当成系统命令。
- 正文中途出现已知命令：仍然是普通文本。
- 不支持一条消息里同时执行多个能力；如检测到第二个命令样式，不得偷偷执行第二项能力。

### 3.4 解析结果采用明确类型

建议新增共享解析模块，例如 `server/utils/capability-command.ts`，输出判别联合类型，而不是继续返回多个布尔值：

- `none`：普通消息；
- `invalid`：已知命令格式错误；
- `image` / `voice` / `vision` / `history`：识别到的命令，携带去掉命令前缀后的自然语言正文。

解析模块只做精确前缀识别、冒号分隔、空内容检查和基本长度限制，不负责判断自然语言是否“像是在要求画图/发语音/查历史”。

### 3.5 消息来源 kind 的语义（2026-11-27 调查结论）

解析器读到的 `kind`（`AI` / `HUMAN` / `UNKNOWN`）来自消息来源标记，其语义经过一次专门调查确认如下，第二阶段做执行鉴权时必须以此为准：

1. **`UNKNOWN` 不代表可疑来源，而是身份表的默认值。** `ExternalIdentity.kind` 的数据库默认值就是 `UNKNOWN`（`schema.prisma:511`），枚举为 `UNKNOWN` / `HUMAN` / `AI`。
2. **开发库实测**：QQ 身份共 620 条，其中 `UNKNOWN` 585 条、`AI` 25 条、`HUMAN` 10 条；`kindSource = MANUAL`（手动分类过）的仅 34 条。
3. **新建身份默认 `UNKNOWN`，自动分类不回写身份表，只有管理员接口能改 `kind`。** 建档链路 `friends.ts` 只写 `platformUid` / `displayName` / `status`，不写 `kind`；代码里唯一的 `kind` 写入点是管理员接口 `api/admin/identities/[id].patch.ts`（写入时 `kindSource: "MANUAL"`），没有任何自动分类回写。
4. **私聊路径不传 `kind`**：`serve.ts` 的 `handleChannelMessage` 私聊入口没有 `kind` 字段，拿到的是 `undefined`，不是 `UNKNOWN`。
5. **QQ 入站消息里的 `readOnly` 防护条件当前不可达**：`readOnly` 只出现在 background / context 行上，而那些行不参与命令解析。
6. **第一阶段只负责命令识别、不执行能力，因此上述 UNKNOWN 问题当前没有直接执行风险**；第二阶段接上执行后必须按第 9 节的权限前置要求处理。

## 4. 各能力迁移要求

### 4.1 出图

当前重点位置：

- `server/utils/image-generation.ts`：`parseExplicitImageRequest` 等自然语言触发解析；
- `server/utils/image-request-policy.ts`：请求来源、收件人和执行资格校验；
- `server/utils/image-offer.ts` 及相关规划逻辑：自主提议与确认；
- `server/utils/channel-adapter/pipeline.ts`：对话轮次规划与执行接线。

改造要求：

1. 用户主动要求出图的入口改为 `&出图：自然语言画面描述`。
2. 普通自然语言中的“画、来、出、整、搞、做”等词不再启动用户主动出图解析。
3. 命令正文作为画面意图交给现有模型/生图提示词流程理解；保留现有提示词校验、图像配置、每日额度、互斥、失败降级等保护。
4. 命令不能绕过群聊收件人校验：群聊中仍必须确认请求确实面向我们的角色，不能因为消息里有命令就替其他成员执行收费操作。
5. 重画/重试应由 `&出图：再画一次` 或明确的重试语义承载，不再靠普通文本中的“再画一次”正则触发。
6. 现有自主配图概率/冷却/每日上限属于独立的“角色主动行为”策略，不等同于用户主动命令。迁移时必须把它与用户命令入口拆开，不能让自然语言触发解析混进自主分支。是否保留自主配图策略不在本次默认改动范围内，除非用户另行决定。

### 4.2 语音

当前重点位置：

- `server/utils/voice.ts`：`isVoiceRequested`；
- `server/utils/channel-adapter/pipeline.ts`：`planVoiceReply` 及语音回复规划；
- `docs/voice.md`：现有语音行为约定。

改造要求：

1. 用户主动要求语音改为 `&语音：`。
2. 普通文本中的“发语音、用语音说、引用他说一句”等自然语言组合不再通过正则强制开启 TTS。
3. 命令表示本轮回复采用语音表达；TTS 仍然使用模型生成的回复文本，不把命令正文直接当作必须逐字朗读的文本。
4. 保留语音开关、服务商配置、60 字限制、语音段格式、失败回退文字、引用/@ 段限制等既有安全与兼容逻辑。
5. 当前随机语音概率是独立的角色行为策略，不应与用户显式命令解析混在一起；本次不要顺手改变其配置语义。

### 4.3 看图

当前重点位置：

- `server/utils/media-questions.ts`：`isExplicitMediaQuestion`、最新生成图片/提示词追问判断；
- `server/utils/channel-adapter/quoted-image-observation.ts`：引用图片与最新生成图片观察；
- `server/utils/channel-adapter/pipeline.ts`：视觉预算与图片描述注入。

改造要求：

1. 需要主动调用视觉理解时使用 `&看图：`。
2. 不再因“图/表情”与“看看/解释”等词语共现，就在模型调用前启动视觉调用。
3. `&看图` 必须绑定真实可访问的图片来源：本轮附件、明确引用的图片，或受权限范围限制的最新生成图片；没有目标图片时给出清楚提示。
4. 继续共用现有单轮视觉预算、图片来源校验和安全下载机制。
5. 仅查询已经保存的图片描述/事实，不产生新视觉调用的只读路径，应与真正调用 Vision 的路径分开，避免把两者混成一个命令触发器。

### 4.4 群历史查询

当前重点位置：

- `server/utils/owner-private-history.ts`：`planOwnerHistory` 等查询计划；
- `server/utils/owner-history-intent.ts`：历史查询意图分析；
- `server/utils/channel-adapter/pipeline.ts`：历史上下文加载与续问。

改造要求：

1. 新的用户主动历史查询任务必须由 `&查记录：` 开始。
2. 普通聊天中提到“群里、之前、记录、说过”等词，不再自动启动群历史查询。
3. 保留已明确启动任务后的上下文续问能力。例如用户先发 `&查记录：昨天群里讨论了什么`，接着问“后来是谁回复的”，可在既有任务有效期和同一会话范围内延续。
4. 话题切换、明确取消、会话/权限范围变化时，必须清除或终止旧查询计划；不得让旧任务污染普通聊天。
5. 继续执行现有群/私聊范围、角色身份、用户授权、时间范围与数据访问限制。

## 5. 不在本次迁移范围内的能力

以下能力目前不是由上述自然语言正则直接触发，本次不要为了统一外观而强行改成命令：

- 本地观察工具：模型可以提出文件写入、命令、浏览器操作、Git 等审批提案；除只读公开网页外，现有工具只生成审批单，不直接执行。保留当前审批与权限边界。
- 表情包/贴纸：仍由模型从白名单中选择；保留现有可用性、互斥和白名单检查。
- 普通聊天、记忆、知识检索等能力：继续按现有模型/领域逻辑工作，不新增命令前缀。

## 6. 统一接入要求

实现前先梳理 QQ 与网页聊天两种入口，确认各自如何表示：

- 当前用户的真实文本；
- 引用/转发文本；
- 附件、图片和 OCR 描述；
- AI 消息、只读消息与历史消息；
- 群聊 @ / 收件人信息。

解析器必须在“当前用户真实消息”边界上运行，不能对整个 prompt、拼接历史或所有 message 做正则扫描。

解析结果应成为本轮结构化上下文（例如 `capabilityCommand`），由各领域能力消费。不要让领域模块重复解析 `&出图` 等字符串，也不要只把前缀从文本中删掉却丢失命令类型。

如果移除命令前缀后把正文交给模型，必须同时把已识别的能力类型明确传入本轮提示/规划上下文；模型仍负责理解正文和生成适当内容，但不得自行把一种命令改成另一种能力。

## 8. 实施顺序

建议分阶段提交，避免一次性改动过大：

1. **盘点与统一解析器**：确认 QQ/网页入口与所有现存触发调用点；新增类型化解析器和独立测试，不改执行行为。
2. **出图迁移**：将用户主动出图迁到 `&出图：`，保留领域安全校验和自主分支隔离。
3. **语音迁移**：将用户主动 TTS 迁到 `&语音：`，保留语音链路约束。
4. **看图迁移**：将主动 Vision 迁到 `&看图：`，保留只读事实查询与预算边界。
5. **群历史迁移**：将新查询任务迁到 `&查记录：`，保留同一任务内的续问能力。
6. **清理与文档**：确认所有旧自然语言触发入口都已移除或被明确隔离；更新用户说明与开发文档。

每一阶段都应先添加失败用例，再改生产代码。禁止仅删除正则而没有替代入口，也禁止把所有能力改成模型无约束的自动工具调用。

## 9. 第二阶段前置设计要求：命令执行的权限

命令解析与执行是两件事。第一阶段只解析，第二阶段把能力真正挂到命令上之前，必须先把下面的权限要求定清楚并写进设计；这属于第二阶段的前置设计，不是现在就要改的生产代码。

核心：**命令文本本身不授权。** 谁发的、发给谁、这人可信不可信、他有没有这项能力的授权，四件事必须同时成立才允许执行。

- **不能只通过 `kind !== AI` 判断是否允许执行能力。** `kind` 的语义见第 3.5 节：`UNKNOWN` 是默认值，绝大多数人（包括没被手动分类的真人和其他机器人）都落在这里，它不能作为「可以执行」的依据。
- **`UNKNOWN` 默认不能执行高成本或有副作用的命令。** 只有可信度与授权被明确确认后，才允许执行。
- **`AI` 身份禁止执行能力**：其他机器人发来的命令不能触发生图或消耗 API 额度。
- **`HUMAN` 也不能自动等同于拥有所有能力权限**：真人身份是必要条件，不是充分条件，仍要过对应能力的开关、额度与授权校验。
- **`addressedToSelf` 只代表消息可能发给我们的角色，不代表发送者拥有执行权限**：它回答的是「这句话是不是冲着她说的」，不是「这个人能不能让她做事」。
- **命令执行阶段必须同时验证**：消息来源（是不是当前用户本人）、消息接收对象（是否确实面向我们的角色）、身份可信度（`kind` + `kindSource` 等）、对应能力授权（开关 / 额度 / 收件人范围）。
- **其他机器人在群聊里发送 `&出图` 不得触发生图或消耗 API 额度。** 群聊里未 @ 她、或 @ 她但来源不可信的 `&出图` 都应被挡住。

### 9.1 第三轮修订（2026-11-27）：授权依据的调整【仅设计，未实现】

本节上面几条里的「身份可信度（`kind` + `kindSource` 等）」经第三轮代码审查后需要修正。以下四点以第三轮结论为准，本节其余内容不变：

1. **授权依据是独立派生的 `isOwner` 加 `kind`，不含 `kindSource`。** `kindSource`（AUTO / MANUAL）在整个服务端没有任何读取点，它不是可信度凭证；也不能由「HUMAN」「MANUAL」推导出主人身份。`isOwner` 由服务端按渠道计算：网页是「会话用户 id 等于角色 `ownerId`」，QQ 是「事件账号等于连接配置的 `ownerQq`」；每轮重新算，客户端不能传入。
2. **`friendChatPolicy` 只是交流准入，不作能力授权凭证。** BLOCK / ALLOW / DEFAULT 的现有行为保持不变，不接入任何能力执行判断。
3. **网页用户是已认证的角色主人，不按 UNKNOWN 处理。** 网页入口先 `requireActor`，再用 `character.findFirst({ id, ownerId })` 确认归属；没有 `kind` 字段不代表身份未知。只有 QQ 私聊才是「有账号、未查身份」，需要在私聊入口补身份查询。
4. **授权要覆盖全部实际执行入口，不只是 `&出图`。** 目前真实花钱的入口里，普通图片附件描述、入站语音转写、自动收表情包打标签这三处没有任何身份校验；生图的旧自然语言入口和自主生图对 UNKNOWN 不设防。授权应挂在执行点上，让旧入口与新命令过同一次授权调用，再开始命令迁移。

五个概念（主人身份、外部身份分类、分类来源、能力授权、收件人判断与执行确认）分开，按「认证 → 分类 → 主人确认 → 收件人判断 → 能力授权 → 能力自身确认 → 执行」的顺序判断。完整设计、接入点清单、测试矩阵和待定决策见 [UNKNOWN 语义与第二阶段权限前置审查](../2026-11-27-UNKNOWN-语义与第二阶段权限前置审查.md)「第三轮·第四部分」。

**第二阶段开工条件目前不满足。** 第一阶段只完成了命令的解析和透传，`&出图` 当前没有执行效果；在所有实际执行入口都能接受统一授权约束之前，不应给任何命令接上执行逻辑。

### 9.3 第五轮修订（2026-11-27）：授权配置的可信来源与凭证绑定【仅设计，未实现】

第四轮的授权接口让调用方传 `switches: { master: boolean, group: boolean }`，是普通布尔值，调用方可以随意传入，授权函数无从确认它是否来自当前角色的真实配置。本轮改为三个各有一个构造入口的对象（构造入口的名称按第六轮收敛后的写法，见 9.5、9.6）：

| 对象 | 构造入口 | 输入来自 | 构造几项 |
| --- | --- | --- | --- |
| 身份 `CapabilityIdentity` | 两个渠道专用入口：`deriveOnebotCapabilityIdentity`、`deriveWebCapabilityIdentity` | QQ：连接记录、绑定、协议事件；网页：会话用户 id、已校验归属的角色行。加查到的分类 | 每条消息一份 |
| 配置 `CapabilitySwitches` | 随 `beginCapabilityTurn` 一并读出 | 本轮加载的角色行（`id`、`modelConfig`），带 `characterId`，开关按生图、看图、转写、合成四个能力族分开存 | 每轮一份 |
| 凭证 `CapabilityGrant` | `turn.authorize` | 上面两个对象，加能力、触发方式、收件人事实 | 每条消息 × 每项能力一份 |

- **角色 id 只来自已验证的上下文**：QQ 是绑定上的 `characterId`，网页是 `where: { id, ownerId }` 查出来的角色行。开关只从服务端当前角色配置读取。
- **读不到就不执行**：配置缺失、类型不对，开关一律按关处理；角色查不到或查询出错，本轮不执行任何能力。没有任何一条路径通向放行。
- **两条授权路径分开**：主人看自己的开关，依据记为 `owner`；群友看 `allowGroup*`，依据记为 `group_member`。接口里没有 `master` 这个参数，走主人路径的唯一条件是 `isOwner`。
- **一个族一个开关**：允许群友生图不会顺便允许看图、转写、合成。
- **凭证的绑定**：绑定角色、发送者、能力、触发方式和来源消息；只在内存里存在，一轮之内有效，不落库，不跨消息复用。生图提议的确认必须重新授权。生图后的自检用单独派生的子凭证，父子凭证的有效期分开算，见 9.5。
- **执行点核对**：真正发起外部调用之前，用手头的真实上下文比对凭证的角色、发送者、能力、来源消息和触发方式。出站回复另有一道：发送器绑定到轮次，并且核对「现在调用发送器的是不是本轮的代码」，整次发送都受保护，见 9.5。
- **类型标记的局限**：它在运行时会被擦除，防的是误用，不防 `any` 和断言。所以另加登记表、执行点的数据比对和接线测试，不依赖类型。

本轮还修正了 D-2 的状态（见 9.2 的表）。**第二阶段仍不具备开工条件。**

### 9.4 第五轮补充修订（2026-11-27）：身份派生与执行凭证的运行时边界【仅设计审查，未实现】

第五轮的 `deriveCapabilityIdentity` 还留着一个口子：入参 `owner: { matches: boolean }` 让调用方可以直接写 `true`，比较发生在函数外面。本轮补上。

**身份派生只收原始事实，比较在函数内部做。**

```ts
deriveCapabilityIdentity({
  characterId,                                   // 已验证的角色上下文：QQ 用 binding.characterId，网页用查出来的 character.id
  sender: { channel, account } | { channel: "web", userId },   // QQ 用 event.userId，网页用会话用户 id
  owner: { source: "connection_owner_qq", configuredAccount }  // QQ 用 record.ownerQq（它在连接上，不在角色绑定上）
      | { source: "character_owner", ownerId },                 // 网页用 character.ownerId
  classification,                                // 身份表查到的分类，查不到为 null
})
```

接口里没有布尔值。想得到主人身份，调用方必须交出一个等于主人的账号或用户 id，而这两样只能来自协议事件和会话。消息正文、昵称、群名片、请求体都不能作为输入。

类型标记防不住服务端内部代码故意伪造账号，所以运行时的可信靠两件事：派生函数只在四个位置调用（`serve.ts` 的私聊分支和 `flushGroupRound`、`chat.post.ts`、七个网页付费接口），以及一组接线测试把这些调用点的实参钉死。**第六轮把这个通用函数收起来了：业务代码只能调两个渠道专用入口，它们收整个对象、自己取事实，见 9.6。上面这段代码块说明的是比较规则，规则没变，入口变了。**

**执行点核验补齐为五项**：角色、发送者、能力、来源消息、触发方式，给了的必须全等。执行点上下文里来源消息缺失时不通过，不是跳过。授权依据 `basis` 只在签发时写入并冻结，只用于审计。消息 ID 缺失、重复、重放、戳一戳的合成 ID、网页的 `requestKey`，各有明确处理，见审查文档 6.10.3。

**出站回复的凭证登记是必须的，而且要能主动撤销。** 不用 `WeakSet`：授权模块用登记表，以凭证对象本身为键；每轮开始登记，结束时撤销这一轮的全部凭证，另有过期时间兜底；出站语音的凭证核验通过即作废。对象字面量、`any`、JSON 反序列化得到的对象都不在表里，一律不通过。`tts.synthesize` 的凭证只在一个计划点签发，由接线测试保证。

这一段在第五轮时的标题是「出站语音的执行点核不全」，说法是「发送端核不了发送者和来源消息，所以在签发处定死；没有有效凭证时退回文字」。**第六轮改了**：发送端核不了发送者和来源消息，这一点没变；但发送端现在核「当前轮次上下文」，跨轮次的调用在发送之前就被拒绝；没有有效凭证时是**整次拒绝，什么都不发**，不再退回文字。现行机制见 9.5。

产品决策状态没有变：D-1 已定，D-2 到 D-6 待定。**第二阶段仍不得开工。**

### 9.5 第五轮最终补充（2026-11-27）：凭证的轮次隔离与消费语义【仅设计审查，未实现；2026-11-28 第六轮改写】

上一轮定义了 `beginCapabilityTurn()`，但轮次没有贯穿到签发和核验。第五轮把轮次做成一个对象；第五轮的复审加了发送器绑定；**第六轮再加当前轮次上下文，并把对外接口收敛到轮次句柄上**。下表是现行版本，此前「回复选项携带凭证和 `turnId`」的做法已作废：

| 步骤 | 接口 | 轮次怎么参与 |
| --- | --- | --- |
| 入口派生身份 | `deriveOnebotCapabilityIdentity`、`deriveWebCapabilityIdentity` | 此时还没有轮次；每条消息一份；收整个对象，自己取事实（见 9.6） |
| 轮次开始 | `beginCapabilityTurn({ characterId, conversationKey, modelConfig, baseSender })` | 每轮一次，一并读出配置开关、绑定本轮的底层发送器；返回轮次句柄 |
| 执行本轮 | `turn.run(fn)` | 在「当前轮次 = 本轮」的异步上下文里执行 `fn`，`finally` 里结束本轮 |
| 绑定身份 | `turn.bindIdentity(identity)` | 把身份绑到本轮；这是得到带轮次身份的唯一途径 |
| 签发 | `turn.authorize({ identity, capability, trigger, addressedToSelf })` | 凭证登记到本轮 |
| 普通执行点 | `turn.consume(candidate, { authorKey, capability, sourceMessageId, trigger })` | 核对轮次、角色、发送者、能力、来源消息、触发方式，然后一次性消费 |
| 发送任何回复 | `turn.replySender` | 发送前核对：当前异步上下文存在、就是自己绑定的轮次、那一轮开着；不通过则整次拒绝 |
| 出站语音 | `turn.replySender` 的一步，加底层发送器里的 `consumeVoiceDelivery` | 凭证核验通过后签发一张一次性投递票；底层发送器只认投递票，并再核一次当前轮次上下文 |
| 生图自检 | `turn.deriveSelfCheck(parent)` | 从生图凭证派生一份新凭证；五个阶段，失败关闭；同一张父凭证最多派生一次 |

- **`end()` 只撤销本轮的东西。** 每轮有自己的凭证、身份、投递票三个集合；结束时只清这三个集合，把自己的发送器标记为已结束，不扫描全局。
- **跨轮次发送隔离是运行时保证。** 发送器绑定回答「这个发送器属于哪一轮」，当前轮次上下文（`AsyncLocalStorage`，由 `turn.run` 建立）回答「现在调用它的是哪一轮的代码」。两者缺一不可。B 轮的代码即使同时拿到 A 的凭证、A 的轮次对象、A 的发送器，调用也会在发送任何内容之前被拒绝。轮次结束后调用该轮的发送器同样被拒绝。
- **保护的是整次发送。** 文字、分段、引用、@、表情、贴纸、生成的图、语音，全部走 `turn.replySender`。拒绝时不降级成「只发文字」，文字本身就是可能泄露的内容。
- **`AsyncLocalStorage` 的限制。** 在上下文之外创建的资源所触发的回调里，上下文会丢失。丢失的后果是拒绝发送，是可见的失败，不是泄露。另有四条系统主动发起的出站路径（公告、两种主动联系、群内主动发言）不经过发送器，上下文核验管不到，靠接线测试限制它们的调用点。
- **所有凭证一次性消费。** 一份凭证等于对付费入口函数的一次调用；函数内部的多个请求（一条消息三张图）属于这一次调用，受现有每轮预算约束。先核验、同步标记消费、再调用外部服务；单线程下并发消费只有一个成功。
- **外部失败后不恢复凭证（已定）。** 失败后走现有的降级，用户要再试就再说一次。函数内部的传输层重试属于同一次调用，必须有上限。项目主人于 2026-11-28 确认「一律要求用户重新发起」，见 9.7。
- **触发方式必填。** 普通执行点必须交出真实的触发方式，省略或传非法值都不通过；出站语音的核验不收这个参数，核对的是签发时登记的值，而签发位置只有一处。
- **派生是异常安全的。** 登记条目记录父凭证有没有派生过。派生分五个阶段：只读检查、准备、置父标记、登记子凭证、返回。登记阶段出异常时清理并逐项确认，确认干净才恢复父标记，确认不了就保持拒绝派生。只有生图凭证能派生，父凭证已消费是唯一允许的例外，父子同属一轮、一起失效。
- **父子凭证的有效期分开算。** 子凭证从派生那一刻起算自己的有效期，不继承父凭证的剩余时间；但仍然受轮次约束，轮次一结束就失效。过期判断用单调时钟，读数严格小于过期读数才算有效，时钟读数异常按过期处理。
- **过期时间先收集数据再定（已定）。** 此前写的「2 分钟」没有数据依据，已撤回。项目主人于 2026-11-28 确认先收集一轮最长耗时、生图耗时、自检耗时的分布再定数值，在此之前不写具体数字。能确定的只有一点：有效期是兜底，必须长于任何合法轮次。
- **对象不可变，判断只读登记表。** 轮次、身份、凭证都是冻结的外壳，事实存在模块私有的表里。改字段不改变判断结果；字面量、`any`、JSON 反序列化造出来的对象不在表里，一律拒绝。`end()` 是唯一允许的状态变更，只会让事情变严。
- **并发分析。** 同一会话的两轮不会并发（事件按会话键排队，`serve.ts:1715`）。同一角色不同会话、不同角色的并发靠轮次对象、角色比对和各自独立的异步上下文隔开。
- **仍然不是运行时保证的几件事。** 身份构造的入参是否真的来自协议事件、连接记录和会话（见 9.6）；跨轮次持有**真**对象去签发；发送的内容本身对不对；接线测试查不了的语义部分。这些靠结构检查和评审，登记表会把它们的后果限制在原来的轮次内。

产品决策状态没有变。设计层面按「权限边界或信息泄露边界」衡量没有未解决的阻塞项；「`AsyncLocalStorage` 列为必须项」已于 2026-11-28 被项目主人采纳（见 9.7）。**第二阶段仍不得开工。**

### 9.6 第六轮补充（2026-11-28）：接口收敛、身份入口与结构测试【仅设计审查，未实现】

**对外接口收敛。** 第五轮最终补充里有八个自由函数，业务代码要把轮次对象当参数传来传去。现在业务代码能碰到的只有：两个渠道身份入口、`beginCapabilityTurn`、轮次句柄上的六个成员（`run`、`replySender`、`bindIdentity`、`authorize`、`deriveSelfCheck`、`consume`），以及一个只给底层发送器用的 `consumeVoiceDelivery`。五张登记表全部在模块内部。校验规则一条没变。没有合并的东西（身份派生与轮次、签发与消费、五张表）各有不同的生命周期，合并会混淆状态；评估过「只留上下文」「只留登记表」「凭证改字符串令牌」三种更小的方案，都会降低保证，所以保留现有设计。设计体量偏大这件事如实记在风险表里，由项目主人权衡。

**身份构造收敛到两个渠道专用模块。** 通用的身份构造函数不再对业务代码导出。QQ 模块收连接记录、绑定、协议事件三个对象，自己从里面取主人账号、发送者账号、消息 ID 和角色 id；网页模块收会话用户 id、按归属查出来的角色行和 `requestKey`，自己比对归属。业务代码不再有机会分别填「发送者账号」和「主人账号」。新平台接入必须新增自己的渠道模块并过评审。用 ESLint 的引入限制和结构测试来限制谁能引入这两个模块。

**这仍然不是运行时的身份真实性保证。** 入参对象本身可以被伪造；类型标记和 `readonly` 不提供任何运行时保证；拦住刻意绕过的是评审。

**关键接线测试改为语法树结构检查。** 用 `typescript` 编译器接口（已是开发依赖）解析 `server/`，断言：指定函数的调用点集合；身份构造的实参是直接的属性访问（`event.userId`、`record.ownerQq`、`binding.characterId`），转手即报错；网页调用前存在按 `id` 和 `ownerId` 查角色的调用；对发送器的调用位于 `turn.run` 的回调里；合成调用位于投递票核验通过的条件分支里；四个传输函数的调用点集合；受限模块没有被违规引入或转手导出。

**结构测试证明不了任意代码的语义正确。** 它证明「调用点和实参是规定的写法」；被调函数的实现有没有被改、传进去的对象在别处有没有被替换、规定本身对不对，这些靠人工独立评审。两者的分工在实现说明里也要写明。

产品决策状态没有变。**第二阶段仍不得开工。**

### 9.8 自查复审（2026-11-28）：拒绝的返回值形态【仅设计审查，未实现】

项目主人要求评审第 5、6 节。**自查不是独立评审**，结论只是「拿代码对了一遍断言」，完整记录见审查文档 6.31。四处缺口里有三处是文档层面的（自主生图的来源事实取不到、触发消息没有定义、私聊非主人仍挂【待定】），只有一处会改到既有代码形状，记在这里：

**拒绝必须是一个独立的返回值。** 出站保护拒绝发送时，原设计只说「返回失败结果」。现有签名里没有它的位置：`ChannelReplySender` 返回 `Promise<void | ChannelReplyDelivery>`（`pipeline.ts:210`），`ChannelReplyDelivery` 只有 `emoji`、`image`、`at` 三段发送后状态（`:197-208`）。

- 写成抛错：会落进底层发送器处理传输失败的那段（`serve.ts:530-541`），与真实故障混同，还会被「已生成、只差重发」的队列重试分支（`serve.ts:1657`）收走。
- 写成 `void`：与「发出去但没有投递信息」无法区分。

决定：`ChannelReplyDelivery` 增加可选段 `refused?: { reason }`，拒绝时返回 `{ refused }`，不调用底层发送器、不抛错；`pipeline.ts:1591` 之后要先判 `refused`，跳过投递记录与「请求了 @ 却补记 suppressed」的兜底（`:1595-1600`）；拒绝是终态，不进入重试。

这一项改动很小（一个可选字段、一个分支），但必须写进设计——不写，实现会自己发明一种拒绝方式，而无论发明成哪种，都会和「发送失败」或「没发」纠缠在一起。

## 10. 完成标准

- 普通自然语言不再触发用户主动出图、TTS、主动 Vision 或新建群历史查询。
- 四种显式命令在 QQ 与网页入口行为一致。
- 命令内容由模型/领域逻辑理解，不再靠自然语言触发正则猜测意图。
- 引用、转发、历史、AI 消息和图片 OCR 中的命令文本不会触发能力。
- 权限、预算、开关、目标图片校验、群聊收件人校验、失败降级与既有互斥逻辑全部保留。
- 命令执行前完成消息来源、接收对象、身份可信度与能力授权四重校验；`UNKNOWN` / 不可信来源 / 其他机器人发来的命令不会触发生图或消耗 API 额度。
- 自主配图/自主语音等独立角色行为策略没有被误删或混入用户命令解析；是否保留其产品行为另行决定。
- 相关专项测试通过，typecheck、lint、build 按项目现行验收要求通过。
