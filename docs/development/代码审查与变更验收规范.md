# 代码审查与变更验收规范

> 状态：现行开发规范
> 建立日期：2026-11-27
> 适用范围：忆灵空间全部代码、配置、数据库结构、提示词、自动化流程与开发文档变更
> 目的：让审查深度与变更风险匹配，避免低风险改动过度审查，也避免核心改动审查不足。
>
> 本文规定今后的最低审查要求，不代表历史功能已经按本文标准审查，也不代表通过审查就能证明系统绝对没有缺陷。

---

## 1. 基本原则

### 1.1 风险决定审查深度

- 不按代码行数决定审查等级。几行身份判断、权限判断或数据删除代码，也可能属于最高等级。
- 不要求所有变更都进行多轮审查。普通 UI 和低风险修改应保持效率。
- 一项变更涉及多个等级时，按其中最高等级执行。
- 文档、提示词或配置如果会改变权限、数据流、模型行为或执行边界，也必须按实际风险定级。
- 审查结论必须基于当前分支的实际 diff、调用链和测试证据，不能只看开发者总结或 AI 自述。

### 1.2 测试通过不等于设计正确

测试、类型检查、Lint 和构建只能证明已覆盖的部分符合预期。审查还必须考虑：
- 未覆盖的调用入口和绕过路径；
- 并发、重试、超时、取消和异常；
- 权限与身份的可信来源；
- 数据生命周期、迁移、删除和恢复；
- 新旧路径、旧数据和兼容逻辑；
- 实际执行点是否落实了设计约束。

### 1.3 先确认事实，再判断风险

审查开始前先确认：
1. 当前审查的仓库、分支和基准提交；
2. 本次变更的提交范围与完整 diff；
3. 变更影响的模块、入口、调用链和数据；
4. 相关规范、设计文档和既有测试；
5. 本地 AI 或其他开发者是否还有未提交改动。

不得把未检查的文件、路径或运行时行为描述为“已确认安全”。

## 2. 变更风险分级

| 等级 | 名称 | 常见范围 | 最低审查要求 |
|---|---|---|---|
| P1 | 常规变更 | 文案、样式、纯展示 UI、局部低风险体验优化、无业务语义的重构 | 一轮审查 + 相关测试 |
| P2 | 重要变更 | 对话流程、记忆读写与检索、工作流、提示词组装、模型路由、数据处理、跨模块接口 | 实施后审查 + 独立复审 + 相关回归 |
| P3 | 核心/高风险变更 | 身份认证、权限授权、安全边界、隐私、密钥、不可逆操作、数据迁移/删除、并发控制、凭证生命周期、自主执行、外部付费能力 | 设计审查 + 实施审查 + 独立复审；必要时多轮修订；关键场景测试 |

### 2.1 P1：常规变更

适用条件：
- 不改变业务规则、权限、持久化数据和外部副作用；
- 不新增或改变跨模块调用链；
- 不涉及敏感数据或不可逆操作。

检查项目：
- diff 是否只包含预期文件；
- 是否有明显错误、遗漏或破坏现有交互；
- 对应 lint、类型检查、构建或相关测试是否通过；
- 文档或截图是否需要同步。

如果审查中发现实际影响超出 P1 范围，立即升级等级，不得为了减少工作量继续按 P1 放行。

### 2.2 P2：重要变更

适用条件：
- 会改变核心业务逻辑或多个模块间的协作；
- 会影响对话、记忆、工作流、模型调用或持久化数据；
- 失败可能导致数据不一致、回复异常或功能回归，但影响范围可控、通常可恢复。

最低流程：
1. 实施者说明设计、影响范围和测试方案；
2. 完成实现后，审查者独立阅读 diff 和关键调用链；
3. 运行相关单元、集成和回归测试；
4. 对异常、边界和旧路径进行检查；
5. 更新对应文档与进度记录。

独立复审不能只复述实施者的结论，应从需求和实际代码重新验证。

### 2.3 P3：核心/高风险变更

命中以下任意一项即按 P3：
- 谁可以执行、代表谁执行、能访问什么数据；
- 任何绕过正常入口即可触发敏感能力的路径；
- 记忆、私密对话、图片、音频等用户数据的读取、处理、传输或删除；
- 身份派生、授权、凭证签发/核验/撤销/消费；
- 并发请求、角色切换、异步回调和跨轮次状态；
- 自主执行、自动操作、外部付费或不可逆操作；
- 数据库结构迁移、批量修复、备份恢复或数据清理；
- 安全配置、密钥、认证会话和管理员边界。

最低流程：
1. **设计审查**：先检查威胁模型、信任边界、数据流、所有入口和失败策略；设计存在未决问题时不得进入实现。
2. **实施审查**：实现后逐项对照设计，确认真实代码没有偏离。
3. **独立复审**：由未承担主要实现工作的审查者重新追踪关键路径，不以实施者报告代替代码证据。
4. **针对性测试**：覆盖正常、拒绝、边界、异常、并发、重试、取消和旧路径。
5. **修订复审**：修复者提交变更后，审查者必须检查修复本身及其回归影响。若修订改变设计前提，退回设计审查。
6. **放行记录**：记录最终提交、测试证据、未解决问题和明确的限制。

P3 可以进行多轮审查，但每一轮都必须对应明确的新问题或新证据。不得为了“多审几次”而重复同一份检查。

## 3. 审查角色与独立性

### 3.1 实施者

负责说明需求、设计意图、影响范围和风险等级；提供实现提交、测试结果和文档变更；解释关键决策、兼容策略和未覆盖场景；修复审查发现的问题。

### 3.2 审查者

负责独立检查实际 diff、调用链和数据流；验证需求是否完整实现；主动寻找遗漏入口、绕过路径和边界条件；区分已证实问题、潜在风险和待验证假设；明确给出通过、有条件通过或阻塞结论。

### 3.3 独立复审

- P2、P3 必须有独立复审视角。
- 同一个 AI 可以参与设计或实现，但不能仅凭它自己的“自检通过”作为独立复审证据。
- 如果当前只能使用同一个模型，应采用不同审查提示、重新从需求和源码出发，并明确标注“独立性有限”；P3 尽可能由不同模型或人工进行交叉复核。
- 不以模型品牌、模型名称或自称身份作为可靠性证明。以实际代码理解、证据质量和可复现检查为准。
- GLM、DeepSeek 或其他模型都只是工具；模型选择不能替代审查流程。

## 4. 通用审查清单

所有等级都应先检查适用项目；P2、P3 需要更深入地覆盖。

### 4.1 需求与范围
- [ ] 实际实现与需求、已确认决策一致；
- [ ] 没有擅自把“建议”“待确认”改成已定产品规则；
- [ ] 没有顺手扩大范围或引入未批准功能；
- [ ] 删除、禁用或替换旧逻辑前，检查全部依赖和调用方。

### 4.2 代码与调用链
- [ ] 检查完整 diff，而不只是新增代码；
- [ ] 搜索所有调用点、入口、事件处理器和后台任务；
- [ ] 检查旧入口、备用入口、自动触发路径和管理路径；
- [ ] 检查类型定义、运行时校验和实际数据形态是否一致；
- [ ] 检查错误处理、资源释放和状态清理。

### 4.3 数据与兼容性
- [ ] 数据读写是否保持一致性；
- [ ] 新字段是否有默认值、空值和旧数据处理策略；
- [ ] 迁移是否可验证，是否有备份和恢复方案；
- [ ] 删除、覆盖、批量更新是否具备保护措施；
- [ ] 是否会泄露敏感信息到日志、提示词或外部服务。

### 4.4 异步与并发
- [ ] 是否可能出现过期响应覆盖新状态；
- [ ] 是否正确处理取消、超时和失败；
- [ ] 并发任务是否会共享不应共享的状态或凭证；
- [ ] 重试是否可能重复产生副作用；
- [ ] finally、锁、队列、事务或清理逻辑是否覆盖所有退出路径。

### 4.5 测试与交付
- [ ] 新增或更新了能验证关键行为的测试；
- [ ] 运行了与风险等级相匹配的测试；
- [ ] 记录测试命令、结果和未运行项目；
- [ ] 检查文档、配置示例、功能总表或进度文档是否需要同步；
- [ ] 确认最终提交中没有混入无关文件或临时调试内容。

## 5. P3 专项检查清单

P3 必须结合具体功能建立威胁模型，以下项目是最低基线，不是完整清单。

### 5.1 身份与权限
- [ ] 身份来自可信认证上下文，而不是调用方任意传入的布尔值或字符串；
- [ ] 明确区分身份事实、权限配置、授权决策和执行凭证；
- [ ] 默认拒绝缺失、格式错误、过期或无法验证的权限信息；
- [ ] 每个真实执行点都进行必要的授权核验；
- [ ] 旧入口、自动路径、提议确认路径不能绕过授权；
- [ ] 权限变化后，旧授权是否立即失效有明确规则。

### 5.2 凭证与生命周期
- [ ] 凭证绑定主体、角色/资源、能力、来源和有效轮次；
- [ ] 凭证签发、验证、消费、撤销和清理规则明确；
- [ ] 一次性凭证的消费具备原子性，并发下不能重复成功；
- [ ] 可重复凭证必须有明确次数、范围和有效期；
- [ ] 重试策略不会造成重复扣费、重复发送或重复写入；
- [ ] 轮次结束、角色切换和异常退出不会误清理其他并发轮次的凭证。

### 5.3 并发与异步
- [ ] 同角色并发请求彼此隔离；
- [ ] 跨角色请求彼此隔离；
- [ ] 旧请求不能覆盖新请求的状态或结果；
- [ ] 取消、超时和异常后不会留下可继续使用的状态；
- [ ] 共享缓存、队列和临时文件有明确的所有权与清理策略。

### 5.4 数据与不可逆操作
- [ ] 明确操作影响范围和目标对象；
- [ ] 执行前验证授权、目标和当前状态；
- [ ] 对批量或不可逆操作提供预览、确认、备份或回滚策略（按场景适用）；
- [ ] 幂等性和重复执行行为明确；
- [ ] 审计日志不记录不必要的秘密或隐私内容。

## 6. 测试策略

测试应围绕风险和行为设计，不以测试数量作为质量指标。

| 测试类型 | 主要用途 |
|---|---|
| 单元测试 | 规则、边界值、状态转换、纯函数 |
| 集成测试 | 模块之间的数据传递、数据库和服务协作 |
| 调用链测试 | 从真实入口走到实际执行点，验证没有绕过 |
| 回归测试 | 确认既有行为没有被破坏 |
| 并发测试 | 交错执行、重复消费、状态竞争、轮次隔离 |
| 故障注入 | 超时、网络失败、模型失败、数据库失败、取消和重试 |
| 迁移测试 | 旧数据升级、默认值、回滚或恢复 |
| 手工验收 | UI、真实渠道、外部服务和真实用户场景 |

### 6.1 重要要求

- P1 运行与改动直接相关的测试。
- P2 至少运行相关单元/集成测试和必要回归。
- P3 必须为关键安全属性设计正向与反向测试。只测试“允许成功”不够，还要测试“未授权时确实失败”。
- 测试失败不能通过删除断言、跳过测试或弱化预期来换取绿色结果；如确认为过时测试，必须说明原因并更新测试。
- 如果测试环境无法覆盖真实外部服务，应明确标记为未验证，并给出后续真实环境验收方案。

## 7. 审查结论与放行标准

每次审查必须给出明确结论：

- **通过**：没有发现阻塞问题，要求的测试和证据齐全。
- **有条件通过**：没有已知阻塞问题，但存在明确记录的低风险遗留项；必须指定后续处理方式，不能把未验证事项写成已验证。
- **阻塞**：存在正确性、安全、数据完整性或关键测试问题；修复并复审前不得合并或进入依赖该变更的下一阶段。

问题严重程度建议：

| 等级 | 定义 | 处理 |
|---|---|---|
| Blocker | 可导致越权、严重数据丢失、秘密泄露、不可控副作用或核心流程无法安全运行 | 必须修复 |
| P1 | 高影响正确性/安全缺陷，或关键路径明显错误 | 必须修复后放行 |
| P2 | 局部缺陷、重要边界遗漏或回归风险 | 原则上修复；有条件放行需说明 |
| P3 | 低风险体验问题、非关键维护性问题 | 可记录排期 |

不能只按编号机械判断。权限绕过、数据破坏等问题即使只涉及一行代码，也应按实际影响升级。

## 9. 开发协作流程建议

适用于“ChatGPT 负责设计/复杂实现，本地 AI 辅助编码与检查”的协作方式，也适用于其他开发者。

1. **先定级**：任务开始时明确 P1/P2/P3 和理由。
2. **先读规范**：查看 docs/INDEX.md 中对应的现行规范、功能设计和安全约定。
3. **设计先行**：P2、P3 先明确方案和验收标准；P3 未完成设计审查不得直接进入实现。
4. **实施提交**：实施者说明改动文件、关键路径、测试和已知限制。
5. **独立审查**：审查者自行检查提交，不只看实施者的总结。
6. **修复与复审**：修复问题后重新检查相关 diff 和受影响路径。
7. **同步文档**：需要时更新功能总表、进度文档、设计文档和索引。
8. **记录放行**：明确结论、提交 SHA 和未解决事项。

### 9.1 给本地 AI 的审查要求

交给本地 AI 审查时，应明确要求：
- 先读取本规范，并按本次任务风险等级执行；
- 以指定基准提交和目标提交之间的真实 diff 为准；
- 主动搜索所有调用点和旁路，不得只检查修改文件；
- 报告必须区分“已验证”“推测”“未验证”；
- 每个问题尽量提供文件路径、行号、触发条件、影响和修复建议；
- 不得为了让测试通过而删除或弱化测试；
- 不得擅自修改代码（如果任务只是审查）；
- 不得把文档方案当成已经实现的运行时保证；
- 输出测试命令与实际结果；没有执行的测试必须明确写出；
- 最终给出通过、有条件通过或阻塞结论。

## 10. 历史代码与渐进采用

本规范自建立之日起作为后续变更的统一标准。

- 不要求立即对整个仓库所有历史代码进行一次性全面重审。
- 历史代码在被修改、扩展、暴露新入口或纳入高风险链路时，应按本规范重新评估。
- 对身份、权限、数据删除、密钥、并发和自主执行等高风险旧模块，可单独安排专项审计。
- 历史提交曾经通过普通代码检查，不等于已经通过本规范的 P2/P3 审查。
- 发现历史问题时，按实际风险建立修复任务，不要为了追求形式上的全覆盖而盲目大规模改动。

## 11. 与项目其他规范的关系

- 本文规定“审查做到什么程度”。
- docs/security.md 规定安全与隐私的具体原则。
- docs/test-organization.md 规定测试组织和运行约定。
- docs/engineering-lessons.md 记录已发生事故及其硬性经验。
- docs/INDEX.md 是文档导航入口。
