# 桌面化架构评估（阶段一预检）

> 评估日期：2026-11-19
> 对应方向文档：[产品定位与跨平台架构原则](<产品定位与跨平台架构原则.md>)
> 评估性质：**只读代码与配置的预检**，没有启动 Electron/Tauri 原型，没有修改业务代码。
> 结论先行：**桌面化可行，Electron 是当前更合适的路线；但现有仓库有四个硬约束，必须先解决，否则做出来的只是「浏览器套壳」，达不到桌面端要的可靠本地运行环境。**

## 1. 结论摘要

| 判断 | 结论 |
| --- | --- |
| 能否复用现有 Nuxt/TypeScript/服务端 API | 能。业务逻辑已在 `server/api`、`server/utils`，页面可直接复用 |
| 能否直接把网页塞进 Electron | 不能。数据库、数据目录、后台进程、启动器都还是「开发机仓库」形态 |
| 最大硬约束 | PostgreSQL 专用能力太深，不能换 SQLite；桌面端必须自带或连接 PostgreSQL |
| 第二硬约束 | 28 处运行时代码依赖 `process.cwd()/.data`，从开始菜单启动会读错/写错目录 |
| 第三硬约束 | Worker 用 `tsx` 直接跑 TypeScript 源码，迁移依赖 Prisma CLI；打包不是复制 `.output` 就够 |
| 第四硬约束 | 当前启动器只守护 Worker，**不启动 Scheduler**；桌面端必须补齐，否则自动记忆不会推进 |
| 推荐技术路线 | 阶段二用 Electron；Tauri 仅作为后续体积/安全的备选评估 |
| 推荐数据库路线 | **Docker（已确认）**：桌面 supervisor 负责拉起 Docker Desktop 与数据库容器；不内置 PostgreSQL |
| 参考实现 | 用户已有的 `D:\AI\Mimitale` Electron 桌面端：可复用其数据目录、单实例、preload 隔离与启动收尾模式 |
| 推荐进程模型 | Electron 主进程只做 supervisor；Nitro、Scheduler、Worker、OneBot 都是独立子进程 |

## 2. 评估范围

本次只检查与「桌面端能不能可靠跑起来」直接相关的部分：

- Nuxt/Nitro 的构建产物与启动方式；
- Prisma、PostgreSQL、迁移与备份；
- Scheduler、Worker、Watchdog 的生命周期；
- QQ / OneBot / SnowLuma 的本机依赖；
- 数据目录、`.env`、凭据与文件落盘位置；
- 现有启动脚本与使用版镜像的打包方式；
- Electron/Tauri 与现有 Node 技术栈的兼容性。

不包含：桌面 UI 设计、本地执行代理的具体实现、鸿蒙客户端、商业化与多人云端部署。

## 3. 现状盘点

### 3.1 构建与启动

| 项 | 现状 | 对桌面化的影响 |
| --- | --- | --- |
| Web 框架 | Nuxt 4 + Nitro，`nuxt build` 产出 `.output/server/index.mjs` | 可独立进程启动，桌面端通过 `http://127.0.0.1:<port>` 加载 |
| 开发启动 | `启动忆灵空间.bat` → `scripts/launch.mjs`：检查 Node/yarn、装依赖、起 `nuxt dev`、打开浏览器 | 这是开发启动器，不是桌面 supervisor；不应在安装包里复用它 |
| 生产启动（仓库内） | `scripts/launch.mjs --production` → `scripts/local-production-entry.mjs` → `.output` | 已经接近「起本地生产服务」的形态，但仍依赖仓库目录与 `.env` |
| 使用版启动 | `docker-compose.prod.yml` + `scripts/launch-prod.mjs`：`migrate deploy` → 首个管理员 → Web + Worker | 逻辑可借鉴，但路径、数据库、容器假设都不同 |
| 健康检查 | `GET /api/health` 只返回时钟与服务名，不检查数据库 | 桌面 supervisor 需要额外做 DB readiness 与页面 readiness |

### 3.2 进程与调度

| 进程 | 入口 | 现状 |
| --- | --- | --- |
| Web | `.output/server/index.mjs` / `nuxt dev` | 需要外部 supervisor |
| Scheduler | `scripts/run-memory-scheduler.ts --watch` | **`launch.mjs` 与 `launch-prod.mjs` 都没有启动它**；文档也写明「启动器不会自动启动 Scheduler」 |
| Worker | `scripts/run-memory-worker.ts --watch`，由 `scripts/memory-worker-supervisor.mjs` 守护 | 有跨进程锁、父进程 IPC 守卫、崩溃退避；可复用 |
| Watchdog | `scripts/watchdog.ts --watch` | 只在 `start-qq-stack.ts` 里顺带启动，不是核心必需 |
| OneBot 适配器 | `scripts/run-onebot-adapter.ts` | 由网页「启动适配器」或 `start-qq-stack.ts` 拉起，Windows 终端窗口 |
| SnowLuma | 外部程序，`start-qq-stack.ts` 找到目录后 `node index.mjs` | 不在仓库内，路径靠发现链与用户配置 |

**这是当前最容易被忽略的问题：** 自动快照、忆泡、日记等周期任务需要 Scheduler 入队；只起 Web + Worker 时，Worker 没有任务可领，页面看起来正常，但记忆不会自动推进。桌面端必须把 Scheduler 和 Worker 放在同一个 supervisor 下。

### 3.3 数据库与迁移

- `prisma/schema.prisma` 的 datasource 是 `postgresql`，没有 SQLite 分支。
- schema 中有 430 处 PostgreSQL 专用列类型（`@db.Uuid` / `@db.Timestamptz` / `@db.JsonB`），其中 39 处 `JsonB`。
- 服务端有 125 处 `$queryRaw` / `$executeRaw`，使用 `::jsonb`、`FILTER`、`::uuid` 等 PostgreSQL 语法。
- Prisma 7 使用 `@prisma/adapter-pg` + `pg`（driver adapter），**没有 Rust query engine**；但 `prisma migrate deploy` 仍需要 `@prisma/engines/schema-engine-windows.exe`。
- `scripts/launch-prod.mjs` 每次启动都执行 `prisma migrate deploy`，这是使用版「数据库自动升级」的机制。
- 备份脚本 `scripts/backup-db.ps1` / `restore-db.ps1` 依赖 Docker 容器和 `pg_dump`。

**结论：** 不能把桌面端换成 SQLite；迁移到 SQLite 等于重写数据层。
**决策（2026-11-19）：桌面端继续使用 Docker。** 桌面 supervisor 负责：检查 Docker Desktop → 必要时自动启动 → 启动/复用 `yiling-hub-db` 容器 → 等待端口可连 → 执行 `prisma migrate deploy`。数据仍在 Docker volume 里；`.data` 只放凭据、表情包、语音临时文件等本机文件。
代价是普通用户需要先安装 Docker Desktop；这是已确认接受的产品取舍，用启动引导与明确错误提示来兜底，不再评估内置 PostgreSQL。

### 3.4 数据目录与凭据

全仓有 28 处使用 `process.cwd()`，其中运行时关键路径包括：

- `server/utils/credential-encryption.ts:16`：`process.cwd()/.data/credentials-encryption.key`
- `server/utils/stickers.ts:86,140`：表情包与原件备份
- `server/utils/channel-adapter/onebot/runtime.ts:33,140,642`：适配器状态、SnowLuma 目录、启动器 pid
- `server/utils/channel-adapter/onebot/serve.ts:872`：语音临时文件
- `server/api/characters/[id]/voice/test-connection.post.ts`：语音探针
- `server/utils/character-delete.ts:135`：删除角色时的 `.data` 根目录

桌面应用从开始菜单启动时，`cwd` 可能是 `C:\Windows\System32`、安装目录或用户目录，**不可控**。后果包括：新建空 `.data`、读不到已有表情/凭据、把文件写进 Program Files 被拒绝，甚至在错误的目录下判断「哪些文件可以删」。

此外 `.env` 也是按 cwd 读取的（`dotenv/config`、`prisma.config.ts`、启动脚本）。桌面端需要显式指定配置文件与数据目录，不能依赖 cwd。

### 3.5 打包与运行时依赖

| 依赖 | 现状 | 打包注意 |
| --- | --- | --- |
| Node 运行时 | 项目要求 Node ≥ 20.19；Electron 自带 Node | 可用 Electron 的 Node 或随包带 `node.exe` |
| `tsx` | Worker 以 `--import tsx` 直接跑 `server/**/*.ts` | 必须把 `tsx`、`server/`、`scripts/`、`src/generated` 一起带上，或预编译 Worker |
| esbuild | `tsx` 依赖 `@esbuild/win32-x64/esbuild.exe`（约 12MB） | 需要 `asarUnpack` |
| Prisma CLI / engines | `prisma`（约 41MB）+ `@prisma/engines`（约 20MB，含 `schema-engine-windows.exe`） | 迁移需要，必须随包；`asarUnpack` |
| sharp | `@img/sharp-win32-x64`（约 19MB），N-API 预编译 | 需要 `asarUnpack`，在 Electron 的 Node 下验证 |
| silk-wasm | `node_modules/silk-wasm/lib/silk.wasm` | `nuxt.config.ts` 已用 `traceInclude` 显式带上 |
| `@audio/decode-amr` | wasm 内嵌 base64 | 已 external 化，随 node_modules |
| 全量 `node_modules` | 当前 839MB（含 devDependencies） | 直接打包会做出 1GB+ 安装包，必须先裁剪 |

`.output` 当前约 54MB；Electron 自身与安装器还会增加体积。**安装包体积不是阻塞项，但需要单独做生产依赖裁剪与资源白名单。**

### 3.6 渠道与外部程序

- OneBot 适配器依赖本机 QQ 客户端与 SnowLuma；SnowLuma 不在仓库内，默认路径甚至是硬编码的 `D:\Tools\SnowLuma`，发现链会扫盘、查 netstat、调 PowerShell。
- 网页上的「启动适配器」通过 `cmd.exe /k yarn onebot:run` 打开终端窗口；桌面端应改为受管子进程 + 日志面板。
- QQ 未启动、SnowLuma 未安装时，不能让主界面启动失败；这些是可选渠道。

### 3.7 认证与本地访问

- 会话 Cookie 名默认 `yiling_session`，可通过 `YILING_SESSION_COOKIE` 覆盖；桌面 supervisor 默认设成 `yiling_session_desktop`，避免与开发版互相顶登录。
- `SameSite=Strict`、同源校验、`127.0.0.1` 绑定这些对 Electron 加载本地页面是兼容的。
- 生产构建没有开发身份回退；桌面端首次使用仍需要正常登录/初始化管理员。

## 4. 硬约束与风险清单

| 级别 | 问题 | 证据 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| 阻塞 | PostgreSQL 专用能力无法换 SQLite | schema + 430 处 PG 类型 + 125 处 raw SQL | 不能把数据库嵌进单文件 | 继续用 Docker（已确认） |
| 阻塞 | 运行时路径依赖 `process.cwd()` | 28 处 `.data` / 凭据 / 表情 / 临时文件 | 从桌面图标启动会读写错误目录 | 已支持 `YILING_DATA_DIR`；换目录时 supervisor 自动复制 `credentials-encryption.key` 与 `snowluma-home.json` |
| 阻塞 | Worker/迁移依赖源码与 CLI | `--import tsx`、`prisma migrate deploy`、Dockerfile 注释 | 只复制 `.output` 会导致后台静默不工作 | 打包 `server/scripts/src/generated/tsx/prisma`，或预编译 Worker |
| 阻塞 | 启动器不启动 Scheduler | `launch.mjs` / `launch-prod.mjs` 无 scheduler；`deployment.md:132` | 记忆不自动推进，页面看似正常 | 桌面 supervisor 统一管理 Scheduler + Worker |
| 中 | Docker Desktop 依赖 | 需要用户安装/启动 Docker；未装时无法启动 | 首次启动门槛高、自动启动可能卡在登录/更新 | 已补首次引导与错误码（docker_missing / docker_daemon_down / db_start_failed / db_timeout）+ 错误页打开日志；Docker 不可用时仍允许只读浏览/提示修复（后续） |
| 高 | 单实例与端口管理 | 无 `requestSingleInstanceLock`；固定 3000/8801 | 重复启动、端口冲突、双 Worker | 已加 PID 标记兜底（Chromium 锁失败时仍能启动）；启动器检测到已有实例时不再起第二套 supervisor |
| 高 | Cookie 名跨端口共享 | `auth.ts:8` | 开发版与桌面版互踢登录 | 已支持 `YILING_SESSION_COOKIE`；桌面端默认 `yiling_session_desktop` |
| 中 | 更新与迁移不可逆 | `migrate deploy` 启动即执行；无签名/自动更新 | 迁移失败可能打不开旧数据 | 更新前备份、保留旧版本、失败恢复流程 |
| 中 | QQ/SnowLuma 外部依赖 | 硬编码路径、扫盘、`cmd /k` | 未装时启动卡住或报错 | 可选渠道、启动不阻塞、明确未配置状态 |
| 中 | 原生资源未做 asar 规划 | esbuild/schema-engine/sharp/wasm | 打包后运行时找不到二进制 | `asarUnpack` + 安装后自检 |
| 中 | 安装包体积 | 839MB node_modules | 分发困难 | 生产依赖裁剪、资源白名单、预编译 |
| 中 | 移动端无法本地跑核心 | Postgres + Worker + Nitro | 鸿蒙端不能照搬桌面架构 | 移动端连桌面/托管核心，先稳定 HTTP API |
| 低 | 无代码签名 | 无签名配置 | SmartScreen/企业分发阻力 | 阶段二后补签名 |

## 5. Electron 与 Tauri 对比

| 维度 | Electron | Tauri |
| --- | --- | --- |
| 复用 Nuxt/Nitro/Node | 直接；可用 `utilityProcess` 或 `ELECTRON_RUN_AS_NODE` 起子进程 | 需要额外 Node sidecar；Rust 侧不跑 Nuxt/Prisma |
| 进程管理 | `child_process` / `utilityProcess` 成熟 | sidecar 管理可行，但 Node 服务仍要自己带 |
| 原生模块 | N-API 的 sharp 可用；需 asarUnpack 验证 | 同样要带 Node sidecar 与原生资源 |
| 安装包 | 较大（Electron + 资源） | 壳更小，但加 Node/资源后优势缩小 |
| 自动更新 | electron-updater 成熟 | tauri-plugin-updater 可用 |
| Windows 体验 | Chromium 一致，成熟 | WebView2 依赖系统组件 |
| 鸿蒙 | 不支持 | 目前也不能直接覆盖鸿蒙 |
| 团队/维护 | 与现有 JS/TS 栈一致 | 引入 Rust 工具链与额外维护面 |
| 结论 | **阶段二推荐** | 作为后续体积/安全备选，不作为首版 |

选 Electron 的核心理由不是「Electron 更好」，而是**现有产品本来就是一个 Node 服务 + Nuxt 页面**；Electron 能把「窗口」和「服务监管」分开做，Tauri 仍要带 Node sidecar，省不下最重的那部分。

## 6. 推荐桌面架构

```text
Electron 主进程（只做 supervisor / 平台适配）
├─ 配置与数据目录（AppData）
├─ PostgreSQL（Docker Desktop + yiling-hub-db 容器）
├─ prisma migrate deploy
├─ Nitro Web 服务（127.0.0.1，随机端口）
├─ Scheduler（watch）
├─ Worker（watch）
├─ OneBot 适配器（可选，按连接启用）
└─ BrowserWindow → http://127.0.0.1:<port>

渲染进程：只加载本地页面，不开放 Node
Preload：窗口控制、打开数据目录、日志、更新等有限 IPC
```

### 6.1 启动顺序

1. 单实例锁；第二个实例唤起已有窗口。
2. 解析/创建数据目录与配置；迁移旧 `.data`（如用户选择）。
3. 检查 Docker Desktop 与数据库容器；必要时自动启动并等待端口可连。
4. `prisma migrate deploy`；失败则停止并提示，不启动半套服务。
5. 启动 Nitro（`NITRO_HOST=127.0.0.1`，随机空闲端口）。
6. 轮询 `/api/health` 与数据库 `SELECT 1`。
7. 启动 Scheduler 与 Worker，确认心跳/日志。
8. 打开 BrowserWindow；显示启动进度与失败原因。
9. 可选：按连接配置启动 OneBot；失败只影响该渠道。

### 6.2 退出顺序

1. 停止接受新请求/关闭窗口（可选托盘继续运行）。
2. 停止 Worker 与 Scheduler（SIGTERM，超时再强杀）。
3. 停止 OneBot 适配器（若由桌面端启动）。
4. 停止 Nitro。
5. 停止数据库容器（若由桌面端启动）；不退出用户原本就在用的 Docker Desktop。
6. 写退出日志与最后一次健康状态。

### 6.3 失败恢复

- 子进程崩溃：指数退避重启，超过阈值在窗口内提示。
- 数据库崩溃：不要反复重启 Nitro；显示数据库错误与日志位置。
- 迁移失败：停止启动，保留旧版本与备份，给出恢复入口。
- 端口占用：重新选端口；数据库端口冲突则提示配置。

## 7. 阶段二最小实施范围（建议顺序）

按「先运行时、后窗口」推进，避免先做 UI 再补基础设施。

1. **运行时路径抽象**：`YILING_DATA_DIR`、`YILING_ENV_FILE`，默认仍兼容仓库内 `.data`；把 28 处 `process.cwd()` 收敛到一个模块。先做这一项，风险最低、收益最大。
2. **桌面 supervisor 原型（无 Electron）**：一个 Node 脚本完成 DB 检查/迁移/Nitro/Scheduler/Worker/健康检查/优雅退出；可在 CI 与命令行验证。
3. **Docker 生命周期验证**：复用 `launch.mjs` 的 Docker Desktop 启动/容器等待逻辑，验证未装、未启动、登录卡住、容器密码不一致、端口占用五种失败形态与提示；确认关闭应用时只停容器、不退出 Docker Desktop。
4. **Electron 最小壳**：单实例、窗口、托盘、日志、打开数据目录、失败页；先不追求 UI 改造。
5. **打包与自检**：`asarUnpack` 原生资源、生产依赖裁剪、安装后自检（DB、迁移、Worker、Scheduler）。
6. **更新与备份**：更新前备份、失败恢复、旧版本保留；代码签名后再对外分发。
7. **QQ/SnowLuma 可选接入**：不阻塞主启动；未配置时明确显示。
8. 以上稳定后，再进入阶段三的本地执行代理。

### 7.1 已开始的落地（2026-11-19）

- `server/utils/data-dir.ts`：统一数据目录，支持 `YILING_DATA_DIR`，默认仍是 `<cwd>/.data`；凭据、表情、语音、OneBot 状态已改走这里。
- `scripts/desktop-supervisor.mjs`：无界面 supervisor 原型，顺序为 Docker 数据库 → `prisma migrate deploy` → Nitro → Scheduler → Worker → QQ 栈，输出 JSON 行并处理退出收尾。
- QQ 栈：桌面 supervisor 用**系统 Node**启动 `start-qq-stack.ts --managed`（Electron 的 run-as-node 在部分机器上带不起 SnowLuma），同时检查面板 `5099` 与 `3001/3002`；退出时通过 stdin 停 adapter / watchdog / SnowLuma；Nitro 的 `onebot-autostart` 在桌面模式下关闭（`YILING_ONEBOT_AUTOSTART=0`），避免双开。
- `desktop/`：Electron 壳原型（`main.cjs` / `preload.cjs` / `launch.cjs`）：单实例、加载页 → 本地 Nitro 页面、错误对话框、F12/Ctrl+Shift+I 开发者工具；窗口状态持久化、关闭到托盘、托盘菜单（打开窗口/数据目录/日志/退出）；渲染层 `contextIsolation: true` / `nodeIntegration: false`。
- 启动器 `launch.cjs` 是普通 Node：先起 supervisor，拿到 ready URL 后再开 Electron；窗口退出时停 supervisor。这样 Nitro/Worker/QQ 栈都不在 Electron 子进程里跑 —— Electron 子进程在部分 Windows 安全策略下拿不到正常文件权限，SnowLuma 会在 `mkdir <SnowLuma>\tmp` 处 EPERM。
- 已验证：
  - `node scripts/desktop-supervisor.mjs --port 0 --skip-migrate --no-worker --no-scheduler` 能起 Nitro 并通过 `/api/health`；

## 8. 阶段二验收标准

- 已安装 Docker Desktop 的 Windows 机器（不装 yarn、不手动开终端）双击后能完成：启动容器 → 迁移 → 建管理员 → 打开页面。
- 关闭窗口/退出应用后没有残留 Node/PostgreSQL/Worker 进程。
- 再次启动能复用原数据库与 `.data`，不需要重新登录或重新配置。
- Scheduler 与 Worker 都在运行；任务监控能看到新任务入队与完成。
- 拔掉网络时，除模型/QQ 外的基本页面与记忆读取仍可用。
- 升级模拟：旧版本数据 → 新版本启动 → 迁移成功；迁移失败时能回到旧版本并恢复备份。
- 未安装 SnowLuma/QQ 时，应用正常启动，QQ 渠道显示「未配置」。

## 10. 参考 Mimitale 的桌面实践

`D:\AI\Mimitale` 是用户已经跑通的 Electron 桌面端，以下模式可以直接借鉴：

| Mimitale 的做法 | 对忆灵空间的适用性 |
| --- | --- |
| `main/data-dir.js`：程序旁 `data\` 优先，写不进去才回退 `%APPDATA%`；真写探针；只迁移用户数据，不搬 Chromium 缓存 | **直接适用**。忆灵空间只需改一个 `YILING_DATA_DIR`，不用把 28 处 cwd 都改一遍 |
| 单实例：`requestSingleInstanceLock()` + PID 标记兜底（Chromium 锁创建失败时仍能启动） | **直接适用**。比只用 Electron 锁更稳 |
| `main.js` 只做生命周期与装配，窗口/IPC/存储拆到 `main/` | **直接适用**。我们的 supervisor、DB、日志也按模块拆 |
| `preload.js` + `contextIsolation: true` + `nodeIntegration: false` | **必须照做**。渲染层只拿有限 IPC |
| `before-quit` 里同步收尾（桌宠位置、单实例标记） | **直接适用**。忆灵空间要在这里停 Worker/Scheduler/Nitro/容器 |
| `Start-Mimitale.cmd` + `.ps1` 检查 Node/npm/依赖，中文提示放 UTF-8 文件 | **部分适用**。我们还要检查 Docker Desktop；提示文案同样不要写进 .cmd |
| 主进程 `uncaughtException` 只记日志，不弹系统对话框 | **直接适用** |
| 无打包器、源码目录直接 `npm start` | **不适用**。忆灵空间要带 Nuxt 构建产物、Worker 源码与原生资源，必须有自己的打包/裁剪方案 |

不能照搬的部分：

- Mimitale 的主进程就是后端；忆灵空间必须把 Nitro、Scheduler、Worker 作为独立子进程，主进程只做 supervisor。
- Mimitale 没有数据库；忆灵空间要管 Docker 容器、迁移与备份。
- Mimitale 的渲染层是零构建静态页；忆灵空间加载的是本地 Nitro 服务，需要健康检查与端口管理。
