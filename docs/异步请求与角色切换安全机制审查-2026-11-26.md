# 第一部分　初审报告

## 一、现状总览

项目没有 Pinia，全局状态只有 `useState` / `useAsyncData` 两条通道。异步请求安全机制整体成熟度高于同类项目，尤其在成长系统（`growth/**`）和记忆链路打磨得很细。但存在明显的两层分裂：

- **页面与组件层**：大部分核心页面已经有一套成熟的「请求序号 + 角色代际 + 生命周期」防护，但是逐页手写复制的，没有下沉成共享工具。
- **少数子页明显掉队**：`catchphrases.vue`、`stickers.vue` 没有角色切换防护，`daily-life.vue` 的写操作没有防重复提交。

统一传输层（`app/utils/request.ts`）实际只统一了四件事：路径规范化、参数映射（`method`、`body`、`query`、`signal`、`timeout`）、`retry: 0` 禁用自动重试、SSR 与客户端的传输实例注入。它没有统一错误归一化、默认超时、取消语义、响应结构校验。

## 二、已验证有效的局部实现样板

| 样板 | 位置 | 机制 |
|---|---|---|
| 代次 + 上下文比对 | `app/utils/chat-session-state.ts:13-31`，用于 `chat.vue` | `begin()` 递增代际并快照上下文，`isCurrent()` 同时比对代际、角色、视图、搜索词 |
| 序号 + 角色 ID 双重作废 | `characters/[id]/settings/memory.vue:98-137` | `loadSeq` + `requestedId` + `isCurrent()`，拦截写入、报错、复位 loading |
| 多序号 + 切角色全量作废 + 卸载作废 | `journal.vue:81-87`、`:493-527`、`:547-555` | 7 个独立序号，切角色时递增全部并清空状态 |
| 代际 + 卸载标志 + 服务端回显校验 | `growth/index.vue:26-90` | 额外校验返回的角色 ID |
| AbortController 存控制器而非布尔值 | `useMemoryProgress.ts:96-160` | 在途控制器 + 8 秒超时 + 强制刷新先掐旧请求 + `finally` 只清自己 |
| 切角色归零所有忙碌标记 | `CharacterModelSettings.vue:34-64` | 解决「旧请求的 `finally` 不再为新角色清零」 |
| 动作布尔守卫 | `useMemoryActions.ts:47-133` | 入口 `if (busy) return` + `finally` 复位 |

## 三、已发现的问题及严重程度

### 高

1. **`catchphrases.vue` 缺角色切换防护**：只有 `onMounted(load)`，没有 `watch(id)`；`load()` 无序号，`submit()` 无 `saving` 守卫。
2. **`stickers.vue` 同病**：`onMounted` 无 `watch(id)`；`loadCharacter()` 无条件写入；`submit()` 无 `saving` 守卫。

### 中

3. **`daily-life.vue` 写操作缺防护**：`savePlan`、`startPlanned`、`completeCurrent`、`associate` 无忙碌守卫；`actingId` 是共享单值。
4. **`memory-progress-last-finished` 单槽位**：每轮只取一个完成项，多角色同时完成时其余完成事件丢失。
5. **`memory-progress-jobs` 全局不按角色隔离**：靠消费端各自过滤。
6. **API 层默认无超时、无取消**：只有 `roleplay`（240 秒）和 `useMemoryProgress`（8 秒）主动使用。

### 低

- `character-list-error` 全局单槽错误态，切角色不清。
- `loadCharacters`、`useAuthSession.refresh`、`useDesktopIdentity.refreshStatus` 无代次校验。
- `CharacterProfileDialog.vue` 保存时读取的是保存时刻的角色 ID。
- 服务端无全局鉴权中间件；角色归属校验靠逐个接口手写。

## 四、建议统一抽象的部分

1. 提取轻量的 `useAsyncGuard` 或 `createRequestGuard`，收敛请求代次、角色 ID 快照、忙碌守卫三件事，底层复用 `chat-session-state.ts` 的思路。
2. API 层提供可选的默认超时，让 `signal` 透传更顺手，不强改 `roleplay`、聊天等特殊场景。
3. `memory-progress` 引入完成事件队列或按角色分槽。

## 五、不应该统一或暂时不需要改造的部分

1. 服务端幂等机制（快照、忆泡、聊天三条链路）不动。
2. 服务端角色归属校验不改逻辑；共享封装单独排期。
3. 后台任务队列、租约、fencing 不动。
4. `useMemoryProgress` 的在途控制器模式保留并推广。
5. `useAsyncData` 的页面不强行改成手写模式。
6. 不把所有异步请求改造成同一种模式，不引入新依赖。

## 六、分阶段改造计划

|---|---|---|

2. `memoryProgressPollDelay` 分档测试。

# 第二部分　复审总结

## 复审结论

初审的大方向成立，但两条「高」是误报，三条「中」被高估，测试清单里一半已经存在。原定的 P1 应当撤销。

误报的根源是同一个：初审直接采用了对页面层的批量探查结果，没有核对 Nuxt 的页面 key 机制。复审把关键结论逐条对回了源码，同样没有改任何代码。

## 一、被推翻的结论

| 初审结论 | 复审结果 | 依据 |
|---|---|---|
| 高：`catchphrases.vue` 切角色后显示旧角色数据 | **不成立**。切角色时页面重建，`onMounted` 重新加载；单个实例存活期间角色 ID 不会变 | Nuxt 默认页面 key 是代入参数后的路径（`node_modules/nuxt/dist/pages/runtime/utils.js:7-13`、`page.js:97`）；侧栏切换会替换路径参数（`AppShell.vue:152-158`） |
| 高：`stickers.vue` 同上 | **不成立**，原因相同 | 同上 |
| 中：`memory-progress-jobs` 未按角色隔离 | **不是缺陷**。面板本来就要显示所有角色的任务，四处消费端都按角色过滤 | `DaysWorkspace.vue:432`、`SnapshotsWorkspace.vue:467`、`MemoryWorkspace.vue:790`、`growth/memory/index.vue:84` |
| 中：`daily-life.vue` 的 `savePlan` 可重复提交 | **不准确**。按钮带 `:loading="saving"`，界面层已挡住，只是缺函数级守卫 | `daily-life.vue:541` |
| 低：`character-list-error` 属于角色隔离缺口 | **定性错误**。它是「角色列表拉取失败」的提示，本身不分角色 | `useActiveCharacter.ts:15-36` |

连带影响：`settings/memory.vue` 的 `watch(id)` 和 `requestedId` 比对（初审推荐为范本）在这些页面里实际不会触发，属于防御性代码。

## 二、核实后仍然成立的问题（等级全部下调）

| 问题 | 位置 | 初审等级 | 复审等级 |
|---|---|---|---|
| 开关无进行中保护，快速连拨会发出两个并发更新，界面以最后返回的响应为准 | `catchphrases.vue:412`；`stickers.vue:923` | 中 | 低到中 |
| 进行中标记是单个值：点活动 X 再点 Y，X 结束时清掉 Y 的标记，Y 可被重复提交 | `daily-life.vue:109/115`、`142/148` | 中 | 低到中 |
| 每轮轮询只记录第一个完成的任务；别的角色任务排在前面时，当前页面少一次自动刷新 | `useMemoryProgress.ts:142` | 中 | 低到中 |
| API 层无默认超时，只有两处用 `signal` | `roleplay.ts:25,27`、`model-logs.ts:147,159` | 中 | 低到中 |

`catchphrases.vue` 的提交、保存编辑、扫描（第 356、476、309 行）同样有按钮 `:loading`，界面层已挡住。

## 三、初审漏掉的事实

- **两类页面，防护需求不同**：

| 页面类型 | 角色 ID 来源 | 切角色时 | 需要的防护 | 例子 |
|---|---|---|---|---|
| 路径参数型 `/characters/[id]/**` | 路径参数 | **组件重建** | 只需操作级防重复、卸载后不弹提示 | 梗语录、表情包、记忆周期设置、模型设置 |
| 查询参数型 `?c=` | 地址栏与 cookie | **组件不重建** | 请求序号、角色代际、卸载作废 | 聊天、日记手账、日常生活、角色扮演、形象档案、成长系统各页、各 Workspace |

- **竞态测试已经有了一整套**：`test:chat-session-state`、`test:memory-progress-poll`、`test:page-harness`、`test:role-switch-lock-reset`，以及 memory、snapshot、days、journal、friend、knowledge、users、growth-deliveries、reflection 各自的 `*-page-races`。初审第七节的 1、2、6 项是已有资产。
- **服务端鉴权的证据更扎实**：`server/api` 下 291 个文件中 265 个直接调用 `requireActor*`。不直接调用的 25 个里，日记组经 `requireJournalCharacter`（`journal-api.ts:10-21`）、角色扮演组经 `roleplayApi`（`roleplay-api.ts:7`）完成校验，登录、注册、健康检查本就公开。
- **真正的竞态区是查询参数型页面**，初审判定这些地方防护较好。

## 五、整理时补查的结果

- 表情包页的开关和梗语录页一样没有进行中保护（`stickers.vue:344-356`、`:923`），已确认。
- 日常生活的重复提交：服务端有唯一约束（`daily-life/activities/index.post.ts:43-44`），不会产生脏数据，只会多弹一条「已有进行中的活动」。
- **现有约定早已定过两条规则**（`docs/frontend-api-requests.md`）：「长时间生成不设置统一短超时」和「并发序号与过期结果保护由页面负责、不批量替换」。初审把前者当问题提、后者想收口成共享工具，都与约定相反。
- 新发现：本机绘画引擎探测接口（`server/api/local/draw.get.ts`）没有鉴权，只受同源校验约束。标为低优，超出本次范围。
- 工作日志里上午记录的「`memory.vue` P0 竞态」按同样的理由不可达，`743f5c7` 的修复没有害处。
