## 9. 环境运行边界

- Web、Scheduler、Worker、QQ适配器、B站适配器是不同执行者；页面能打开不说明后台在工作。
- 为审查代码启动进程前，先核对现有进程与端口，避免重复执行任务。
- Worker/真实渠道可能调用付费模型或产生外部动作，未授权不启动。
- 整个项目统一Yarn，不混装npm/pnpm，不提交额外lock。
- 保留数据库/容器/角色卡格式等旧基础设施标识，不因品牌名改动而重命名。
- 全局/本人私人/外部身份记忆严格分离；删除会话不应删除已经形成的记忆。
- 清理/回填脚本先读源码和dry-run，不能为验收随手在真实数据上`--apply`。

## 阶段总结版本与生成流程专项记录（2026-11-05，续）

- 立即归档的周期缺口：复用在途任务时旧实现按请求时刻 `now + 间隔` 推进 `nextSnapshotAt`。旧 `RETRY_WAIT` 任务只归档到自己的结束点，游标却跳到 `now + 间隔`，调度器下一轮反推就会永久跳过中间那段。现改为按**实际归档到的 `periodEnd` + 间隔**推进，且只在本次目标全部成功时推进；剩余缺口由下一次点击或调度器从最新自动归档的结束点接着补。
- 并发排期：在途检查与入队原来在事务外，幂等键含各请求的毫秒 `now`，两个并发请求会各排一份重叠周期、都写 `CURRENT`。现在排期在范围行的锁内完成（与手动版本、Worker 提交同一把锁），第二个请求复用第一个刚排的任务。新增 DB 回归用区间门闸模拟真实并发。
- 只执行目标任务：立即归档原来调用无 `jobId` 的 `processNextMemoryJob`，会把队列里的忆泡/清理任务先跑掉并混进报告；现在只传本次的 `jobId`，回归断言无关清理任务的 `status` 与 `attemptCount` 未变。
- 不再因「已有更晚的总结」作废在途任务：那只是说明后面有归档，不代表中间那段已经归档过。现在只有该任务覆盖的区间确实被一份自动总结完整覆盖时才作废，且在途任务按周期最早的一条优先。
- `pending` 现在包含 `RUNNING`，运行中的任务不会被当成已完成而提前推进游标。
- AI 重新提炼去重：在途检查原来在事务外、且按单个快照 ID 匹配，双击或两个标签页会各排一条。现在在范围行锁内按**逻辑快照 `snapshotKey`** 匹配（覆盖该快照的所有历史版本），重复提交返回同一条任务并带 `duplicate: true`。手动版本同样在该锁内读最大版本号再写新版本，与 Worker 的版本提交串行。
- 调度器原子性：全局任务和周期游标在一个事务里，主人私聊与朋友范围的任务却在提交后才补排。进程在两步之间退出，游标已前进、这些范围的该周期永远不会再排。现在三类范围与游标在同一事务提交；朋友范围查询失败不再 `catch` 成空数组静默成功，而是整体回滚并在下一轮重试。
- 新增隔离回归：`scripts/test-snapshot-generate-db.ts`（复用在途任务的周期连续性、并发单周期、定向执行、同一逻辑快照只排一条 AI 重提炼）、`scripts/test-memory-scheduler-atomic-db.ts`（注入主人私聊入队失败，断言全局任务与游标一起回滚、下一轮三个范围全部补上）。
- 最终验收：49 个 migration、15 个隔离数据库脚本通过，临时库已删除；完整 `yarn typecheck`、50 个 SFC、`yarn lint`（0 error / 126 既有 warning）、OpenAPI YAML 解析与 `yarn build` 通过；无真实业务库写入、付费模型或渠道副作用。
- 遗留：`yarn check:privacy` 仍报 42 处可疑内容，分布在 12 个文件（`server/utils/group-activity-stats.ts`、`onebot/group-chat.ts`、若干 `scripts/test-*.ts` 与一篇笔记），均不在本专项改动范围内，未修改。

### 已确认的问题与风险

1. **高优先级：普通值班流的公开评论没有经过发布前脱敏。**
   - `server/utils/channel-adapter/bili/duty-pipeline.ts`：`judgeVideo()` 从模型输出提取评论；`deliverComment()` 只做 trim/长度截断就写入临时文件并执行 `bili comment post`，调用前没有 `sanitizePublicText()`。
   - 同一项目的主人投稿评论路径 `owner-watch.ts` 已调用 `sanitizePublicText()`，动态路径 `buildDynamicText()` 也调用了它；普通推荐流评论却漏掉这一道。
   - 影响：模型若把私密称呼、主人相关内容、@ 提及或长数字写进评论，会被直接公开。提示词约束不能替代代码侧发布前校验。
   - 建议：所有公开评论统一走同一个发布边界，脱敏后为空则跳过；增加普通值班流评论的脱敏回归测试。现有脱敏器不是完整语义 DLP，不能宣称能拦截所有隐私泄露。

2. **高优先级：手动值班与定时值班之间没有共享的跨进程执行锁。**
   - 手动入口 `server/api/admin/bili/run-round.post.ts` 直接调用 `runDutyRound()`。
   - 定时入口 `scripts/run-bili-adapter.ts` 的 `inFlight` 只是该 Node 进程内的 Set；它无法阻止 Web 服务进程同时启动同一 binding 的值班。
   - `runDutyRound()` 在执行完外部投递后才写报告；`roundIndex` 也是先从旧报告计算。并发时可能重复评论/私信/互动，或在末尾撞报告唯一约束，但外部动作已经发生。
   - 建议：手动入口和定时入口共用数据库级 per-binding lease/锁，必须在任何外部副作用之前成功认领；增加并发验收，确认同一 binding 只能有一个活动轮次。

3. **中高优先级：CLI 命令写操作保护依赖前端传来的 `itemId`，没有核对真实 `argv`。**
   - `server/api/admin/bili/run.post.ts` 根据 `itemId` 查询 catalog 的 `write` 标记；没有验证 `argv` 是否与该 catalog 项匹配，也没有拒绝未知/缺失 `itemId`。
   - 例如把只读命令的 `itemId` 与 `video coin`、`comment post` 等写命令的 `argv` 组合，服务端就可能不追加 `--dry-run`。接口仍有管理员鉴权，因此这不是匿名越权，但服务端安全护栏可被请求内容不一致绕过。
   - 另一个具体遗漏：catalog 的 `owner.set` 会改 bili CLI 的主人配置，但没有标记 `write: true`；专用 `owner.put.ts` 也明确说明它是真写操作。
   - 建议：服务端从可信 catalog 生成 argv，或严格校验 argv 与 catalog 命令定义一致；未知命令拒绝执行；把 `owner.set` 纳入写操作保护，并增加路由级测试。

4. **中优先级：值班窗口内遇到“没有候选”等提前返回时，调度器可能每分钟重复跑同一轮。**
   - `scripts/run-bili-adapter.ts` 每 60 秒扫描；`refreshState()` 用 `BiliRoundReport.createdAt` 重建窗口已运行标记。
   - `server/utils/channel-adapter/bili/duty-pipeline.ts` 在没有候选（以及部分模型配置/额度错误）时提前返回，尚未执行最后的报告写入事务。
   - 因为没有报告时间戳，下次扫描仍可能判定当前窗口未运行，在同一窗口里重复拉推荐/热榜/搜索并重复撞同一个错误。
   - 建议：把“窗口尝试/结束状态”与“日报内容”分开持久化；无候选、认证失败、模型未配置等结果也要明确记录，按错误类型决定是否允许重试，而不是仅靠日报时间戳判断窗口是否跑过。

5. **中优先级：同一个 B站连接绑定多个角色时，部分动作额度和去重按 binding 计，不按账号计。**
   - `configure.ts` 会加载连接下所有活动 binding；`run-bili-adapter.ts` 会逐个 binding 跑值班。
   - 主人投稿互动的 `owner-done`、每日投币计数等都按 `bindingId` 查询；Prisma 的 `BiliAction` 也只保存 `bindingId`，没有账号级唯一键/额度锁。

   - 建议：先明确产品规则是“一账号只允许绑定一个角色”还是“一个账号多角色共用动作额度”。若支持多角色，账号级动作去重与额度应以 connection 为边界，角色自己的记忆/日报仍按 binding 隔离。

6. **功能缺口待确认：多账号配置目录与网页扫码登录没有按账号打通。**
