## 9. 环境运行边界

- Web、Scheduler、Worker、QQ适配器、B站适配器是不同执行者；页面能打开不说明后台在工作。
- 为审查代码启动进程前，先核对现有进程与端口，避免重复执行任务。
- Worker/真实渠道可能调用付费模型或产生外部动作，未授权不启动。
- 整个项目统一Yarn，不混装npm/pnpm，不提交额外lock。
- 保留数据库/容器/角色卡格式等旧基础设施标识，不因品牌名改动而重命名。
- 全局/本人私人/外部身份记忆严格分离；删除会话不应删除已经形成的记忆。
- 清理/回填脚本先读源码和dry-run，不能为验收随手在真实数据上`--apply`。

## 阶段总结版本与生成流程专项记录（2026-11-05，续）

- 立即归档的周期缺口：复用在途任务时旧实现按请求时刻 `now + 间隔` 推进 `nextSnapshotAt`。旧 `RETRY_WAIT` 任务只归档到自己的结束点，游标却跳到 `now + 间隔`，调度器下一轮反推就会永久跳过中间那段。现改为按**实际归档到的 `periodEnd` + 间隔**推进，且只在本次目标全部成功时推进；剩余缺口由下一次点击或调度器从最新自动归档的结束点接着补。
- 并发排期：在途检查与入队原来在事务外，幂等键含各请求的毫秒 `now`，两个并发请求会各排一份重叠周期、都写 `CURRENT`。现在排期在范围行的锁内完成（与手动版本、Worker 提交同一把锁），第二个请求复用第一个刚排的任务。新增 DB 回归用区间门闸模拟真实并发。
- 只执行目标任务：立即归档原来调用无 `jobId` 的 `processNextMemoryJob`，会把队列里的忆泡/清理任务先跑掉并混进报告；现在只传本次的 `jobId`，回归断言无关清理任务的 `status` 与 `attemptCount` 未变。
- 不再因「已有更晚的总结」作废在途任务：那只是说明后面有归档，不代表中间那段已经归档过。现在只有该任务覆盖的区间确实被一份自动总结完整覆盖时才作废，且在途任务按周期最早的一条优先。
- `pending` 现在包含 `RUNNING`，运行中的任务不会被当成已完成而提前推进游标。
- AI 重新提炼去重：在途检查原来在事务外、且按单个快照 ID 匹配，双击或两个标签页会各排一条。现在在范围行锁内按**逻辑快照 `snapshotKey`** 匹配（覆盖该快照的所有历史版本），重复提交返回同一条任务并带 `duplicate: true`。手动版本同样在该锁内读最大版本号再写新版本，与 Worker 的版本提交串行。
- 调度器原子性：全局任务和周期游标在一个事务里，主人私聊与朋友范围的任务却在提交后才补排。进程在两步之间退出，游标已前进、这些范围的该周期永远不会再排。现在三类范围与游标在同一事务提交；朋友范围查询失败不再 `catch` 成空数组静默成功，而是整体回滚并在下一轮重试。
- 新增隔离回归：`scripts/test-snapshot-generate-db.ts`（复用在途任务的周期连续性、并发单周期、定向执行、同一逻辑快照只排一条 AI 重提炼）、`scripts/test-memory-scheduler-atomic-db.ts`（注入主人私聊入队失败，断言全局任务与游标一起回滚、下一轮三个范围全部补上）。
- 最终验收：49 个 migration、15 个隔离数据库脚本通过，临时库已删除；完整 `yarn typecheck`、50 个 SFC、`yarn lint`（0 error / 126 既有 warning）、OpenAPI YAML 解析与 `yarn build` 通过；无真实业务库写入、付费模型或渠道副作用。

### C. 设计规则（后续实现必须遵守）

1. **身份与交流权限始终分开**：HUMAN / AI / UNKNOWN 回答“对方是谁”；DEFAULT / ALLOW / BLOCK 回答“当前角色是否与对方交流”。不得合并成一个字段。
2. **人工判断优先级最高**：MANUAL 分类不可被自动识别覆盖；自动识别只补充未人工确认的身份。
3. **权限隔离保持现状**：身份类型按平台账号共享；交流策略按角色关系隔离。未来增加群级覆盖时必须写清策略优先级。
4. **BLOCK 是硬限制**：被明确禁止的对象不能因为 @、话题续聊、群聊模式或其他入口而绕过。
5. **连聊保护不等于身份识别**：连续 AI-only 轮数只统计已确认且被允许交流的 AI；UNKNOWN 不应被擅自当作真人或 AI。
6. **不破坏已有记忆**：调整交流权限只影响后续上下文与处理策略；历史原文、长期记忆、阶段总结的回溯变更必须单独设计、可审计并经用户确认。

### 登录 / 注册链路审查发现的待确认项

- 注册接口调用登录失败计数作为限流依据，但当前仅在注册成功后写入 `recordLoginAttempt(... succeeded: true)`；注册失败尝试没有形成独立的失败计数。因此需确认注册限流是否实际有效，并评估是否需要独立的注册频率记录/限流策略，避免把登录失败统计和注册频率混用。
- 登录验证密码与创建 Session 是两个独立步骤。需审查密码重置/账号停用与登录请求并发时，是否可能出现旧密码已通过验证、管理员已撤销会话、但登录请求随后又创建新会话的竞态；若存在，应在服务端用事务/锁或重新校验凭据版本，确保密码/账号状态变更后不会遗留新会话。
- `resolveSessionUser()` 先读取会话状态，再异步刷新 `lastUsedAt`；刷新只改最后使用时间，不会恢复撤销状态，但仍应覆盖并发撤销测试，确认旧请求不能重新使会话有效。

### 登录 / 注册链路修复与验收结果（2026-11-07）

针对上面三条待确认项的落地结果：

- **并发注册回落成 500**：已确认存在。两个请求同时通过查重后，落败的一方把 Prisma `P2002` 暴露成 500。现在捕获唯一约束冲突并按 409 返回，账号仍然只会有一条。
- **注册失败没有计数**：已确认存在。重复邮箱在查重处直接抛 409，没有写 `loginAttempt`，因此可以无限次探测邮箱是否已注册。现在重复注册（含并发落败）都会写入一次失败尝试，复用登录的按邮箱/按 IP 限流：同一邮箱连续 5 次失败后第 6 次返回 429。
- **旧密码并发登录**：已确认存在。登录在应用层校验密码后再建会话，中间窗口内管理员重置密码，会让旧密码开出的新会话逃过撤销。现在新增 `createSessionForVerifiedPassword()`：在事务内对账号行 `SELECT ... FOR UPDATE`，比对刚才校验过的密码哈希与账号状态，再从同一事务插入会话。重置事务更新同一行，两者因此严格串行。

`server/api/auth/login.post.ts` 相应改为"验证通过 → 事务内建会话 → 再记成功"，旧密码窗口期被拒时按登录失败计数与审计。
