# 记忆系统与周期快照规则

## 1. 数据层次

### 原始消息与事件
保存标准化消息、平台事件、发生时间、来源平台标识和去重信息。它是记忆提炼的依据，可按独立的原始消息保留政策过期清理。

### 周期快照
按配置时间间隔归档一段经历。默认间隔 3 天，角色可设置 1–8 天（2026-11-03 从 1–365 收紧）。快照包含阶段摘要、重要事件、事实/偏好变化、关系、目标/承诺、未解决事项和相对上一份快照的变化。

**手动跑一次（2026-11-05）**：本地开发常常没起调度器，周期任务就不会自己来。`POST /characters/{id}/snapshots/generate` 按 `[now - 间隔, now)` 为全局与主人私人范围各排一条 `GENERATE_SNAPSHOT`（幂等键沿用调度器的 `auto-snapshot:{scope}:{start}:{end}`），排完当场驱动 Worker 执行；真的产出总结后把 `nextSnapshotAt` 推进到 `now + 间隔`，避免调度器醒来把同一段再归档一遍。

它和页面上的「手动存档」不是一回事：后者是 `kind = MANUAL`，不调模型、只存当下的结构化副本（`generatedBy: "manual"`），也不进 AI 总结的版本链。界面用「立即 AI 归档」和「手动存档（不调模型）」两个按钮区分，列表里对应的徽标是「AI 总结」和「仅存档」。

### 长期记忆
保存之后仍然有价值的事实、偏好、关系和承诺。长期记忆有自己的生命周期，不能仅因为来源消息到期就自动删除。

### 忆泡（事件层）
一条「某天发生了什么」的记录：发生时间、模糊时段、地点、参与者、事件、详情、关键词、来源消息与置信度。它与长期记忆的分工是**事实 vs 结论**：

- 忆泡只追加，不覆盖；新 `ev:v2:` 去重键使用角色本地日期 + 会话 + 规范化整标题（范围仍由数据库唯一约束限定）。旧记录按实际本地日、会话及规范化标题识别，不沿用 UTC 日期碰撞。只凭公共六字或相同人物不足以证明同一事件，改写标题可能保留重复，优先避免不同事项被静默吞掉。
- 长期记忆可以新增、替代、失效；忆泡不会因为后续总结而改写。
- 忆泡只由按天任务产出（2026-11-01 起）：周期快照读当周期的忆泡，不再顺带产出 `events`；**重新提炼（历史重放）也不写忆泡**。
- 除此之外，调度器**每天**为「昨天」排一个 `EXTRACT_EVENTS` 任务，单独整理当天忆泡（收口幂等键 `events-final:{scopeId}:{dayKey}`，当天没有对话就不排）。忆泡不等快照周期，第二天的对话第二天就能查到。该任务只写忆泡，不写快照和长期记忆；`autoSnapshotEnabled` 关闭时不排，避免绕过用户选择产生模型费用。
- **历史补排**：每轮、每个允许的范围最多补排 **24 个有原文的历史日期**（包含昨天，不含今天/未来），按角色时区从旧到新取。查询在限额**之前**排除 `memory_event_days.state = FINAL` 的日期和已有 `events-final:` / 旧版 `daily-events:` 任务；已持久化的任务就是扫描进度，下一轮会继续后面的缺失日期，不依赖进程内游标，也不会永远卡在最老的 24 天。已有收口任务不分状态（包括 FAILED / CANCELLED）都不会复制，失败或取消需在任务监控中重试；只有小时任务的 DRAFT 日期仍可补排收口。补排同样受 `autoSnapshotEnabled` 控制，范围仍是全局 + 主人私人 + 非主人外部身份的 `c:` 私聊，外部范围里的旧群会话不会触发补排。幂等键唯一约束防止并发扫描重复入队；不新增补排游标表。**有界的是每轮返回日期/入队数量，不是数据库扫描行数**，长历史仍可能增加查询成本；原文已清理的缺失日期无法恢复，已标 FINAL 的旧日期不会自动重开。无数据库/模型调用回归：`node node_modules/tsx/dist/cli.mjs scripts/test-memory-event-backfill.ts`。
- 忆泡有「还在长」的状态：`DRAFT`（当天或尚未完整抽取，继续追加）与 `FINAL`（历史日期已完整收口）。`memory_event_days` 记录每天的进度，`extractedAt` 之后的消息才算增量；调度器每小时排一次当天增量（`events-hour:{scopeId}:{dayKey}:{hour}`，最近一小时没有新消息就不排），夜间排 `events-final:{scopeId}:{dayKey}` 收口。查询不区分状态 —— 「今天做了什么」读 DRAFT，「前天」读 FINAL。
- **原文兜底**：忆泡有小时级产出延迟，超过最近对话窗口、又还没进忆泡的那一段靠原始消息补。问句指向某一天时，先查那天的忆泡，再按同一时间区间查原文（`server/utils/message-retrieval.ts`，预算 `rawMessageTokenBudget` 默认 900、`rawMessageLimit` 默认 6，已进对话窗口的消息不重复注入）。原文是未整理的证据，提示词要求「只当证据、不当结论，与忆泡冲突时以忆泡为准」。原文过了保留期就真的没了，那时只能靠忆泡与快照 —— 这是保留策略的取舍，不是检索缺陷。
- 只有能落到具体日期、且有来源消息支撑的事件才会写入；没有日期的泛泛而谈、群友之间与她无关的闲聊不记。
- 检索时先按问句里的日期框住那一天（支持今天/昨天/前天/N 天前/上周三/本周三/2026-10-25/10月25日/上午·下午·晚上等），框不住才退化成关键词；`participants` 目前是显示名，**不是身份引用**，跨平台同名不合并。
- 忆泡与长期记忆一样受范围隔离：只读 `resolveChatMemoryScopes()` 放行的范围。
- **群聊归属**：群消息落库时带 `metadata.mentionTargets`（`self` / `other` / `all`），提炼时逐条交给模型，用来判断「这句话是不是冲她说的」——群里同时跑着别的 bot 时，别人 @ 另一个号说的话很容易被记成「群友说她」。历史数据没有这个字段，可用 `yarn backfill:mention --apply` 从正文的 `@数字` 回填（幂等，已有值的会跳过）。2026-10-31 实测：回填 799 条后重跑当天，同一件事从「群友嫌她『我认』AI 味太浓」变成「有人立誓不再说『我认』」。

#### 参与者身份引用

`participants` 是显示名（模型抄来的，会改名、会重名、群聊里可能是 `member_3`），单独用它回答不了「和小明都经历过什么」。所以忆泡另存一列 `participantRefs`：

```json
[{ "kind": "self" },
 { "kind": "owner" },
 { "kind": "external", "platform": "qq-onebot", "externalId": "10000006" }]
```

- **推导方式**：从证据消息的作者来，不经过模型 —— `ASSISTANT` → `self`，`isOwner` → `owner`，其余带 `authorOpenId` 的 → `external`；
- 同一个人只记一次；拿不到账号的消息跳过（宁缺勿编）；
- `external` 项带 `displayName`（当时的渠道昵称）：昵称会改，留着才能回溯「那时他叫什么」；
- 显示名仍以 `participants` 为准，引用只回答「是谁」；
- 历史数据用 `yarn backfill:participants --apply` 回填（幂等，已有 refs 的跳过；证据消息被清理过的补不了引用）。

跨平台同一个人**不会自动合并**：合并必须走验证绑定流程，这里只给出 `platform + externalId`。

#### 参与者显示名清洗（2026-11-03）

`participants` 长期有三个毛病：群聊里模型认不出人时写「群友」，等于没记名字；把角色自己写进「相关人物」；改名后名字和引用对不上。2026-11-03 实测：87 条忆泡里 37 条（43%）带「群友 / 群成员 / 对方」这类泛称，82 条没有 `sourceMessageIds` 可供回溯 —— 有一条写着「群友」和角色打趣的忆泡，答题的人已经彻底查不出来了。整条链分三段修：

- **抽取时看得见人**：`MemoryAiMessage` 补 `speaker` / `member`，`memory-worker.ts` 的 `toAiMessage` 从 `readMessageSpeaker()` 取值。以前模型只拿到 `role: user` + 正文 + `origin`，只能在正文里猜发言人，猜不出就写「群友」。手账链路（`journal-ai.ts`）一直带着这两个字段，忆泡这条漏了同一个修复。提示词同步加三条硬规矩：不写自己、群聊必须写 `speaker` 里的具体名字、分不清就写空数组。
- **落库前确定性校正**：`resolveEventParticipants()`（`memory-change-apply.ts`）不经过模型做三件事 —— 剔掉她自己（靠 `ctx.characterName`）；证据里**恰好剩一个**没被点名的人时，把泛称换成那个真实昵称；证据里的人都已点名（说明「群友」是模型把同一个人写了两遍）时让泛称退场。候选多于一个就保留泛称：写错人比没写更糟，但「当时有别人在」这个信息也不能丢。
- **清洗排在判重之前**：近似判重拿 `participants` 算交集，未清洗的「群友」之间永远有交集，会把两条本来不同的事吞成一条。

存量清洗用 `yarn backfill:participants --apply`（预演不带 `--apply`，会打印每条的名字变化）。它对**所有**忆泡跑一遍确定性规则：剔自己永远做（不需要证据），泛称换名只在证据消息还在时做。`sourceMessageIds` 为空的旧忆泡只能剔自己 —— 没有证据就补不出名字，这部分只能靠她在对话里重新提起才会生成新的忆泡。

#### 私聊覆盖范围（2026-11-01）

按天任务的范围跟着 `memoryScope` 走：`CHARACTER_GLOBAL` + 角色主人的 `USER_PRIVATE` + **每个有 `c:` 私聊会话的 `EXTERNAL_IDENTITY` 范围**（主人自己 QQ 的老范围除外，见下）。

| 私聊类型 | 会话挂在哪 | 排按天任务 |
| --- | --- | --- |
| 桌面对话（`channelBindingId = null`） | `CHARACTER_GLOBAL` | 是 |
| 主人 QQ 私聊（`speaker.isOwner`） | 主人的 `USER_PRIVATE` | 是 |
| 群友私聊 | 该账号的 `EXTERNAL_IDENTITY` | 是（私聊也算她这一天的记忆） |

- **先落库，再回不回**：私聊消息在模型检查（模型未配 / Key 解密失败 / 额度用完）之前就写进 `messages`，生成失败、进程崩在模型调用里也一样留得下；预落库标 `storedReason: "recorded"`，幂等靠 `(conversationId, externalMessageId)` 唯一键。图/语音转成文字后会同步更新那一行的正文。
- **私聊不进原文清理**：`CLEAN_EXPIRED_MESSAGES` 只删群会话与桌面会话的过期原文，`c:` 私聊全部保留 —— 否则还没整理成忆泡的那几天会被直接抹掉。历史遗留的群会话即使挂在同一个 `EXTERNAL_IDENTITY` 范围里，也仍按保留策略清理。
- **私聊忆泡只读 `c:` 会话**：外部身份范围里可能还挂着历史群会话，按天任务与调度器都只把 `c:` 会话当作「今天有私聊」，群消息不会触发某个人的私人时间线。
- 桌面对话没有渠道账号，USER 消息按主人处理（`readSourceMessageIsOwner`）。不标的话，桌面对话的 `participantRefs` 只剩一个 `self`，读起来像「她自己跟自己发生了这件事」。
- 主人私聊的会话可能早于 `USER_PRIVATE` 功能创建，还挂在该 QQ 的 `EXTERNAL_IDENTITY` 上；会话按 `(binding, externalConversationId)` 唯一、找到就复用，所以主人下次开口时把它归位到主人范围（`resolveOwnerPrivateScopeRepair`），手动「立即整理」也会先做一次归位。只往主人方向搬，不往回搬 —— 猜错等于把主人的私聊暴露给外人。归位时把这条会话已写进旧范围的忆泡一起搬过去（`memory-event-move.ts`），并重算两边的当天条数。只有两边都 FINAL 才保持收口；任一边未完成或缺少进度时，将目标日期改为 DRAFT 并清空时间与消息游标，宁可去重重读，也不把另一范围的较大水位当成目标已处理进度。若目标日期已有成功的收口任务，需手动重新整理/重试，补排器不会另造任务键重开已存在的任务。**主人自己 QQ 的外部范围不排按天任务**（调度器按 `metadata.ownerQq` 识别）：写进那里的事件主人在私聊里读不到，归位后还会重复提一遍；等会话归位后由 `USER_PRIVATE` 正常整理。私聊检索同时带主人自己 QQ 的旧身份范围，老记忆不会因为归位而读不到。
- **一条忆泡只归属一个会话**：虽然分页块可包含桌面、群聊与私聊消息，但每个块按会话分别请求模型，事件只能引用该会话的新消息及同会话前文。混合会话来源作为完整块失败并回滚，不再按最早证据截来源、却留下混写正文。
- **记录入口**：记忆页「已记录对话」的「私聊记录」抽屉（接口 `GET /characters/{id}/private-chats`）按 QQ 号列出私聊（最多 50 个），默认最近 200 条、用 `before` 往前翻；只列 `c:` 会话，桌面本地对话仍走 `/chat`。
- 手动「立即整理忆泡」与调度器同范围（全局 + 主人私聊 + 各群友私聊）。同小时新消息通过进度游标检测后可重排已完成增量；不重开已完成 FINAL，不抢占 RUNNING，也不自动复活 FAILED/CANCELLED。worker按目标 jobId 执行，避免一个角色的手动请求顺带运行同 owner 的其他任务。
- 群聊规则的提示词段落明确限定 `origin` 以「QQ群 」开头：私聊和本地对话里对方说的每句都是对她说的，模型不能拿「没 @ 她」当理由漏记私聊事件。
- **边界**：8 天快照与日记/手账仍只取全局 + 主人私人范围，群友私聊只产出按天忆泡、不生成长期记忆与手账素材。要扩到长期记忆需要先决定「别人的私聊记忆存哪、给谁读」。
- 回归测试：`yarn test:private-chat-events-db`（覆盖 / 参与者引用 / 跨会话收口 / FINAL 进度）、`yarn test:owner-private-scope-db`（老会话归位 + 模型不可用时先落库）、`yarn test:memory-scheduler-db`（私聊范围排程 + 清理豁免）、`yarn test:memory-event-move-db`（归位时忆泡搬家与当天条数重算）、`yarn test:memory-events-db`（跨会话收口单测）。

#### 快照读忆泡（2026-11-01 起）

周期快照不再从零散消息重造事件：worker 先查出该周期的忆泡（`periodEvents`，按时间升序、最多 80 条）交给模型，提示词写明「periodEvents 就是发生过什么的权威时间线，summary / importantEvents 以它为准，messages 只用来提炼偏好、关系、情绪与结论」；同时 `emitEvents: false`，模型不再产出 events，服务端也不再写忆泡。

分工因此是一条直线：

| 产出 | 谁负责 | 频率 |
| --- | --- | --- |
| 忆泡（事实） | 按天任务（每小时增量 + 夜间收口） | 每天 |
| 总结 / 长期记忆（结论） | 周期快照，**读**当周期的忆泡 | 每个周期（默认 3 天） |

好处是同一天不会被两套规则各判一次（以前快照顺带产 events，会和按天任务撞 dedupeKey，行为取决于谁先跑）。调度器停机错过的日期在恢复后会有界补排，但补排入队不等于 Worker 已完成：积压尚未处理时，周期仍可能没有忆泡可读，快照仍能出总结；历史快照不会因后来的忆泡补齐而自动重写。`watchdog` 的 `scheduler_stalled` 仍用于提醒排期停滞。

#### 忆泡去重（三层）

重跑同一天、或每小时增量与夜间收口重叠时，同一件事很容易被写两遍。去重按三层从松到紧：

1. **精确键**：`ev:v2:` 键含角色本地 `dayKey`、会话 ID 与 NFKC/大小写/标点空白归一化后的完整标题。UTC 跨日同标题与不同会话的同标题互不碰撞。
2. **旧数据兼容**：历史记录不迁移；按本地日、会话与归一化完整标题查重，不把旧 UTC 哈希碰撞当成重复事实。
3. **保守判重**：`isNearDuplicateEvent` 只在归一化完整标题相同时认作重复。不再凭公共子串长度或相同参与人猜测语义；改写标题可能留下重复，这是避免静默丢失不同事实的取舍。`existingEvents` 提示模型避免重述，重复条目仍可人工隐藏。

真实模型的同义去重效果尚未重新评测；本地确定性测试只验证键隔离与不会误吞不同完整标题。

#### 分块抽取（按天任务）

按天抽取要的是**覆盖**，不是「每会话公平取样」。改前有两道截断叠加，一天几百条时大部分内容根本没进模型：

1. 来源选择层：每会话 80 条 / 全天 250 条（这套配额是给 8 天快照设计的）；
2. 进模型前再截成「最早 60 + 最新 60」= 120 条。

2026-10-31 实测：一晚上 368 条，只有 80 条进了模型，全天只出 10 条忆泡。

现在的做法（`runDailyEventJob`）：

- 每轮读取最早尚未处理的 `120 × 8`（`EVENT_AI_CHUNK_SIZE` × `MAX_EVENT_CHUNKS`）条，额外读 1 条探测积压，按 `(occurredAt, id)` 正序 keyset 分页，不再用最新消息抽样冒充全天覆盖；
- 进度持久化为 `MemoryEventDay.extractedAt + extractedMessageId`，同一时间戳的消息也能跨轮继续；老的 timestamp-only 进度会包含边界重读，靠事件去重兜底，宁可重读而不漏。仍有积压时保持 DRAFT，并把同一个任务退回 RETRY_WAIT 继续处理，只有完整处理后才 FINAL。**升级须先按正常迁移流程应用 `20261105010000_memory_event_message_cursor` 并重新生成 Prisma Client**（新增可空消息游标字段；补排逻辑本身不需要额外迁移）；不要未经备份直接对重要数据库执行测试或迁移。
- 每个原始块按会话分别调模型；所有会话子组成功后**整块立刻落库**，事件与游标同事务。某个子组超时或失败时，该块不推进，已提交的前块成果保留，重试从失败块继续；
- 已记过的事件按会话传入 `existingEvents`，本块前面实际落库的事件才加入后续已知列表，不能用被拒草稿污染后续判重；同会话最多带六条严格早于本块首条的前文，前文不能单独产生事件；
- 每块打一行日志：`[events] {day} 第 i/n 块：输入 X 条（本批 Y 条），N 个会话请求，模型给 N 条，落库 M 条`，少了事件时不用猜是哪一环。
- 回归：`yarn test:memory-event-pagination` 无数据库写入；`yarn test:memory-reliability-isolated` 会创建独立的本机临时数据库、应用迁移并运行数据库回归，结束后删除该临时库（需要本地账号具备建库权限），不会把测试写进业务库。

同一晚上的重跑结果：6 块全部跑完，落库 8 条，10-31 从 17 条涨到 25 条，20:00 之后那段（之前完全没进模型）补出 8 条。

**超时配置是这条路线的隐性前提**：`.env` 里 `LLM_TIMEOUT_MS=60000` 会把每块卡在 60 秒（思考型模型一轮块级抽取常常 60~120 秒），表现为「每块都 abort、任务进重试、事件一条不落」。默认值已调到 180 秒，本机 `.env` 也要一起调。

#### 分层保留（按 storedReason）

清理任务分两档删原文：

- **纯上下文行**（`metadata.storedReason` 为 `silent` 或 `context`）：只保留 **7 天**。它的作用只是「理解当时在聊什么」，一周后回顾价值很低。两档的区别是她看没看见：
  - `silent`：她看过但没开口的那一轮；
  - `context`：**主人在群里说的话**，这一轮被闸门挡下（概率/日上限/群规限流），她没看见，但私聊里要能接上（`cross-channel-context.ts`）。它只服务「刚才那两小时」，留一个月没有意义，而且会跟着群消息量一路涨 —— 别把它并进证据类。
- **证据类**（`replied` / `mentioned`）：按角色设置的保留天数走（新建角色默认 30 天）。

Prisma 的 JSON 过滤器没有 `in`，上面两档写成 `OR` 两个 `equals`（`memory-worker.ts`）。改的时候不要图省事换成字符串比较，那会一条都删不掉，而且静默失效。

上下文窗口取 `min(7, 角色设置)` —— 用户填的数字更小时以用户为准。两档都受同一个清理开关约束（`rawMessageCleanupEnabled` 默认关），审计里额外写 `contextCutoff` / `contextMessages`。

## 2. 周期时间规则

- 每个记忆范围有自己的启用锚点与周期设置。
- 时间戳以 UTC/标准化时间存储，显示和日历计划使用范围配置的 IANA 时区。
- 周期使用左闭右开区间：`[period_start, period_end)`。
- 下一周期从当前周期的结束边界开始。
- 修改周期默认在当前周期结束后生效，不回溯修改已归档内容；等待生效的间隔保存到 `pendingSnapshotIntervalDays`，当前周期仍使用 `snapshotIntervalDays`。
- 选择“立即重算”时更新当前生效间隔并清除待生效值；选择“下一个周期”时只设置待生效值，调度器在周期边界切换后再推进后续周期。
- 原始消息清理默认关闭。只有 `rawMessageCleanupEnabled` 开启且保留期限为正数时，未来清理任务才允许删除过期原始消息；永久保留时不应排入清理任务。
- 手动生成快照默认不改变自动计划时间，且应记录覆盖范围与快照类型。
- 周期内没有活动时可以跳过模型调用，但必须记录跳过原因并推进计划。

例：锚点为 2026-11-01 00:00，时区 Asia/Shanghai，周期 8 天；首段为 [11 月 1 日 00:00, 11 月 9 日 00:00)，下一段从 11 月 9 日 00:00 开始。

## 3. 快照内容与来源

每份快照需要保存：
- 覆盖起止时间与快照类型。
- 简短总结。
- 重要事件。
- 事实与偏好变化。
- 关系变化。
- 目标、承诺与待办。
- 尚未解决的话题。
- 相比上一份快照的差异。
- 模型、提示模板等生成元信息。
- 来源记录关联。

事实应尽可能能追溯到来源。对不确定信息应保留置信度或标记为推断，不得把推测当作确定发生的事件。

## 4. 长期记忆生命周期与回收站

- `ACTIVE` 表示当前有效；`ARCHIVED` 表示暂时收起；`INVALIDATED` 表示已经确认不再成立；`SUPERSEDED` 表示已有新记忆替代。
- 移入回收站使用 `TRASHED` 状态，并保存移入前状态与时间。回收站条目不应出现在普通记忆时间线或当前检索集合中。
- 恢复时回到移入回收站前的状态；普通状态编辑不能绕过回收站。
- 永久删除仅能对回收站条目执行：删除当前 `MemoryItem`，但不改写已有快照。快照中已保存的内容副本和来源记录继续保留；来源外键置空后，来源标识仍保留以便解释历史版本。因此，永久删除当前条目不等于抹除所有历史快照中的相关文字。

## 5. 版本规则

同一逻辑快照可以有多个版本。重新生成时创建下一个版本，旧版本标记为 superseded/已被替代并保留以便追溯。人工修正应保留修订审计；不得无痕覆盖历史版本。

需要通过数据库约束防止同一快照逻辑键的版本号重复。自动任务的幂等键与版本号是不同概念：任务重试不应无意创建重复的有效版本。

## 6. 记忆范围

- 每个角色都有一个 `character_global` 全局范围。
- 当有明确内部用户身份时，可按角色与用户组合创建 `user_private` 私人范围。
- 无法验证跨平台关联时，应保留为独立外部身份，不得仅凭昵称合并。
- 快照和记忆检索必须严格限制在当前允许的范围。

建议使用确定性的 `scope_key`，并对其设置唯一约束。实际 key 规则以数据库模型为准。

## 7. 可靠性

- 到期周期任务写入持久化任务表。
- 通过幂等键和唯一约束避免重复处理。
- Worker 领取任务时需处理并发争用。
- 任务成功必须包括数据持久化成功。
- 失败任务保存错误摘要、尝试次数和重试时间。
- 服务恢复后识别错过的周期并补处理。
- 对模型调用做并发、超时和成本控制。
- 不在普通日志中记录 API 密钥或不必要的私人聊天全文。

## 8. 周期调度与 AI 记忆引擎（当前实现边界）

- `CharacterMemorySetting.nextSnapshotAt` 表示下一个待处理的周期结束边界；启用自动快照但缺少边界的设置，会根据 `anchorAt + snapshotIntervalDays` 自动修复并在日志中报告。
- 调度器会检查启用/禁用设置、缺失边界与未到期设置。若 `jobsQueued=0`，请先查看 `settingsDisabled`、`settingsNotDue`、`settingsWithoutNextSnapshotAt` 和 `missingGlobalScope`，不要默认判断为代码故障。
- 当周期到期，调度器把每段周期写入 `MemoryJob` 队列并推进下一边界；稳定幂等键与数据库唯一约束防止重复排队。每次最多补处理 24 个周期（可由调用参数覆盖），剩余逾期周期在后续扫描补齐。
- 手动运行 `yarn scheduler:run`，或单独运行 `yarn scheduler:watch`（默认每 60 秒扫描；`YILING_MEMORY_SCHEDULER_INTERVAL_MS` 可调整，最小 5 秒）。
- Worker 的模型调用在数据库事务外执行，避免长耗时 HTTP 请求占用事务；只有在模型返回通过验证、快照和记忆变化都持久化后任务才标记为成功。
- AI 通过服务端 OpenAI-compatible Chat Completions 接口调用。配置 `LLM_BASE_URL`（默认 `https://api.openai.com/v1`）、`LLM_API_KEY`、`LLM_MODEL` 和可选的 `LLM_TIMEOUT_MS`。密钥不能以 `NEXT_PUBLIC_*` 命名，也不能写入仓库或日志。
- 快照保存周期摘要、重要事件、事实/偏好变化、关系变化、目标/承诺、未解决话题、与上一快照差异、模型/提示版本/用量元数据和消息来源。模型输出先经过 JSON 与来源 ID 校验；模型编造的消息 ID 不会作为有效来源采纳。
- 长期记忆变化支持 `ADD`、`UPDATE`、`INVALIDATE`。新增记忆必须含至少一条本周期有效原始消息作为证据，并将 `sourceMessageId`、`sourceSnapshotId` 保存到数据库；更新通过创建替代条目并把旧条目标记为 `SUPERSEDED` 保留历史，失效则保留条目并标为 `INVALIDATED`。所有自动变更会写审计日志。
- 置信度低于 0.65 的变化不会自动写入长期记忆。模型输出中的 UPDATE/INVALIDATE 只能指向本次上下文中存在的活动记忆，且必须附有本周期原始消息证据。
- 没有配置模型时，Worker 不领取/消耗排队任务，而是输出提示并保留任务；配置完成后可继续消费。模型暂不可用、超时或返回格式错误时，任务按退避策略重试。
- **并发限制**：已为每次任务领取分配独立 fencing token，忆泡/快照/手账/清理产物事务、状态完成与失败回写均按 `jobId + RUNNING + lockedBy token` 条件校验，旧领取者在 retry/cancel 或新领取后不能提交或覆盖状态；snapshot 内 current/global scope 以固定顺序加锁，清理先取任务表锁再锁 job/policy。仍未实现同一范围/日期的小时任务与收口任务互斥，也不做租约续期；超过 5 分钟的长任务仍可能被回收，旧执行者会被 fencing 拒绝，任务应由新领取者重试。
- 模型服务会收到所选周期对话文本和活动长期记忆。使用外部供应商前，应确认其数据处理和隐私条款；本项目不在普通日志中记录完整聊天正文。


### 忆泡取材与内容约束（2026-11-05）

- 每个正序消息块内按会话分别提取，全部子组成功后才在同一事务保存该块事件与进度。失败保留先前块的成果，不越过失败块。
- 每次调用携带同会话、周期内、严格早于本次首条消息的最多六条前文。前文可参与来源引用，但事件必须至少引用一条本次新消息，不能只凭前文重新记旧事。
- 原消息正文完整传递，不再无提示地截掉 1200 字以后的内容。长输入超过供应商限制时任务重试，不把未提取内容视为已完成。
- 已发生、明确计划/约定、尚未证实的说法、助手建议与角色扮演须区分；不得补写来源未支持的结果、感受和地点。提示词升级至 `memory-extraction-v7`。这些规则及模拟请求测试不代表已通过真实模型的语义质量评测。
- 混合会话证据直接拒绝并回滚当前块，不再裁掉部分来源却保留混合正文。普通存储或审计错误也必须冒泡，不可当作重复事件跳过。
- 「立即整理」沿用自动任务键；等待或重试中的目标可唤醒，已成功/跳过的小时任务在游标后有新消息时可再入队。成功收口、运行中、失败及取消任务不会自动重开；失败/取消由任务监控明确重试。当场执行限定本次目标任务。

## 8.1 快照重新提炼与任务操作

- 自动 AI 快照可以提交 `REGENERATE_SNAPSHOT` 任务；Worker 在同一 `snapshotKey` 下创建递增版本、将旧的当前版本标记为 `SUPERSEDED`，并保存审计日志。
- 为避免历史周期重放覆盖当前状态，重新提炼提出的长期记忆变化会写入新快照供审核，但不会自动修改当前 `MemoryItem`。
- 审核清单与正常生成走同一套门槛：低于 `MIN_MEMORY_CONFIDENCE`、或拿不出本周期真实来源消息的条目不会进入清单，只在 `memoryChangesRejected` 里计数（页面上显示为「另 N 条未通过来源校验」），避免把零校验的脏数据摆到最需要人判断的位置。
- `UPDATE` / `INVALIDATE` 类的审核条目除 `supersededMemoryId` 外还带 `supersededCategory` 与 `supersededContent`（被指向记忆在提炼当时的原文），否则「更新成什么」没有对照组。证据 ID 只保留本周期真实存在、能回溯到来源列表的那些。
- 审核建议可以逐条**采纳**或**忽略**（`POST /characters/{id}/snapshots/{snapshotId}/review`）。采纳调用与 Worker 自动生成完全相同的落库函数 `applyMemoryChange`，因此去重、来源消息、`validFrom`、审计与自动路径一致，只是审计动作前缀为 `memory.review_`；忽略只记录决定，不改动任何记忆。
- 处置结果存 `memory_reviews`（`snapshotId + changeIndex` 唯一），**不回写快照正文** —— 快照是不可变的审计产物，人的决定单独可查，快照照旧能证明「当时模型提了什么」。
- 采纳时用数据库里最新的记忆状态做对照，而不是提炼当时的快照：这条记忆可能已被后面的归档改过。若目标记忆已不是 `ACTIVE`，接口返回 409 并提示只能忽略，不会静默失败。证据消息若已被保留期限清理，只丢来源指针，不阻塞采纳。
- 后台任务可取消 `QUEUED`/`RETRY_WAIT` 状态的任务；生成快照、重新提炼、清理原始消息、手账与忆泡整理都可在 `FAILED`、`RETRY_WAIT` 或 `CANCELLED` 时手动重新入队。`RUNNING` 任务不支持强制取消。
- **运行中但租约过期**（领取超过 5 分钟，`server/utils/memory-job-lease.ts`）的任务可以「回收并重新入队」：租约不续期；超时可能是执行者失联，也可能是长调用仍在运行，回收后旧 token 会被 fencing，拒绝其产物和状态写入。任务不会自己回到队列。自动回收发生在「下一次有人领取任务」时（`reclaimExpiredMemoryJobs`），所以整机没有 Worker 在跑时不会自动发生 —— 这正是 2026-11-01 那条卡了 3 小时的忆泡任务。审计动作沿用 `memory_job.manual_retry`，`details.recoveredLease = true` 区分「回收」与「重试」。

## 9. 对话时检索

每次回复只选择：
1. 当前对话需要的近期消息；
2. 与当前用户/角色范围匹配的有效长期记忆；
3. 与当前话题相关的快照；
4. 必要时查找对应来源消息。

当前词法检索从英文词和中日韩字符片段中提取关键词，并尽量保留短主题短语；常见提问意图词会被过滤，以减少“用户喜欢”“之前聊过”等表达对内容匹配的干扰。排序会结合短语长度、候选集合内的逆文档频率（IDF）和更新时间；只有得到正相关分数的条目才会进入上下文。这里的 IDF 仅基于本次候选集合，无法可靠理解同义改写或概念关联，因此不应视为语义检索。未来如果真实对话测试证明关键词召回不足，再评估向量检索或独立重排器。

### 9.1 检索范围与身份隔离

- 可读范围只由 `resolveChatMemoryScopes()` 决定：`character_global` 范围始终可读；`user_private` 范围仅当它属于当前操作用户（`scope.userId` 等于当前用户）时才可读。
- 来自外部身份的 `user_private` 范围必须满足“身份已验证且已绑定到当前用户”（`status = VERIFIED` 且 `linkedUserId` 等于当前用户）才可读；未验证身份、绑定到其他用户、范围类型未知、以及既无用户也无身份的范围一律拒绝。
- 数据库查询本身再用这个白名单的 `memoryScopeId in (...)` 过滤，属于第二层约束；即使上层筛选出错，也不会读到他人才有权限的范围。
- 每次回复的上下文按 **token 预算**装配，不再是「取前 N 条」的硬截断：长期记忆预算默认 1800 token、快照预算默认 2500 token（各自独立，因为一篇周期总结动辄两三千字，共用池子会互相饿死），条数上限默认 20 条（范围 1–50）。最近对话窗口默认 40 条（`modelConfig.recentMessageLimit`，范围 20–200）。两类来源都只来自上述可读范围；会话仍保存在角色全局范围下，历史消息结构不变。
- 排序分 = 相关度 × 重要度权重 × 时间衰减 × 召回加成。时间衰减用半衰期（默认 30 天），参照点是 `lastRecalledAt`（上次真被模型引用），没有则回落到 `updatedAt`。衰减下限 0.55 —— 重要的旧事排序靠后但不会消失。
- 预算装不下时跳过该条而不是截断正文；但**第一条永远放行**，否则一次有相关命中的提问会变成「她什么都不记得」。
- 预算与条数都可在角色的 `modelConfig` 里覆盖：`memoryTokenBudget`、`snapshotTokenBudget`、`memoryItemLimit`（「模型参数」页可改）。
- 提示词每轮注入「现在」：当地日期时间、星期、IANA 时区与同一时刻的 UTC（`server/utils/chat-time-context.ts`，时区取角色 `CharacterMemorySetting.timezone`，坏值回落 `Asia/Shanghai`）。「前天」「上周」这类相对说法由服务端换算，模型不自己算日期。
- 长期记忆进提示词时带 `occurredAt`（取 `validFrom`，没有则退回 `createdAt`），快照带 `periodStart` / `periodEnd`。模型被要求用这些日期回答「什么时候」，并且**没有相关记录时必须明说没有**，不得编造日期或用另一段记忆顶替。
- 提示词里只出现 `scope: "character" | "private"` 语义标签，不发送范围 ID、用户 ID 或 `scopeKey`。模型被要求把 `private` 内容当作当前用户的私人上下文，不得当成共享知识或转述给其他人。
- 私人记忆范围在写入时按 `character:{characterId}:user:{userId}` 生成确定性 `scopeKey`，因此同一用户与同一角色的私人记忆只有一个范围。
- 当前身份来自本地开发用户（`DEV_OWNER_ID`）；正式登录完成后，同一套范围规则应以登录会话为准，而不是放宽校验。
- 对应回归测试：`yarn test:memory-budget`（token 估算、预算装配、首条保底、衰减与重要度、召回加成）、`yarn test:chat-private-memory`（范围允许列表、未验证身份拒绝、去重、提示词不带标识符）与 `yarn test:chat-private-memory-db`（真实数据库查询下的跨用户与未验证身份隔离、时间线标注）。

> 事件记忆层（忆泡）的设计构想见 [忆泡设计构想（未实现）](忆泡设计构想.md)。该文描述目标形态与后续阶段，不是当前行为；本节的检索与范围规则仍是当前实现。

### 9.2 群聊记录与来源配额

- 群聊会话挂在角色全局记忆范围下，本来就算她的记忆。群会话标题写 `QQ群 <群号>`，`metadata` 带 `kind: "group"` 与 `groupId`；老会话的标题是首条消息截断出来的，页面一律按群号展示，不依赖标题。
- 记忆页的时间线只取 `memory,snapshot`（原始消息不进这条流），所以群聊原文不在时间线里。要按群翻她跟别人聊了什么，走 `GET /characters/{characterId}/group-chats`：群列表 + 选中群最近 120 条消息（发言人昵称、群内成员代号）。
- 闸门丢掉的那一轮仍然不落库：群里的闲聊默认只保留 5 分钟内存上下文，不产生原文，也不产生记忆。这是有意的成本控制，不是丢数据。
- 周期快照的来源消息改为**按会话配额**取（`server/utils/memory-source-selection.ts`）：每个会话先保住最新一条，再在 250 条总预算内按时间填满，单会话上限 80 条。原来「整个范围按时间取最早 125 + 最晚 125 条」会让一天几十条的群聊把私聊整段挤出窗口。
- 一对一（私聊、本地对话）的来源优先级高于群聊：会话查询时非群聊会话先全量取、群会话再用剩余名额补，来源选择的锚点也把非群聊排在群聊前面。群再多，也不能把私聊整段挤出预算 —— 从「消息级」和「会话级」两层都保证。
- 来源消息带 `origin`（`QQ群 <群号>` / `私聊` / `本地对话`）进入提炼提示词。群聊里只有与她本人相关的内容（她说过的话、答应的事、有人点名找她、她参与的群内话题、群里怎么称呼她、她跟谁熟）才写成长期记忆；群友之间与她无关的闲聊只进摘要，群友的隐私（病情、住址、感情、财务、工作内幕）不写入长期记忆。
- 对应回归测试：`yarn test:memory-source-selection`（会话配额、预算上限、去重、时间序、一对一优先）与 `yarn test:memory-ai-request`（`origin` 进提示词、系统提示词包含群聊边界）。

### 9.3 主人专属记忆范围

- 「主人」是角色 `Character.ownerId` 指向的站内用户；QQ 渠道里主人的私聊（`speaker.isOwner` 为真）会话挂在主人的 `USER_PRIVATE` 范围下（`ensureOwnerPrivateScope`，`scopeKey = character:{角色}:user:{主人}`），而不是该账号的外部身份范围。
- 主人的私人范围跟随角色全局的周期节奏一起排快照（`memory-scheduler.ts` 在全局推进周期后，为 owner scope 用相同周期边界补排 job，幂等键含 scope id 不冲突）；该周期内没有主人私聊时 worker 按既有逻辑 SKIPPED。
- 主人的私人记忆只在主人自己的对话里可读（`resolveChatMemoryScopes` 对 `USER_PRIVATE` 按 `userId` 放行），不混进全局、不串给群友或其他人。
- 群聊里主人发的消息带 `isOwner` 标记（落库在消息 metadata，提炼时作为来源字段进提示词），让角色在群里也能把「主人说的」和「群友说的」分开记。
- 记忆提炼提示词增加两条规则：主人发言优先记住并体现「主人」身份；当判断某个对话对象值得长期记住时，写一条 `RELATIONSHIP` 记忆（含称呼、来源、关系要点），不给泛泛之交写关系记忆。
- 对应回归测试：`yarn test:identity`（主人范围建立 + 幂等 + 仅主人可读）、`yarn test:memory-ai-request`（`isOwner` 进提示词 + 系统提示词含主人与关系记忆规则）。
