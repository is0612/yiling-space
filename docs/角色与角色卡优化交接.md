## 2. 已完成内容

### 2.1 角色管理

1. 创建角色时，仅未提供称呼才默认“主人”；显式空字符串/空白表示不特意称呼。
2. 复制角色补齐对话示例，采用资料白名单，不复制密钥、模型配置、记忆和渠道绑定；长名称为“副本”后缀预留长度。
3. “更多”菜单按角色阻止重叠操作，包含等待确认阶段；取消和异常后释放。
4. 列表记忆数改为 Prisma 带 `ACTIVE` 过滤的 `_count`，不再加载所有记忆 ID；渠道绑定只查询所需字段。
5. 编辑资料严格区分缺省/空字符串/错误类型：缺省不改，可选文本空字符串清空，错误类型返回 400，名称不可为空。

### 2.2 角色卡完整性

1. **私人阶段总结漏导**：新建、合并均导入私人总结；只有私人总结而没有私人记忆时，也创建当前导入者的 `USER_PRIVATE` 范围。合并保留本地已有周期总结。
2. **去重键碰撞漏导**：导入记忆不继承来源机器的 `dedupeKey`，避免本机或同包键碰撞静默丢失；继续按稳定身份和正文判断重复。
3. **日记版本口径不一致**：每天最多 80 版，`DIARY` 和 `HANDBOOK` 各 40 版，整包最多 8000 版，解决导出的合法卡无法原样导回的问题。

### 2.3 删除可靠性

1. 必要的 `character.deleted` 审计和数据库删除同事务提交；审计失败则回滚删除。
2. 文件仅在事务提交后删除；目录检查只将 `ENOENT` 视为不存在。
3. 文件清理失败不再把已完成的数据删除报成失败，而是返回可选 `cleanupWarning`，前端移除角色并显示警告。
4. 缓存即使遇到文件清理异常也会失效；日志不暴露原始异常、路径或凭据。
5. 删除成功后的审计详情补充为尽力而为，不影响核心审计留痕。

### 第二步：准备环境和静态检查

先读 [本地开发与迁移规范](local-development-and-data-migration.md)，确认 Node >=20.19、Yarn Classic 1.22。

### 第三步：有本地 PostgreSQL 时跑隔离集成测试

```bash
yarn test:character-isolated
```

- 脚本要求 `DATABASE_URL` 指向回环地址，并需要当前数据库用户有创建测试库的权限。
- 它连接本地服务创建随机命名的 `yiling_character_test_<uuid>`，只向该新库写入测试数据和应用迁移，结束时删除该测试库。
- 删除集成测试还会在当前项目 `.data` 中生成并清理随机测试角色的表情包目录，不会使用真实角色 ID。
- 没权限、没有 PostgreSQL 或公司不允许创建测试库时，记录未执行项，另配专用测试实例；不要为跑测试擅自提权。
- **不要直接把 `test:character-card-db`、`test:character-delete-db` 或全量 `verify:local` 指向含重要数据的库。** 全量校验包含其他写库测试，不等于隔离校验。

### 第四步：浏览器人工验收（建议优先做）

使用开发环境和专用测试账号/测试角色，避免删除或改动正式角色；真实模型保持关闭即可完成下列验收：

- [ ] 新建时清空称呼，保存后仍为空；编辑后刷新仍为空。
- [ ] 复制带对话示例的角色，示例和称呼正确，记忆/渠道/密钥没有被复制。
- [ ] 快速重复点击复制、启停或删除，只产生一次有效菜单操作；取消后可再次操作。
- [ ] 含私人阶段总结的角色卡导入后，私人数据只归导入账号；合并同张卡第二次无新增。
- [ ] 日记+手账合计超过 40 版但每种不超过 40 版的测试卡能导入。
- [ ] 同源合并不会因相同外来 `dedupeKey` 漏掉不同记忆，本地资料和已有总结不被覆盖。
- [ ] 删除测试角色后，列表更新正常；正常路径有成功提示。

## 7. 下一轮建议：按优先级处理

### P1：模型设置并发保存丢更新

角色 PATCH 仍有读取整块 `modelConfig` 后合并写回的并发风险。一个页面保存模型参数、另一个同时切开关时，可能用旧配置覆盖对方。

- 先在隔离库补并发复现测试。
- 再选数据库原子 JSON 更新或 CAS/锁+重试方案。
- 单纯在读写外包一层普通事务不等于解决丢更新。
- 不能改变空密钥表示沿用、密钥加密和 owner 过滤等现有约定。

### P2：文件清理失败后的持久化重试

本轮解决“已删除却报失败”和漏审计，但暂时没有持久化自动重试队列。收到 `cleanupWarning` 后仍需要管理员处理残留文件。

- 后续可设计持久化清理任务，带有限重试、状态与审计。
- 不在失败时谎报“原本就没有目录”。
- 手工清理必须先核对绝对路径和实际孤儿状态，先 dry-run，未经确认不执行批量删除。

### P2：角色卡上传的实际字节上限

审查发现入口目前主要依赖 `Content-Length` 判断 32MB；缺失或不可信长度时，对真实读取字节的限制仍需单独验证与加固。

- 先确认 Nuxt/h3 当前请求体限制行为，再补缺失长度/超限场景测试。
- 应在读取阶段限制真实字节，避免先把超大请求完整读入内存。
- 兼容现有前端 JSON 提交，不顺手重构整个导入协议。

### P3：契约与历史实现的一致性

本轮已同步修改涉及的空称呼、编辑校验、删除警告、日记版本上限。其他历史漂移（列表分页/包装结构、字段别名和状态枚举等）没有整体重写。

先盘点实际调用方再更新文档或做兼容迁移，**不要照旧文档直接改变当前列表响应形状**。
