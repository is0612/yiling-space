# 回复延迟诊断（2026-11-24）

> 症状：私聊里她回得偏慢，群里回得更慢，怀疑是网络问题。
> 结论：**不是网络问题**。私聊慢在「模型本身要考虑多久」，群里慢在每轮回复前多跑的一次「语境助手」。
> 诊断时间 17:36–17:50，数据来自本机数据库 `model_usages` / `messages`、`.data/onebot-adapter.log`，以及对 DeepSeek 端点的实时探测。

---

## 0. 一句话版本

| 场景 | 典型耗时 | 时间花在哪 |
|---|---|---|
| 私聊 | 2–7 秒（中位 3.9s） | 模型生成正文 + 思考 token，本地开销只有约 1 秒 |
| 群聊（跑语境助手） | 15–32 秒 | 攒批 4s + **语境助手 10.6s** + 记忆 1.4s + 回复 3.3s |
| 群聊（没跑语境助手） | 4–6 秒 | 攒批 + 回复 |

网络这一段只占几百毫秒，和 10 秒级的差异不是一个量级。

---

## 1. 网络链路实测：干净

在本机直接打 `https://api.deepseek.com`（角色实际用的端点，无代理）：

| 指标 | 结果 |
|---|---|
| DNS 解析 | 32 ms |
| TCP 连接（3 次） | 19 / 6 / 10 ms |
| TLS 握手（3 次） | 51 / 9 / 5 ms |
| 35 token 小请求，端到端 | 0.8–1.3 s |
| **24,010 token 提示词，首字延迟** | **398 ms**（整包 532 ms） |
| 3 个请求并发 | 各 0.9–1.3 s，和单发一样，不排队 |
| 系统代理 | 无（WinHTTP 直连） |

其他两段链路也没问题：

- **QQ 适配器**：15:37 起一条 WS 连接，期间没有重连、没有断线事件。
- **消息落库**：`occurredAt → ingestedAt` 差 3 ms，说明网关送到就是即时的。

所以「网络慢」可以排除。顺带说明：**提示词大不是问题**——2.4 万 token 的预填充只要 0.4 秒，DeepSeek 的 prefill 很快。

## 2. 私聊：时间几乎全在模型出字

最近 3 天，私聊会话 124 次回复：

| 指标 | 值 |
|---|---|
| 平均 | 5.3 s |
| 中位 | 3.9 s |
| p90 | 7.7 s |
| 最长 | 34.3 s |
| 超过 15 秒 | 6 次（4.8%） |
| 超过 30 秒 | 1 次 |

把 128 个可配对的回合拆开：**平均 5.2s = 模型 4.2s + 本地 1.05s**。本地那 1 秒是取记忆、拼 2.5 万 token 提示词、写库（不含发送网络）。

今天 17:37–17:41 模型阶段实测 2.0 / 2.8 / 2.8 / 3.5 秒——正常。

### 那次 34 秒是怎么回事

17:32:43 那轮：`prompt 10,414 tok`，输出 `3,533 tok`，其中 **思考 3,400 tok、正文只有 130 字左右**。等于她为一句「你有个地方弄错主语了」想了 3400 个 token。这是感受上「突然卡了」的来源。

统计上，**思考 token 稳定占输出的 39%**（中位），波动范围却是几十到几千。开启状态来自 `chatThinking` 默认值，代码里写死 `reasoning_effort: "high"`。

## 3. 群聊：回复前多跑一次「语境助手」，平均 10.6 秒

这是群里慢的主因，也是这次最值得改的地方。

群聊一回合的阶段是**串行**的：`context → memory → knowledge → response`。近 4 天 244 个群回合的实测（244 个回合里只有 91 个最终发言，其余是沉默轮，但语境助手照样会跑）：

| 阶段 | 实际跑了几轮 | 平均 | 中位 | p90 |
|---|---|---|---|---|
| 语境助手（判断谁在对谁说话） | 120 / 244 | **10.6 s** | 10.3 s | 15.5 s |
| 记忆助手 | 66 / 244 | 1.4 s | 1.3 s | 1.7 s |
| 正式回复 | 244 / 244 | 3.7 s | 3.3 s | 5.6 s |

两个现场样本（来自回合详情的 stages 字段）：

```
15:43:17  语境 15.6s + 记忆 1.2s + 回复 2.5s = 19.3s
15:44:25  语境 27.4s + 记忆 1.6s + 回复 2.2s = 31.3s
```

语境助手虽然已经用的是 `reasoning_effort: "low"`，但实测单次仍会产出 2,700–3,100 个 token（大部分是思考），按当时的出字速度就是 15–27 秒。它的产物是一段带 `summary / uncertainty / participation / evidence` 的 JSON，本质上是**每次都在重新读一遍群里的谁在说谁**。

再加上 `mention` 档下被 @ 后还有约 4 秒攒批，所以群里「@ 她一下，二十秒后才回」是结构性的，不是偶发。

最近 3 天群聊 91 次回复：平均 12.9 s，中位 4.6 s，p90 33.7 s。分布是**两峰**的——跑了语境助手的那半就是 15–30 秒，没跑的那半是 4–6 秒。

### 还有个副作用：群限流会静默吃掉消息

这个群配了 `replyLimitPerWindow: 2 / 1 分钟`。你在一分钟内 @ 她超过两次，后面那次会被**直接丢掉**，不回复也不报错——容易被误读成「又慢了」。

## 4. 为什么感觉「时快时慢」

同一角色、同样的 2.5 万 token 提示词，服务商出字速度一天之内能差 3–7 倍：

| 时段（本地） | 出字速度 |
|---|---|
| 11:00–15:00（午间高峰） | 约 19–42 tok/s |
| 16:00–18:00 | 约 95–140 tok/s |

按天看也是逐日变化的：11-16 约 50 tok/s，11-19 约 45，11-23 约 79，11-24 约 128。

还有一次极端样本：15:16 那轮输出 133 个 token 用了 37.4 秒（4.4 tok/s），属于服务商侧卡顿，本地无法修复。

**这三件事叠加**——思考量波动（39% 且范围极大）+ 语境助手固定 10 秒 + 服务商高峰变慢——就是「有时候 3 秒，有时候 30 秒」的全部原因。

## 5. 可调项与代价（按性价比排序）

| # | 动作 | 收益 | 代价 | 怎么改 |
|---|---|---|---|---|
| 1 | 关掉「语境助手」 | 群里约一半回合省 **10 秒** | 她更容易搞错「刚才谁在说谁、在跟谁说」 | 模型设置页里关（`contextAssistantEnabled`）。能接受就可以先试一天 |
| 2 | 关掉「深度思考」 | 私聊首字 ~1s → ~0.35s；输出 token 少约 39%；群聊回复阶段也快 1s | 复杂推理、自我反省类对话会变浅 | 角色管理页的「深度思考」开关，即点即存 |
| 3 | 给语境助手关掉思考（改代码） | 群里省 5–10 秒，**保留**群话题判断 | 判断质量可能下降，需要跑回归 | 改 `server/utils/context-assistant.ts`，把 `thinking: { type: "enabled" }` 关掉，然后跑 `test:group-context` 等相关用例 |
| 4 | 调小回复模型的思考预算 | 减少 30 秒级的尖峰 | 深聊时她「想得更浅」 | 需要改 `chat-reply.ts` 里写死的 `reasoning_effort: "high"`，属于代码改动 |

我的建议顺序：**先只关「语境助手」观察一天**（不用改代码，随时能开回来），群里的体验会立刻从 15–30 秒掉到 5–8 秒。私聊如果还嫌慢，再关「深度思考」。第 3、4 项是代码改动，适合在你确认「群判断可以不要那么细」之后再做。

不建议的方向：流式输出对 QQ 没用（她是一条完整消息发出去的），换更小的模型会改变她的说话质量。

## 6. 以后怎么复查

### 一键测链路和出字速度

```powershell
$env:DS_KEY = (docker exec yiling-space-db psql -U yiling_hub -d yiling_hub -tAc "select ""modelConfig""->>'chatApiKey' from characters limit 1").Trim()
node .data/notes/probe-llm-latency.2026-11-24.mjs
```

看两个数：`prefill-24k` 的 ttft（正常 < 600ms，超了才是网络/预填充问题）和 `gen600` 的 tok/s（正常 100+，掉到 40 以下就是服务商高峰或卡顿）。

### 查某一轮到底卡在哪个阶段

助手日志 → 打开该轮详情，看 `collaboration.stages` 四个阶段的 `durationMs`；数据库里等价于：

```sql
select (metadata->>'durationMs')::int as total_ms,
       (metadata->>'turnDetail')::jsonb -> 'collaboration' -> 'stages' as stages
from model_usages
where kind = 'channel' and "createdAt" > now() - interval '2 hours'
order by "createdAt" desc limit 5;
```

### 查回复间隔分布

```sql
with t as (
  select role, "occurredAt",
         lag(role) over (order by "occurredAt") as prev_role,
         lag("occurredAt") over (order by "occurredAt") as prev_at
  from messages
  where "conversationId" = '<会话 id>' and "occurredAt" > now() - interval '3 days'
)
select count(*), round(avg(extract(epoch from "occurredAt" - prev_at))::numeric, 2) as avg_s,
       round(percentile_cont(0.5) within group (order by extract(epoch from "occurredAt" - prev_at))::numeric, 2) as p50_s,
       round(percentile_cont(0.9) within group (order by extract(epoch from "occurredAt" - prev_at))::numeric, 2) as p90_s
from t where role = 'ASSISTANT' and prev_role = 'USER';
```
