# 指派式搭话（群 / 人）：第一次开口

状态：§3 断点已修（`group-chat.ts` + 单测），§5 闸门已削到三条；仍卡在 §6 的两个决策项。
适用：QQ OneBot。群聊与私聊各一条目标类型，共用一个执行器。

---

## 0. 一句话

主人一句话 → 她**只发 1~2 句** → 之后的对话完全交给现有接话链路。
不新建常驻流程、不新建表、不新增调度。

---

## 1. 为什么一次就够

这是产品判断，也是代码事实：

- **有人回她**：群友的消息照常进 `flushGroupRound` 的攒批 → 闸门 → 模型，她自然接下去。
- **没人回她**：现有链路默认就是沉默（`allowSilent`、ambient 抽签），她不会自说自话。

所以这个功能的产出物只有一句话，没有"会话状态"。任何"指派后再盯 10 分钟"的设计都是多余的——
盯梢是接话链路本来就干的事。

---

## 2. 复用与新增

| 目标 | 复用 | 真正新增的 |
|---|---|---|
| 群 | `group-initiative.ts`：素材读取、发送、`group_activities` 记账 | 目标可指定、语境换成"加入聊天"、绕过 `not_idle`、**登记话题参与**（见 §3） |
| 人 | `proactive.ts` 的 `deliverIntent`：发送、落库、`lastMessageAt` 推进 | 目标换成"她认识的某个人"、一句自己的提示词 |

**私聊这条路不要复用目的池**（`refillIntents` / 置信度打分）。
那套是"她自己攒着想说的话"，而指派场景下目的已经由主人给定，走目的池等于把指令稀释成候选。

---

## 3. 关键断点：她开的口，系统不认作"参与"

必须先修，否则这个功能只有一半效果。

### 3.1 事实

- `group-context.ts:336` `recordReply()` 登记"她参与了这个话题"，唯一调用点是 `serve.ts:1426`——
  **只有走完 pipeline 的回复才登记**。
- `group-initiative.ts:235` 直接 `sendOnebotGroupMessage()`，**不碰 GroupContext**。
- `GroupContext` 是 `serve.ts:1144` 里的 per-handler 实例，未导出，initiative 拿不到。

### 3.2 后果

她开口后，群友顺着她说"对啊我也这么觉得"——没有 @、没有叫她名字：

```
direct = false
named  = false
topicCandidate = false   ← 没有话题锚点
→ 只剩 ambientChance = 0.15
```

也就是 **85% 的接话她根本看不见**。而"顺着说"恰恰是开场句最典型的回应方式
（她说的是一句陈述，不是一个问题）。

### 3.3 实际采用的补法（已实现）

**不用共享上下文，也不新建模块。** 实施时发现 `serve.ts` 早就在读这个事实：

```ts
const lastAssistant = await prisma.message.findFirst({
  where: { conversationId, role: "ASSISTANT" },
  orderBy: { occurredAt: "desc" },
});
const lastSpokeAt = lastAssistant?.occurredAt ?? null;
```

而 `group-initiative` 发的消息同样以 `role: "ASSISTANT"` 落进**同一个群会话**（`ensureGroupConversation`
用的是和 pipeline 一样的 `(channelBindingId, externalConversationId)` 唯一键）。所以"她刚说过话"
这个信号一直在手上，只是闸门只拿它算间隔（`too_soon`），没拿它算相关性。

改动落在 `group-chat.ts` 一个文件里，新增两个常量：

| 常量 | 值 | 作用 |
|---|---|---|
| `FOLLOWUP_WINDOW_MS` | 3 分钟 | 她说完话之后这么久之内，群里的话算"在接她的话" |
| `FOLLOWUP_MIN_GAP_MS` | 20 秒 | 接话场景的最短间隔，替代 90 秒的 `minGap` |

闸门里 `continuing` 为真时返回 `{ allowed: true, reason: "continuing", mustReply: false }`，
并且**只替换间隔下限，不绕过任何硬闸门**（安静时段、每日上限、`mention` 档照旧）。

### 3.4 已知的取舍

- **窗口内不区分"是不是真在接她"**。她说完话三分钟内，群里的任何消息都会送进去看一眼。
  这与本文件开头的原则一致：闸门决定"送不送到她眼前"，"说不说"仍交给模型（`mustReply = false`）。
- **没有用"引用回复"当判据**。它精确、不会误拉，但 QQ 群里大多数回话不引用，拿它当唯一判据
  会漏掉绝大多数真实接话。`send group_msg` 拿得到自己的 message_id，将来可以把它修成第二条
  更硬的线索（"有人引用了她那条"→ 直接放行且可绕过间隔）。
- **`mention` 档的群不受益**：那是用户"只要 @"的显式意图，接话也不破例。

建议 N = 3 分钟，与 `topicTtlMs` 的"短期关注"口径一致。

## 4. 语境三分（本方案的核心）

同样是"去说一句"，三种场合的话术完全不同。

| 场合 | 素材 | 基调 | 硬禁止 |
|---|---|---|---|
| 私聊找人 | 该人记忆范围最近消息 + 聊过几次 | 开场。可以问一件事 | 不提"被指派"、一次只问一件 |
| 群里·有人在聊 | `group_activities.recentLines` | **加入聊天**：接住当前这句，不重新开场 | 不 @ 人、不说"大家好"、不复述别人刚说的话 |
| 群里·没人聊 | 最近 12 条或无 | 起个头（直接复用现有 initiative 提示词） | 同上，且允许输出 `-` 表示不说 |

**判定**：`recentLines` 最后一条距今 < 10 分钟 → 加入聊天；否则起头。

这条判定同时解释了一件事：现有 `evaluateGroupInitiativeGate` 里 `not_idle` 的注释写着
*"群里还在说话就不叫找话题，那叫插嘴，由接话链路负责"*——指派场景要的正是"插嘴"，
所以必须专门绕过它，并换一份提示词，而不是把 `not_idle` 调松。

---

## 5. 闸门：只留三条

### 5.1 为什么能只留三条

主人说"去群里聊两句"的那一刻，**时机已经被判断过了**：他会在凌晨两点差遣她，是因为他知道那个群那个点有人；
他会挑群里最热闹的时候让她插一句，是因为他知道那句话接得上。

这条链路上**人就是那个阀门**。再叠一层程序判断，等于把同一个决定做两遍；两遍结论不一致时，
用户看到的现象只有一个——**她不动**。而"为什么不动"在群里和"她不想说话"长得一模一样。

所以这里只保留两类闸门：

| 留下 | 类型 | 为什么砍不掉 |
|---|---|---|
| `enabled` 开关 | 授权 | 关掉这个功能是主人的意图，不是时机 |
| 每日条数（每群 3） | 成本/保护第三方 | 没有它，连发十次指令就是十条消息，被吵的是群友 |
| 模型额度 | 成本 | 没有它，一条指令可以烧掉一晚上的额度 |

### 5.2 砍掉四条（其中一条是降级，不是删）

| 砍掉 | 它原本在判断什么 | 砍掉后由谁判断 |
|---|---|---|
| 安静时段 | 现在是不是半夜 | 主人（他半夜还在发消息） |
| `not_idle` 冷场 | 群里是不是正在聊 | 主人（他挑的就是"有人在聊"的时刻） |
| 最短间隔 | 是不是刚说过话 | 主人（他不会再点一次）+ 每日条数兜底 |
| `mention` 档破例 | 这个群的整体意图 | 见 §6 决策一，降级成**每次确认**，不做成闸门 |

前三条被砍的都是**时机判断**，留下的都是**授权与成本**。这条界线和上一节修 `continuing` 是同一个方向：
一个是不拿抽签替她判断"这句话跟她有没有关系"，一个是不拿阈值替她判断"现在是不是说话的时机"。

### 5.3 实现上的一个注意

现有 `runGroupInitiativeTick({ force: true })` 的 `ignoreTimeGates` 会把**每日条数一起跳过**
（见 `group-initiative-settings.ts:172`，它在 `daily_limit` 之前就返回 ok）。那对页面上的
"立即试一次"是合理的，但指派不能照抄——指派要跳过安静时段/冷场/间隔，仍判每日条数。

所以第 2 步的改动不是复用 `force`，而是给它加一个区分：`dispatched` 跳时机、留条数。
净效果仍是**减层**（少判三条，多一个布尔）。

## 6. 两个待定决策

**决策一：`mention` 档（仅被 @ 时回复）的群，主人指派要不要开口？**

- 允许：主人是显式授权，比"仅 @"更高优先级。
- 拒绝：`mention` 是用户对这个群的整体意图，一句话就破例，等于让档位失去意义。

我的倾向：**允许，但每次都要显式确认一次**（"这个群设的是仅 @ 时回复，仍要她去说吗"），
而不是靠配置永久放行。

**决策二：私聊别人，安静时段真的不可绕过吗？**

我的倾向：不可绕过。理由不是技术而是风险——群里说错话的代价是跑题，私聊说错话的代价是骚扰，
而且暴露的是"有人在背后操纵她"。

---

## 7. 目标解析

- **群**：纯数字 5~12 位，`isGroupId()` 已有。
- **人**：昵称 → `ExternalIdentity.displayName` 或她自己给人起的叫法（`FriendAliasSuggestion`）。
- **歧义**：命中多于一个人 → **停下来问主人**，不许自己挑。系统早就知道群昵称会重名
  （`friends.ts` 的 `groups` 字段就是为"A 群的小肥鱼 / B 群的小肥鱼"设的）。
- **群名**：不支持，因为全项目没有 `get_group_info` / `get_group_list`。这是另一件事。

## 9. 不做什么

- 不做"指派后的连续对话接管"——接话链路已经在做。
- 不做群名解析——缺群信息接口，值得单独一次。
- 不做"她自己决定去哪个群"——这次只做主人指派，自主选择是另一条产品线。
- 不做"程序替主人判断时机"——安静时段、冷场、间隔三条不设闸门，见 §5.1。
