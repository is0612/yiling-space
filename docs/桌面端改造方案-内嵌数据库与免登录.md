# 桌面端改造方案：内嵌数据库 + 本机免登录

> 状态：**已实现内嵌 PG、迁移备份、安装接线，以及安装态主人绑定/私有会话免登录切片；正常 launcher 与源码入口分别验证。旧库自动迁移、跨 OS 恢复及另一台机器的免登录升级尚未全面验收，VC 等发布前置仍需处理**。实施记录已合并为 [桌面端：内嵌数据库、安装包与免登录](desktop-app.md)，本文只保留当时的方案与取舍。
> 关联文档：[桌面化架构评估](<桌面化架构评估.md>)、[产品定位与跨平台架构原则](<产品定位与跨平台架构原则.md>)、[本地开发与数据迁移](local-development-and-data-migration.md)。
> 实施按隔离可验证的切片推进，不将尚未验收的设计标成已实现。本文提出替代原评估中“桌面端只用 Docker”的方向，原有安装在完成显式迁移前继续使用原数据库。

## 1. 目标与实施边界

目标是让全新 Windows 用户不安装 Docker、Node 或 Yarn，也能安装、启动和使用；绑定本机主人后，桌面窗口无需每次输入密码。保留现有 PostgreSQL、HTTP API、User / Session / ownerId 和业务数据模型。

本期不换 SQLite、不改全量 IPC 架构、不做云同步、不做启动 PIN，也不在设置里放尚不能使用的开关。免登录只针对当前操作系统用户的桌面安装，不意味着整台电脑的所有用户都拥有主人权限。

变更范围包括启动器、数据库管理、备份恢复、受限桌面桥，以及退出和身份恢复入口的少量前端改动。**不再承诺“前端和 API 零改动”**。若新增认证接口或响应字段，必须同步 OpenAPI、Mock 与测试；优先通过私有启动通道处理桌面认证，保持公共 API 不变。

服务器部署和普通浏览器的登录行为不变；桌面使用生产构建的 Nitro，不能通过 `NODE_ENV !== production` 识别桌面模式。桌面与 Web 同机共存是必须覆盖的验收条件。

## 2. 当前实现与需要纠正的假设

- 正常入口是 `desktop/launch.cjs` 启动 supervisor，收到 URL 后通过 `YILING_DESKTOP_URL` 启动 Electron；`desktop/main.cjs` 会走外部 URL 分支。只修改 main 中自行启动 supervisor 的 ready 处理，无法覆盖正常入口。
- supervisor 的 `log()` 同时写 stdout 与日志文件。**ready、普通日志、命令行和 URL 都不能携带 Session Token 或启动凭证。**
- `ensureFirstAdmin()` 在用户表非空时跳过建号，没有“本机主人自动绑定”的能力。`YILING_FIRST_ADMIN=0` 会跳过首次建号，不能当作“只停止输出密码文件”的开关。
- `migrateDatabase()` 已有检测待应用迁移并执行升级前备份的路径，需适配运行时和可靠性，不重复建立第二套迁移流程。
- `desktop-backup.mjs` 当前通过 Docker 执行 dump；`desktop-installer.mjs` 的卸载流程目前没有内嵌数据库的停止与验证步骤。
- HTTP 健康接口可用不等于数据库可登录、实例正确或 Worker 已就绪；TCP 端口可连也不能证明连到了本应用的库。

## 3. 改造 A：数据库运行时与数据归属

### 3.1 选择规则：故障不触发换库

保留 `YILING_DB_RUNTIME` 作为显式配置入口，支持 `embedded`、`docker`、`external`。其中 external 表示仅连接用户配置的数据库，不管理其进程。开发与服务器不因本方案自动切换运行时。

全新桌面安装默认 embedded。首次成功初始化或接入后，将运行时、安装实例 ID、数据库身份和配置版本原子写入受保护的本地清单；清单不得保存明文连接密码。此后按持久化绑定启动，不按 Docker 当前是否可用重新选库。

**取消原方案的 auto 故障回落。** 升级时识别到旧配置、旧数据目录或无法确认归属的数据库，就进入旧安装识别/恢复流程；不得因为端口不通、密码不匹配或 Docker 失败而创建新空库。已有外部连接不得被当成本应用拥有的 Docker 实例。

端口只用于连接。复用前通过实际 SQL 登录验证目标库、服务端版本、预期用户、应用结构及安装绑定；实例身份的可信来源与持久化方式在 A0 原型中验证，不能仅凭库名或存在几张表确认。未确认归属时停止，不迁移、不写入。

### 3.2 内嵌数据库初始化

1. 随包提供经过校验的 PostgreSQL 发行物，固定主版本和补丁版本，记录来源、哈希、依赖库、许可证和更新方式。PG16 是初始目标，实施前核对现有容器和真实数据库版本，不能按文档推断。安装包增量以实测为准。
2. 数据放在当前系统用户可写的持久化目录，不能随安装目录更新覆盖；开发、桌面与发布版的数据目录和实例绑定分开。Windows 明确设置仅当前用户及必要系统主体可读写的 ACL，不能只依赖 POSIX mode。
3. 获取实例锁，在独立临时目录执行 `initdb`。指定明确的初始化超级用户、UTF-8、SCRAM 认证和已验证的 locale 策略。密码文件使用排他创建和受限 ACL，成功失败都清理，不进入命令行或日志。
4. 创建业务角色和业务数据库，使 DATABASE_URL 的用户名、密码、库名与真实创建结果一致；初始化管理凭据与业务凭据分别管理。初始化账号权限需满足 Prisma 迁移，不能简单假设运行时永远需要超级用户。
5. 验证 `PG_VERSION`、配置和 SQL 登录后才提交初始化状态。目录存在不等于初始化完成；中断的目录保留诊断，只有确认属于本安装的临时产物才允许清理重试，禁止覆盖未知 pgdata。
6. 凭据保存到受保护的本地凭据文件或操作系统保护存储；文件不进版本库、普通日志或发布包。运行时合成 DATABASE_URL，仅传给确实需要的子进程。

### 3.3 排序规则与跨平台恢复

Linux Docker 的 libc locale 名称不能直接复制到 Windows；名称相同也不能证明排序语义和版本一致。先记录源库的 encoding、locale provider、collation 及其版本，再验证 Windows 发行物实际支持的组合。

A0 必须选定并记录可复现的初始化策略。如果采用 ICU，固定发行物及 ICU 版本并验证支持；若源库策略不可在 Windows 复现，列为迁移兼容性问题，通过逻辑恢复、索引重建和查询验证处理，不能直接复制源 pgdata。

排序验收同时检查中文、大小写、标点、重音、唯一约束及实际使用的搜索表达式；不笼统声称“设置相同 locale 后 LIKE 和排序都相同”。列表需要稳定次序时，确认有确定性的次级排序键。不能保证同序的情形必须明确展示差异并在迁移前解决。

### 3.4 进程、端口与环境传播

- 内嵌 PostgreSQL 仅监听回环地址并强制密码认证。选择端口后启动仍可能冲突，需要有界重试；每次重新选择都更新本次统一运行配置。
- 迁移、Nitro、Scheduler、Worker、QQ 适配器和备份恢复全部消费同一份解析后的数据库配置，不允许某个进程回读旧 `.env` 而连接另一实例。独立启动备份工具时也必须能解析持久化运行时绑定。
- 每个数据目录只允许一位进程管理者。记录管理归属、数据目录和实例身份；接入已有 Docker/external 实例只连接，不在退出时停止它。
- 关闭顺序：停止接收新任务，停止各消费者和 Scheduler，关闭 Web，再对本次管理的 PostgreSQL 执行 `pg_ctl stop -m fast` 并等待。超时只处理已确认归属的进程，不按进程名批量结束 postgres/node。
- 崩溃恢复有次数限制和退避，恢复前重新验证实例身份与 SQL 就绪；数据库不可用期间停止新的业务处理，防止重复启动消费者。父进程异常退出和系统重启都需覆盖，不能只测试正常窗口关闭。
- 卸载必须先退出应用并确认数据库已停止，再保留/迁移整个用户数据目录，包括 pgdata、身份绑定、解密密钥和素材。停止或移动失败则中止卸载；不能只移动 pgdata，也不能对移动失败的数据继续删除。

### 3.5 备份、升级与显式换库

数据库访问和 dump/restore 命令从同一个运行时描述生成：Docker 使用已确认容器内的工具，embedded 使用随包工具，external 使用与服务端兼容且显式配置的客户端工具。备份客户端不得低于服务端主版本。

备份不是只有 dump：还需包含解密密钥、必要配置、身份绑定与素材或其可恢复副本，并记录版本和校验信息。凭据材料需保护，备份不进入 Git。恢复时不复用旧启动凭证或旧 Session，目标安装重新建立桌面信任。

升级前仅在确有迁移需求时备份；备份失败、迁移状态不可判定或空间不足时停止升级，不能继续启动新服务。迁移失败保留备份和错误，不自动把旧 dump 覆盖回正在使用的库；数据库恢复和程序版本回退需要成对验证。

Docker → embedded 和 PostgreSQL 大版本升级是显式流程：

1. 停止源应用的写入、Worker、Scheduler 和适配器，确认没有另一套服务仍在消费同一库。
2. 备份源数据库及配套文件，源库和原数据卷保留不动。
3. 在新目录初始化目标实例，使用逻辑 dump/restore，恢复所需扩展、角色映射和权限；不得直接移动跨平台或跨主版本 pgdata。
4. 验证角色与各层记忆数量、来源关联、日记版本、任务状态、索引/约束、素材和加密凭据实际可用；旧的运行中租约按现有恢复机制处理，不能同时运行两套 Worker。
5. 校验通过并获得用户明确切换确认后，原子更新运行时绑定，再启动目标服务。失败可回原实例；目标尚未接管前不得删除源库。切换后已有新写入时，回退必须另行处理增量，不能直接切回旧库丢弃新数据。

## 4. 改造 B：绑定本机主人并自动建立 Session

### 4.1 信任边界与身份绑定

桌面免登录建立在当前系统用户的受保护安装和启动通道上，不能扩大为“任何访问回环端口的客户端都能登录”。同一用户权限下已能读取进程和文件的恶意程序不在免登录方案可独立防御的范围内，但其他系统用户和普通网络客户端不应因此获得访问权。

- 全新空库首次建号成功后，持久化明确的主人 userId，并与数据库实例/安装绑定关联；原有 ownerId 不改写。
- 旧库、恢复库或多账号库进行一次显式认证和主人绑定。不能按第一条用户、第一位管理员、用户名相似度猜主人；即使只有一个账号也不自动授予已有数据的访问权。
- 主人不存在、被停用、绑定与实例不符时停止自动认证并给出恢复入口；不换成另一管理员，也不通过建号绕过限制。
- 绑定不等于未来同步身份，`originId` 和业务授权继续遵循既有逻辑。

### 4.2 自动认证通道

保留正常入口与直接 Electron 入口，但共用同一份启动协议：

`launch → supervisor → 私有认证通道 → Electron main → 注入 Cookie → 加载本机页面`

直接 Electron 启动时也必须完成同样的握手。实现需同时修改 `desktop/launch.cjs`、`desktop/main.cjs` 和 supervisor，不能只修改 main 的 ready 回调。

- supervisor 的公开 ready 事件只传 URL、状态等非敏感信息。启动凭证和 Session Token 走独立、受 ACL/句柄访问控制保护的通道；可选专用继承管道或受限命名管道，在 B0 原型验证连接双方身份和 Windows 行为。不得用普通 stdout、环境变量、命令行、磁盘临时 token 文件或 URL 参数转交 Token。
- 使用每次启动随机、短时且有用途限制的握手凭证，绑定安装实例和本次服务实例；重放或跨实例使用必须失败。服务重启使旧握手失效。可重复建立 Session 的控制通道只能由已认证主进程持有，不能永久复用首次兑换凭证。
- Session 的签发、哈希、有效期、账号状态校验和撤销走共用服务端实现，避免 supervisor 复制 SQL 后绕过校验。90 天不作为固定值；若需要桌面专用有效期，必须在统一认证策略中显式设计并测试。
- 不新增仅凭回环地址、环境开关、文件存在即可调用的 `local-enter` 接口。桌面开关用于限定功能部署范围，不能代替请求认证；“非生产环境”也不是授权条件。
- Electron main 在加载业务 URL 前 await Cookie 写入，名称、Path、HttpOnly、SameSite 和桌面回环 HTTP 的 Secure 策略须与服务端签发/清除保持一致。采用专用 Electron Session 分区，桌面/Web Cookie 名分开；Cookie 不按端口隔离，随机端口不能作为认证边界。
- 生命周期管理只撤销此安装确实签发的桌面 Session，不能撤销同一用户全部 Web Session。签发记录需要可信的安装归属，不能仅凭可伪造的 userAgent 字符串认领。是否需要新增持久化字段在 B0 决定；若需要，按 Prisma migration 管理，不能为“零 schema 改动”牺牲正确性。

### 4.3 页面入口与失效恢复

preload 只暴露 `isDesktop`、退出应用、重新建立本机 Session 等有限方法，不暴露 Token、数据库凭据、任意 URL 请求或通用 IPC 调用。

主进程处理 IPC 时校验发送窗口、主框架和当前加载来源；仅允许已登记的本应用回环 origin，阻止导航后的外部页面和子框架调用。`isDesktop` 只控制显示，不能充当服务端权限证明。

桌面侧边栏显示“退出应用”，走受控收尾，不再执行普通 Web logout。Web 仍保持退出登录。

Cookie 清空、会话过期或主动撤销后，不把失效 Cookie 回退成开发身份；页面通过桌面桥请求主进程重新认证，主进程经私有通道验证当前绑定和账号状态后注入新 Cookie。此行为属于明确启用的桌面免登录策略：撤销旧 Session 仍然生效，但可信桌面实例可以创建新 Session。用户希望禁止后续免登录时须撤销桌面绑定/关闭该策略，账号停用也必须立即阻止重建。

登录页只在真实桌面桥存在时提供“重新连接本机身份”，不由匿名 HTTP 接口宣布“可无密码登录”。通道断开、身份失效时显示明确错误和重新启动/认证绑定入口，不能无限自动重试或选择其他账号。首次旧库绑定可能需要登录，因此不再承诺任何异常下永不出现登录页。

### 4.4 首次建号与密码

拆开“创建首个账号”和“生成首次密码说明文件”的控制职责。桌面全新安装仍必须创建合法账号，只是不要求用户日常输入初始密码；不能用 `YILING_FIRST_ADMIN=0` 跳过整个建号过程。

已有账号密码不重设。忘记密码时，桌面重新认证只能恢复已授权绑定的会话，不能声称既有改密接口已经支持免旧密码重置。若要增加桌面密码恢复，需要独立设计当前用户证明、审计和 Web 隔离，本期不顺手开放。普通 Web 注册、登录、改密与管理员授权保持原行为。

## 5. 实施切片与止损点

| 阶段 | 最小可评审结果 | 止损点 |
| --- | --- | --- |
| A0 数据库原型 | Windows 随包 PG 的版本/locale/ACL 验证，空目录初始化、SQL 登录、干净停止；明确实例身份方案 | 不连业务库、不切旧安装 |
| A1 全新安装 | 接入统一运行配置、打包、自检、备份恢复及退出/卸载 | 无 Docker 环境可恢复测试未过，不进入旧用户迁移 |
| A2 旧安装迁移 | 隔离副本的 Docker → embedded 演练，数据校验和失败回退报告 | 用户未确认不切真实绑定，不删除源库 |
| B0 认证原型 | 正常/备用入口私有握手、明确主人绑定、Cookie 兼容、重放与越权测试 | Token 不得落日志，不开放匿名本机登录口 |
| B1 交互与发布 | 桌面退出/重连、Web 共存回归、安装包真机验收 | 绑定错误、停用绕过或 Web 行为变化即停止发布 |

每个阶段完成后交付差异和验收结果，再由用户判断下一步。A、B 可独立回滚；数据库已发生新写入后的回退不能假装只是切换配置。

原“4～5 天”仅能作为早期原型的粗略参考，不作为交付承诺。完成 A0/B0 后，根据 Windows 打包依赖、认证通道和迁移实测重新估时，分别列出新安装与旧用户迁移工作量。

## 6. 验收清单

### 数据库与数据安全

- [ ] 无 Docker/Node/Yarn 的全新 Windows，普通用户权限完成安装、初始化、SQL 校验和打开窗口。
- [ ] 二次启动复用正确实例；端口被其他 PG/程序占用、密码错误、Docker 停止时均不静默换库。
- [ ] 初始化中断、磁盘满、不可写目录、路径含空格/中文、主版本不兼容均能保留数据并给出可操作错误。
- [ ] 每个子进程使用同一目标库；桌面/Web/发布版独立实例无重复消费和串库。
- [ ] 多开、正常退出、崩溃、系统重启后无重复管理者；停止操作不影响外部数据库。
- [ ] 备份实际恢复到隔离实例，验证记忆、来源、日记版本、任务和加密凭据/素材可用。
- [ ] 有迁移时备份失败即停止；人为迁移失败保留原实例和可恢复备份，不带错误 schema 启服务。
- [ ] 跨平台 collation/搜索/唯一约束实测；不支持的源配置明确阻止迁移或给出经过验证的转换。
- [ ] 卸载前数据库停止；保留整个数据目录，移动失败中止，不删除未确认归属的数据。

### 桌面身份与 Web 共存

- [ ] 正常 launcher 与直接 Electron 两条入口都能在 Cookie 注入后进入页面。
- [ ] 日志、命令行、URL、错误页和渲染层均不出现启动凭证或 Session Token。
- [ ] 非当前系统用户、普通本机 HTTP 客户端、外部页面、子框架、重放/跨实例凭证不能建立主人会话。
- [ ] 旧库多账号、恢复库、主人被删/停用/绑定错误不猜身份；仅可信绑定可恢复登录。
- [ ] Cookie 清空、会话过期、撤销旧会话后按策略重新认证；撤销绑定或停用账号后不能重建。
- [ ] 桌面退出执行收尾；Web 退出、改密、Session 撤销与授权维持原行为，桌面清理不误删 Web 会话。
- [ ] 新安装不生成无用的密码说明文件，但必有合法首个账号；已有账号密码不被修改。

### 工程与发布

- [ ] Windows CI/真机冒烟：临时数据目录 → initdb → 目标库 SQL → 迁移 → 服务及消费者就绪 → 停止 → 重启复用。
- [ ] 运行适用的认证、桌面启动、数据库迁移、备份恢复回归；`yarn check`、`yarn typecheck`、`yarn build` 通过；改 Vue 时必须有 `yarn check:sfc`。
- [ ] 按测试计划运行相关数据库隔离测试；未执行的全量测试与真实 Windows 场景明确列出，不用原型冒烟替代发布验收。
- [ ] 发布包记录 PG 发行物哈希/许可证/版本，验证无开发机私有数据与凭据。

## 7. 预计涉及文件与契约

| 区域 | 预计职责 |
| --- | --- |
| `desktop/launch.cjs`、`desktop/main.cjs` | 两种入口的私有握手、Session 注入与生命周期 |

| `server/utils/auth.ts`、必要的私有认证桥模块 | 共用 Session 签发/撤销、主人状态与安装归属校验 |

| 桌面/认证/数据库测试与 CI、安装文档 | 覆盖失败路径、权限隔离、旧安装迁移和真机验收 |
